# 09 业务流程与项目状态机

> 版本：v2.1
> 更新日期：2026-08-21
> 项目性质：投标文件智能编制与合规审核平台 V1  
> 适用场景：云启智联作为投标人/供应商参与政府采购信息化服务项目；平台由南京知衡智能科技交付给云启智联使用。  
> 关联文档：`07-客户画像与场景设定.md`、`08-招投标术语与业务知识手册.md`

## 一、目标与边界

本文件定义甲方投标管理中心使用平台时的业务流程、主状态、状态转换、角色职责和异常处理规则。它是后续PRD、数据库设计、Deep Agents运行适配和评测用例的共同依据。

本文件只描述**甲方作为投标人/供应商**的内部工作流；不描述乙方向甲方交付软件的实施流程，也不替代采购人、采购代理机构、评审专家或交易平台的法定行为。

### V1 范围

- 聚焦政府采购信息化服务项目，支持单个投标项目、单个标包；
- 覆盖从项目编号查询、分级数据接入、版本确认、要求抽取、历史参考、报价确认、章节生成、审核返工到内部受控交接的主流程；
- 支持企业证据混合检索、响应矩阵、章节初稿、风险审查和人工确认；
- 支持招标文件、澄清/更正文件及常见企业证据材料的版本关联；
- 业务模型可以记录多标包、联合体和工程招标，但 V1 不实现这些场景的完整编制与审核闭环。

### V1 实现分级

| 优先级 | V1 内容 | 验收口径 |
|---|---|---|
| P0 | 单项目、单采购包、分级数据接入与版本管理 | 能通过来源平台和项目编号创建项目；自动获取失败时可人工上传兜底 |
| P0 | 文档解析与要求抽取 | 能定位资格条件、实质性要求、评审因素和时间节点的原文与页码 |
| P0 | 企业证据混合检索 | 通过 PostgreSQL 原生词法检索、向量检索、元数据过滤、RRF 融合和有限重排返回带来源的资质、人员、案例和证明材料；无证据时拒答或转人工 |
| P0 | 响应规划与标书初稿 | 能生成响应矩阵、章节任务和带引用的初稿，不直接视为最终投标文件 |
| P0 | 历史参考与报价闭环 | 能确认参考项目池、治理受控报价模板、比较有效候选方案并由人工确认最终报价 |
| P0 | 多 Agent 审核与人工闭环 | 能执行资格/合规、评分点覆盖、一致性和风险复核，并支持退回修改 |
| P0 | 内部交接与人工递交记录 | 能冻结版本、受控交接给递交责任人，并记录人工递交状态与回执 |
| P1 | 受控 GraphRAG、更多规则和复杂证据关系 | 基于 P0 已确认关系扩展检索与影响分析，不替换关系型事实源，不影响主流程 |
| 后续 | 多标包、联合体、工程招标兼容、复杂权限和更多文件格式 | 仅保留领域模型、提示或实验，不纳入 V1 验收 |

明确不做：无授权的大规模平台采集、系统自动操作电子交易平台、CA 签章、真实评委评分、中标预测和全自动投标决策。V1 允许对已配置且可合法访问的平台进行项目查询与公开文件获取。

### 状态建模原则

1. **项目状态、文件状态、审核任务状态分开建模**：一个项目编制中，不代表每份文件都已解析或每项审核都已完成。
2. **关键转换必须由人确认**：是否投标、资格是否满足、风险是否接受、是否内部提交，均不能由 Agent 自动决定。
3. **新版本文件优先级高于旧版本结果**：澄清、更正、补遗或重新上传的文件会使依赖旧版本的分析与审核结论失效。
4. **状态只前进，不覆盖历史**：撤回、退回、过期等均以事件和新状态记录，不删除既有审查轨迹。
5. **外部事实与内部判断分离**：采购文件中的截止时间、资格条件属于外部事实；是否投标、是否接受风险属于内部决策。

## 二、角色与职责

| 角色 | 主要职责 | 可触发的关键动作 |
|---|---|---|
| 投标经理 | 商机判断、项目统筹、任务分配、内部提交确认 | 创建项目、发起投标决策、提交审核、确认内部提交、放弃/撤回 |
| 商务标编写人 | 资格、商务响应、业绩和证明材料准备 | 上传证据、维护商务章节、处理证据缺口 |
| 技术方案人员 | 技术响应、实施方案和评分点覆盖 | 维护技术章节、处理技术评分项缺口 |
| 报价测算人员 | 管理经批准的报价输入和口径说明 | 上传报价测算结果、确认引用版本 |
| 商务审核人员 | 核验商务响应、报价引用和证明材料 | 提出问题、退回修改、复核关闭 |
| 合规审核人员 | 核验资格、实质性要求、形式要求和风险结论 | 确认/驳回审核、标记必须处理风险 |
| 资料管理员 | 维护证书、人员、业绩、模板和有效期 | 更新企业知识资料、确认材料版本 |
| 投标递交责任人 | 接收内部交接包并完成人工外部递交 | 确认最新版本、记录递交结果、上传回执 |
| 系统管理员 | 配置角色、词表、规则版本和保留策略 | 管理权限、启停规则、查看审计日志 |
| 主 Deep Agent | 在单次阶段运行内规划任务并委派专业 Subagent | 仅创建结构化委派、提出重试/人工介入建议，不直接改变项目主状态 |
| 专项 Agent/工具节点 | 解析、抽取、检索、覆盖检查、一致性检查和风险汇总 | 不改变项目主状态，不作最终业务决定 |

## 三、对象与状态总览

平台至少维护六条相互关联但不互相替代的状态线：

```text
投标项目主状态：决定是否继续参与和当前协作阶段
采购文件状态：决定分析结果是否可用
审核任务状态：决定风险结论是否已获得人工处理
交付基线状态：决定哪些内容可作为内部提交版本
报价方案状态：决定哪个报价版本可以进入正文和交接基线
递交记录状态：记录递交责任人的接收与人工外部递交结果
```

### 3.1 投标项目主状态

| 状态码 | 中文状态 | 含义 | 是否可编辑内容 |
|---|---|---|---|
| `DRAFT` | 草稿 | 已创建项目，基础信息尚未完成 | 是 |
| `DECISION_PENDING` | 待投标决策 | 已具备初步公告/文件信息，等待人工决定是否参与 | 是 |
| `PREPARING` | 编制中 | 决定参与，正在解析文件、准备材料和编制响应 | 是 |
| `REVIEW_PENDING` | 待内部审核 | 已形成待审版本，等待商务/技术/合规审核 | 受限，仅可补充说明 |
| `REWORKING` | 退回修改 | 审核发现问题，需由责任人修订材料或响应内容 | 是 |
| `READY_FOR_HANDOVER` | 待内部提交 | 必要审核已完成，等待投标经理确认交接基线 | 受限，修改会解除就绪状态 |
| `INTERNALLY_SUBMITTED` | 已内部提交 | 已记录内部交接、版本和确认人；不等同于外部递交 | 否，需先重新打开 |
| `ARCHIVED` | 已归档 | 项目结束，保留文件、结论和审计记录 | 否 |
| `NOT_BIDDING` | 不参与 | 已决定不参与该项目 | 否 |
| `WITHDRAWN` | 已撤回 | 原计划参与但因内部原因终止 | 否 |
| `EXPIRED` | 截止失效 | 截止时间已到且未形成内部提交记录 | 否 |

`NOT_BIDDING`、`WITHDRAWN`、`EXPIRED` 和 `ARCHIVED` 为终态。若要重新参与，应克隆为新投标项目或由投标经理明确重新打开，并保留原项目链路。

> “受限”边界：`REVIEW_PENDING` 仅允许补充说明性备注，禁止改动正文、证据、报价和文件版本；`READY_FOR_HANDOVER` 允许查看和补充交接信息，但对文件、响应内容或证据的任何修改都会使当前 `HANDOVER_BASELINE` 失效并使项目回到 `PREPARING`。

### 3.2 采购文件状态

| 状态码 | 中文状态 | 触发条件 | 后续影响 |
|---|---|---|---|
| `UPLOADED` | 已上传 | 文件进入项目资料区 | 等待解析 |
| `PARSING` | 解析中 | 文档解析任务已启动 | 不允许使用不完整结果做正式审核 |
| `PARSE_FAILED` | 解析失败 | OCR、格式识别或结构化提取失败 | 创建人工处理或重试任务 |
| `PARSED` | 已解析待确认 | 已生成章节、表格、页码和来源 | 可查看，关键字段待人工抽查 |
| `CONFIRMED` | 已确认可用 | 人工确认关键页面、版本和来源无误 | 可触发要求抽取和审核 |
| `SUPERSEDED` | 已被替代 | 更正、澄清、补遗或新版本覆盖 | 依赖该文件的结论标记为过期 |
| `INVALID` | 无效文件 | 重复上传、文件错误或不属于本项目 | 不参与后续计算 |

采购文件中的澄清、更正和补遗不自动删除原文件；系统通过 `supersedes_document_id` 维护覆盖关系，并提示用户确认覆盖范围。

### 3.3 审核任务状态

| 状态码 | 中文状态 | 含义 |
|---|---|---|
| `NOT_STARTED` | 未开始 | 尚未满足任务前置条件或未被调度 |
| `RUNNING` | 执行中 | Agent 或规则正在执行 |
| `WAITING_HUMAN` | 等待人工 | 缺少证据、存在歧义或需要业务判断 |
| `PASSED` | 已通过 | 本任务范围内未发现必须处理问题 |
| `ISSUES_FOUND` | 发现问题 | 发现风险或缺口，等待责任人处理 |
| `RESOLVED` | 已解决 | 责任人补充材料或修改后，经复核关闭 |
| `WAIVED` | 已豁免 | 有权限人员记录接受风险的依据和有效范围 |
| `STALE` | 结果失效 | 依赖文件、证据或章节版本发生变化 |
| `FAILED` | 执行失败 | 工具、模型或数据异常，需重试或人工接管 |

### 3.4 内部提交基线状态

| 状态码 | 中文状态 | 含义 |
|---|---|---|
| `NONE` | 未生成 | 尚未形成可审查的提交版本 |
| `DRAFT_BASELINE` | 草稿基线 | 已汇总文件和章节，但仍可自由编辑 |
| `REVIEW_BASELINE` | 审核基线 | 提交审核时冻结的版本集合 |
| `HANDOVER_BASELINE` | 内部交接基线 | 投标经理确认内部提交时冻结的版本集合 |
| `INVALIDATED` | 基线失效 | 关键文件、响应内容或证据更新后不再可用于提交 |

### 3.5 报价方案状态

| 状态码 | 中文状态 | 含义 |
|---|---|---|
| `DRAFT` | 测算中 | 报价假设或计算结果尚未完成 |
| `INVALID` | 无效方案 | 不满足硬约束，不得被推荐或进入正文 |
| `CANDIDATE` | 有效候选 | 规则校验通过，可供比较和推荐 |
| `SELECTED` | 商务已选择 | 等待项目负责人确认 |
| `CONFIRMED` | 已确认 | 可进入正文、报价表和交接基线 |
| `STALE` | 待复核 | 模板、假设、预算或采购文件变化 |

### 3.6 递交记录状态

| 状态码 | 中文状态 | 含义 |
|---|---|---|
| `PENDING_RECEIPT` | 待接收 | 已生成交接包，等待递交责任人确认 |
| `RECEIVED` | 已接收 | 已确认收到并核对最新版本 |
| `SUBMITTING` | 人工递交中 | 正在外部平台执行人工递交 |
| `SUBMITTED` | 已记录递交 | 已记录平台、时间、状态和操作人 |
| `RECEIPT_UPLOADED` | 已上传回执 | 已保存外部平台回执或截图 |
| `FAILED` | 递交失败 | 记录失败原因并创建处理任务 |

## 四、端到端业务流程

### 4.1 主流程

```text
创建投标项目（DRAFT）并补充基本信息与负责人
→ 在后续数据连接步骤输入来源平台和外部项目编号
→ 数据连接器查询公告和采购文件，失败时人工上传兜底
→ 发起参与决策（DECISION_PENDING）
├─ 决定不参与 → NOT_BIDDING
└─ 决定参与 → PREPARING
   → 上传并确认采购文件
   → 解析、抽取要求、建立证据映射
   → 推荐同类项目并确认参考项目池
   → 运行受控 Excel/内部报价模型，比较有效候选方案并确认报价
   → 编制商务/技术响应、图表、风险提示和说明材料
   → 生成审核基线
   → 提交内部审核（REVIEW_PENDING）
   ├─ 项目负责人、商务和合规/法务审核通过 → READY_FOR_HANDOVER
   └─ 结构化问题任务 → REWORKING → 仅重审受影响内容
   → 投标经理确认内部交接（INTERNALLY_SUBMITTED）
   → 受控交接给投标递交责任人
   → 外部递交由人工完成，系统记录状态和回执
   → 归档（ARCHIVED）

（旁路）任何非终态若截止时间到达且未形成内部提交 → EXPIRED
```

### 4.2 主状态转换规则

| 当前状态 | 触发动作 | 目标状态 | 发起人 | 前置条件 | 系统动作 |
|---|---|---|---|---|---|
| `DRAFT` | 发起投标决策 | `DECISION_PENDING` | 投标经理 | 项目名称、采购方式、采购人/招标人、截止时间至少已知或标为待确认 | 创建决策记录与待确认项 |
| `DECISION_PENDING` | 决定参与 | `PREPARING` | 投标经理 | 已记录决策依据和责任人 | 初始化编制任务与时间倒排 |
| `DECISION_PENDING` | 决定不参与 | `NOT_BIDDING` | 投标经理 | 填写不参与原因 | 写入原因和操作留痕 |
| `PREPARING` | 提交内部审核 | `REVIEW_PENDING` | 投标经理 | 至少一份有效采购文件已确认；审核基线已生成 | 冻结 `REVIEW_BASELINE` 并创建审核任务 |
| `REVIEW_PENDING` | 审核通过 | `READY_FOR_HANDOVER` | 合规审核人员或投标经理 | 商务、技术和合规必审任务均为 `PASSED`、`RESOLVED` 或有效 `WAIVED` | 生成待交接清单 |
| `REVIEW_PENDING` | 退回修改 | `REWORKING` | 审核人员 | 至少存在一项明确的修改意见或阻断风险 | 关联责任人、截止时间和问题清单 |
| `REWORKING` | 回到编制继续准备 | `PREPARING` | 投标经理 | 修改涉及重新上传文件、补充证据或重写章节 | 重新开放编辑并保留审核意见 |
| `REWORKING` | 重新提交审核 | `REVIEW_PENDING` | 投标经理 | 所有退回问题均已处理或豁免；审核基线重新生成 | 旧审核任务标记为历史版本 |
| `READY_FOR_HANDOVER` | 确认内部提交 | `INTERNALLY_SUBMITTED` | 投标经理 | 截止时间未到；`HANDOVER_BASELINE` 已生成；确认人和交接方式已填写 | 记录版本、时间、确认人和摘要哈希 |
| `INTERNALLY_SUBMITTED` | 归档 | `ARCHIVED` | 投标经理/资料管理员 | 已补充外部递交结果或标记为不在系统内管理 | 固化审计记录 |
| 非终态（已确认过文件） | 采购文件更正/澄清/补遗 | `PREPARING` | 系统（检测新文件版本） | 新文件覆盖旧版本且影响范围经投标经理确认 | 依赖旧文件的分析、审核与基线标记 `STALE`/`INVALIDATED` |
| `PREPARING`/`REVIEW_PENDING`/`REWORKING`/`READY_FOR_HANDOVER` | 主动撤回 | `WITHDRAWN` | 投标经理 | 填写撤回原因 | 关闭未完成任务但保留证据 |
| 非终态 | 截止时间到达 | `EXPIRED` | 系统定时任务 | 未存在有效 `HANDOVER_BASELINE` | 通知负责人并保留当前快照 |

### 4.3 重新打开规则

- `INTERNALLY_SUBMITTED` 后发现内部错误，投标经理可执行“重新打开”，状态回到 `REWORKING`；原 `HANDOVER_BASELINE` 必须标记为 `INVALIDATED`。
- 采购文件发生更正、澄清或补遗时，项目不自动改为终态，但所有依赖旧文件的审核任务、响应矩阵和提交基线必须标记为 `STALE` 或 `INVALIDATED`；项目主状态回到 `PREPARING`。
- `EXPIRED`、`NOT_BIDDING` 和 `WITHDRAWN` 默认不重新打开。若业务确有需要，创建克隆项目，并在新旧项目间保存 `cloned_from_project_id`。

## 五、关键业务规则与人工关口

| 规则编号 | 规则 | 系统行为 | 人工关口 |
|---|---|---|---|
| BR-01 | 未确认采购文件不得作为最终合规结论依据 | 允许预览，不允许生成可提交审核基线 | 资料管理员或投标经理确认版本 |
| BR-02 | 澄清/更正/补遗会影响原文件结论 | 使相关抽取、审核、响应矩阵和基线失效 | 投标经理确认影响范围和重新审核任务 |
| BR-03 | 高风险资格、实质性要求、截止时间和保证金事项必须可定位原文 | 无原文、页码或来源时标记 `WAITING_HUMAN` | 合规审核人员确认或补录 |
| BR-04 | 证书、人员和业绩材料须在相关时点有效 | 工具计算有效期并提示风险，不自动认定满足资格 | 资料管理员/合规审核人员确认 |
| BR-05 | Agent 不能决定“是否投标”“是否接受风险”“是否内部提交” | 仅输出建议、证据和待确认事项 | 投标经理或授权审核人操作 |
| BR-06 | 一个阻断风险未处理时不能进入内部提交 | 阻止生成有效 `HANDOVER_BASELINE` | 仅授权人员可填写豁免依据 |
| BR-07 | 报价由 Excel 或内部模型计算，大模型只能比较规则有效的候选方案 | 校验模板、假设、结果和跨章节一致性；输出推荐理由与风险，不修改计算结果 | 商务人员选择，项目负责人确认 |
| BR-08 | 所有人工确认必须可追溯 | 记录操作者、时间、对象版本、原因和备注 | 系统强制留痕 |
| BR-09 | 人工确认采用例外驱动模式 | 低风险自动、中风险批量、高风险逐项、阻断风险必须解决或授权豁免 | 对应业务责任人或审核人 |
| BR-10 | 人工编辑内容不得被局部重生成静默覆盖 | 生成新版本、展示差异并要求确认 | 章节责任人确认 |

## 六、异常场景与处理路径

| 场景 | 检测信号 | 状态变化 | 处理责任人 |
|---|---|---|---|
| 文件无法解析或 OCR 质量过低 | `PARSE_FAILED`、缺页、表格识别异常 | 文件保持失败；项目不自动前进 | 资料管理员补传/人工录入，系统重试 |
| 澄清文件修改截止时间 | 新文件包含更正后的时间节点 | 旧时间节点和依赖结论 `STALE`；项目回到 `PREPARING` | 投标经理确认新倒排计划 |
| 资格证书临近到期或已过期 | 有效期与投标截止日冲突 | 审核任务转 `ISSUES_FOUND` | 资料管理员和合规审核人员 |
| 评分项缺少可用业绩/验收材料 | 证据映射不完整 | 评分覆盖任务转 `ISSUES_FOUND` | 商务标编写人或技术方案人员 |
| 跨章节人员、金额、日期或参数冲突 | 一致性检查命中冲突 | 一致性任务转 `ISSUES_FOUND` | 对应章节责任人 |
| 规则与文件文本存在歧义 | 检索证据不足、规则冲突或模型低置信 | 任务转 `WAITING_HUMAN` | 合规审核人员 |
| 截止时间已到 | 定时任务检查到期 | 未内部提交则 `EXPIRED` | 投标经理复盘/归档 |
| 项目拆分多个标包 | 一个公告含多个独立包件 | V1 仅记录多标包标识并提示拆分；不实现多个标包的完整独立审核与提交基线 | 投标经理 |
| 联合体投标 | 文件要求联合体协议或成员资格 | V1 仅提示联合体风险并保留领域关系；不实现成员级完整证据闭环 | 投标经理与合规审核人员 |

## 七、时间倒排与任务节奏

以投标截止时间为 `T0`，系统仅提供默认节奏，投标经理可按项目实际情况调整：

| 默认时间点 | 业务动作 | 平台动作 | 负责人 |
|---|---|---|---|
| T-30 至 T-25 | 创建项目、决定参与、上传采购文件 | 解析文件并提取初步时间节点、资格和评审因素 | 投标经理、资料管理员 |
| T-25 至 T-20 | 核验资格与企业材料 | 生成证据缺口、有效期和高风险提示 | 商务标编写人、合规审核人员 |
| T-20 至 T-15 | 编制响应、分配章节任务 | 生成响应矩阵和评分点覆盖清单 | 投标经理、商务/技术人员 |
| T-15 至 T-10 | 评分覆盖和一致性检查 | 检查章节、人员、日期、金额和参数冲突 | 技术方案人员、商务标编写人 |
| T-10 至 T-5 | 合规复核和问题收敛 | 汇总阻断风险、待确认事项和证据引用 | 合规审核人员 |
| T-5 至 T0 | 冻结基线、内部提交和人工外部递交 | 记录内部提交版本与审计信息 | 投标经理 |

系统必须按项目配置的实际截止时间驱动提醒，不以演示案例中的 T-30/T-5 作为硬编码规则。

## 八、Agent 与工作流触发规则

```text
已确认采购文件
→ 文档解析工具节点
→ 要求抽取/时间节点抽取
→ 资格与合规审查 Agent
→ 响应规划 Agent
→ 评分点覆盖 Agent
→ 一致性审查 Agent
→ 风险复核 Agent
→ 人工确认或退回修改
```

- 主 Deep Agent 依据前置状态在单次阶段运行内规划任务；领域服务负责创建运行、暂停、重试、人工关口续接和状态转换，主 Agent 不直接改变项目主状态。
- 文件解析、OCR、表格提取、日期计算、版本比较等稳定工作使用工具节点或规则节点，不单独包装为 Agent。
- 任一 Agent 发现信息不足、置信度不足、规则冲突或可能影响投标有效性的事项时，必须创建 `WAITING_HUMAN` 任务，并附原文、页码、文件版本和理由。
- Agent 运行结果绑定 `project_id`、`document_version_id`、`baseline_id` 和 `rule_set_version`；任一依赖对象变更后，结果可被精确标记为 `STALE`。

## 九、审计与可追溯要求

每次状态变化至少记录：

```text
事件编号、项目编号、对象类型、对象编号、旧状态、新状态、触发动作、操作者、操作者角色、发生时间、关联文件版本、关联基线、原因/备注
```

以下操作必须保留不可修改的审计事件：决定参与或不参与、确认采购文件、确认参考项目池、确认报价、风险豁免、提交内部审核、审核通过/退回、确认内部交接、递交责任人接收、记录外部递交结果、重新打开、撤回和归档。

V1 只实现轻量审计与版本留痕；不承诺替代电子交易平台回执、CA 签章日志或法定归档系统。

## 十、与后续文档的衔接

- `10-核心业务对象与数据字典.md`：为本文件中的项目、标包、文件版本、审核任务、风险项、基线和审计事件定义字段、主键和关联关系。
- PRD：按本文件中的状态、角色、前置条件和异常路径拆分页面、接口、权限和验收标准。
- Agent运行设计：Deep Agents负责阶段内规划和Subagent协作，状态转换与人工关口继续由领域服务显式控制，避免以自然语言提示词隐式控制流程。
- 评测方案：以状态转换正确性、版本失效正确性、阻断风险召回率、人工接管率和审计完整性作为可测指标。

## 十一、面试表述

> 我没有把多 Agent 设计成自由对话，而是先把投标项目、采购文件和审核任务拆成三条状态线。文件更新会使依赖旧版本的审核结论失效，关键节点如是否投标、风险豁免和内部提交必须由业务人员确认。这样既能展示 Agent 编排能力，也能符合高风险投标业务对版本、证据和审计的要求。

## 十二、2026-08-21 Deep Agents运行续接规则

- `workflow_run`贯穿长期业务流程，状态可以在`RUNNING`与`WAITING_HUMAN`之间转换；
- 每个阶段创建新的短期`agent_run`，Agent完成DRAFT产物后结束，不跨四个领域人工关口恢复旧运行；
- 人工确认接口在同一事务中校验权限、关口、输入哈希和版本，冻结基线并创建下一阶段`agent_run`与`task_run`；
- 主Deep Agent的内部规划不能直接改变业务状态，必须输出七种结构化决策之一并通过领域服务校验；
- A2A只保存结构化委派Envelope和结构化产物引用，不保存整份文件、完整模型上下文或自由文本记忆；
- 输入版本变化时旧`agent_run`和产物标记`STALE`，基于新输入创建新运行，不倒带改写历史。
