# 10 核心业务对象与数据字典

> 版本：v2.0  
> 项目性质：投标文件智能编制与合规审核平台 V1  
> 适用范围：单个政府采购信息化服务投标项目、单个采购包、从分级数据接入到内部受控交接及人工递交记录。  
> 关联文档：`07-客户画像与场景设定.md`、`08-招投标术语与业务知识手册.md`、`09-业务流程与项目状态机.md`

## 一、目标与使用方式

本文件将 `09` 中的状态机落为可实现、可追溯的数据对象。它不等同于最终数据库 DDL，而是为 PRD、后端接口、证据检索索引、Agent 状态、测试数据和评测标签提供统一语义。

V1 的数据模型遵循以下原则：

1. **源文件优先**：采购文件、企业材料和原始章节是事实来源；抽取结果、风险结论和 Agent 输出必须能回溯到来源版本和页码。
2. **版本不可覆盖**：文件、响应内容、规则集和提交基线通过新版本或新记录演进，不直接改写历史事实。
3. **关系显式保存**：要求、评分项、响应章节、证据、风险和审核任务之间使用关联对象保存，不能只放在自然语言备注中。
4. **交付关系与采购关系分离**：云启智联是系统建设项目的甲方客户，但在采购项目中是投标人/供应商；不能使用同一个字段表达两种角色。
5. **检索索引不是事实库**：PostgreSQL 词法索引与向量索引只保存可检索的派生数据；业务主数据、版本、权限和审计必须以关系型数据存储为准。

## 二、建模范围与命名约定

### 2.1 V1 对象范围

```text
投标项目
├─ 采购参与方、项目成员、单个标包
├─ 采购文件 → 文件版本 → 文档片段
├─ 要求项、评审因素/评分项、时间节点
├─ 企业知识资料 → 证据材料
├─ 数据连接器 → 来源记录
├─ 历史参考项目池 → 章节用途绑定
├─ 报价模板 → 报价假设版本 → 报价候选方案
├─ 响应章节、响应矩阵、证据关联
├─ 图表资产、说明材料、审核问题、风险项
└─ 提交基线、交接包、递交记录、审计事件
```

多采购包、联合体和工程招标完整规则作为后续扩展；V1 已纳入受控 Excel 报价模板、候选方案和人工确认，但不把复杂计算公式重写为统一报价引擎。基于已确认关系的受控 GraphRAG 作为后续检索增强能力。

### 2.2 字段命名与通用字段

- 主键统一为 `UUID`，字段名使用 `snake_case`。
- 业务显示编号使用可读编码，例如 `BID-2026-0001`，不作为关系主键。
- 时间统一保存为带时区的时间戳；招标文件中的截止时间同时保留原文值、标准化值和来源片段。
- 金额使用整数分或定点小数，不使用浮点数。
- 所有核心对象默认具有：`id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`is_deleted`；审计对象除外，不允许软删除或修改。
- 枚举值以英文状态码为准，中文仅用于展示；状态定义以 `09` 为唯一来源。
- `source_document_version_id`、`source_segment_id`、`source_page_no` 用于保存事实或结论的原文定位。

### 2.3 数据分层

| 数据层 | 典型对象 | 说明 |
|---|---|---|
| 事实层 | `bid_project`、`document_version`、`evidence_item` | 由用户上传、人工录入或公开文件确认的事实 |
| 结构化派生层 | `document_segment`、`requirement_item`、`scoring_item` | 从文件解析/抽取得到，必须保留来源和置信度 |
| 业务协作层 | `response_section`、`response_matrix_entry`、`review_task`、`risk_item` | 用于编制、审核和人工处理 |
| 运行与审计层 | `user_session`、`agent_run`、`rule_set`、`project_baseline`、`audit_event` | 保证会话可撤销、运行可重跑、结果可解释和操作可追溯 |
| 接入与交接层 | `data_connector`、`source_record`、`handover_package`、`submission_record` | 管理外部来源、受控交接和人工递交记录 |
| 检索索引层 | 向量、PostgreSQL 词法索引、检索片段 | 可由主数据重建，不作为唯一事实来源 |

## 三、核心对象关系

```text
Organization ──< User ──< UserSession
                       └──< ProjectMember >── BidProject ──< BidPackage
                                      │             │
                                      │             ├──< ProcurementDocument ──< DocumentVersion ──< DocumentSegment
                                      │             │                                              │
                                      │             ├──< RequirementItem ───────────────────────────┘
                                      │             ├──< ScoringItem ───────────────────────────────┘
                                      │             ├──< ResponseSection ──< ResponseMatrixEntry >── RequirementItem
                                      │             ├──< EvidenceItem ──< EvidenceLink >──────────── RequirementItem/ScoringItem/ResponseSection
                                      │             ├──< ReferenceProjectPool ──< ReferenceBinding
                                      │             ├──< PricingScenario >── PricingTemplate / PricingAssumptionVersion
                                      │             ├──< ReviewTask ──< ReviewIssue / RiskItem
                                      │             ├──< ProjectBaseline ──< BaselineItem ──< HandoverPackage
                                      │             ├──< SubmissionRecord
                                      │             └──< AuditEvent / AgentRun
                                      │
                                      └── RuleSet（被 ReviewTask、RiskItem、AgentRun 引用）
```

- `BidProject` 是 V1 的聚合根，所有项目内对象都必须带有 `project_id`。
- `DocumentVersion`、`ResponseSectionVersion`、`EvidenceItem` 和 `ProjectBaseline` 共同构成可追溯版本链。
- `EvidenceLink` 不只描述“某材料匹配某条要求”，还必须表达匹配目的、人工确认状态和来源依据。
- `RiskItem` 由规则或 Agent 发现，但关闭、豁免和风险接受必须由人工动作驱动。

## 四、组织、人员与参与方

### 4.1 `organization`：组织

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |

| `organization_type` | `CLIENT` / `VENDOR` / `PROCUREMENT_PARTY` | 是 | 系统建设关系中的组织类别 |
| `tenant_key` | `yunqi` | 是 | 多租户预留；V1 可固定为一个甲方租户 |

V1 中至少存在系统甲方客户云启智联和系统乙方交付方南京知衡智能科技两条组织记录。采购人/招标人可作为项目参与方保存，不应误写为系统建设甲方。

### 4.2 `user`：平台用户

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `organization_id` | UUID | 是 | 所属组织 |
| `login_name` | String | 是 | 登录账号；组织内唯一 |
| `display_name` | 陈志强 | 是 | 展示姓名；演示数据需标记模拟 |
| `account_status` | `ACTIVE` / `DISABLED` | 是 | 账户状态 |
| `system_role` | `BID_MANAGER` / `COMMERCIAL_WRITER` / `TECHNICAL_WRITER` / `COMPLIANCE_REVIEWER` / `MATERIAL_ADMIN` / `ADMIN` | 是 | 平台权限角色 |
| `password_hash` | String | 是 | Argon2id 密码哈希，不保存明文密码 |
| `must_change_password` | Boolean | 是 | 管理员重置密码后首次登录必须修改 |
| `password_changed_at` | Timestamp | 否 | 最近密码变更时间 |
| `last_login_at` | Timestamp | 否 | 最近成功登录时间 |

`system_role` 描述平台权限，不等同于采购项目中的投标人、采购人或评审专家角色。V1 账号只由系统管理员创建、禁用和重置，不开放自助注册。修改密码、禁用账号或修改关键平台角色后必须撤销该用户全部有效 Session。

### 4.3 `user_session`：服务端登录会话

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 会话主键 |
| `user_id` | UUID | 是 | 登录用户 |
| `token_hash` | SHA-256/HMAC Hash | 是 | 随机 Session Token 的哈希；原文只存在于 Cookie |
| `created_at` | Timestamp | 是 | 登录时间 |
| `last_seen_at` | Timestamp | 是 | 最近有效活动时间 |
| `idle_expires_at` | Timestamp | 是 | 空闲过期时间，默认最近活动后 30 分钟 |
| `absolute_expires_at` | Timestamp | 是 | 绝对过期时间，默认登录后 8 小时 |
| `reauthenticated_at` | Timestamp | 否 | 最近一次敏感操作重新认证时间 |
| `revoked_at` | Timestamp | 否 | 主动退出或系统撤销时间 |
| `revoke_reason` | String | 否 | `LOGOUT` / `PASSWORD_CHANGED` / `ACCOUNT_DISABLED` / `ROLE_CHANGED` / `ADMIN_REVOKED` / `EXPIRED` |
| `client_fingerprint_hash` | String | 否 | 可选的浏览器与来源摘要，不保存完整敏感终端信息 |

浏览器 Cookie 只保存随机 Token，并使用 `HttpOnly`、生产环境 `Secure` 和 `SameSite=Lax`。写操作另行执行 CSRF 防护。`user_session` 以撤销和过期方式结束，不软删除历史记录；Session Token 原文不得进入数据库、日志或审计事件。

### 4.4 `project_party`：采购项目参与方

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `project_id` | UUID | 是 | 所属投标项目 |
| `party_name` | 滨江市大数据管理局 | 是 | 参与方名称 |
| `procurement_party_role` | `PURCHASER` / `TENDERER` / `AGENCY` / `BIDDER` / `SUPPLIER` | 是 | 招投标法律关系角色 |
| `is_our_company` | Boolean | 是 | 是否为甲方投标企业 |
| `source_document_version_id` | UUID | 否 | 名称或角色的来源文件 |

系统建设关系中的甲乙方角色统一由 `organization.organization_type`（`CLIENT`/`VENDOR`）表达，不得写入 `procurement_party_role`；`procurement_party_role` 只描述招投标法律关系中的角色。V1 的投标项目中，云启智联对应 `BIDDER` 或 `SUPPLIER`。

### 4.5 `project_member`：项目成员

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `project_id` | UUID | 是 | 所属项目 |
| `user_id` | UUID | 是 | 平台用户 |
| `project_role` | `BID_MANAGER` / `BID_WRITER` / `TECHNICAL_WRITER` / `PRICING_OWNER` / `COMMERCIAL_REVIEWER` / `COMPLIANCE_LEGAL_REVIEWER` / `SUBMISSION_OWNER` | 是 | 本项目中的协作职责 |
| `assignment_status` | `ACTIVE` / `REMOVED` | 是 | 是否仍参与项目 |
| `assigned_at` | Timestamp | 是 | 分配时间 |

> 平台权限（`user.system_role`）与项目职责（`project_member.project_role`）是两个维度：前者决定可进入的模块，后者决定在特定项目中的分工。`BID_WRITER` 与 `PRICING_OWNER` 在平台侧复用 `COMMERCIAL_WRITER`，`COMMERCIAL_REVIEWER` 与 `COMPLIANCE_LEGAL_REVIEWER` 复用 `COMPLIANCE_REVIEWER`，`SUBMISSION_OWNER` 复用 `BID_MANAGER` 的交接模块入口，但具体项目动作仍由 `project_role` 区分。前端六类权限视图只是显示分组，不替代这七个项目职责。

## 六、采购文件、版本与文档片段

### 6.1 `procurement_document`：采购文件逻辑对象

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `project_id` | UUID | 是 | 所属项目 |
| `document_type` | `ANNOUNCEMENT` / `PROCUREMENT_FILE` / `CLARIFICATION` / `CORRECTION` / `ADDENDUM` / `BID_TEMPLATE` / `RESULT_ANNOUNCEMENT` / `CANDIDATE_ANNOUNCEMENT` | 是 | 文件类别 |

| `current_version_id` | UUID | 否 | 当前确认可用版本 |
| `supersedes_document_id` | UUID | 否 | 被覆盖的逻辑文件；用于澄清/更正关系 |
| `document_status` | 见 `09` 文件状态 | 是 | 当前文件状态 |

> `RESULT_ANNOUNCEMENT`（中标/成交公告）与 `CANDIDATE_ANNOUNCEMENT`（中标候选人公示）作为历史结果检索语料，用于中标结果查询与历史案例检索；它们不参与采购文件覆盖链，但同样需关联 `project_id` 与来源版本。

### 6.2 `document_version`：文件版本

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `document_id` | UUID | 是 | 所属逻辑文件 |
| `version_no` | `v1` / `v2` | 是 | 同一逻辑文件内递增 |
| `file_name` | `采购文件.pdf` | 是 | 原始文件名 |
| `storage_uri` | 对象存储路径 | 是 | 原文件地址 |
| `content_hash` | SHA-256 | 是 | 去重和版本校验 |
| `uploaded_at` | Timestamp | 是 | 上传时间 |
| `parse_status` | `UPLOADED` / `PARSING` / `PARSED` / `PARSE_FAILED` / `CONFIRMED` / `SUPERSEDED` / `INVALID` | 是 | 解析/确认状态 |
| `data_classification` | `PUBLIC` / `INTERNAL` / `CONFIDENTIAL` / `RESTRICTED` | 是 | 文件版本的数据出域等级 |
| `effective_at` | Timestamp | 否 | 文件生效时间（如可识别） |
| `superseded_by_version_id` | UUID | 否 | 覆盖本版本的新版本 |
| `confirmed_by` | UUID | 否 | 人工确认人 |
| `confirmed_at` | Timestamp | 否 | 人工确认时间 |

同一 `document_id + content_hash` 不允许重复。对澄清、更正、补遗必须建立覆盖关系；不能仅凭上传时间自动判断其替代全部内容。

### 6.3 `document_segment`：可定位文档片段

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `document_version_id` | UUID | 是 | 来源版本 |
| `parse_id` | UUID | 是 | 产生该片段的解析记录 |
| `page_id` | UUID | 否 | 对应物理页面记录 |
| `segment_type` | `HEADING` / `PARAGRAPH` / `LIST` / `TABLE` / `TABLE_ROW` / `FIGURE` / `OTHER` | 是 | 业务语义片段类型 |
| `parent_segment_id` | UUID | 否 | 上级章节、列表或表格区域 |
| `page_no` | Integer | 否 | 页码 |
| `section_path` | `第三章/二/3.1` | 否 | 章节路径 |
| `content_text` | Text | 是 | 清洗后的原文 |
| `char_start` | Integer | 否 | 在页面或原始文本中的起始字符位置 |
| `char_end` | Integer | 否 | 在页面或原始文本中的结束字符位置 |
| `source_bbox` | JSON | 否 | 坐标，用于 PDF 高亮定位 |
| `source_hash` | SHA-256 | 是 | 原始来源内容摘要，用于变化检测和引用校验 |
| `metadata_json` | JSONB | 否 | 表格结构、图表解释和解析器扩展信息 |
| `confidence` | Decimal | 否 | 解析或 OCR 置信度 |
| `segment_status` | `DRAFT` / `CONFIRMED` / `STALE` / `INVALID` | 是 | 片段状态 |
| `embedding_status` | `PENDING` / `INDEXED` / `FAILED` | 是 | 向量索引状态 |

`document_segment` 是要求抽取、页码引用、证据检索和风险解释的共同定位对象。切片优先按标题、段落、列表项、表格逻辑区域或表格行、规则单元和图表区域形成完整语义单元，过长时再按句子或段落拆分，不按固定 Token 机械切割。

检索时的 `project_id`、知识范围、文件状态、有效期、组织范围和保密等级从所属项目、文件版本、知识资料或证据对象读取，不在每个片段重复保存。V1 不新增独立来源锚点、表格单元格和检索块表。

## 七、要求、评分与响应内容

### 7.1 `requirement_item`：要求项

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|

| `item_type` | `DOCUMENT_VERSION` / `RESPONSE_SECTION_VERSION` / `EVIDENCE_ITEM` / `REVIEW_TASK` / `RISK_ITEM` | 是 | 快照对象类型 |
| `item_id` | UUID | 是 | 快照对象主键 |
| `item_version_or_hash` | String | 是 | 版本号或内容哈希 |
| `inclusion_reason` | Text | 否 | 纳入原因 |

### 10.3 `audit_event`：审计事件

| 字段 | 类型/示例 | 必填 | 说明 |
|---|---|---:|---|
| `id` | UUID | 是 | 主键 |
| `project_id` | UUID | 是 | 所属项目 |
| `event_type` | `PROJECT_STATUS_CHANGED` / `DOCUMENT_CONFIRMED` / `RISK_WAIVED` / `BASELINE_CREATED` / `HANDOVER_CONFIRMED` / `PROJECT_REOPENED` | 是 | 事件类型 |
| `object_type` | String | 是 | 发生变化的对象类型 |
| `object_id` | UUID | 是 | 对象主键 |
| `before_snapshot` | JSON | 否 | 变化前关键字段 |
| `after_snapshot` | JSON | 否 | 变化后关键字段 |
| `actor_user_id` | UUID | 否 | 操作者；系统任务可为空 |
| `actor_type` | `USER` / `SYSTEM` / `AGENT` | 是 | 操作主体 |
| `reason` | Text | 否 | 原因或备注 |
| `metadata_json` | JSONB | 否 | 外部模型调用等事件的供应商、模型、来源引用、字段清单、脱敏策略、请求响应哈希和用量 |
| `occurred_at` | Timestamp | 是 | 发生时间 |

审计事件是追加写入记录；不允许更新或删除。对风险豁免、重新打开和内部提交，`reason` 必填。

外部模型调用使用 `event_type=EXTERNAL_MODEL_CALLED`；策略拒绝使用 `EXTERNAL_DATA_BLOCKED`；项目出域策略变化使用 `EXTERNAL_AI_POLICY_CHANGED`。审计默认保存对象引用、字段名、分类、脱敏版本和哈希，不保存完整 Prompt、图片或模型回复正文。

认证审计至少使用 `LOGIN_SUCCEEDED`、`LOGIN_FAILED`、`LOGOUT`、`PASSWORD_RESET`、`PASSWORD_CHANGED`、`ACCOUNT_DISABLED`、`SESSION_REVOKED` 和 `SENSITIVE_REAUTHENTICATED`。认证审计不得保存密码、Session Token 原文或完整 Cookie。

## 十二、版本失效与级联规则

| 变更对象 | 直接影响 | 系统动作 |
|---|---|---|
| 新增澄清/更正/补遗文件 | 依赖旧文件的要求、评分项、时间节点 | 标记为待复核；相关 `review_task` 和 `risk_item` 转 `STALE` |
| 修改/新增响应章节版本 | 响应矩阵、覆盖检查、一致性检查 | 相关检查任务转 `STALE`；若已冻结基线则基线 `INVALIDATED` |
| 企业证据过期或被替换 | 证据映射、资格与评分支持 | `evidence_link` 转 `STALE` 并创建风险项 |
| 规则集升级 | 规则类审核结论 | 不改写历史；按需重新运行并关联新 `rule_set_version` |
| 项目截止时间更新 | 倒排任务、证据有效性、提交资格 | 更新待办；重新计算 `valid_at_deadline`，必要时使基线失效 |
| 参考项目池或章节用途变化 | 依赖历史参考的章节版本 | 相关章节转待复核，不覆盖人工编辑内容 |
| 报价模板、假设或结果变化 | 报价引用、报价表、商务章节、交接基线 | `pricing_scenario` 转 `STALE`，相关章节与审核任务重新打开 |
| 图表数据源变化 | 图表资产与引用章节 | `chart_asset` 转待更新并标记关联章节待复核 |
| 审核问题重新打开 | 原问题、修改章节和审核任务 | 保留旧轮次，创建新的复核状态和差异快照 |
| 交接基线失效 | 交接包和递交准备 | 撤销下载链接，`handover_package` 转 `REVOKED`，旧文件标记禁止递交 |

级联失效是“需要复核”的提示，不等同于自动判定投标无效。

## 十三、P0 与后续数据实现边界

| 范围 | P0 实现方式 | P1/后续方式 |
|---|---|---|
| 单标包 | `bid_package` 保留对象，但仅一个 `is_v1_primary=true` | 多标包各自响应矩阵、审核任务和提交基线 |
| 证据关系 | `evidence_link` 关系表作为事实源 | P1 投影为受控 GraphRAG 节点和边 |
| 检索 | `document_segment`、`evidence_item` 建立向量与 PostgreSQL 词法索引 | 混合检索、图扩展、查询规划 |
| 文档版本 | 文件版本、章节版本、基线快照 | 差异比对、精细影响分析与批量重评 |
| 权限与认证 | 管理员维护本地账号、PostgreSQL Session、项目成员和平台角色 | OIDC/统一登录、多因素认证、细粒度字段、下载和导出权限 |
| 数据接入 | 配置平台连接器、公开文件获取和人工上传兜底 | 更多地区平台、统一凭据中心和高可用连接器 |
| 报价 | 管理受控模板、假设、候选结果、校验和人工确认 | 复杂敏感性分析和统一报价计算引擎 |
| 交接 | 交接包、清单、哈希、接收确认和人工递交记录 | 与电子交易平台或法定归档系统正式集成 |
| 多标包/联合体 | 记录标识、风险提示和关联占位 | 完整独立工作流、成员级证据闭环 |

## 十四、最小验收数据集

P0 演示至少准备以下数据，以验证对象关系真实可用：

- 1 个模拟投标项目、1 个主标包、1 个采购人/代理机构/投标人参与方关系；
- 至少 1 个管理员和 4 个不同业务角色账号，覆盖登录、禁用、密码重置、会话过期和强制撤销；
- 1 份公开采购文件、1 份澄清或更正文件，形成明确版本覆盖链；
- 20 条左右要求项，至少包含资格、实质性、技术、格式和时间要求；
- 10 条左右评分项，包含至少 1 个需要业绩/验收材料支持的评分项；
- 15 至 30 份明确标记 `[SIMULATED]` 的企业证据材料；
- 1 套响应矩阵、若干响应章节版本、至少 3 个风险项和 1 个风险豁免样例；
- 1 个审核基线和 1 个内部交接基线，以及可查询的审计事件链。
- 1 个可用数据连接器和 1 个自动获取失败后的人工上传兜底样例；
- 3 个历史参考项目、1 个确认参考池及至少 3 种章节用途绑定；
- 1 个受控报价模板、2 个有效候选方案、1 个无效方案和 1 个确认报价版本；
- 至少 1 个图表资产、3 类说明材料、2 个结构化审核问题和 1 条人工递交记录。

## 十五、与 PRD 的衔接

PRD 不应重新发明业务对象，而应引用本文件中的对象、字段和状态：

- 登录与权限：`user`、`user_session`、`project_member`；
- 项目列表/详情页：`bid_project`、`bid_package`、`project_member`、`project_party`；
- 文件中心：`procurement_document`、`document_version`、`document_segment`；
- 要求与评分工作台：`requirement_item`、`scoring_item`、`response_matrix_entry`；
- 企业知识与证据检索：`knowledge_document`、`evidence_item`、`evidence_link`、`retrieval_trace`；
- 审核中心：`review_task`、`risk_item`、`rule_set`、`agent_run`；
- 提交与审计页：`project_baseline`、`baseline_item`、`audit_event`。
- 数据连接页：`data_connector`、`source_record`；
- 历史参考页：`reference_project_pool`、`reference_binding`；
- 报价工作台：`pricing_template`、`pricing_assumption_version`、`pricing_scenario`；
- 编制与审核页：`chart_asset`、`supporting_document`、`review_issue`；
- 交接与递交页：`handover_package`、`submission_record`。

在面试中可这样概括：

> 我把证据检索结果和 Agent 输出都建模为可定位、可版本化、可审计的业务对象。PostgreSQL 词法索引与向量索引只负责检索，采购文件、企业证据、响应章节、风险和提交基线才是系统的事实源，因此文件更新后可以准确让相关结论失效并重新审核。
