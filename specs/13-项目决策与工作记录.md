## 一、当前项目定位

当前主项目是：

> **投标文件智能编制与合规审核多智能体平台**

它面向云启智联内部的投标准备与审核流程，聚焦政府采购信息化服务项目，帮助投标团队完成文件解析、要求提取、响应规划、证据匹配、风险审核和内部提交前留痕。

### 关键角色关系

```text
系统建设项目
乙方：南京知衡智能科技有限公司（模拟 AI 软件服务商）
甲方：云启智联科技股份有限公司（模拟客户）

采购项目
采购人/招标人：发布采购需求的一方
云启智联：投标人/供应商，也是系统实际使用方
```

“系统甲乙方关系”和“采购项目参与方关系”必须分开表达：

- 系统建设关系：`delivery_party_role`；
- 招投标法律关系：`procurement_party_role`；
- 不得把采购人/招标人称为本系统的“甲方”，也不得把系统乙方写成采购项目投标人。

## 二、已确认的 V1 边界

### P0 必做闭环

```text
单个政府采购信息化服务投标项目 + 单个标包
→ 创建项目
→ 通过一个主要连接器或受控模拟连接器获取文件，人工上传兜底
→ 手动刷新或上传并确认采购文件/澄清更正文件
→ 文档解析、要求/评分项/时间节点提取
→ 企业知识检索与证据映射
→ 响应矩阵、章节任务和带引用初稿
→ 多 Agent 审核、人工确认/退回修改
→ 内部提交基线、审计留痕
→ 离线评估与人工反馈驱动的重评
```

### P1 或后续

- 受控 GraphRAG：基于 P0 已确认的关系数据进行图扩展检索和影响分析；
- 多标包、联合体、工程招标兼容；
- 复杂权限、更多文件格式、精细影响分析；
- 真实系统集成和生产部署。

### 明确不做

- 全国招标公告实时聚合；
- 自动最优报价、高级报价模型、敏感性分析和策略模拟；
- 电子交易平台自动递交、CA 签章和外部回执深度集成；
- 中标预测、真实评委评分、全自动投标决策；
- 将模拟客户、模拟企业知识库或离线效果描述为真实生产交付。

## 三、最新关键需求澄清（最高优先级）

### 3.1 当前主线是 Agent 项目，不是并列的“Agent + RAG 产品”

用户明确指出：**当前做的是 Agent 项目。**

正确架构关系：

```text
投标文件智能编制与审核多智能体平台
├─ Supervisor Agent
├─ 资格与合规审查 Agent
├─ 响应规划 Agent
├─ 评分点覆盖 Agent
├─ 一致性审查 Agent
├─ 风险复核 Agent
└─ 企业证据检索工具
```

Agent 项目内检索能力的定位：

- 是多个 Agent 调用的共享证据检索工具；

- OCR、表格抽取、日期计算、版本比较等也属于工具/规则节点，不应包装为 Agent；
- GraphRAG 不是当前 P0 主链路，只是基于已确认关系的 P1 增强能力。

### 3.4 V1 范围收敛：场景做窄、核心做深

用户确认采用以下建设原则：

> **V1 核心链路做深，V2 扩展业务广度和协同能力，V3 建设质量运营和平台化能力。**

V1 继续保留从项目代码到内部提交留痕的完整闭环和六项核心工作台能力，不简化为只生成文档的 Demo。企业级深度重点体现在来源可靠、权限明确、人工关口不可绕过、状态和版本正确、失败可恢复、全过程可审计以及结论和内容可追溯证据。

V1 的场景广度收敛为：

- 一个主要数据连接器或受控模拟连接器，人工上传正式兜底；
- 手动刷新或人工补充文件，不做自动定时监控；
- 少量受控历史候选、差异说明和用途确认，不做大规模历史分析；
- 至少一个受控 Excel 报价模板或固定结果接入，不做高级策略模拟；
- 固定审核路径和基础风险豁免，不做通用工作流和复杂会签；
- 对象级或章节级影响判断，无法确定时扩大或全量复核，不承诺字段级精确影响；
- 内部交接、接收确认和简单人工递交记录，不做客户版复杂分发控制。

上述后移能力进入 V2；V3 继续承担质量运营、模型回测、跨项目分析、多组织治理和平台化。L1、L2、L3 的评测对象同步限定为收敛后的 V1 范围，但零容忍质量门禁不降低。

## 十、2026-08-19 技术方案讨论检查点

### 10.1 建设标准与开发顺序

V1 正式采用以下折中建设标准：

> **单组织、多角色、支持多个独立项目的可部署旁路试用版。核心流程必须真实、可恢复、可审计，可供小团队受控试用，但不建设完整企业 SaaS。**

开发顺序采用“前端先行 + 契约驱动 + 纵向切片”：

1. 先使用 Next.js 完成页面导航、业务流程和完整状态设计；
2. 同步定义领域对象、OpenAPI/JSON Schema 和 TypeScript 类型；
3. 前端通过 Mock API 覆盖成功、失败、等待人工确认、版本失效和权限不足等状态；
4. FastAPI 后端按纵向切片逐步替换 Mock，不以临时页面字段直接决定数据库结构；
5. 建议依次贯通项目与文件、解析与要求确认、响应矩阵与证据、章节编制、审核风险、交接导出六个切片。

### 10.2 Agent、Skill 和工具数量冻结

技术方案初始基线由原来的 6/8/9、后续 5/6/7 继续压缩，并最终冻结为：

```text
逻辑 Agent：5 个
业务 Skill：4 个
MCP 工具域：4 个
MCP Server：1 个
```

5 个逻辑 Agent：

1. Supervisor Agent；
2. 招标理解与合规 Agent；
3. 响应规划与评分 Agent；
4. 标书编制 Agent；
5. 质量与风险复核 Agent。

4 个业务 Skill：

1. 招标文件理解；
2. 响应规划与证据匹配；
3. 带引用标书编制；
4. 质量与风险复核。

4 个 MCP 工具域：

1. `document.*`：解析、OCR、复杂图表理解、Document IR 读取、预览和导出；
2. `project.*`：项目上下文、版本、状态、人工关口、失效、审计、基线和交接；
3. `knowledge.*`：招标文件、企业证据和历史参考检索、来源读取与引用校验；
4. `business.*`：业务规则、报价读取与校验、一致性检查和确定性门禁。

4 个工具域由一个 `bid-tools-mcp` 服务统一暴露。上述是逻辑边界，不代表独立微服务或容器数量。原 5/6/7 方案被本方案替代，但业务功能、人工关口、审计能力和质量门槛不减少。

### 10.3 历史总体架构与运行方式（Agent 编排部分已替代）

当时冻结的架构为；其中模块化单体、FastAPI、Celery、Redis 和 PostgreSQL 继续有效，LangGraph 编排部分已于 2026-08-21 被 Deep Agents Harness 方案替代：

> **历史方案：模块化单体、异步任务执行与 LangGraph 状态编排。**

- 前端使用 Next.js 构建工作台；
- 后端使用 FastAPI 提供 API、权限和业务服务；
- LangGraph 负责编排 Agent、状态图、暂停、恢复和人工中断；
- Celery 负责文件解析、OCR、Embedding、Agent 运行和导出等长任务；
- Redis 只承担消息队列和临时运行状态，不作为最终业务事实源；
- PostgreSQL 保存业务状态、任务最终状态、版本、权限和审计；
- `backend` 与 `worker` 可以复用同一个 Python 镜像，但采用不同启动命令；
- 5 个 Agent 不拆成 5 个独立服务。

### 10.4 数据与文件存储

数据底座冻结为 PostgreSQL + pgvector：

- PostgreSQL 是唯一核心业务数据库，保存项目、文件版本、要求、证据、章节、Agent 任务、审核问题、基线和审计事件；
- pgvector 是 PostgreSQL 内的向量扩展，不是第二个数据库，用于保存文本向量和执行语义检索；
- 业务状态、项目隔离、版本有效性、权限过滤、来源引用和向量检索必须处于同一数据一致性边界；
- 不引入 Chroma，避免业务库与向量库之间的同步、失效和权限漂移；
- 原始文件、解析产物和导出文件存入 MinIO 等 S3 兼容对象存储。

### 10.5 文档解析与复杂图表处理

解析链路冻结为分层解析，并统一输出 `Document IR`：

```text
原生文本 PDF → PyMuPDF
DOCX → 原生结构解析
XLSX → 原生单元格与公式解析
扫描页或普通图片 → OCR + 版面检测
常规表格 → 表格结构恢复
复杂图表 → 外部多模态 API
全部结果 → 统一 Document IR → 质量校验与人工确认
```

关键边界：

- 原生文本优先，不把普通文本 PDF 全部转图片重新识别；
- 多模态只处理流程图、架构图、甘特图、统计图、多层表头、嵌套表格和其他复杂视觉区域；
- V1 优先调用外部多模态 API，同时保留本地模型适配接口；
- 多模态输出作为 `visual_summary` 或候选结构，不覆盖 OCR 原文；
- 金额、税率、日期、工期、资格条件、否决项、评分分值、技术参数、人员数量、签字和印章等高风险视觉结论必须人工确认；
- 解析失败或定位不可靠时进入 `WAITING_HUMAN`，不得静默跳过或猜测；
- Agent 只依赖统一 `Document IR`，不直接绑定 PyMuPDF、OCR 或多模态供应商。

### 10.6 部署基线

V1 采用单台 Linux 服务器上的 Docker Compose 部署：

```text
Caddy/Nginx
Next.js frontend
FastAPI backend
Celery worker
PostgreSQL + pgvector
Redis
MinIO
```

- 只有网关开放 `80/443`；数据库、Redis、MinIO、前后端内部端口不直接暴露公网；
- 使用持久化卷保存 PostgreSQL 与 MinIO 数据；
- Docker Volume 不等于备份；V1 实现本机自动备份和人工离机副本，自动异机灾备预留接口但不接入；
- 当前不引入 Kubernetes、微服务拆分、数据库集群、Redis Cluster、MinIO 集群、服务网格和自动扩缩容。

### 10.9 Supervisor Agent 设计确认

用户已确认 Supervisor Agent 采用以下定位：

> **Supervisor 是 LangGraph 确定性状态机上的智能协调器。它负责判断下一步由哪个专业 Agent 处理，但不能绕过业务规则、人工关口或直接修改项目主状态。**

控制权分工：

- 确定性状态机负责合法流程、权限、前置条件和人工关口；
- Supervisor 负责语义判断、任务拆解、异常归类和专业 Agent 调度；
- 状态机和权限校验的优先级高于大模型判断；
- 所有业务状态变化必须通过“项目、文件版本与状态管理工具”执行。

Supervisor 负责读取当前状态和有效输入版本、创建专业 Agent 任务、汇总结构化结果、生成后续任务或人工待办、处理重试与恢复、记录运行版本，以及在输入变化后触发旧结果失效。它不负责文件解析、证据检索、报价计算、章节生成、资格通过判定、高风险问题关闭、风险豁免、最终报价确认或交接基线冻结。

核心输入包括 `project_id`、当前项目状态、触发事件、有效文件版本、已确认要求基线、证据范围、报价版本、章节版本、未关闭审核问题、待处理人工任务和历史 Agent 运行记录。

核心输出采用结构化调度决策，限定为 `DISPATCH_AGENT`、`WAITING_HUMAN`、`RETRY_TASK`、`EXPAND_REVIEW_SCOPE`、`INVALIDATE_OUTPUTS`、`BLOCK_WORKFLOW` 或 `COMPLETE_STAGE`，并携带目标 Agent、任务类型、输入基线、原因、后续人工关口和幂等键。

LangGraph 共享状态只保存少量运行控制字段，完整业务数据仍以 PostgreSQL 为唯一事实源。该处为早期边界结论，最终字段已在 10.18 收敛为七个，不再将各类有效基线 ID、任务列表、阻断问题列表和下一动作分别放入 State。

Supervisor 原则上不直接执行 4 个专业业务 Skill，只调度拥有对应 Skill 的专业 Agent。它主要调用 `project.*` 和 `business.*`，用于读取状态、校验调度、执行门禁和记录审计。

以下情况必须进入 `WAITING_HUMAN`：有效文件版本、要求、证据用途或报价版本未确认；可能覆盖人工章节；存在阻断问题或待豁免风险；等待交接基线冻结；输入版本冲突；自动重试达到上限。

恢复策略：临时网络或限流错误由 Celery 指数退避重试；结构化输出持续失败、版本冲突或权限不足转人工或阻断；Worker 异常通过 PostgreSQL 任务状态和幂等键恢复；输入版本变化时旧结果标记为 `STALE` 并基于新版本重新创建任务。

### 10.10 招标理解与合规 Agent 设计确认

用户确认该 Agent 采用“规则召回 + LLM 结构化理解 + 确定性校验 + 人工确认”的混合方案，负责回答“采购文件要求是什么”，不负责判断“本企业最终是否满足”。

处理管线为：

```text
确定性预处理
→ 规则召回候选
→ LLM 结构化抽取
→ Schema 与来源校验
→ 跨文件冲突检查
→ 要求原子化和去重
→ 风险与置信度分级
→ 人工确认
→ Requirement Baseline
```

主要职责包括抽取项目事实、预算、限价、截止时间、资格、否决项、实质性要求、评分项、技术服务要求、附件、签章和格式要求；识别正文、评分表、附件、澄清和补遗之间的引用、覆盖和冲突；形成待确认要求基线和文件差异。

核心输出为 `ProjectFactSet`、`RequirementSet`、`ScoringCriterionSet`、`SubmissionChecklist` 和 `DocumentConflictSet`。每条要求必须记录类型、标准化文本、强制等级、后果类型、来源片段、文件版本、页码、置信度、确认状态和判断摘要。

该 Agent 使用“招标文件理解”Skill，主要调用 `document.*`、`project.*`、`knowledge.*` 和 `business.*` 四个 MCP 工具域。

它不判断企业资格满足、不确认企业证据、不生成响应矩阵和章节、不计算报价、不关闭风险。抽取完成后必须进入 `REQUIREMENT_BASELINE_CONFIRMATION`；未确认结果只能为 `DRAFT`。

补遗或更正文件确认后必须生成 `Requirement Diff`，旧要求基线标记为 `STALE`，人工确认后创建新基线，不能覆盖历史基线。

### 10.12 响应规划与评分 Agent 设计确认

用户确认该 Agent 采用“响应规划 + 企业证据候选匹配 + 评分覆盖”的合并设计，不单独拆出评分 Agent。它负责把已确认的 `Requirement Baseline` 转换为可执行、可追踪的 `Response Plan Baseline`。

处理管线为要求分类、证据检索与过滤、历史参考候选、评分覆盖、章节与任务拆分、缺口和冲突识别、完整度计算及人工确认。主要输出为 `ResponseMatrix`、`ScoringCoveragePlan`、`ChapterPlan`、`EvidenceMatchSet`、`EvidenceGapSet`、`HistoricalReferenceSet`、`WorkAssignmentPlan` 和 `PlanningConflictSet`。

该 Agent 使用“响应规划与证据匹配”Skill，主要调用 `project.*`、`knowledge.*` 和 `business.*`；需要读取原始文件来源时按白名单调用 `document.*`。

关键边界：语义相似不代表企业满足要求；无证据时必须创建缺口；历史项目不能成为当前企业事实或承诺；报价工具不能被 Agent 修改公式或确认最终报价；主观评分项不得预测分数；确定性得分测算必须注明不是评标结果或中标预测。

规划完成后必须进入 `RESPONSE_PLAN_CONFIRMATION`。要求、证据或报价版本变化时，响应计划或相关矩阵项、章节进入 `STALE` 并执行全量或增量复核。人工修改的章节目录不得被 Agent 静默覆盖。

下一步讨论标书编制 Agent。

### 10.13 标书编制 Agent 设计确认

用户确认该 Agent 采用结构化内容块方案，不将整章只保存为一个 Markdown 字符串。章节由标题、段落、表格、图表、报价数据、证据、提示和占位等内容块组成，每个块独立记录来源、版本、编辑和锁定状态。

Agent 根据已确认的 `Response Plan Baseline` 生成 `ChapterDraftVersion`、内容块、引用清单、图表规格、版本差异、缺失输入和生成警告。企业事实、人员、案例、报价和参数必须引用有效来源；无证据时创建占位项，不生成确定性内容。

金额通过系统锁定的 `QuoteDataBlock` 从确认报价版本确定性填充，LLM 不生成金额。图表由 Agent 生成 `VisualAssetSpec`，再由文档渲染工具根据确认数据生成，不允许无来源绘图。

人工编辑保护采用基础版本和块级乐观锁：若 Agent 运行期间章节已被人工修改，系统创建冲突候选版本而不是覆盖当前版本。人工创建、人工修改和锁定块默认禁止自动覆盖，局部重写结果必须由用户选择接受、保留或手工合并。

生成完成后进入 `CHAPTER_DRAFT_CONFIRMATION`，编写人确认后只能进入 `READY_FOR_REVIEW`，不代表审核通过。审核返工由结构化问题驱动，编制 Agent 不能自行关闭问题、降低风险或接受豁免。

下一步讨论质量与风险复核 Agent。

### 10.14 质量与风险复核 Agent 设计确认

用户确认使用统一复核 Agent 的多阶段审核方案，不拆分多个审核 Agent。每次审核创建不可变 `ReviewBaseline`，固定要求、响应计划、章节、报价、证据、附件、模板、规则、模型和提示词版本；任何输入变化后原结论失效。

风险等级统一为 `BLOCKING`、`HIGH`、`MEDIUM`、`LOW`。Agent 执行确定性预检、资格合规、评分覆盖、证据引用、报价数据、跨章节一致性、履约承诺和外发内容检查，并生成结构化问题、风险、报告和复核范围。

审核与风险状态沿用现有数据字典，不新增冲突枚举：`review_issue.status` 使用 `OPEN`、`PROPOSED`、`WRITER_CONFIRMED`、`PENDING_REVIEW`、`CLOSED`、`REOPENED`、`WAIVED`；`risk_item.risk_status` 使用 `OPEN`、`IN_PROGRESS`、`RESOLVED`、`WAIVED`、`STALE`。

Agent 只能创建问题、提出修改建议和使依赖失效的风险结论进入 `STALE`，不能关闭问题、解决风险、降低等级或批准豁免。复核范围分为对象、章节、多章节和全项目；无法判断影响范围时必须扩大复核。

预检结束后进入 `REVIEW_RESULT_CONFIRMATION`。只有必审任务完成、所有阻断风险已解决或合法豁免，且审核基线仍有效时，状态管理工具才允许进入 `READY_FOR_HANDOVER`。

至此 5 个逻辑 Agent 的详细职责和人工边界已经全部确认。下一步讨论统一 `Document IR` 字段与版本模型。

### 10.15 简化版 Document IR 设计确认

用户认为完整节点树、来源锚点、单元格表和独立检索块方案对 V1 过于复杂，因此确认将 Document IR 压缩为：

```text
document_version
→ document_parse
→ document_page
→ document_segment

document_correction 作为人工修正覆盖层
```

`document_segment` 继续作为要求抽取、检索、引用和原文定位的稳定业务来源单元；只新增解析记录、页面和人工修正三个轻量技术对象。

V1 的 Segment 类型只保留标题、段落、列表、表格、图表和其他。页码、章节路径、文本、坐标、置信度直接保存在 Segment；表格简单行列、复杂图表解释和解析器扩展结果放入 JSONB。

人工修正不得覆盖原始解析值，使用 `document_correction` 保存原值、修正值、原因和确认记录。更换解析器创建新 `document_parse`；文件内容变化才创建新 `document_version`。

V1 直接在 `document_segment` 上建立全文与向量索引，不建立通用节点树、独立来源锚点、单元格表、独立检索块和通用文档结构编辑器。后续仅在真实查询、表格或检索版本需求出现后再拆分。

原 `10.16`—`10.21` LangGraph 方案演进章节已删除；相关决策已被 2026-08-21 的 Deep Agents Harness 迁移决策替代，当前实施以本章第十二节及正式规格文档为准。


### 10.22 Skill 与 MCP 收敛方案确认

用户确认 V1 必须真实使用 Skill 和 MCP，但不按每个细能力部署独立模块。最终数量基线为 `5 Agent + 4 Skill + 4 MCP 工具域 + 1 MCP Server`。

4 个 Skill 分别承载招标文件理解、响应规划与证据匹配、带引用标书编制、质量与风险复核。Skill 是版本化业务能力包，包含目标、Prompt、输入输出 Schema、规则、引用与拒答要求，以及允许调用的 MCP 工具白名单；Skill 不作为独立进程、容器或微服务运行。

4 个 MCP 工具域统一由 `bid-tools-mcp` 暴露：`document.*` 负责文档处理与导出，`project.*` 负责项目状态、版本、关口和审计，`knowledge.*` 负责检索、来源读取与引用校验，`business.*` 负责业务规则、报价校验、一致性检查和确定性门禁。具体方法仍拥有独立的 Pydantic 契约、权限、超时、错误码和审计记录。

Supervisor 不执行专业 Skill，只通过 `project.*` 和 `business.*` 完成调度校验。四个专业 Agent 分别绑定一个主要 Skill，并根据白名单调用所需工具域。Agent 不得动态发现或调用白名单外工具，高风险状态变更仍必须经过 FastAPI 领域服务、PostgreSQL 事务、权限和状态机校验。

该收敛只减少命名数量、部署单元和平台化能力，不删除解析、OCR、复杂图表多模态、混合检索、引用校验、报价校验、文档导出、版本失效、人工关口和审计能力。V1 不建设 Skill 市场、动态安装、多个 MCP Server 编排、MCP 服务发现和第三方任意工具接入。

下一步讨论 Skill 包与 MCP 方法的最小调用契约，包括版本、请求上下文、白名单、权限、错误、超时重试和审计字段。

### 10.23 MCP 通信与内部访问控制确认

用户确认 `bid-tools-mcp` 采用内部 Streamable HTTP，由 FastAPI、Celery Worker 和 Agent Runtime 通过 `http://mcp-tools:8000/mcp` 共享调用。V1 不采用每个 Worker 启动独立 MCP 子进程的 stdio 方案，也不使用普通 Python 函数调用代替真实 MCP 协议。

`mcp-tools` 只加入 Docker 内部应用网络，不暴露宿主机端口和网关路由。V1 不建设完整 OAuth 授权服务器，调用方使用部署时配置且不进入代码仓库的内部服务凭证。每次调用在 MCP `_meta` 中携带请求、追踪、用户、项目、工作流、Agent 运行和 Skill 版本上下文。

MCP Server 必须依次校验内部服务凭证、Skill 工具白名单、项目访问权限、对象所属项目和输入版本有效性。状态修改、基线冻结、人工关口推进和交接等高风险操作继续由 FastAPI 领域服务在 PostgreSQL 事务和状态机约束下执行，MCP Server 不成为第二套业务后端。

MCP 连接不保存业务会话状态。网络超时和临时不可用允许按工具配置有限重试；权限、白名单、版本冲突和业务门禁错误不得自动重试。未来只有在 MCP Server 对外开放时，才升级为面向第三方 Client 的标准授权体系。

下一步讨论统一 `McpCallContext`、Skill 包清单和 MCP 工具输入输出的最小字段。

### 10.24 Skill 与 MCP 最小调用契约确认

用户确认 V1 使用 `SkillManifest`、`McpCallContext`、`McpToolRequest`、`McpToolResponse` 和 `McpError` 五个逻辑契约对象，不建设通用插件协议或万能工具接口。

`SkillManifest` 固定 Skill 标识与版本、目标、输入输出 Schema、工具白名单、模型策略、引用与拒答策略、超时和最大重试次数。Skill 是 Prompt、结构化契约和业务约束的组合，不是单独的 Prompt 文件。一次 `agent_run` 内不得静默切换 Skill 版本。

`McpCallContext` 通过 MCP `_meta` 传递请求、追踪、用户、项目、工作流、Agent 运行和 Skill 版本上下文。`McpToolRequest` 逻辑上包含工具名与版本、独立业务参数、幂等键和输入版本引用，不传递整份项目状态。

`McpToolResponse` 使用 `SUCCEEDED`、`PARTIAL` 和 `REJECTED` 三种状态。小型结构化结果直接返回；大文本、文件和批量结果写入 PostgreSQL 或 MinIO，通过 `output_refs` 返回。部分成功必须说明警告和缺失范围，不能被调用方静默当作完整结果。

统一错误码为 `TRANSIENT_ERROR`、`VALIDATION_ERROR`、`PERMISSION_DENIED`、`VERSION_CONFLICT`、`BUSINESS_BLOCKED`、`DUPLICATE_REQUEST`、`NOT_FOUND` 和 `INTERNAL_ERROR`。仅临时错误允许最多 2 次重试，内部错误最多 1 次；权限、版本和业务错误直接阻断或转人工。重复请求优先返回首次结果引用。

下一步讨论 4 个 Skill 分别允许调用哪些具体 MCP 方法，以及 V1 最少需要暴露多少个方法。

### 10.25 MCP 方法数量与 Skill 白名单确认

用户确认 V1 冻结为 4 个工具域、14 个 MCP 方法。该粒度比 10 个聚合方法更容易独立配置权限、超时、重试和审计，同时避免 20 个以上细粒度方法带来的维护负担。

`document.*` 包含 `document.ingest`、`document.read`、`document.render` 和 `document.export`。解析、OCR、版面识别和复杂图表多模态路由统一由 `document.ingest` 处理；最终导出只允许确定性交接任务调用。

`project.*` 包含 `project.get_context`、`project.validate_inputs` 和 `project.validate_transition`。状态转换方法只做合法性校验，真正状态写入仍由 FastAPI 领域服务执行。审计由 MCP 中间件自动记录，不设置独立审计工具。

`knowledge.*` 包含 `knowledge.search`、`knowledge.read_sources` 和 `knowledge.validate_citations`。招标文件、企业证据和历史参考共享检索入口，但必须通过参数和权限限制知识范围。

`business.*` 包含 `business.validate_structure`、`business.validate_quote`、`business.check_consistency` 和 `business.evaluate_gate`，分别负责结构、报价、一致性和阶段门禁校验。

四个专业 Skill 按职责拥有固定方法白名单；Supervisor 只允许使用 `project.*` 和 `business.evaluate_gate`；确定性交接任务额外允许调用 `document.export`。白名单由 `SkillManifest` 声明并由 MCP Server 二次校验，模型不能动态扩大工具权限。

### 10.26 MCP 同步执行与 Celery 异步边界确认

用户确认采用“单层 Celery 异步 + MCP 方法同步执行 + `task_run` 统一进度”。FastAPI 或工作流先创建并投递 `task_run`，Celery Worker 再调用同步 MCP 方法；MCP Server 不创建第二层 Celery 任务。专业 Agent 已经运行在 Worker 中时直接调用 MCP，不重复创建子任务。

`document.ingest`、`document.render`、`document.export` 和全项目 `business.check_consistency` 默认通过 Celery 执行。其余 10 个方法默认同步调用，但检索最多返回 50 条候选，来源读取和引用校验单次最多处理 100 项；超过上限由调用方拆批或在已有 Celery 任务中执行。

默认超时预算为：项目与门禁校验 5 秒，结构和报价校验 10 秒，检索和来源处理 20 秒，文件解析及 OCR 30 分钟，预览和一致性检查 10 分钟，最终导出 15 分钟。临时错误允许有限重试，权限、版本、白名单和业务错误不得自动重试。

`McpCallContext` 增加可选 `task_run_id`。长任务更新 `current_step`、`progress_percent` 和 `heartbeat_at`，输出和错误继续写入 `result_refs` 与 `last_error_code`。前端使用 `GET /api/v1/task-runs/{task_run_id}` 每 2～3 秒轮询。V1 不建设 WebSocket、SSE、消息推送和 MCP 内部异步队列。

权威 `task_run` 字段同步更新到 `10-核心业务对象与数据字典.md`，补充预览、一致性任务类型及进度、心跳字段。

### 10.27 ModelGateway 与双模型配置确认

用户确认 V1 采用应用内部 `ModelGateway` 和两个模型配置档，不新增独立模型服务。`TEXT_PRIMARY` 统一支持四个专业 Agent，`VISION_CHART` 只处理 `document.ingest` 通过确定性规则识别出的复杂图表。OCR、报价计算、状态转换和业务门禁不交给大模型。

专业 Skill 通过 `SkillManifest.model_policy` 固定使用文本配置档，模型不能自行选择多模态或切换配置。V1 不为每个 Agent 分配独立模型，也不做成本驱动或模型自评的动态路由。具体供应商和模型名称保留为实测项，通过统一网关适配。

模型输出依次经过 JSON Schema/Pydantic、引用完整性和确定性业务规则校验后，才由领域服务写入 PostgreSQL。JSON 结构错误只允许一次结构修复；再次失败转人工。缺少必需引用的输出拒绝入库，信息不足时保留缺口，不要求模型编造。

网络或限流错误最多重试 2 次。多模态失败时保留 OCR 和原图并转人工确认。模型不得修改项目主状态、计算或确认报价、关闭风险、通过人工关口或冻结交接基线。

每次 `agent_run` 固定并记录模型配置档、供应商、请求模型名、实际模型标识、配置和参数摘要、Skill、Prompt、Schema 版本及 Token 用量。对应权威字段已同步到数据字典。同一次运行不得静默换模，配置变化需要新运行或使受影响结果失效。

### 10.28 混合检索与引用定位确认

用户确认 V1 采用 PostgreSQL 原生词法检索、pgvector 语义检索、RRF 融合和有限候选重排，不额外部署 Elasticsearch 或 OpenSearch。正式文档统一使用“PostgreSQL 原生词法检索”这一术语。

检索先执行项目、权限、版本、有效期和保密范围过滤，再进行两路召回。词法和向量默认各取 Top 30，去重后通过 RRF 取 Top 30，再交给 Reranker 取最终 Top 10。单次请求最多返回 50 条候选，超出范围由调用方拆批或通过 Celery 任务执行。

每个结果必须返回来源片段 ID、文件版本、页码、章节路径、字符或坐标范围、原文、召回路线和得分。Agent 只能引用已返回且仍有效的来源片段；版本失效后必须重新召回。

Embedding 不可用时降级为 PostgreSQL 词法召回并记录降级码；Reranker 不可用时使用 RRF 结果并记录降级码；两路都不可用时不得生成确定性结论，创建证据缺口并转人工。检索索引是派生层，PostgreSQL 业务表仍是唯一事实源。

混合检索架构已冻结，Embedding 和 Reranker 的具体模型继续通过真实招标文件、企业证据和引用定位评测确认。

### 10.29 语义切片与引用定位确认

用户确认以 `document_segment` 作为 V1 最小引用单位，优先按标题与正文、段落、列表项、表格逻辑区域或表格行、资格/评分/否决等规则单元、图表 OCR 文本和多模态摘要进行业务语义切片。只有单元过长时才继续按句子或段落拆分，不以固定 Token 数机械切割。

`document_segment` 权威字段补充 `parse_id`、`page_id`、`char_start`、`char_end`、`source_hash`、`metadata_json`、`confidence` 和 `segment_status`，片段类型统一为 `HEADING`、`PARAGRAPH`、`LIST`、`TABLE`、`TABLE_ROW`、`FIGURE` 和 `OTHER`。`parent_segment_id` 只表达轻量章节、列表和表格父子关系。

检索前过滤项目、知识范围、文件版本和状态、有效期、组织范围、保密等级及片段类型。这些权限与业务元数据从所属项目、文件版本、知识资料和证据对象读取，不全部冗余存入片段。

引用校验检查片段存在、版本有效、来源哈希匹配、页码与章节一致、引用文本属于该片段且用途允许。文件版本或来源变化后，旧引用和依赖结果进入 `STALE` 并重新检索。V1 继续不建设独立来源锚点表、单元格表和检索块表。

对应权威字段已同步到 `10-核心业务对象与数据字典.md`。

下一步讨论 Embedding 和 Reranker 的部署形态：放入现有 Worker 镜像、本机模型服务，还是使用外部 API。

### 10.30 纯 CPU Embedding 与 Reranker 部署确认

用户确认生产试用服务器没有 GPU，V1 按纯 CPU 运行。Embedding 与 Reranker 不使用外部 API，也不新增独立模型服务或容器，而是在现有 `mcp-tools` 中通过 `EmbeddingProvider` 和 `RerankerProvider` 本地加载。

`mcp-tools` 对每类模型只保留一个持久实例，并使用一个有界 CPU 推理通道、固定线程上限、容器内存限制和独立健康检查。不得动态启动多个模型进程。文档批量向量化通过 Celery 异步执行，查询向量化允许同步；RRF 后最多重排 30 个候选并返回 Top 10。

重排队列已满、超时或模型不可用时直接降级为 RRF，不阻断主要检索流程。文档向量化任务继续留在 Celery 队列。优化顺序为缩短输入、限制批量与候选、调整线程和增加安全缓存，再根据实测决定 ONNX 或 INT8，不在初始版本同时引入量化和独立推理服务。

Embedding 保留 BGE-M3 为首个候选；Reranker 将当前候选与更小的 CPU 模型比较。最终依据 Recall@K、MRR/nDCG、引用正确率、P95 延迟、CPU 和内存冻结。若重排性能不满足要求，可关闭 Reranker 并使用 RRF，不影响业务闭环。

下一步讨论文档渲染与导出：如何从结构化内容块生成可编辑 DOCX、预览 PDF 和最终交接文件。

### 10.31 文档渲染与导出方案确认

用户确认 V1 使用“结构化内容块 → `DocumentModel` → 受控 DOCX 模板 → DOCX → LibreOffice Headless PDF”的同源管线。Markdown 和 HTML 不作为最终文档事实源，`DocumentModel` 只是运行时中立结构，不新增数据库表。

持久化模板对象统一命名为 `document_template_version`，避免与交接包混淆。模板保存 DOCX 对象引用、变量 Schema、样式与章节映射、允许块类型、哈希和状态，由管理员上传并验证后使用；普通用户不能上传任意模板脚本。权威对象已补充到数据字典。

`document.render` 生成带草稿或内部标识的预览 DOCX/PDF，允许占位、待确认内容和警告，但预览不能进入交接包。`document.export` 只由确定性交接任务调用，必须通过审核确认、交接门禁、版本、报价、引用、风险和模板校验。

存在占位块、内部内容混入外发正文、失效引用、未确认报价、阻断风险、版本冲突或无效模板时必须阻断最终导出。成功后生成 DOCX、同源 PDF、清单和 SHA-256；DOCX 成功但 PDF 失败时仅为 `PARTIAL`，不能形成有效交接包。

渲染和导出通过 Celery 执行，LibreOffice 初始并发为 1，每个任务使用独立临时目录和用户配置目录。worker 镜像直接包含 `docxtpl`、`python-docx` 和 LibreOffice，不新增在线 Office 或独立渲染服务。

下一步讨论缓存与 Redis 边界：哪些数据可以缓存，哪些状态必须每次读取 PostgreSQL，以及如何避免缓存导致版本和权限错误。

### 10.32 Redis 缓存与业务状态边界确认

用户确认 Redis 只承担 Celery Broker、可重建缓存、限流计数和短期锁，不保存业务事实，不承担工作流状态。项目状态、人工关口、权限、输入哈希、报价版本、引用有效性、`workflow_run`、`task_run` 最终状态、`agent_run` 和审计事件始终以 PostgreSQL 为准。

检索结果缓存的 Key 必须绑定项目、知识范围、文件版本、要求基线、查询哈希和检索配置版本；查询 Embedding 缓存绑定模型版本和标准化查询哈希；草稿预览只缓存临时对象引用。所有缓存设置 TTL，并允许丢失后重建。

Redis 锁只能减少并发，不能替代 PostgreSQL 行锁、唯一约束和幂等校验。Redis 不可用时，任务保持 `QUEUED` 等待补投，检索绕过缓存重新执行，CPU 推理重新计算，限流退化为应用级保护。Redis 故障允许性能下降，但不能改变业务状态和审计结果。

下一步讨论安全与缓存隔离：敏感企业证据是否允许进入缓存，以及缓存内容如何脱敏和清理。

### 10.33 敏感证据缓存边界确认

用户确认 Redis 不缓存完整企业证据、招标文件、章节正文、人员身份证件与联系方式、报价明细或内部审核意见。检索缓存只保存来源片段 ID、文件版本、召回路线、排序分数和过期时间；查询 Embedding 可以缓存，但 Key 使用带模型版本的标准化查询哈希，不保存原始敏感查询文本。

缓存命中后仍必须回 PostgreSQL 校验用户权限、项目归属、文件版本、有效期、保密等级和引用状态，再从 PostgreSQL 或 MinIO 读取正文。缓存不能保存或复用权限判断的最终结果。

检索和重排结果默认缓存 5～15 分钟，脱敏短摘要不超过 15 分钟，查询 Embedding 为 30 分钟至 24 小时，最终根据内存和命中率调整。任何权限或版本校验失败都丢弃缓存并重新检索。

下一步讨论外部大模型和多模态 API 的数据出域边界：哪些内容允许发送、如何最小化、脱敏和记录审计。

### 10.34 外部模型数据出域控制确认

用户确认在 `ModelGateway` 前增加应用内部 `DataEgressGuard`，统一执行数据分类、项目授权、权限、用途、字段白名单、最小化和脱敏，不新增服务或容器。

数据等级为 `PUBLIC`、`INTERNAL`、`CONFIDENTIAL` 和 `RESTRICTED`。项目默认 `PUBLIC_ONLY`，投标经理可以明确批准内部或机密资料的有限使用；`RESTRICTED` 永不出域。项目级 `external_ai_policy`、批准人和批准时间已加入数据字典，文件版本与知识资料同步使用统一数据等级。

文本模型只接收任务所需来源片段、已确认结构化事实和 Schema；多模态模型只接收复杂图表局部裁剪及必要 OCR。账号凭证、完整身份证号码、无关联系方式、完整报价底表、成本明细、内部审核意见、风险豁免和受限数据禁止发送。

每次外部调用使用 `audit_event.metadata_json` 记录供应商、模型、分类、来源对象、字段名、脱敏版本、请求响应哈希、Token 用量和时间，不在普通日志保存完整 Prompt、图片或回复正文。策略拒绝返回 `EXTERNAL_DATA_BLOCKED`，不得自动重试，只能走本地能力或人工处理。

### 10.35 Docker Compose 密钥与凭证管理确认

用户确认 V1 采用 Docker Compose Secrets 配合宿主机仓库外受保护文件，不引入 Vault、云 KMS 或独立密钥管理服务。普通非敏感配置使用环境变量，密码、签名密钥、内部服务凭证和外部 API Key 通过 `/run/secrets/<name>` 按服务最小授权读取。

Secret 文件统一放在 `/opt/bid-agent/secrets/`，不进入 Git、镜像、构建参数或普通 `.env`，由部署专用账号持有，文件权限为 `600`。前端不得读取后端 Secret；PostgreSQL 至少拆分管理员、应用和迁移账号；MinIO 拆分 Root 与应用凭证；MCP 服务凭证不能替代用户和项目权限校验；外部模型 Key 不保存到 PostgreSQL。

日志、异常、健康检查、任务参数、审计元数据和诊断包不得输出 Secret 值、请求头或完整连接串。本地开发只保留不含真实值的 `.env.example`，开发、测试和生产环境不得复用凭证。

轮换采用新旧值短期并存、更新授权、滚动重建调用方、验证新值、撤销旧值的顺序。Compose Secrets 在非 Swarm 模式下不负责加密宿主机文件，因此必须同时依赖宿主机权限、仓库外存放、最小挂载、凭证分权和日志脱敏。未来升级 Vault/KMS 时复用 `*_FILE` 接口，不要求修改业务模块。

### 10.36 身份认证与服务端会话确认

用户确认 V1 使用平台本地账号和 PostgreSQL 服务端 Session，不接入企业统一登录，不开放自助注册。账号只由系统管理员创建、禁用和重置密码，未来预留 OIDC 认证适配器，但不改变既有 RBAC 和项目成员权限模型。

密码使用 Argon2id 哈希。浏览器 Cookie 只保存随机高熵 Session Token，并设置 `HttpOnly`、生产环境 `Secure` 和 `SameSite=Lax`；PostgreSQL 的 `user_session` 只保存 Token 哈希、用户、活动时间、过期时间、重新认证时间和撤销状态。写操作必须执行 CSRF 防护。

会话默认空闲 30 分钟过期，绝对最长 8 小时。修改密码、禁用账号或修改关键平台角色后撤销该用户全部有效 Session。报价确认、风险豁免和最终交接等敏感操作要求重新输入密码。登录失败使用 Redis 短期限流，Redis 故障时退化为应用级保护。

登录、退出、失败登录、密码重置、账号禁用、会话撤销和敏感操作重新认证写入审计。V1 不实现短信或邮箱验证码、Refresh Token、JWT 黑名单、复杂设备管理和多因素认证。

权威数据字典已补充 `user` 登录字段和 `user_session` 对象。下一步讨论反向代理方案，确认 V1 使用 Caddy 还是 Nginx，以及 TLS、上传限制和安全响应头边界。

### 10.37 公网部署与 Caddy 反向代理确认

用户确认 V1 不部署在企业内网，使用正式公网域名和固定公网 IP，DNS 指向单台 Linux 部署服务器。现有 `gateway` 容器确定运行 Caddy，不增加容器。

服务器只向公网开放 `80/443`。Caddy 自动申请和续期 HTTPS 证书并强制 HTTP 跳转 HTTPS；`/api/*` 转发至 FastAPI，其余请求转发至 Next.js。PostgreSQL、Redis、MinIO、MCP、前端和后端容器端口均不直接暴露公网。

单文件上传初始限制为 200 MB，上传请求最长 10 分钟，普通 API 超时 60 秒。上传成功后返回 `task_run_id`，解析、OCR、Agent 和导出继续异步执行。登录与普通 API 执行基础限流，Caddy 添加安全响应头并输出脱敏访问日志。

MinIO 不提供公网匿名访问，下载前必须经过后端权限、项目归属和版本校验，再生成短期签名地址。Caddy 只承担 TLS、路由和入口保护，认证、RBAC、文件授权和业务状态仍由 FastAPI 与 PostgreSQL 负责。

V1 不采用 Nginx + Certbot，不增加云负载均衡、CDN 或 WAF。下一步讨论轻量可观测性方案：结构化日志、错误收集、指标与告警具体使用哪些组件。

### 10.38 零新增容器的本地可观测性确认

用户确认 V1 不接入外部 Sentry，异常堆栈和运行日志不发送第三方平台；需要对服务宕机、任务连续失败、磁盘不足和备份异常主动通知管理员，但通知只包含脱敏摘要。

FastAPI、Celery Worker、MCP 和 Caddy 输出结构化 JSON 日志，贯通请求、项目、工作流、Agent 和任务 ID。Docker 日志初始按单文件 20 MB、最多 5 个文件轮转。文件正文、Prompt、模型完整回复、Cookie、凭证、报价和完整证据不得写入日志；业务审计仍以 PostgreSQL `audit_event` 为准。

管理员运行看板复用 `task_run`、`agent_run`、`workflow_run` 和 `audit_event`，不部署 Grafana。宿主机使用 `systemd timer` 每分钟运行轻量 Watchdog，检查容器健康、服务连通性、Worker 心跳、磁盘、队列、连续失败和备份时效，不新增监控容器。

磁盘超过 80%、失败增加或队列积压触发 `WARNING`；服务连续 3 次不可用、磁盘超过 90%、数据库不可连接、Worker 心跳失效或备份严重过期触发 `CRITICAL`。通过企业微信机器人或管理员邮箱发送环境、服务、错误编号、时间、请求或任务 ID 和后台路径，不发送业务正文或完整堆栈。

V1 不部署 Prometheus、Grafana 和 Loki。后续规模扩大时优先增加 Prometheus + Grafana，只有日志检索成为瓶颈时再增加 Loki。下一步讨论备份与恢复细节，包括频率、保留周期、异机备份和恢复目标。

### 10.39 轻量备份与恢复确认

用户确认 V1 暂不接入云对象存储、NAS 或自动异机备份，采用本机自动备份、每周人工导出加密包和预留 `BackupTarget` 接口的折中方案。该选择不影响 Agent、编制、审核和导出等核心业务功能，但降低整机灾难恢复能力。

备份统一放在 `/opt/bid-agent/backups/`。PostgreSQL 每 6 小时使用 `pg_dump -Fc` 备份，MinIO 每天增量复制，部署配置每天备份；本机保留最近 7 天。每个批次保存应用与迁移版本、对象数量、文件大小、SHA-256 和恢复清单，并校验命令结果、文件完整性和 `pg_restore --list` 可读性。

管理员每周通过部署命令生成 `.tar.age` 加密备份包，下载到管理员电脑、加密移动硬盘或企业批准的网盘。V1 不建设备份管理页面，不自动上传第三方存储，加密私钥不留在部署服务器。

应用内部定义 `BackupTarget`，V1 只实现 `LocalBackupTarget`；`S3BackupTarget` 和 `NasBackupTarget` 只保留 `upload`、`download`、`list`、`verify`、`delete_expired` 和 `health_check` 契约，不提前引入厂商 SDK。

上线前必须在空环境执行一次完整恢复演练，之后每季度一次。本方案不正式承诺 RPO 6 小时或 RTO 4 小时，对外表述为“具备本机自动备份、人工离机副本和恢复演练能力；自动异机灾备待后续接入”。

### 10.47 新建项目三步向导确认

### 10.48 项目总览页面确认

用户确认项目总览采用“项目抬头 + 横向阶段条 + 当前行动卡 + 业务摘要 + 风险与变化”的结构，定位为阶段导航和行动入口，不做复杂数据大屏。

顶部展示项目名称与编号、采购方式、负责人、截止时间、项目状态、当前阶段和当前人工关口。阶段条固定为“文件解析 → 要求与评分 → 响应规划 → 标书编制 → 审核与风险 → 交接与递交”，阶段状态包含未开始、进行中、等待人工确认、已完成、已失效和阻断。

当前行动卡突出当前责任人最需要处理的事项，例如要求基线确认、高风险要求、低置信度结果和复杂图表人工确认，并跳转到对应业务页面。总览不直接执行四个人工关口确认，无权限成员只读查看责任人与状态。

摘要展示文件版本、要求与评分覆盖、章节编制进度、阻断风险、待确认事项和运行任务。其他区域展示阻断与高风险事项、成员待办、最近变化和运行任务；变化数据只来自 `audit_event`、`workflow_run` 与业务版本记录，不展示虚构 Agent 动态。

初版接口为 `GET /api/v1/projects/{project_id}/overview`，返回 `project`、`stage_progress`、`current_action`、`summary`、`blocking_items`、`member_tasks`、`recent_changes`、`running_tasks` 和 `allowed_actions`。Mock 覆盖草稿、解析中、等待要求基线确认、编制中、阻断、临期、等待交接、完成、输入版本失效和只读成员。

下一步讨论“文件与解析”页面，明确文件版本、解析进度、原文对照、OCR 与复杂图表人工确认、解析修正和新澄清文件影响提示。

### 10.49 文件与解析页面确认

用户确认文件与解析页面使用“左侧文件与版本、解析目录和异常筛选；中间原文预览；右侧结构化结果、置信度与人工处理”的三栏校对工作台。页面只处理采购文件的上传、版本、解析、校对、修正和影响提示，不直接确认要求基线、关闭风险或生成标书。

机器解析结果永久保留，人工修正以原值、修正值、处理人、时间和原因组成的新记录保存，不覆盖原始结果。正文、标题、表格、图片和复杂图表使用不同处理方式；复杂图表默认 OCR，按出域策略调用多模态，调用失败、被策略拦截或低置信度时转人工确认并保留原图与 OCR。

截止时间、资格条件、实质性要求、最高限价、评分分值和格式签章要求属于关键字段，其修正必须由投标经理或合规审核人员二次复核。普通低置信度内容可带标记进入要求与评分；关键字段未处理、解析失败或可能影响要求/评分的复杂图表待确认时，不允许发起 `REQUIREMENT_BASELINE_CONFIRMATION`。

澄清、更正和补遗创建新文件版本，不覆盖旧结果。解析后对照当前有效版本与已确认结果，标出影响的要求、评分项、章节和审核结论，创建待办与失效标记，并跳转到对应业务页面处理。旧审核结论转待复核，不删除历史。

所有项目成员可查看文件和解析结果；编写、技术和报价职责成员处理普通修正；投标经理上传、重新解析、查看影响和指派处理责任人；商务与合规审核人员复核关键字段。上传、OCR、重新解析和复杂图表处理统一异步执行并返回 `task_run_id`。

初版采用 8 个接口：文件列表和上传、文件版本查询、解析视图、重新解析、片段修正、修正复核和文件影响查询。Mock 覆盖未上传、解析中、无异常、低置信度、关键字段复核、复杂图表、多模态拦截、解析失败、澄清失效和只读成员。

下一步讨论“要求与评分”页面，确定要求和评分项的工作台结构、证据定位、人工基线确认和澄清后的重新确认方式。

### 10.50 要求与评分页面确认

用户确认要求与评分页面采用同一工作台的三个标签页：“要求清单｜评分项｜冲突与待确认”，每个标签页使用“左侧分类与数量、中间清单与筛选、右侧详情与来源”的布局。该页面确认采购文件要求和评分规则，不匹配企业证据、不生成响应矩阵、不预测得分、不生成标书。

要求项按资格、实质性、技术、格式、时间、商务和其他分类，记录强制等级、后果、来源、置信度和状态。资格、实质性、截止时间、格式签章等关键要求逐条确认；低风险同类项可批量确认，但必须显示数量、共同来源范围和审计摘要。

评分项记录评分维度、分值、条件、评分方式、材料要求和来源。评分方式包括客观、主观、公式、混合和无法判断；材料要求只表示采购文件所需材料，不表示企业已经满足。主观评分只记录覆盖目标，不能预测得分；公式不完整、单位或上下限无法确定时标记规则歧义。分值、公式、报价评分规则、门槛和材料要求修正必须逐条确认。

冲突页集中处理跨文件冲突、澄清覆盖、关键字段低置信度、重复或矛盾要求、评分表与正文不一致和规则不完整。“已豁免”只能记录规则解释或处理方式决定，不能豁免资格、实质性或法定要求；无法确定时保持阻断。澄清或文件版本变化后，旧要求基线标记 `STALE`，通过新版本重新确认，不覆盖历史。

第一个人工关口 `REQUIREMENT_BASELINE_CONFIRMATION` 只有在当前有效文件解析完成、关键字段完成必要复核、影响要求/评分的复杂图表已处理、没有未解决阻断项、要求与评分均可定位来源时才能发起。投标经理负责确认，合规审核人员协助复核但不能代替确认。确认后创建只读 `Requirement Baseline`，响应规划只读取已确认且未失效的版本。

初版使用 10 个接口，覆盖要求、评分、冲突查询，要求修改、合并、拆分，基线校验、确认和当前版本查询。Mock 覆盖无异常、低置信度、高风险、公式完整/歧义、截止时间冲突、澄清失效、门禁未满足、可确认、已确认只读和只读成员。

### 10.51 响应规划页面确认

用户确认响应规划页面使用“响应矩阵、评分覆盖、章节与任务、缺口与冲突”四个标签页，将已确认要求基线转换为响应方式、证据候选、评分覆盖、章节任务、责任人和报价依赖。语义相似证据只能作为候选，不自动判定满足；主观评分不预测得分；不适用理由和关键证据用途必须人工确认。

只有高风险响应方式、证据用途、评分映射、缺失材料任务、章节负责人、报价依赖和阻断均处理完成时，投标经理才能通过 `RESPONSE_PLAN_CONFIRMATION`，创建只读 `Response Plan Baseline`。初版使用 8 个接口，Mock 覆盖无基线、规划中、证据缺失、报价未确认、冲突、可确认、只读和输入失效。

### 10.52 标书编制页面确认

用户确认标书编制页面采用左侧章节目录、中间结构化编辑器、右侧要求/评分/证据/历史参考的布局。章节按内容块保存，人工编辑默认锁定；无来源时创建待补充项，历史标书不得作为当前事实，报价未确认时只显示占位，图表必须记录数据来源，局部重生成不能静默覆盖人工内容。

编辑采用乐观锁并显式处理版本冲突。只有必备章节、关键要求和评分覆盖、有效引用、确认报价、内外内容隔离和阻断待补充项均通过时，才可发起 `CHAPTER_DRAFT_CONFIRMATION`。章节负责人确认本人章节，投标经理完成阶段确认。初版使用 8 个接口。

### 10.53 审核与风险页面确认

用户确认审核与风险页面使用“审核总览、审核问题、风险清单、一致性检查”四个标签页，覆盖资格合规、评分覆盖、商务报价、技术响应、格式签章、跨章节一致性和引用有效性。编写人不能关闭自己的问题；商务和合规审核只能关闭各自审核域的问题。

阻断风险必须解决，高风险接受必须留存依据、责任人和有效范围。只有审核域全部完成、无阻断、整改已复核、报价和一致性通过、引用有效且输入未失效时，才能发起 `REVIEW_RESULT_CONFIRMATION`。商务与合规审核分别确认审核域，投标经理完成阶段确认。初版使用 10 个接口。

三页按要求基线、响应计划基线、章节草稿基线和审核结果串联；要求变化整体失效，证据和报价变化精确失效，人工章节修改只重开关联审核。下一批讨论交接与递交、项目记录。

### 10.54 交接与递交页面确认

用户确认交接与递交页面采用“交接准备、交接包、递交记录”三个标签页。交接门禁必须检查审核结果确认、全部输入版本、阻断与高风险、报价、附件、内外内容隔离、DOCX/PDF 生成条件和递交责任人；失败时显示原因和跳转，不允许绕过。

投标经理重新输入密码并确认内部交接后创建只读 `HANDOVER_BASELINE`。任何正文、证据、报价、附件或采购文件变化都会使基线与旧交接包失效。交接包包含正式 DOCX、同源 PDF、附件/版本清单、检查清单、哈希和内部说明；部分成功不能作为有效交接包。

递交责任人确认接收最新交接包后，人工完成外部递交并登记时间、渠道、状态、流水号、原因、备注和回执。平台不登录交易平台、不操作 CA。初版使用 10 个接口，Mock 覆盖门禁、生成、接收、递交和失效状态。
