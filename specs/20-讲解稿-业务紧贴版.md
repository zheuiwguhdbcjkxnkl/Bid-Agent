## 0. 开场 30 秒：这个系统有什么用？（功能：必须是有用的）

> **一句话**：这是一个服务投标企业的**投标文件智能编制与合规审核工作台**——企业输入一个项目编号，系统自动完成「读招标文件 → 抽要求 → 配证据 → 写标书 → 审合规 → 内部交接留痕」全流程，**把重复、标准化、可规则化的工作交给 AI，人只做判断和拍板**。

**为什么「必须是有用的」**（对应 PRD 九个业务痛点的核心）：

| 业务痛点（真实存在） | 系统给的功能 | 对应模块 |
|---|---|---|
| 标书编写人反复读招标文件、逐条对要求 | 自动解析 + 要求抽取 | FR-201 / FR-301 |
| 数据口径不统一、Excel 反复对 | 报价规则校验 + 单一数据源 | FR-501 |
| 写完才发现承诺无依据（合规暴露偏后） | **Agent 预检 + 引用校验 + 风险中心** | FR-701 / FR-702 |
| 版本、分发记录不清 | 交接基线 + 哈希 + 审计 | FR-801 |
| 同类项目重复劳动 | 历史参考池 + 差异说明 | FR-402 |

**金句**：「我们不替代人做投标决策，我们替代的是**反复读文件、对要求、查证据、改格式**这些标准化劳动——人把时间花在报价策略、方案判断这些真正值钱的事上。」

## 1. 业务全流程（15 步闭环，对应 V1主业务流程图.html）

```text
①输入项目代码 → ②自动获取/人工补充采购文件 → ③确认有效文件版本
→ ④提取项目事实/要求/评分项/时间节点 → ⑤匹配企业证据与历史参考
→ ⑥人工确认响应矩阵和报价版本 → ⑦生成带引用的标书初稿
→ ⑧工作台展示任务/结论/证据/风险/进度 → ⑨预览章节/来源/图表
→ ⑩Agent 预检 → ⑪人工审核/退回/结构化修改 → ⑫关闭阻断问题
→ ⑬冻结内部交接版本 → ⑭责任人确认接收 → ⑮保存版本/清单/哈希/审计
```

**四个阶段 × 四道人工关口**（业务层的人机责任边界）：

| 阶段 | 关口 | 谁确认 | 确认什么 |
|---|---|---|---|
| 文件理解与规划 | ①要求基线确认 | 投标团队 | 理解对不对 |
| 文件理解与规划 | ②响应计划确认 | 投标团队 | 怎么答 |
| 编制与审核 | ③章节草稿确认 | 编写人 | 答得好不好 |
| 编制与审核 | ④审核结论确认 | 审核人 | 能不能交 |

> **核心设计思想**：Agent 可以生成、可以建议，但**四个阶段级关口必须人工确认**。**Agent 干活，人拍板。**

## 2. 版本规划：V1 / V2 / V3 各做什么（对应 16 号版本规划）

**一条主线**：**V1 做深，V2 做广，V3 做厚**——先跑通单项目闭环，再扩场景和协同，最后把积累的数据变成质量运营能力。

| 版本 | 定位 | 做什么 | 解决什么问题 |
|---|---|---|---|
| **V1**（当前实施） | 单项目标书生成与内部交接工作台 | 从输入项目代码到内部提交留痕的**完整闭环**：解析→抽取→匹配→编制→审核→交接→留痕，四个 Agent + 六项工作台能力 | 「写标书的重复劳动 + 合规暴露偏后」——**先把一件事做对做深** |
| **V2**（已确认方向） | 多场景与团队协同增强版 | 更多标书类型、更多数据源与持续监控、历史模板增强、报价策略增强、团队协同、客户版与对外版本 | 「场景窄、单人用」——**横向扩场景、支持团队** |
| **V3**（已确认方向） | 投标质量运营与平台化版本 | 投标质量评估产品化、Agent 与模型回测、跨项目知识沉淀、平台化与生产级能力 | 「数据积累后怎么持续改进」——**纵向把数据变成运营能力** |

**V1 内部六个里程碑**（研发顺序，不是对外版本）：M1 项目与文件 → M2 要求与证据 → M3 标书生成与工作台 → M4 审核合规与返工 → M5 内部交接与版本留痕 → M6 评估修复与交付验收。

**演进原则**（16 号原文精神）：
- V1 坚持「场景做窄、核心做深」——用有限场景验证来源、权限、人工关口、状态、版本、失败恢复、审计、证据追溯，**不以功能数量代替企业级深度**
- 新版本在上一版本核心闭环稳定后启动；优先复用 V1 的项目/文件/要求/证据/章节/审核/审计对象
- **不为后续版本提前建设没有 V1 使用价值的通用平台能力**

> **讲法**：V1 回答「能不能做对一件事」，V2 回答「能不能做更多场景」，V3 回答「能不能越做越好」——**现在所有精力在 V1，把一条闭环磨到能过四层评估**。

## 3. A2A：五个智能体各自干什么、怎么通信？（我负责的核心，对应 投标Agent编排架构图.html）

### 2.1 先认识五个智能体（每个是干什么的）

| 智能体 | 一句话职责 | 业务上回答的问题 |
|---|---|---|
| **Supervisor（总控）** | 任务拆分、路由决策、状态流转、人工关口调度、失败恢复 | 「下一步谁干、要不要停」 |
| **招标理解与合规 Agent** | 读招标文件，抽取资格条件、实质性要求、评分项、时间节点 | 「招标方要什么、哪些是硬杠」 |
| **响应规划与评分 Agent** | 把要求映射成响应矩阵，匹配企业证据，检查评分项覆盖 | 「每条要求怎么答、拿什么证明」 |
| **标书编制 Agent** | 按响应矩阵生成带引用的章节初稿，支持局部重写和锁定保护 | 「每章写什么、引用哪个证据」 |
| **质量与风险复核 Agent** | 检查覆盖度、引用正确性、跨章节一致性，风险分级并给返工建议 | 「哪里有问题、风险多高、该谁改」 |

> 注：交接基线之后的「门禁判定 + 导出交接包」不是 Agent 干的——是**确定性交接任务**（无模型参与，规则写死）。**稳定步骤工具化，不让模型碰规则**。

### 2.2 通信流程：一次投标任务里它们怎么接力（重点）

```text
① 用户发起/恢复任务 → 加载校验节点（校验权限/版本/输入哈希）
② Supervisor 路由决策（输出七种结构化决策之一：DISPATCH_AGENT）
③ ──A2A 派发──▶ 招标理解与合规 Agent
      ├─ 收「结构化任务 + 文件版本引用」（不传文件正文）
      ├─ 干活（Skill 指导 + MCP 工具：document.ingest / knowledge.search）
      └─ 回传：结构化产物引用（RequirementSet）
④ Supervisor 判断 → 进入【人工关口①：要求基线确认】→ 投标团队确认
⑤ ──A2A 派发──▶ 响应规划与评分 Agent
      ├─ 收「要求基线引用 + 企业证据范围」
      └─ 回传：响应矩阵 + 证据匹配结果
⑥ 【人工关口②：响应计划确认】→ 投标团队确认
⑦ ──A2A 派发──▶ 标书编制 Agent
      ├─ 收「响应矩阵引用 + 报价版本引用」
      └─ 回传：章节草稿（带证据引用）
⑧ 【人工关口③：章节草稿确认】→ 编写人确认
⑨ ──A2A 派发──▶ 质量与风险复核 Agent
      ├─ 收「章节版本引用」
      └─ 回传：问题清单 + 风险分级（阻断/高/中/低）
⑩ 【人工关口④：审核结论确认】→ 审核人确认
⑪ 确定性交接任务：门禁校验（business.evaluate_gate）→ 冻结交接基线
⑫ 导出交接包（document.export）→ 递交登记 → 全程审计留痕
```

**通信的三个规矩**（A2A 契约）：

1. **只传结构化消息**：任务、业务对象引用、上下文引用、产物引用 + 阻断原因、人工关口状态、下一步动作——**绝不传整份文件、完整资料、自由文本记忆**（正文永远按引用去 PostgreSQL 读）
2. **干完回传也是结构化产物引用**，不是「我干完了」的自由文本
3. **每条消息绑定 workflow_run_id + 收发方 + 阶段 + 输入版本**——谁在什么时候让谁做了什么，全链路可追溯

> **A2A vs MCP 一句区分**：A2A 是智能体之间的「交接单」（谁把活交给谁），MCP 是智能体与系统能力的「工具间」（干活时碰什么工具）——**A2A 管交接，MCP 管干活**。

## 4. Skills：4 个专业 Skill（白名单表共 6 个调用方）（我负责的核心）

**先说清数量**（17 号 3.1.1 / 3.1.4 原文）：

- **4 个专业业务 Skill**（4 个聚合能力域）——绑定 4 个专业 Agent
- 白名单表共 **6 行调用方**：4 个专业 Skill + Supervisor + 确定性交接任务（后两者是**系统调用方**，不是业务 Skill）
- 早期方案曾是「6 个 Skill + 7 个工具服务」，后来**聚合收敛为 4 个聚合能力域 + 1 个 MCP Server**，避免重复边界和部署负担

**4 个专业 Skill × Agent × 业务环节**：

| # | Skill | 绑定的 Agent | 对应业务环节 |
|---|---|---|---|
| 1 | 招标文件理解 | 招标理解与合规 Agent | ④提取要求/评分项 |
| 2 | 响应规划与证据匹配 | 响应规划与评分 Agent | ⑤⑥响应矩阵 |
| 3 | 带引用标书编制 | 标书编制 Agent | ⑦章节生成 |
| 4 | 质量与风险复核 | 质量与风险复核 Agent | ⑩Agent 预检 |

**Skill × Agent 对应关系**（每个专业 Agent 绑 1 个 Skill）：

```text
招标理解与合规 Agent  → 招标文件理解 Skill
响应规划与评分 Agent   → 响应规划与证据匹配 Skill
标书编制 Agent        → 带引用标书编制 Skill
质量与风险复核 Agent   → 质量与风险复核 Skill
```

**白名单表另外 2 个调用方（不是 Skill）**：

```text
Supervisor      → 是 Agent（主智能体），但不绑业务 Skill——行为是七种结构化路由决策（代码规则）
确定性交接任务   → 不是 Agent（无模型参与）——门禁 + 导出规则写死
```

> 它们出现在白名单表里，是因为**它们也调 MCP 工具（读上下文、判门禁、导出），防越权必须给所有调用工具的主体登记权限清单**——但「有白名单行」≠「是 Skill」。

**Skill 是什么**（17 号 3.1.3 完整定义）：版本化业务能力包，**七个要素的组合**：

```text
SkillManifest = 业务目标 + Prompt（教模型怎么干业务）
              + 输入输出 Schema（格式）
              + 业务规则 / 引用要求 / 拒答要求（规矩和红线）
              + allowed_tools（工具白名单）← 只是七个要素之一
              + 失败策略（timeout / max_retries）
```

**概念层级**（防混淆的关键）：

```text
Skill = 完整业务能力包（Prompt + 规则 + Schema + 白名单 + ...）
白名单 = Skill 的其中一个字段（「允许碰哪些工具」）
白名单表 = 所有调用方的工具权限清单（4 个 Skill + 2 个系统调用方）
```

> **「调用工具」≠「Skill」**：Skill 是「教模型怎么干业务」的完整能力包；Supervisor 没有业务 Prompt 和规则，所以只是白名单表上的「调用方」，不是 Skill。`skill_id + skill_version` 在一次 agent_run 内固定。

**为什么不用 SKILL.md 而用 SkillManifest**（三个理由递进）：
1. **形态**：SKILL.md 是给开发工具读的 markdown 文档；SkillManifest 是代码内结构化定义，过 Schema 校验、随部署走
2. **1:1 绑定**：每个 Agent 固定绑 1 个 Skill，不需要「渐进式披露」（SKILL.md 的目录+按需加载机制用不上）
3. **版本管理**：改 Skill 走「改定义 → bump 版本 → 校验 → 部署」四步；agent_run 记录每次用了哪个版本——审计、回滚、权限边界

**Skill 怎么评估**（15 号评估体系，触发率 = 业务环节质量指标）：

| 业务环节（Skill） | 关键评估指标 | 最低发布线 |
|---|---|---|
| 要求抽取（Skill 1） | 普通要求**召回率**、分类准确率、原子化准确率 | 召回 ≥95%，分类 ≥93% |
| 要求抽取（Skill 1） | 高风险要求召回率 | **100%（零容忍门禁）** |
| 响应规划（Skill 2） | 响应矩阵映射准确率 | ≥95% |
| 证据匹配（Skill 2） | Recall@10、nDCG@10、无证据拒答正确率 | 拒答 ≥98% |
| 章节生成（Skill 3） | 普通要求覆盖率、有证据事实支持率 | ≥95% / ≥98% |
| 风险审核（Skill 4） | 中低风险召回率、阻断风险召回 | 阻断风险 **100%** |

> **讲法**：Skill 不是「会什么功能」，而是「**在这个业务环节，按什么规矩干活**」——每个 Skill 的触发就是对应业务环节的完成，所以评估直接对标业务指标（召回率、覆盖率），**Skill 触发率 = 该环节自动化完成的正确率**。

## 5. MCP：14 个方法，公共工具 + 白名单领用（我负责的核心）

**数量**：V1 冻结为 **4 个工具域、14 个 MCP 方法**（17 号 3.1.4）——不拆 20+ 细工具，也不做带大量 operation 参数的万能方法。

**定性先行：工具是公共的还是专属的？**

> **全部 14 个方法是「公共工具」**——统一注册在 bid-tools-mcp 一个 Server 里，不归任何单个 Agent 所有；**但「谁能领」由 Skill 白名单决定**（SkillManifest 声明 + MCP Server 二次校验）。所以准确说法是：**公共工具箱 + 白名单领用**；其中 2 个是「公共注册、专属领用」的特殊工具。

**完整映射：每个方法 → 调用它的 Skill → 解决什么问题**（17 号 3.1.4 白名单表）：

| 方法 | 谁在用（Skill） | 解决什么问题 |
|---|---|---|
| `document.ingest` | 招标文件理解 | 把 PDF/Word 解析成结构化 Document IR（版本/页面/片段） |
| `document.read` | 招标文件理解、带引用标书编制、质量与风险复核 | 按版本/页码/片段读取原文 |
| `document.render` | 带引用标书编制、质量与风险复核 | 根据章节内容块生成预览 |
| `document.export` 🔒 | **仅确定性交接任务** | 生成 DOCX/PDF 交接文件（专业 Skill 不开放） |
| `project.get_context` | 4 个专业 Skill + Supervisor + 确定性交接 | 读当前项目、有效版本、基线、人工关口摘要 |
| `project.validate_inputs` | 4 个专业 Skill + 确定性交接 | 检查文件/要求/证据/报价/章节/审核输入是否仍有效 |
| `project.validate_transition` | Supervisor、质量与风险复核 | 判断状态转换和前置条件是否合法 |
| `knowledge.search` | 招标文件理解、响应规划与证据匹配、带引用标书编制 | 统一检索招标文件 + 企业证据 + 历史参考 |
| `knowledge.read_sources` | 招标文件理解、响应规划、标书编制、质量复核 | 读取命中项对应的完整来源片段和版本信息 |
| `knowledge.validate_citations` | 质量与风险复核 | 检查引用是否存在、版本有效、内容相符、用途允许 |
| `business.validate_structure` | 4 个专业 Skill | 校验要求/响应矩阵/章节/审核结果的结构 |
| `business.validate_quote` | 响应规划与证据匹配、带引用标书编制 | 限价、金额、计算公式、税率、单位校验 |
| `business.check_consistency` | 带引用标书编制、质量与风险复核 | 跨章节/证据/人员/日期/参数/承诺一致性检查 |
| `business.evaluate_gate` 🔒 | **仅 Supervisor + 确定性交接任务** | 检查人工关口和交接门禁是否满足（专业 Skill 不开放） |

**共用 vs 独占的真实例子**（讲公共性最好的三个例子）：
- `knowledge.search`——**3 个 Skill 共用**（理解/规划/编制都要检索）
- `business.validate_structure`——**4 个专业 Skill 全用**（每个环节输出都要过结构校验）
- `document.export`——**1 个独占**（只有确定性交接任务能碰，标书编制 Agent 想导也导不了）

**MCP 是什么**：工具协议层 + 能力适配层（bid-tools-mcp，一个 MCP Server，内部 Streamable HTTP）。**调用 = 双保险校验**：Skill 白名单声明 + MCP Server 二次校验（服务凭证 → 白名单 → 项目权限 → 版本有效性）。每次调用记录 `request_id / trace_id / skill_id / skill_version` ——**谁、在哪个项目、哪个 Agent、用哪个 Skill 版本、调了什么工具，全链路可审计**。

> **讲法**：14 件工具全公共（一个工具间），但领用权在白名单（胸牌）——**12 件多 Skill 共用，2 件专属领用（导出、门禁判定）**。导出和门禁这两个高风险动作，从工具层就封死了专业 Agent 越权的可能，这是合规审核平台的底线设计。

## 6. 记忆机制（我负责的核心，对应 记忆与上下文流转图.html）

**两类真记忆**（存储侧）：

| 记忆 | 存在哪 | 装什么 | 类比 |
|---|---|---|---|
| 长期业务记忆 | PostgreSQL + MinIO | 要求基线、响应计划、章节版本、审核结论、企业证据、历史参考、人工确认、审计 | **档案柜**（业务事实源） |
| 短期运行记忆 | LangGraph Checkpoint + workflow_run/agent_run/task_run | 当前阶段、已完成节点、待处理关口、失败原因、重试次数 | **值班日志**（恢复执行用） |

**三条铁律**：
1. **Checkpoint 不存业务正文，只存 ID 引用**——业务正文永远在 PostgreSQL 查，恢复时重新校验 input_hash
2. **Agent 不能直接写长期记忆**——输出结构化产物 → 领域服务校验（权限/版本/规则/人工关口）→ 才形成新业务版本。**模型自由文本永远成不了业务事实**
3. **长期记忆版本化、可授权、可引用、可失效**——旧基线标 STALE，新基线创建，从不覆盖历史

**金句**：记忆是仓库（档案柜+值班日志），模型说的话只有变成结构化产物、过了校验，才配进仓库。

## 7. 上下文管理与压缩（我负责的核心）

**Context Envelope 机制**（喂给模型侧）：

```text
每次 Agent 运行前，Context Manager 根据：
  input_refs / input_hash / 当前人工关口 / 用户权限 / 项目职责 / 有效业务版本
→ 组装 Context Envelope（只装当前任务必需的摘要、结构化对象、来源引用）
→ 需要正文时通过 document.read / knowledge.read_sources 按引用读取
→ 绝不把全部文件和历史对话一次性塞入模型上下文
```

**三层压缩防爆炸**：

| 层 | 机制 | 内容 |
|---|---|---|
| 第 1 层 | Skill 紧凑定义 | 1 个 Skill 的结构化定义（固定加载） |
| 第 2 层 | Context Envelope | 摘要 + 引用清单（按任务组装） |
| 第 3 层 | 正文按引用读取 | 整份招标文件绝不预装，需要哪页读哪页 |

**类比**：胸牌印一行岗位+规矩（Skill），进考场只带当前题目的纸条（Envelope），书留图书馆按借书单取用（按引用读取）——**不是把整本操作手册背进考场**。

**诚实说明**：机制已确认；具体 token 预算数字待实测后写文档，不预先承诺。

## 8. 系统怎么跑起来（简单过一遍，对应 V1总体架构图.html）

**就四条流程线**（指着图从左往右讲）：

```text
① 用户操作：浏览器打开系统 → 一个入口（自动 HTTPS 加密）→ 进页面/接口
② 请求直达：页面操作 → 后端接口 → 直接读写数据库（查项目、确认关口等即时操作）
③ 后台任务：耗时长的活（解析文件、跑 Agent、导出标书）→ 丢进任务队列
             → 后台工人排队执行 → 干完写回数据库
④ 文件存取：招标文件、导出的标书 → 存文件仓库；数据库只存「文件在哪、是什么、谁能拿」
```

**部署一句话**：单机一台服务器 + Docker 一键拉起全部服务；公网只有**一个入口**，数据库、文件仓库、Agent 工具间全在内网，外面碰不到。

**我负责的部分（金色 2 个节点）**：③ 后台任务里的 **Agent 运行** + Agent 干活用的 **工具间**（MCP Server）——其余前后端由团队共建。

**金句**：一条线走即时请求，一条线走后台任务；金色是大脑（Agent），其余是身体（底座）。

## 9. 数据怎么流转（一条线走完，业务语言版）

```text
输入：项目编号 + 招标文件
  ↓ 解析：文件变成结构化「片段」（每段带页码、原文位置）
  ↓ 抽取：识别出资格条件、实质性要求、评分项（每条都能回溯到原文）
  ↓ 匹配：要求 ↔ 企业证据 ↔ 历史参考（响应矩阵成形）
  ↓ 编制：按响应矩阵写章节（每段内容带引用，有依据才敢写）
  ↓ 审核：发现问题清单 + 风险分级（阻断/高/中/低）
  ↓ 冻结：交接基线锁定版本（旧版本标失效，从不覆盖）
  ↓ 导出：DOCX/PDF + 文件哈希
输出：递交登记 + 全程审计记录（谁在什么时候做了什么，可查）
```

**三个要点**：
1. Agent 的输入输出都是**结构化格式**（不是聊天文本），过 Schema 校验
2. 高风险结论必须能定位到原文片段，不能只写「见文件第 X 页」
3. 所有输出过校验才入库——**「有依据才敢写」是数据流的灵魂**

## 10. 每一步怎么评估？（对应 15 号评估体系，对应 评估四层金字塔图.html）

**四层评估金字塔**（自下而上分层准入）：

| 层级 | 评估什么 | 通过意味着 |
|---|---|---|
| **L1 单模块** | 9 个模块各用九字段评估卡独立评估 | 模块发布与链路测试准入 |
| **L2 业务链路** | 5 条子链路（项目→解析、要求→响应依据、报价→章节、初稿→返工、变更→递交） | V1 技术完成 |
| **L3 单项目端到端** | 五类项目样本全流程闭环（四道判定门） | 交付验收与试点就绪 |
| **L4 试点业务价值** | 真实项目旁路 vs 人工基线（五类价值指标） | 扩大使用决策 |

**评估三原则**：

1. **分层准入**：上游不过，不进下游
2. **零容忍优先**：资格、否决项、实质性要求、关键报价、阻断风险必须 **100% 正确**，不能被普通指标高分抵消
3. **两级阈值**：最低发布线（必须达标）+ 目标优秀线（持续优化），禁止跨域抵消

**每一步怎么评估（业务环节 × 指标速览）**：

| 业务环节 | 怎么评估 |
|---|---|
| 数据接入 | 自动获取成功率 ≥90%；人工上传兜底 100% |
| 文档解析 | 正文识别 ≥97%；表格还原 ≥92% |
| 要求抽取 | 普通要求召回 ≥95%；**高风险要求召回 100%** |
| 证据检索 | Recall@10 ≥90%；无证据拒答正确率 ≥98% |
| 章节生成 | 普通要求覆盖率 ≥95%；有证据事实支持率 ≥98% |
| 风险审核 | 阻断风险召回 100%；中低风险召回 ≥90% |
| 交接递交 | 版本失效、状态转换、哈希、审计 **100% 正确** |
| 效率指标 | 人工时间变化率、退回轮次、人工接管率（跟人工基线对比） |

**金句**：L1 证明模块能用，L2 证明链路能跑，L3 证明闭环能交，L4 证明业务值得——**四层都过，才敢上线**。

## 11. 多余功能：V1 明确不做什么（对应 16 号版本规划）

**V1 坚持「场景做窄、核心做深」**——以下明确不做（这些是 V2/V3 的事，不提前建设）：

| 不做的事 | 为什么不做（V1 的边界理由） |
|---|---|
| 通用 BPMN 工作流引擎 | 用固定投标流程，做深比做泛重要 |
| 自动定时监控公告 | 支持手动刷新/人工补充即可 |
| 在线 Office、多人实时编辑 | 提供章节预览和可编辑导出足够 |
| 自动外部平台递交、CA 签章 | 递交必须人工，责任边界清晰 |
| 自动最优报价引擎 | 报价决策必须商务人员+项目负责人确认 |
| Skill 市场、动态安装、第三方工具接入 | 14 个受控工具够用，开放性不是 V1 目标 |
| 大规模跨项目分析、中标归因 | 数据量不够，先跑通单项目闭环 |
| 多个 MCP Server 编排 | 1 个 Server + 4 域 14 方法足够 |

**边界哲学**：收敛的是**场景广度和自动化复杂度**，**不降低**正确性、权限、版本、人工确认、审计、拒答、阻断、可追溯的质量底线。
