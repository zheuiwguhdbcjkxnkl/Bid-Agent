## 零、文档职责与使用规则

### 0.1 文档职责

本文档是 V1 的正式评估基线，负责定义：

- `L1` 单模块评估；
- `L2` 业务链路评估；
- `L3` 单项目端到端评估；
- `L4` 试点业务价值评估；
- 测试数据、金标准、指标公式、门禁、样本量、失败处理、回归和评测报告要求。

本文档不改变 PRD 已确认的产品范围、人工决策权和质量底线。技术方案、开发计划和测试实现可以细化执行方式，但不得降低本文档规定的零容忍门禁。

### 0.2 真实性边界

- 模拟评测结果只能证明受控数据下的技术正确性和安全边界；
- 旁路试点结果只能证明试点样本中的业务表现；
- 正式生产结果必须与模拟评测、隐藏验收和旁路试点结果分开报告；
- 未评测指标必须标记为“未评测”或“待继续评测”；
- 不得用模拟数据推算甲方已经实现的效率提升、成本下降或中标率改善；
- 中标率只作为长期观察指标，不作为 V1 核心验收标准。

### 0.3 人机责任边界

Agent 可以执行提取、检索、生成、校验、推荐、预检、影响分析和修改建议，但不能替代人工决定：

- 是否投标；
- 最终报价；
- 企业事实和证据是否可用于当前项目；
- 风险是否接受或豁免；
- 审核是否通过；
- 是否完成内部交接；
- 是否执行外部递交。

正确拒答、阻断、降级或转人工属于有效系统结果，不因自动化率下降而直接判定失败。

### 0.4 V1 评测范围边界

评测对象以 PRD v3.0 收敛后的 V1 范围为准：一个主要数据连接器或受控模拟连接器、人工上传兜底、手动刷新、少量受控历史候选、至少一个受控 Excel 报价模板、固定审核路径、对象级或章节级影响判断、内部交接和简单人工递交记录。

以下能力不进入 V1 的 L1、L2 和 L3 验收：多连接器覆盖率、自动定时监控、大规模历史项目分析、高级报价策略模拟、通用审批配置、字段级精确影响分析、自动最小化增量复核、客户版复杂分发控制和外部平台深度集成。

范围收敛不降低质量底线。来源、权限、版本、状态、人工关口、拒答、阻断、哈希、审计和证据追溯仍按零容忍或既定高风险门禁评估。

### 0.5 M1第一纵向切片验收矩阵

M1第一纵向切片只验收认证会话、个人工作台、项目创建、项目列表和项目总览，不据此宣称完整M1、L1或L2通过。至少执行以下自动化测试：

| 验收域 | 必测行为 | 通过条件 |
|---|---|---|
| 认证 | 正确登录、错误凭据、禁用账号、Session查询、退出 | 错误凭据不泄露账号存在性；撤销后不可继续访问 |
| 会话 | 空闲30分钟、绝对8小时、改密撤销其他Session | 过期与撤销状态以PostgreSQL为准，Cookie原文不入库不入日志 |
| 首次改密 | `must_change_password=true`访问业务接口 | 只允许Session查询、退出和修改密码，其余返回`PASSWORD_CHANGE_REQUIRED` |
| Cookie与CSRF | Cookie属性、缺失或错误CSRF Token | Session Cookie为`HttpOnly`，生产启用`Secure`；非法写请求返回`CSRF_VALIDATION_FAILED` |
| 登录防护 | 非法来源、账号与来源组合限流、Redis降级 | 非法来源被拒；超限返回`LOGIN_RATE_LIMITED`；Redis故障不改变账号状态 |
| 组织与权限 | 非投标经理创建、跨组织负责人、无成员关系查看项目 | 分别返回`FORBIDDEN`、`OWNER_ORGANIZATION_MISMATCH`或资源权限错误，不泄露他组织数据 |
| 创建事务 | 项目、主标包、负责人关系、幂等结果和审计 | 任一步失败全部回滚，不产生半成品业务事实或成功幂等响应 |
| 创建幂等 | 缺失键、同键同请求、同键不同请求、并发重放、事务失败后同键重试 | 强制`Idempotency-Key`；缺失返回`IDEMPOTENCY_KEY_REQUIRED`；同请求返回首次结果；不同请求返回`IDEMPOTENCY_CONFLICT`；并发只产生一个项目；失败事务不留下成功响应且可安全重试 |
| 项目查询 | 列表过滤、只看我的项目、总览权限与空运行态 | 只返回有权项目；未实现的运行集合为空，不伪造Agent动态 |
| 审计 | 登录成功/失败、退出、改密、会话撤销、项目创建 | 组织归属正确；项目与操作者可空规则正确；不保存密码、Token原文或完整Cookie |
| 错误契约 | 认证、权限、校验、幂等、内部错误 | 错误体均包含`code`、`message`、`request_id`、`details`，内部错误不暴露堆栈 |

第一切片测试使用独立PostgreSQL测试库，不使用SQLite替代PostgreSQL事务、部分唯一索引和并发幂等语义。

## 一、四层评估与发布关系

### 1.1 四层评估

```text
L1 单模块评估
→ L2 业务链路评估
→ L3 单项目端到端评估
→ L4 试点业务价值评估
```

| 层级 | 评估对象 | 核心问题 | 结论用途 |
|---|---|---|---|
| `L1` | 单个模块的输入、输出、规则、版本、拒答和人工兜底 | 模块是否达到进入业务链路的最低要求 | 模块发布与链路测试准入 |
| `L2` | 多模块之间的数据传递、确认、异常处理和版本传播 | 链路是否完成真实业务任务 | V1 技术完成 |
| `L3` | 从项目输入到内部交接和人工递交记录的完整项目 | 是否形成正确、安全、可审核、可追溯的闭环 | V1 交付验收与试点就绪 |
| `L4` | 真实项目旁路数据与人工基线对比 | 是否产生可验证的真实业务价值 | 业务价值验证与扩大使用决策 |

### 1.2 发布关系

```text
核心 L1 + 五条 L2 通过
→ V1 技术完成

L3 通过
→ V1 交付验收通过、试点就绪

L4 业务价值验证通过
→ 可进入扩大使用或规模化推广决策
```

L4 的通过、未通过或待继续评测不直接撤销已经完成的 L3 软件交付验收。若 L4 发现新的零容忍缺陷，则按缺陷影响范围重新评估相关 L1、L2 或 L3，并依据复评结果处理状态。

### 1.3 通用原则

1. **零容忍优先**：严重错误不能被普通指标高分抵消；
2. **分层准入**：上游评估未通过，不进入下游评估；
3. **证据优先**：每个结论必须保留输入、版本、金标和结果证据；
4. **版本冻结**：数据集、指标公式、阈值和系统配置必须版本化；
5. **隐藏验收**：正式验收集不得用于调优；
6. **人工复核**：金标准和业务结论必须由有权人员确认；
7. **失败回归**：严重失败样本必须进入固定回归集；
8. **禁止综合分掩盖风险**：L3 和 L4 不使用一个综合总分替代分域判断。

## 二、评测数据体系

### 2.1 数据集分层

| 数据集 | 初始规模 | 用途 | 是否允许调优 |
|---|---:|---|---|
| 开发冒烟集 | 5 个项目 | 校准指标、发现失败模式、验证评测工具 | 允许 |
| 隐藏正式验收集 | 15 个项目 | L3 正式验收 | 不允许 |
| 固定回归集 | 初始含 5 个冒烟项目 | 版本变更后的持续回归 | 允许执行，不允许删除失败样本 |
| L4 探索性旁路集 | 建议至少 5 个真实项目 | 验证指标采集和建立前瞻性基线 | 不用于模型直接训练 |
| L4 正式配对试点集 | 建议人工组、Agent 组各不少于 10 个项目 | 业务价值验证 | 不允许事后改变指标口径 |

### 2.2 L3 五类项目

开发冒烟集和隐藏验收集均覆盖以下五类项目：

1. **标准项目**：文件完整、企业资料充分、流程按正常路径运行；
2. **受限接入项目**：项目编号无法自动获取全部文件，需要人工上传或补充；
3. **过程变更项目**：存在澄清、更正、补遗、报价或关键资料变化；
4. **业务缺口项目**：存在资料不足、证据不足、无法响应或需人工决策事项；
5. **异常递交项目**：存在交接失败、链接失效、接收错误、递交失败、更正或撤回记录。

样本分配：

- 5 个开发冒烟项目：五类各 1 个；
- 15 个隐藏正式验收项目：五类各 3 个；
- 固定回归集持续加入零容忍缺陷、严重回归和高频失败案例。

### 2.3 L3 数据来源

甲方不能提供完整历史项目资料时，L3 使用：

```text
公开采购文件
+ 可控模拟企业数据
+ 受控报价数据
+ 模拟历史项目与工作流
+ 人工构造异常
```

该数据组合可以验证正确性、安全、拒答、版本、审核、交接和审计，但不能证明甲方真实效率提升、中标率或生产效果。

### 2.4 数据隔离规则

- 正式验收集不得用于提示词、规则、检索、重排或模型参数调优；
- 开发人员在正式评测前不得看到完整金标准；
- 同一采购项目不能通过更换测试企业同时进入开发集和正式验收集；
- 正式金标准至少执行“一人标注、一人复核”；
- 若没有真实标书业务人员，至少引入一名招投标领域顾问复核；
- 未经业务复核的结果只能标记为技术自测，不能作为正式 L3 结论；
- 企业资料、报价和个人信息必须脱敏，并记录授权范围。

### 2.5 数据集版本清单

每个数据集版本至少记录：

- `dataset_version`；
- 项目清单和项目类型；
- 文件清单、文件哈希和来源；
- 模拟数据生成或构造规则；
- 金标准版本；
- 标注人和复核人；
- 纳入、排除和变更原因；
- 可用于调优、只可用于验收或只可用于回归的权限标识。

## 三、统一模块评估卡

每个 L1 模块和需要独立评估的 L2 子链路统一使用九字段评估卡。

| 字段 | 必填内容 |
|---|---|
| 1. 评估对象 | 模块、链路、输入输出和业务责任边界 |
| 2. 测试数据集 | 数据集版本、样本类型、正常和异常分布 |
| 3. 金标准 | 正确结果、人工标注规则和复核角色 |
| 4. 质量指标 | 指标名称、公式、统计粒度和数据范围 |
| 5. 硬门禁 | 零容忍错误、权限、版本、状态和人工确认底线 |
| 6. 发布阈值 | 最低发布线、目标优秀线、零容忍门禁及适用范围；未冻结阈值不得进入正式验收 |
| 7. 观察指标 | 耗时、成本、重试、人工接管和使用行为 |
| 8. 样本量 | 样本数、项目数、文件数或要求条目数 |
| 9. 失败处理规则 | 阻断、转人工、修复、复测和回归要求 |

评估卡还必须记录：

- `evaluation_run_id`；
- `evaluation_policy_version`；
- 系统版本、模型版本、提示词版本和规则版本；
- 输入快照、输出快照和运行日志；
- 失败样本及其影响范围；
- 评测人、复核人和签署时间。

## 四、指标定义与计算规则

### 4.1 通用质量指标

| 指标 | 公式或判断方式 | 说明 |
|---|---|---|
| 召回率 `Recall` | `TP / (TP + FN)` | 用于要求、风险、证据和异常召回 |
| 准确率 `Precision` | `TP / (TP + FP)` | 用于要求分类、风险提示和推荐结果 |
| F1 | `2 × Precision × Recall / (Precision + Recall)` | 只作为普通质量辅助指标 |
| 引用正确率 | 正确引用结论数 / 全部引用结论数 | 主体、有效期、适用范围和原文一致才算正确 |
| 来源可定位率 | 可定位到原文件和位置的结论数 / 应定位结论数 | 高风险结论要求 100% |
| 覆盖率 | 已正确响应要求数 / 应响应要求数 | 高风险要求单独统计 |
| 一致性正确率 | 一致字段数 / 应保持一致字段数 | 报价、主体、工期、人员和版本分开统计 |
| 状态转换正确率 | 合法转换成功且非法转换被拦截次数 / 全部状态转换测试次数 | 确定性门禁要求 100% |
| 版本失效正确率 | 应失效且正确失效的依赖数 / 应失效依赖数 | 确定性门禁要求 100% |

分母为零时不得默认记为 100%。该指标应标记为“不适用”，并在报告中说明原因。

### 4.2 效率与工作量指标

| 指标 | 计算方式 |
|---|---|
| 首稿耗时 | 首稿生成完成时间 - 项目有效输入就绪时间 |
| 审核耗时 | 审核版本完成时间 - 首稿提交审核时间 |
| 交接耗时 | 接收人确认时间 - 交接基线生成时间 |
| 人工总投入时间 | 所有业务角色在该项目中的有效操作和判断时间之和 |
| 人工时间变化率 | `(人工基线时间 - Agent 辅助时间) / 人工基线时间` |
| 退回轮次 | 从首次审核到审核通过之间的正式退回次数 |
| 人工接管率 | 需要人工接管的任务数 / 全部可执行任务数 |
| 增量复核比例 | 增量复核内容量 / 全量复核内容量 |

### 4.3 成本与稳定性指标

- 单项目模型 Token 和调用成本；
- OCR、检索、重排、存储和导出成本；
- 单项目失败、重试和人工恢复次数；
- 任务成功率和恢复时间；
- 单项目综合处理成本；
- 受控试点期间的系统可用性。

### 4.4 指标统计原则

- 资格、否决项、实质性要求、关键报价和阻断风险必须单独统计；
- 不同文件类型、项目类型和异常路径必须分组报告；
- 平均值、中央値和分位数按指标特点同时使用，不能只报告最有利结果；
- 人工组和 Agent 组使用相同计时口径和排除规则；
- 指标定义、公式或数据范围变化必须生成新的评估策略版本。

### 4.5 两级阈值与判定规则

V1 普通质量指标采用“最低发布线 + 目标优秀线”两级阈值：

- **最低发布线**：模块、链路或项目进入下一评估层级必须达到的最低要求；
- **目标优秀线**：用于持续优化、演示和试点追踪，首次发布未达到时不单独阻断；
- **零容忍门禁**：仍要求 `100%` 正确或严重错误数为 `0`，不参与普通指标平均；
- **禁止跨域抵消**：任一指标、模块或质量域未达到最低发布线，不得用其他指标高分抵消；
- **单项目下限**：L3 汇总指标达到最低发布线之外，任一单项目的普通质量指标不得低于对应最低发布线 `5` 个百分点以上；
- **样本不足处理**：分母不足、样本类型缺失或置信区间无法支持结论时，标记为“待继续评测”，不得直接判定达到优秀线。

### 4.6 V1 普通质量指标数值基线

| 质量域 | 指标 | 最低发布线 | 目标优秀线 |
|---|---|---:|---:|
| 数据接入 | 可自动获取范围内的获取成功率 | `≥ 90%` | `≥ 95%` |
| 数据接入 | 人工上传兜底成功率 | `100%` | `100%` |
| 文档解析 | 普通正文识别准确率 | `≥ 97%` | `≥ 99%` |
| 文档解析 | 表格结构还原率 | `≥ 92%` | `≥ 97%` |
| 文档解析 | 标题层级准确率 | `≥ 95%` | `≥ 98%` |
| 文档解析 | 普通内容原文定位正确率 | `≥ 98%` | `≥ 99.5%` |
| 要求抽取 | 普通要求召回率 | `≥ 95%` | `≥ 98%` |
| 要求抽取 | 要求分类准确率 | `≥ 93%` | `≥ 97%` |
| 要求抽取 | 要求原子化准确率 | `≥ 90%` | `≥ 95%` |
| 要求抽取 | 响应矩阵映射准确率 | `≥ 95%` | `≥ 98%` |
| 要求抽取 | 普通冲突识别召回率 | `≥ 90%` | `≥ 95%` |
| 证据检索 | `Recall@10` | `≥ 90%` | `≥ 95%` |
| 证据检索 | `nDCG@10` | `≥ 0.80` | `≥ 0.88` |

| 失败处理 | 阻断下游要求提取，修复接入或解析结果，产生新版本后重新执行整条链路 |

### 6.2 L2-02 要求到响应依据

```text
要求提取
→ 企业证据
→ 历史参考
→ 响应矩阵
```

| 项目 | 要求 |
|---|---|
| 场景 | 证据充分、证据缺失、证据过期、主体错误、权限受限、相关与不相关历史项目、冲突要求 |
| 金标准 | 完整要求、正确证据、拒答状态、历史参考差异、章节用途和最终响应矩阵 |
| 核心指标 | 高风险要求召回率、证据引用正确率、无证据拒答正确率、历史推荐相关性和矩阵映射准确率 |
| 硬门禁 | 高风险要求漏项、编造证据、过期证据误用、越权引用、历史参考变成当前承诺、错误肯定均为 0 |
| 通过条件 | L1-03、L1-04 和 L1-05 均通过；高风险要求和关键事实 100% 可追溯并具有真实响应状态 |
| 失败处理 | 阻断受影响章节生成，修正要求、证据或参考池，更新矩阵版本并重新执行链路 |

### 6.3 L2-03 报价确认到章节引用

```text
报价测算
→ 规则校验
→ 人工确认
→ 章节引用
```

| 项目 | 要求 |
|---|---|
| 场景 | 多候选方案、无效方案、限价边界、税率和单位变化、人工修改、重新确认和跨章节更新 |
| 金标准 | 有效方案集合、无效原因、计算结果、授权确认、冻结报价版本和全部引用位置 |
| 核心指标 | 规则校验正确率、最终报价正确率、人工确认完整率和跨章节一致性正确率 |
| 硬门禁 | 无效报价入标、未确认报价引用、越权确认、大小写或单位错误、不同章节使用不同版本均为 0 |
| 通过条件 | L1-06 通过；最终报价和所有正式引用位置 100% 使用同一冻结版本 |
| 失败处理 | 阻断生成、审核或交接，产生新报价版本，重新生成全部受影响位置并执行商务复核 |

### 6.4 L2-04 初稿审核与结构化返工

```text
章节生成
→ Agent 预检
→ 人工审核
→ 结构化返工
```

| 项目 | 要求 |
|---|---|
| 场景 | 正常通过、阻断问题、中低风险误报、错误建议、人工修改、锁定内容、部分返工和全量复核 |
| 金标准 | 章节和材料版本、风险清单、问题等级、责任角色、修改建议、差异和应复核范围 |
| 核心指标 | 章节覆盖、阻断风险召回、固定角色路由、建议正确性、人工修改保护、对象/章节影响判断和复核范围安全性 |
| 硬门禁 | 阻断风险漏报、内部信息外泄、Agent 覆盖锁定内容、自动关闭问题、修改后绕过复核均为 0 |
| 通过条件 | L1-07 和 L1-08 均通过；阻断问题全部关闭或经授权豁免，当前版本审核有效 |
| 失败处理 | 重新打开问题，修正内容或豁免，生成新版本，重新预检并完成增量或全量复核 |

### 6.5 L2-05 变更到递交留痕

```text
内容变更
→ 对象级或章节级影响判断
→ 局部复核或安全扩大复核
→ 交接基线
→ 递交记录
```

| 项目 | 要求 |
|---|---|
| 场景 | 文件更正、报价变化、证据失效、章节修改、旧链接、错误接收人、递交失败、更正和撤回 |
| 金标准 | 受影响对象、失效结果、应复核范围、合法状态、交接包、接收确认和人工递交历史 |
| 核心指标 | 对象/章节影响判断正确率、复核范围安全性、版本失效正确率、状态转换正确率、交接完整率和递交记录完整率 |
| 硬门禁 | 旧版继续有效、漏复核、未审核交接、非法状态、错误接收人、虚假递交成功和覆盖历史均为 0 |
| 通过条件 | L1-08 和 L1-09 均通过；交接文件、清单、版本和哈希一致，递交状态来自人工记录 |
| 失败处理 | 失效原交接并回退合法状态，重新审核、重新建立基线和交接，保留全部历史事件 |

### 6.6 L2 总体结论

五条 L2 链路必须全部通过。任一链路未执行、触发零容忍门禁或未达到冻结阈值，V1 不能判定技术完成，也不能进入 L3 正式验收。

## 七、L3 单项目端到端评估

### 7.1 准入条件

进入 L3 前必须满足：

- 九个核心 L1 模块达到发布阈值；
- 五条 L2 链路全部通过；
- `evaluation_policy`、系统配置和隐藏验收集已经冻结；
- 正式验收人员无权在评测过程中临时降低阈值；
- 评测环境、数据权限和审计记录已验证可用。

### 7.2 正式样本

- 15 个隐藏正式验收项目；
- 五类项目各 3 个；
- 每个项目从项目编号或文件输入开始；
- 终点为内部受控交接完成，并形成外部人工递交状态记录；
- 正式验收集不得用于调优或阈值回填。

### 7.3 四道判定门

```text
零容忍门禁
→ AC-01 至 AC-06
→ 七个核心质量域
→ 性能、可靠性与成本门槛
→ 记录效率和人工工作量
```

#### 第一门：零容忍门禁

任一项目出现以下问题即判定该项目不通过：

- AI 编造企业事实、资质、业绩、人员、报价或履约能力；
- 资格、否决项、实质性要求、关键报价或阻断风险漏报；
- 无效、未确认或已失效报价进入正式标书；
- 未解决阻断风险仍能建立有效交接基线；
- 旧版本、未审核版本或错误文件被交接；
- 内部风险、审核意见或敏感信息进入外部文件；
- 越权访问、越权确认、越权关闭问题或越权豁免；
- 系统自动执行外部递交或虚构递交成功；
- 人工修改被静默覆盖；
- 关键审计事件缺失或历史记录被覆盖。

#### 第二门：AC-01 至 AC-06

| 验收场景 | L3 必须验证的结果 |
|---|---|
| `AC-01` 项目编号与分级数据接入 | 自动、部分自动和人工补充路径均可完成，来源和版本完整 |
| `AC-02` 文件解析、变更与影响分析 | 关键内容可定位，补充更正传播正确，旧结果失效 |
| `AC-03` 企业证据、历史参考和拒答 | 证据可追溯、历史复用有边界、无证据正确拒答 |
| `AC-04` 报价方案闭环 | 无效方案排除、人工确认、冻结版本和跨章节一致 |
| `AC-05` 章节生成、审核和增量返工 | 章节完整、风险闭环、人工确认、差异和复核有效 |
| `AC-06` 内部交接与人工递交记录 | 基线、清单、哈希、接收确认和人工递交记录完整 |

`AC-07` 属于 L4，不计入 L3 通过判定。

#### 第三门：七个核心质量域

| 质量域 | 确定性门禁 | 高风险零错误要求 | 普通指标数值基线 | 失败处理 |
|---|---|---|---|---|
| A 项目文件与解析 | 项目、采购包、文件、版本、哈希、状态和关键原文定位 `100%` 正确 | 关键文件、字段、页面漏接入或误解析为 `0` | 获取成功率 `≥ 90%`；正文 `≥ 97%`；表格 `≥ 92%`；标题 `≥ 95%`；普通定位 `≥ 98%` | 阻断依赖文件的生成，修复后重新解析和复测 |
| B 要求与响应矩阵 | 高风险要求均有编号、类型、位置、状态、责任人、章节和证据 | 资格、否决、实质性和关键评分项漏报或错误肯定为 `0` | 普通召回 `≥ 95%`；分类 `≥ 93%`；原子化 `≥ 90%`；矩阵映射 `≥ 95%`；冲突召回 `≥ 90%` | 修正矩阵，重新生成受影响章节并增量审核 |
| C 企业证据与历史参考 | 主体、有效期、范围、权限、关键引用和拒答 `100%` 正确 | 错主体、过期误用、编造、越权和历史内容变当前承诺为 `0` | `Recall@10 ≥ 90%`；`nDCG@10 ≥ 0.80`；普通引用 `≥ 98%`；拒答 `≥ 98%`；历史 `Precision@5 ≥ 80%` | 阻断事实和章节，补充证据后重新生成和复核 |
| D 报价与跨章节一致性 | 模板、公式、结果、确认、冻结和引用版本 `100%` 正确 | 超限价、计算、税率、单位、大小写、越权确认和版本冲突为 `0` | 字段映射 `≥ 99%`；推荐解释一致率 `≥ 90%` | 新报价版本替换全部引用并执行商务复核 |
| E 章节、图表和说明材料 | 必备内容、关键来源、材料分类、锁定和导出版本 `100%` 正确 | 缺章节、无证据事实、关键冲突、内外混入和错误导出为 `0` | 普通覆盖 `≥ 95%`；事实支持 `≥ 98%`；模板 `≥ 95%`；图表引用 `≥ 98%`；导出还原 `≥ 95%` | 生成新标书版本并重新检查、审核和导出 |
| F 风险、审核与返工 | 阻断召回、关闭权限、豁免、必要复核范围和人工修改保护 `100%` 正确 | 阻断漏报、错误降级、自动关闭、越权和绕过复核为 `0` | 中低风险召回 `≥ 90%`；准确率 `≥ 80%`；路由 `≥ 95%`；建议正确率 `≥ 85%` | 重新打开问题，修正或豁免后重新复核 |
| G 版本、交接与递交记录 | 状态、失效、基线、哈希、权限、接收和记录 `100%` 正确 | 旧版交接、未审核交接、错误接收人、虚假递交和覆盖历史为 `0` | 通知、查询、操作体验和恢复耗时作为观察指标，不抵消确定性门禁 | 失效原交接，回退状态并建立新基线和记录 |

#### 第四门：性能、可靠性与成本记录

L3 技术验收同时执行以下运行指标。性能阈值按单台 Linux、无 GPU、一个活跃项目的 V1 部署口径评测；实际 CPU、内存、磁盘、网络、模型和并发配置必须写入报告。

| 指标 | 最低发布线 | 目标优秀线 | 判定说明 |
|---|---:|---:|---|
| 列表、详情类查询峰值吞吐 | `≥ 10 QPS` | `≥ 20 QPS` | 峰值负载期间同时满足时延要求 |
| 列表、详情类查询 `P99` | `≤ 1 秒` | `≤ 500 毫秒` | 不含异步长任务完成时间 |
| BM25、向量和重排证据检索 `P99` | `≤ 5 秒` | `≤ 3 秒` | 包含查询向量化、召回、融合和重排 |
| 100 页级 PDF 异步解析耗时 | `≤ 15 分钟` | `≤ 5 分钟` | 从任务进入可执行状态到解析版本完成 |
| 多 Agent 全审核链路异步耗时 | `≤ 30 分钟` | `≤ 10 分钟` | 不含等待人工确认的时间 |
| 异步任务最终成功率 | `≥ 98%` | `≥ 99.5%` | 正确阻断或转人工不计为系统失败 |
| 可重试任务恢复成功率 | `≥ 95%` | `≥ 99%` | 按可恢复失败任务统计 |
| 幂等性测试正确率 | `100%` | `100%` | 重复请求不得产生重复业务事实或非法状态 |
| Worker 重启后任务状态恢复率 | `100%` | `100%` | 不得丢失任务、版本和审计关系 |
| 受控试点期间系统可用性 | `≥ 99%` | `≥ 99.5%` | 排除双方确认的计划维护窗口 |

性能测试最低执行口径：预热不少于 `2` 分钟；查询峰值负载持续不少于 `5` 分钟；查询样本不少于 `10,000` 次；100 页级 PDF 不少于 `10` 份；多 Agent 全链路不少于 `30` 次。耗时必须同时报告平均值、P50、P95、P99或适用的最大值，不得只报告最快样本。

模型供应商和价格尚未冻结，因此 V1 先采用 Token 与暂定人民币预算双重控制：

| 成本指标 | 最低发布线 | 目标优秀线 | 说明 |
|---|---:|---:|---|
| 单项目模型输入 Token | `≤ 250 万` | `≤ 150 万` | 按一次完整 L3 项目累计 |
| 单项目模型输出 Token | `≤ 25 万` | `≤ 15 万` | 包含结构修复调用 |
| 单项目模型、OCR等可变成本 | `≤ 150 元` | `≤ 80 元` | 不含服务器、数据库和固定运维成本 |
| 无效重试 Token 占比 | `≤ 10%` | `≤ 5%` | 因结构错误、超时或可避免失败产生 |
| 上下文重复内容比例 | `≤ 20%` | `≤ 10%` | 按发送给模型的重复 Token 估算 |

具体供应商、模型和 OCR 服务确定后，必须依据真实单价生成新的成本策略版本并复核人民币阈值；不得通过降低零容忍或质量门槛换取成本达标。成本暂时超出最低线但全部质量、安全和性能门槛通过时，只能形成有条件通过和明确的成本整改项，不能静默忽略。

### 7.4 L3 单项目评估总表

每个项目使用以下六部分：

1. **项目与评测版本**：项目类型、数据集、系统、模型、提示词、规则和评估策略版本；
2. **零容忍门禁**：逐项记录是否触发、证据和影响；
3. **AC-01 至 AC-06**：逐场景记录通过、失败或未执行；
4. **七个核心质量域**：分别记录指标、阈值、结果和失败样本；
5. **效率、成本和人工工作量**：只记录实际数据，不在缺少基线时任意设置否决值；
6. **最终结论与签署**：通过、有条件通过或不通过，并由对应角色签署。

质量域记录模板：

```text
核心指标：
发布阈值：
实际结果：
是否达到阈值：是 / 否 / 未评测
失败样本：
影响范围：
修复与复测要求：
```

### 7.5 L3 结论

#### 通过

- 零容忍门禁全部未触发；
- `AC-01` 至 `AC-06` 全部通过；
- 七个核心质量域全部达到冻结阈值；
- 性能和可靠性指标全部达到最低发布线；
- Token 和可变成本指标达到最低发布线；
- 所有必测内容均已执行；
- 数据、版本、证据和签署完整。

L3 通过后，判定“V1 交付验收通过、试点就绪”。

#### 有条件通过

- 零容忍门禁全部未触发；
- 核心业务闭环能够运行；
- 七个核心质量域、性能和可靠性指标均达到最低发布线；
- 仅存在 Token、可变成本、非阻断观察指标或体验指标未达到最低发布线；
- 遗留问题、责任人、整改期限和复测计划完整。

有条件通过只能继续内部验证，不能进入正式真实项目试点，也不能完成 V1 软件交付验收。

#### 不通过

- 任一零容忍门禁被触发；
- 任一 `AC-01` 至 `AC-06` 不通过或未执行；
- 任一核心质量域未达到冻结阈值；
- 任一性能或可靠性最低发布线未达到；
- 关键版本、数据、证据或评测记录缺失。

不通过项目必须整改，并重新执行受影响的 L1、L2 和 L3 评估。

### 7.6 L3 签署角色

每个正式项目结论至少需要：

1. 评测负责人确认数据、版本和执行过程；
2. 业务复核人确认要求、证据、风险和项目结论；
3. 商务人员确认报价专项结果；
4. 合规或法务人员确认资格、承诺和法律风险专项结果；
5. 产品负责人确认遗留问题和阶段决策。

签署人不能确认自己无权判断的专项内容。结论变更必须生成新版本和审计记录，不能覆盖原结论。

## 八、发布阈值制定、冻结与重评

### 8.1 四类指标

#### 确定性门禁

适用于权限、状态、哈希、版本、无效报价、审核记录和交接前置条件。要求：

```text
100% 正确
或
严重错误数 = 0
```

#### 高风险质量指标

适用于资格条件、否决项、阻断风险、关键报价、关键事实和事实引用。

- 15 个隐藏项目中不得出现关键漏报或错误肯定；
- 同时记录召回率、引用正确率等指标；
- 高风险错误不能由普通指标高分抵消。

#### 普通质量指标

适用于普通技术商务要求、历史推荐、章节结构、语言、图表和格式。本文档给出的两级数值是 V1 初始基线，仍需通过开发冒烟项目验证其可测性和稳定性。验证依据包括：

- 5 个开发冒烟项目的实际分布；
- 失败样本及业务影响；
- 人工质量或领域专家复核结果；
- 业务人员可接受的最低水平；
- 当前系统能够稳定重复达到的水平。

不得脱离样本和风险把所有指标统一设为 `95%` 或其他单一比例。冒烟评测可以发现指标定义、数据或统计口径问题，但不得仅因系统暂时未达到数值就直接降低最低发布线；确需变更时执行 8.4 的版本化重评流程。

#### 观察指标

适用于人工确认、采纳、修改、接管次数、用户行为和缺少可比基线的业务效率数据。V1 已在 L3 为查询、检索、解析、Agent 链路、可靠性、Token 和暂定可变成本设置两级阈值；未列入 L3 门槛的观察指标只采集，不任意设置否决条件。

### 8.2 初始阈值流程

```text
运行 5 个开发冒烟项目
→ 收集指标分布和失败样本
→ 业务人员确定不可接受风险
→ 验证本文档初始阈值的可测性、统计口径和稳定性
→ 必要时按 8.4 发起阈值变更并完整记录依据
→ 冻结 evaluation_policy_v1
→ 运行正式 L1、L2 和 15 个隐藏 L3 项目
```

### 8.3 评估策略版本

每个 `evaluation_policy` 至少记录：

- 指标名称和业务含义；
- 指标公式和统计粒度；
- 数据范围、分组和排除规则；
- 指标类别；
- 发布阈值或门禁；
- 适用模块、链路、项目类型和质量域；
- 制定依据和审批人；
- 生效与失效时间；
- 关联数据集和金标准版本。

### 8.4 阈值变更

正式验收过程中不得为了通过而临时降低阈值。确需调整时：

```text
提出变更原因
→ 评估影响范围
→ 生成新的 evaluation_policy 版本
→ 重新冻结数据和策略
→ 对受影响范围执行完整评测
```

不得覆盖原策略，也不得只重跑失败样本后直接宣告通过。无法可靠确定影响范围时，重新执行完整 L1、L2 和 L3。

## 九、L4 试点业务价值评估

### 9.1 准入与边界

- 只有 L3 通过并完成 V1 软件交付验收后，才能进入正式 L4；
- 人工团队继续按原流程完成正式投标；
- 旁路阶段 Agent 结果默认不直接作为正式递交文件；
- 最终报价、风险接受、审核、交接和外部递交仍由人工决定；
- L4 验证业务价值，不重新定义软件交付完成条件。

### 9.2 五类业务价值指标

| 指标类别 | 核心指标 |
|---|---|
| 效率 | 首稿时间、审核时间、交接时间、人工查找整理时间、重复录入次数、人工总投入时间和退回轮次 |
| 质量 | 关键要求漏报、阻断风险漏报、报价和跨章节错误、首次审核通过率、返工率和记录完整率 |
| 风险与控制 | 版本错误、未审核交接、越权访问、内部信息外泄、阻断问题违规流转和审计完整率 |
| 用户工作量与使用 | 人工确认次数、人工修改比例、建议采纳/修改/拒绝、人工接管和角色使用反馈 |
| 成本与稳定性 | 模型、OCR、检索、存储和导出成本，失败重试、恢复时间、可用性和单项目综合成本 |

用户满意度是辅助指标，不能替代客观质量和安全结果。中标率作为长期观察指标，不作为 L4 通过门槛。

### 9.2.1 L4 暂定业务价值数值基线

以下数值用于首轮试点设计和数据采集校验，不代表尚未发生的真实收益已经实现。完成至少 `5` 个探索性同项目双轨旁路项目后，双方应根据真实人工基线、项目复杂度和数据质量生成并冻结 `business_value_policy_v1`；正式前瞻性配对试点开始后不得根据结果临时降低门槛。

| 指标 | 最低价值线 | 目标优秀线 | 统计口径 |
|---|---:|---:|---|
| 首稿耗时降低 | `≥ 30%` | `≥ 50%` | 相同输入就绪点至可提交人工审核首稿 |
| 审核耗时降低 | `≥ 20%` | `≥ 35%` | 从首次提交审核至审核版本完成 |
| 人工总投入时间降低 | `≥ 20%` | `≥ 35%` | 所有业务角色有效操作和判断时间之和 |
| 查找整理时间降低 | `≥ 30%` | `≥ 50%` | 采购要求、企业证据和历史材料查找整理时间 |
| 重复录入次数降低 | `≥ 30%` | `≥ 50%` | 同一事实、金额、人员或项目字段的重复人工录入 |
| 正式退回轮次降低 | `≥ 15%` | `≥ 30%` | 首次审核至审核通过之间的正式退回次数 |
| 首次审核通过率提升 | `≥ 10` 个百分点 | `≥ 20` 个百分点 | 报告绝对百分点变化，不写成相对百分比 |
| Agent 建议有效采纳率 | `≥ 60%` | `≥ 75%` | 被直接采纳或轻微修改后采纳的有效建议 |
| 人工接管率 | `≤ 35%` | `≤ 20%` | 需要人工接管的可执行 Agent 任务占比 |
| 新增零容忍缺陷 | `0` | `0` | 任一新增零容忍缺陷均阻断扩大使用结论 |

L4 业务价值验证通过必须同时满足：没有新增零容忍缺陷；质量和安全不低于 L3 冻结底线；至少一项核心效率指标达到最低价值线；并且人工总投入时间、审核耗时、正式退回轮次三项中至少两项达到最低价值线。只达到建议采纳率、满意度或单一体验指标，不足以判定业务价值验证通过。

### 9.3 试点设计

采用“少量同项目双轨旁路验证指标，再进行前瞻性配对试点”的组合方案。

#### 探索性双轨旁路

- 建议至少 5 个真实项目；
- 同一项目分别记录人工常规流程和 Agent 旁路结果；
- 用于验证计时、任务、确认、修改、审核、风险和人工接管数据能否可靠采集；
- 结果用于验证本节暂定数值、建立人工基线并冻结业务价值指标，不直接宣称规模化收益；
- 若真实基线表明暂定指标不可比或统计口径不可靠，必须先修正计时和采集规则，再重新完成至少 `5` 个有效双轨项目，不能直接降低门槛。

#### 正式前瞻性配对试点

- 建议人工组与 Agent 组各不少于 10 个项目；
- 按项目类型、文件规模、要求数量、参与角色和时间紧迫度匹配；
- 两组使用相同指标、计时方式和排除规则；
- 试点开始前冻结 `business_value_policy`；
- 查看最终结果后不得改变样本、指标公式或排除规则。

样本不足时只能形成趋势结论，不能宣称业务价值已经得到充分证明。

### 9.4 L4 三种正式结论

#### L4 业务价值验证通过

- 样本和数据采集满足冻结要求；
- 未出现新的零容忍缺陷；
- 质量和安全达到冻结底线；
- 效率、审核、返工、工作量或成本达到双方冻结的业务价值门槛。

该结论支持进入扩大使用或规模化推广决策。

#### L4 业务价值验证未通过

- 已获得足够有效的正式试点样本；
- 评测已经完成；
- 结果未达到冻结的业务价值门槛。

该结论不撤销 L3 软件交付验收，但不能宣称实现预期业务价值或建议扩大使用。

#### L4 待继续评测

- 样本不足；
- 数据采集不完整；
- 试点周期未结束；
- 尚未形成稳定、可比较的人工基线；
- 其他原因导致无法形成有效结论。

该结论不等于通过，也不等于未通过；不撤销 L3 软件交付验收，但不得虚构提升比例。

### 9.5 L4 新缺陷处理

L4 结论本身不撤销 L3。若真实试点发现新的零容忍缺陷：

1. 立即停止受影响能力的扩大使用；
2. 将案例加入失败样本和固定回归集；
3. 判断影响的 L1 模块、L2 链路和 L3 质量域；
4. 修复后执行受影响层级复评；
5. 无法判断影响范围时执行完整 L1、L2 和 L3；
6. 根据复评结果处理试点和交付状态。

## 十、评测执行流程

### 10.1 V1 首次正式评测

```text
准备公开采购文件、模拟企业数据和异常样本
→ 建立开发冒烟集、隐藏验收集和金标准
→ 运行 5 个开发冒烟项目
→ 修正评测工具和指标定义
→ 业务人员确认不可接受风险
→ 冻结 dataset、golden_set 和 evaluation_policy_v1
→ 执行九个 L1 模块评估
→ 执行五条 L2 链路评估
→ 执行 15 个隐藏 L3 项目
→ 签署 L3 结论
→ L3 通过后完成 V1 交付验收并进入 L4
```

### 10.2 单次评测运行

1. 校验数据集、金标、策略和系统版本；
2. 创建 `evaluation_run_id`；
3. 保存输入快照；
4. 执行系统任务并保存日志；
5. 计算确定性门禁和质量指标；
6. 记录失败样本、人工判断和影响范围；
7. 生成评测报告；
8. 由规定角色复核和签署；
9. 将严重失败样本加入回归集；
10. 决定通过、整改复测或进入下一层级。

### 10.3 失败复测

- 先复测直接失败模块；
- 再复测受影响 L2 链路；
- 若影响端到端结论，重新执行受影响 L3 项目；
- 零容忍缺陷必须执行固定回归集；
- 共享模型、提示词、检索或规则变更原则上执行完整 L1 和 L2；
- 无法证明影响范围时不得只做局部复测。

V1首个实现精确锁定`deepagents==0.7.8`并提交完整依赖锁文件。Deep Agents或其核心运行时升级必须生成独立版本和评测记录，禁止自动合并升级。
