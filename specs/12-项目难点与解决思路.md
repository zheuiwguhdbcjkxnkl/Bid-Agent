# 12 项目难点与解决思路

> 版本：v3.0  
> 项目：投标文件智能编制与合规审核多智能体平台  
> 用途：梳理 Agent 项目的核心业务、技术和工程难点，明确方案取舍、实现边界、评估方式与人工兜底，作为系统设计、README 和面试讲解的依据。  
> 关联文档：`07-客户画像与场景设定.md`、`08-招投标术语与业务知识手册.md`、`09-业务流程与项目状态机.md`、`10-核心业务对象与数据字典.md`、`11-产品需求文档（PRD）.md`

## 一、项目主线与技术边界

当前项目只描述一个产品：

> **面向投标企业内部流程的投标文件智能编制与合规审核多智能体平台。**

系统围绕采购文件事实、企业证据、历史参考、报价方案、响应内容、审核风险和交接基线等可版本化对象，完成分级数据接入、文件解析、要求提取、证据匹配、同类项目比较、报价确认、章节编制、专项审核、人工确认和内部受控交接。

企业证据检索是 Agent 调用的共享工具，不是与 Agent 平台并列的第二个产品。P0 使用 PostgreSQL 原生词法检索、向量检索、元数据过滤、RRF 融合和有限重排返回可定位证据；基于已确认业务关系的受控 GraphRAG 只作为 P1 扩展点，不替换关系型事实库，也不进入当前核心叙事。

## 二、难点总览

| 层次 | 核心难点 | 需要解决的问题 |
|---|---|---|
| 业务 | 复杂采购文件解析与定位 | 如何在正文、表格、扫描页和附件混合的长文档中保留章节、页码和版本信息 |
| 业务 | 高风险要求识别 | 如何识别可能导致投标无效、否决投标或重大扣分的要求，同时避免仅凭版式符号下结论 |
| 业务 | 文件更新后的级联失效 | 如何在澄清、更正或补充文件正式发布后，让受影响结论进入复核而不是静默沿用 |
| 技术 | 基于证据的编制与审核 | 如何让 Agent 只使用可核验企业材料，证据不足时正确拒答并转人工 |
| 技术 | 多 Agent 编排与状态边界 | 如何划分专项 Agent、规则工具和人工决策，避免 Agent 越权改变项目主状态 |
| 工程 | 跨章节一致性与审计追溯 | 如何定位人员、日期、金额、参数和案例的冲突，并复现每次运行依据 |
| 工程 | 评估、反馈与重评闭环 | 如何把人工确认、驳回和修订转化为可复跑的评测样本与迭代依据 |
| 工程 | 数据与工具使用合规 | 如何对公开数据源、解析工具和模型依赖逐项核验使用边界 |
| 工程 | 异构平台分级接入 | 如何在 API、公开页面、账号登录、CA 和人工上传之间建立稳定且合规的兜底链路 |
| 业务 | 历史项目可控复用 | 如何推荐相似项目而不把旧客户、报价、人员和承诺错误带入当前项目 |
| 业务 | Excel 报价闭环 | 如何保留现有计算模型，同时统一模板、假设、校验、推荐和人工确认 |
| 工程 | 例外驱动审核与受控交接 | 如何减少机械确认，只复核高风险和受影响内容，并确保递交责任人使用最新版本 |

## 三、核心难点与解决思路

### 难点 1：复杂采购文件解析与原文定位

**业务影响**

- 采购文件可能包含正文、评分表、资格表、附件、图片和扫描页；解析错误会继续传递到要求抽取、响应规划和审核环节。
- 关键结论如果不能回到文件版本、页码和原文，业务人员无法复核，系统也无法形成可信审计记录。

**方案取舍**

- 采用分层解析管线，而不是把所有文件直接交给大模型：文本型 PDF 使用轻量解析通道，复杂版式使用版面解析工具，扫描页使用 OCR 兜底。
- 按标题层级、目录、表格和附件边界切分，避免只按固定 token 数机械切块。
- `document_segment` 保存 `document_version_id`、页码、章节路径、块类型和原文摘要，作为后续抽取与引用的统一来源。

**实现边界**

- P0 优先支持 PDF、DOCX 和常见图片型附件；异常格式进入人工处理队列。
- MinerU、Docling、PaddleOCR 等工具的具体组合以实际测试结果、许可证和部署条件为准，不预先宣称某个工具在所有文档上最优。
- 解析节点只负责恢复文档结构，不负责认定资格是否满足或风险是否可接受。

**评估方式**

- 统计正文、标题、表格和页码恢复的抽样准确率。
- 对资格条件、评分项和时间节点建立端到端可定位率：抽取结果是否能正确跳回来源片段。
- 记录解析失败率、OCR 触发率、人工修复率和单份文件处理时间。

**人工兜底**

- 页面展示原文件与解析结果对照，允许用户修正章节、表格和页码映射。
- 解析失败或页码无法确认时标记 `WAITING_HUMAN`，不得静默跳过。

### 难点 2：高风险要求与评分项的结构化抽取

**业务影响**

- 漏读具有明确投标无效或否决投标后果的实质性要求，可能导致投标失败。
- 把普通要求误判为阻断风险，也会增加无效审核工作，甚至干扰是否投标决策。

**方案取舍**

- 使用“规则召回 + LLM 结构化抽取 + 人工确认”：规则捕获明确后果表述、否定词和常见格式信号，LLM 负责上下文理解与字段归一。
- 强制输出 `requirement_type`、`mandatory_level`、`consequence_type`、`source_segment_id`、置信度和判断理由。
- `★`、黑体、下划线和表格颜色只作为辅助信号，不能单独决定是否属于实质性要求。

**实现边界**

- Agent 可以识别风险和给出建议，不能自动认定投标人具备资格，也不能自动决定是否参与投标。
- 政府采购与依法必须招标的工程项目使用不同规则集；当前 P0 只完整实现政府采购信息化服务项目。
- 报价由受控 Excel 或内部模型计算；规则引擎先排除无效方案，大模型只能比较有效候选方案并解释理由与风险，不得修改计算结果。

**评估方式**

- 对资格条件、实质性要求、评分项和时间节点分别计算 Precision、Recall 和 F1。
- 高风险要求重点观察 Recall，同时单独统计误报率和人工驳回原因。
- 评测结果绑定样本版本、规则版本、提示词版本和模型配置，保证可以复跑。

**人工兜底**

- 高风险要求必须进入人工确认，状态由 `UNCONFIRMED` 转为 `CONFIRMED` 或 `REJECTED`。
- 来源缺失、上下文冲突或置信度不足时，Agent 创建待办并展示原文，不生成确定性结论。

### 难点 3：采购文件更新与结论级联失效

**业务影响**

- 正式发布的澄清、更正或补充文件可能对原采购文件形成解释、补充或变更，需要建立版本覆盖关系并重新检查受影响内容。
- 如果系统继续沿用旧版本的要求、章节、证据映射或审核结论，内部提交基线将失去可信度。

**方案取舍**

- 使用 `document_version` 和 `supersedes_document_id` 保存版本链，不覆盖或删除历史文件。
- 新版本确认后，根据来源片段和对象依赖关系，将相关要求、响应章节、证据映射、风险和审核任务标记为 `STALE`，将提交基线标记为 `INVALIDATED`。
- 先实现对象级依赖和规则级重评；更细粒度的语义影响分析放到 P1。

**实现边界**

- 系统提示“需要复核”而不是自动判断新旧条款的最终法律效力。
- 文件上传不等于版本生效，必须由有权限的用户确认文件类型、发布日期和覆盖关系。
- 旧结论保留为历史记录，不允许物理删除后假装从未产生。

**评估方式**

- 构造文件更正场景，检查受影响对象是否全部进入失效或复核状态。
- 统计错误失效、遗漏失效、重评成功率和人工恢复旧结论的原因。
- 验证任一失效对象能否回溯到触发它的新文件版本和审计事件。

**人工兜底**

- 用户确认版本关系后才触发级联失效。
- 对无法自动判断影响范围的更新，系统扩大复核范围并由投标经理缩小，而不是冒险遗漏。

### 难点 4：基于企业证据的编制、审核与正确拒答

**业务影响**

- Agent 如果编造不存在的资质、人员经历、案例或验收材料，会直接破坏投标文件可信度。
- 同一份证书在不同项目截止日期下可能具有不同有效性，不能只根据企业知识库中的静态状态判断。

**方案取舍**

- P0 使用 PostgreSQL 原生词法检索 + 向量检索召回候选证据，结合组织、资料类型、有效期、保密等级和项目上下文过滤，再使用 RRF 融合和有限重排模型排序；V1 不额外引入独立搜索引擎。
- 检索结果必须返回来源文件、页码或段落、资料版本、有效期和检索分数；Agent 只能引用已返回的证据对象。
- 通过 `evidence_link` 显式保存“要求/评分项/章节—证据”的匹配目的、确认状态和项目截止日有效性。

**实现边界**

- 企业证据检索是共享工具节点，可被资格与合规、响应规划、评分点覆盖和风险复核 Agent 调用。
- 向量索引和 PostgreSQL 词法索引是派生检索层，`knowledge_document`、`evidence_item` 和人工确认的 `evidence_link` 才是事实数据。
- P1 可把已确认关系投影为受控 GraphRAG，用于关系扩展和影响分析；图数据库不成为唯一事实源。

**评估方式**

- 使用 Recall@K、MRR 或 nDCG 评估候选证据排序。
- 使用引用正确率、证据支持率和无证据拒答率评估 Agent 输出。
- 对证书有效期、人员归属和案例证明材料建立项目时点校验用例。

**人工兜底**

- 无可靠证据时输出“证据不足，需人工确认”，不得用模型常识补齐企业事实。
- 用户可以确认、拒绝或替换证据映射；高风险证据必须经过资料管理员或合规审核人员确认。

### 难点 5：多 Agent 编排、工具节点与项目状态边界

**业务影响**

- 投标编制同时涉及资格、评分、章节、一致性和风险检查，单一 Agent 容易混淆目标、上下文和责任边界。
- 如果 Agent 可以直接改变项目状态、接受风险或生成有效提交基线，系统将无法保证人工责任链。

**方案取舍**

- 使用 Supervisor Agent 编排五类专项任务：资格与合规审查、响应规划、评分点覆盖、一致性检查和风险复核。
- OCR、表格提取、日期计算、版本比较、格式校验和检索使用确定性工具或规则节点，不包装成 Agent。
- 每个 Agent 使用结构化输入输出，绑定 `project_id`、`document_version_id`、`rule_set_version`、模型配置和来源引用。
- 通过状态图表达调度、重试、暂停、人工介入和恢复，不把聊天记录当作业务状态。

**实现边界**

- Supervisor Agent 只创建任务、组织执行、处理重试和请求人工介入，不改变项目主状态。
- 专项 Agent 只生成建议、响应计划、风险或待办；是否投标、是否接受风险和是否内部提交由人工操作。
- 稳定规则优先使用代码和配置实现，只有需要语义判断的步骤才调用模型。

**评估方式**

- 统计 Agent 任务成功率、结构化输出通过率、重试率、人工接管率和平均执行时间。
- 对每类 Agent 建立独立评测集，避免用一个综合分数掩盖局部能力问题。
- 构造输入缺失、工具失败、规则冲突和模型超时场景，验证状态是否可恢复。

**人工兜底**

- 置信度不足、输入缺失或规则冲突时进入 `WAITING_HUMAN`。
- 人工处理必须填写结论或理由，并生成审计事件；系统不能只让用户点击“继续”而不留依据。

### 难点 6：跨章节一致性、审核追溯与内部提交基线

**业务影响**

- 同一人员、日期、金额、技术参数或案例可能在多个章节重复出现，局部修改后容易产生冲突。
- 审核结论如果没有输入快照和规则版本，后续无法解释为什么当时通过、现在却失败。

**方案取舍**

- 对人员、日期、金额、参数、案例和附件引用建立可比较的规范化字段，规则先筛选候选冲突，Agent 再判断语义上下文。
- `agent_run` 保存输入对象版本、规则版本、模型配置、输出对象、引用和失败原因。
- 内部提交时生成 `project_baseline`，冻结被认可的文件、章节、证据映射和风险处理结果。

**实现边界**

- 内部提交基线只表示企业内部交接完成，不等同于已在电子交易平台递交，也不替代外部回执。
- 一致性 Agent 只报告冲突及影响范围，不自动修改报价、人员或技术参数。
- 审计事件采用追加写语义，修订通过新事件表达，不改写历史。

**评估方式**

- 对跨章节实体冲突建立准确率、召回率和误报原因统计。
- 验证任一风险、章节和基线条目能否定位到来源版本、处理人和时间。
- 构造基线后文件更新场景，检查基线是否正确失效并重新进入审核流程。

**人工兜底**

- 冲突由责任人选择正确值并决定修改范围，系统记录选择依据。
- 未解决的 `BLOCKING` 风险禁止生成有效内部提交基线，授权豁免必须填写理由。

### 难点 7：业务评估、人工反馈与版本化重评

**业务影响**

- 只展示一次成功 Demo 无法证明系统稳定，也无法说明规则、检索或 Agent 调整是否真正改善业务结果。
- 人工修改如果只覆盖模型输出、不记录错误类型，就无法沉淀为后续评测与改进数据。

**方案取舍**

- 建立“业务结果—能力评估—人工反馈”三层指标：业务层关注遗漏、阻断风险和审核闭环；能力层关注解析、抽取、检索、引用和冲突检测；运行层关注失败、重试、耗时和人工接管。
- 将人工确认、驳回、修订、豁免和失败原因写入反馈队列，并归因为数据、解析、规则、检索、提示词、模型或流程问题。
- 规则、提示词、检索配置或模型调整后生成新版本，在固定评测集上重跑，通过后才用于后续项目。

**实现边界**

- 不预设未经验证的准确率或效率提升数字。
- RAGAS 等指标可以作为检索与生成质量的辅助观察，但不能替代要求召回、风险遗漏、引用正确和人工接管等业务指标。
- 评测集使用公开采购文件和模拟企业资料，避免把模拟结果描述为真实客户生产效果。

**评估方式**

- 解析：结构恢复准确率、来源可定位率、失败率。
- 抽取：分类 Precision、Recall、F1，高风险要求遗漏率。
- 检索与引用：Recall@K、排序指标、引用正确率、无证据拒答率。
- Agent 与流程：任务成功率、重试率、人工接管率、状态恢复成功率。
- 业务闭环：阻断风险未处理数、基线失效正确率、人工驳回与修订原因分布。

**人工兜底**

- 评测失败样本进入反馈队列，由人工确认标准答案和错误归因。
- 新版本未通过离线回归时保持旧版本，不在业务流程中直接试错。

### 难点 8：公开数据、模型与解析工具的合规边界

**业务影响**

- 公开可访问不等于可以不受限制地采集、缓存、再分发或用于训练。
- 第三方解析工具、模型和数据源的服务条款、许可证及访问策略可能变化，绝对化结论容易失真。

**方案取舍**

- 优先使用用户上传文件、公开下载文件和明确允许使用的数据集构建 Demo 与评测集。
- 对每个数据源逐站核验 robots、服务条款、登录要求、访问频率和内容再利用限制。
- 对解析工具、模型和向量库记录版本、许可证和替代方案，避免关键流程绑定单一不可控依赖。

**实现边界**

- 当前 V1 不进行无授权的大规模聚合和爬取，但允许对已配置且合法可访问的平台进行项目查询和公开文件获取。
- README 只陈述实际使用的数据来源、采集方式和用途，不使用“公开数据均可自由抓取”等表述。
- 涉及敏感、登录后或明确限制自动访问的数据源时，采用人工导入或停止使用。

**评估方式**

- 建立数据源与依赖清单，记录核验日期、用途、保存范围和许可证状态。
- 定期抽查依赖版本变化是否影响解析结果、部署方式或可分发性。

**人工兜底**

- 无法确认授权边界时不自动采集，转为用户上传或使用替代公开样本。
- 许可证或服务条款发生变化时，暂停相关管线并重新评估替代方案。

### 难点 9：异构平台连接器与人工兜底

**核心矛盾**：用户希望输入项目编号后尽量自动获取资料，但不同平台存在开放接口、登录、验证码、CA、专用客户端和加密文件等差异。

**解决思路**：建立统一连接器接口和来源记录。公开且允许访问的内容自动获取；正式 API 使用甲方授权；登录后资源在具备授权时接入；CA 和专用客户端场景转为人工下载上传。任一连接器失败只创建局部重试和人工待办，不阻断项目创建。

**评估与兜底**：统计连接器成功率、文件完整率、来源追溯率和人工兜底比例；每份文件保存来源、获取时间、哈希和连接器版本。

### 难点 10：历史项目推荐与章节级安全复用

**核心矛盾**：历史中标方案可以提高编写效率，但整份复制容易带入旧客户名称、报价、人员、日期和不可履行承诺。

**解决思路**：系统只推荐候选项目，人工确认参考项目池；再按技术、结构、资格、评分、案例、报价和风险等用途绑定到具体章节。自有未中标项目可以比较，但 Agent 不推断失败原因。

**评估与兜底**：检查参考项目推荐相关性、越权引用数、旧项目信息残留数和章节绑定完整率；生成前后执行实体、金额、日期和客户名称扫描。

### 难点 11：Excel 报价模型治理与推荐边界

**核心矛盾**：甲方已有大量 Excel 模型，全部重写成本高；只上传最终金额又无法统一口径和追溯过程。

**解决思路**：系统管理模板版本、输入输出映射、公式哈希、假设版本和计算结果；Excel 或内部模型负责计算，规则引擎负责硬约束校验，大模型负责候选方案比较和解释，商务人员最终选择，项目负责人确认。

**评估与兜底**：验证公式未被篡改、预算和最高限价校验、大小写金额一致性、跨章节引用一致性及报价版本失效传播。宏或插件不兼容时采用受控模板下载、本地计算和结果上传。

### 难点 12：风险分级、增量复核与受控交接

**核心矛盾**：逐项人工确认会制造新的工作量，只在最后审核又会让风险集中暴露。

**解决思路**：低风险自动处理并可抽查，中风险批量确认，高风险逐项确认，阻断风险必须解决或授权豁免。审核意见形成结构化问题任务，修改后只重跑受影响对象。交接基线生成清单与哈希，交接包可设置接收人、有效期、下载次数和水印；基线失效时撤销旧链接并标记旧文件禁止递交。

**评估与兜底**：统计人工确认事项数、审核时长、退回轮次、增量复核比例、旧版本误用数和递交回执完整率。

## 四、Agent、工具与人工的责任边界

| 类型 | 主要职责 | 禁止事项 |
|---|---|---|
| Supervisor Agent | 创建和编排任务、处理重试、暂停并请求人工介入 | 不改变项目主状态，不接受风险，不生成有效提交基线 |
| 专项 Agent | 资格与合规审查、响应规划、评分点覆盖、一致性检查、风险复核 | 不代替人工作出是否投标、是否满足资格、是否提交等决定 |
| 工具/规则节点 | 文档解析、OCR、表格提取、日期计算、版本比较、格式校验、证据检索 | 不包装成具有自主决策能力的 Agent |
| 人工角色 | 确认文件版本、要求、证据、风险、章节和内部提交基线 | 关键操作必须留下处理理由与审计记录 |

## 五、P0 与 P1 技术范围

### P0 必须形成的闭环

```text
项目编号查询、分级数据接入与文件确认
→ 文档解析与结构化抽取
→ 要求、评分项和时间节点人工确认
→ 企业证据检索与映射
→ 同类项目推荐、横向对比和参考池确认
→ 受控 Excel 报价、有效方案比较和人工确认
→ 响应矩阵、章节任务、带引用初稿、图表和说明材料
→ 多 Agent 预检、项目负责人和商务/法务审核
→ 结构化返工、差异确认和增量复核
→ 内部交接基线、受控交接和人工递交记录
→ 离线评估、反馈归因与版本化重评
```

### P1 扩展点

- 基于 P0 已确认关系的受控 GraphRAG，用于关系扩展检索和影响分析；
- 更细粒度的文件差异定位与依赖影响分析；
- 更多资格、格式、人员、案例和版本规则；
- 评测集版本管理、失败样本聚类和质量趋势看板。

P1 能力不得成为 P0 闭环成立的前置条件。

## 七、面试讲解主线

> 这个项目的难点不在于调用多个大模型接口，而在于把分散的投标业务做成一个可确认、可追溯、可恢复的 Agent 工作流。系统通过分级连接器获取资料，使用证据和历史参考约束章节生成，保留 Excel 作为报价计算工具，再由规则过滤、模型解释和人工确认形成报价闭环。Supervisor 编排专项 Agent，审核意见转为结构化问题，修改后只复核受影响内容；最终交接包绑定基线、清单和哈希，由递交责任人人工完成外部递交。这样展示的不是自动写标书的聊天 Demo，而是一套有数据接入、业务状态、证据约束、报价治理、审核闭环和质量评估的多智能体应用。
