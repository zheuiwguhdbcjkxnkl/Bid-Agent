# 11 产品需求文档（PRD）

> 版本：v3.0
> 更新日期：2026-08-21
> 文档状态：V1 产品需求基线  
> 产品名称：投标文件智能编制与合规审核平台 V1  
> 产品定位：面向投标企业的单项目投标任务工作台，以“场景做窄、核心做深”和“证据约束生成 + 人工最终确认 + 风险分级审核 + 全过程版本留痕”为原则，辅助完成从项目识别到内部受控交接的投标文件编制流程。  
> 适用范围：政府采购信息化服务项目、单个投标项目、单个采购包。  
> 关联文档：`07-客户画像与场景设定.md`、`08-招投标术语与业务知识手册.md`、`09-业务流程与项目状态机.md`、`10-核心业务对象与数据字典.md`、`12-项目难点与解决思路.md`、`13-项目决策与工作记录.md`、`15-评估体系与测试计划.md`、`16-产品版本规划.md`、`17-技术方案与系统架构设计.md`、`18-数据库设计与实现方案.md`

## 零、文档基线与使用规则

### 0.1 基线定位

- 本文档是 V1 产品范围、用户角色、功能需求、业务规则、验收场景和发布门槛的正式主基线。
- 后续技术方案、版本规划、开发计划、评估体系、生产级增强方案和数据库设计必须以本文档为上游输入，并引用对应的 `FR`、`PRD-BR` 或 `AC` 编号。
- 第六章列出的功能需求均属于 V1 产品范围，除非条目中明确标注为“后续版本”；版本规划可以拆分研发阶段和内部里程碑，但不能静默删除 V1 验收范围。
- PRD 负责定义“做什么、为什么做、边界是什么、如何验收”，不承载完整技术实现、物理数据库结构或具体代码任务。
- 当前 Agent 产品协作口径为“主 Agent + 专业 Subagent”：系统可以自动规划和委派，但跨 Agent 交接必须形成可追溯的结构化记录，不能以不可审计的自由对话直接改变业务状态。
- Agent 完成一个业务阶段后先产生待确认草稿；人工确认、基线冻结和下一阶段启动属于产品流程的一部分，不等同于恢复上一段 Agent 对话。

### 0.2 下游文档约束

- 下游文档可以细化实现方式，但不得扩大、缩小或改变 PRD 已确认的业务范围和人工决策边界。
- 技术方案不得以技术限制为由直接删除需求；确需调整时，应先修改 PRD 并记录决策。
- 版本规划不得把 V1 必须验收的能力直接移到后续版本，除非 PRD 完成版本升级和范围变更。
- 开发计划中的每个任务必须能够回溯到至少一个功能需求、业务规则或验收场景。
- 评估体系可以补充指标定义、样本、公式和阈值，但不得降低 PRD 中的质量底线。
- 生产级增强方案只能补充高可用、安全、可观测性、灾备、性能和运维能力，不得改变核心业务语义。
- 数据库设计必须实现 `10-核心业务对象与数据字典.md` 中的领域语义；物理表、索引和约束变化不得破坏版本、来源和审计要求。

## 一、产品背景

甲方投标团队长期参与政府采购、企业采购和信息化服务类项目，已经使用招投标平台、采购公告平台、企业知识库、历史标书库、内部资料库、Excel 报价模板和合规审核流程。当前问题不是完全依赖人工从零编写，而是现有工具之间缺少统一流程、统一数据口径和可追溯闭环。

### 1.1 九个业务痛点

1. **数据和工具分散**：公告、采购文件、补充文件、企业资料、历史标书、同类项目、中标结果、报价模型和审核记录分散在不同系统中。
2. **数据口径和计算过程难统一**：商务指标、报价假设、Excel 模板、公式版本和计算结果缺少统一管理与追溯。
3. **同类项目对比和报价测算重复劳动较多**：参考项目池、历史中标方案、报价系数和策略假设需要反复整理。
4. **标书正文格式和图表标准不统一**：章节结构、引用、图表、风险提示、来源说明和附件容易不一致。
5. **合规问题暴露偏后**：资格缺口、实质性要求遗漏、评分点未覆盖、风险提示不足和说明文件缺失经常在临近递交时集中出现。
6. **标书提交和后续维护缺少统一闭环**：文件变更、版本更正、内部交接、递交结果和回执缺少一致的版本管理。
7. **多人协作、任务分配和进度跟踪缺少统一管理**：章节责任、截止时间、依赖任务、修改范围和审核状态难以统一查看。
8. **企业资料的有效性、完整性和使用权限难以统一管理**：资质、人员、案例、合同和验收材料可能过期、缺失、越权使用或无法证明与当前要求的关系。
9. **AI 生成内容缺少事实依据、来源定位和可信审核机制**：模型可能编造企业能力、错引历史内容、遗漏要求或产生跨章节冲突。

### 1.2 产品边界

平台服务投标人/供应商内部团队，不服务采购人、招标代理机构、评标委员会或其他供应商。平台生成的是可编辑、待确认、待审核的投标文件初稿，不替代标书编写人的业务判断，也不自动形成具有法律效力的最终投标文件。

## 二、核心价值与产品目标

### 2.1 核心价值

```text
让系统承担重复、标准化、可规则化的工作；
让标书编写人聚焦标包/项目类别理解、项目判断、报价假设和投标方案确认；
让负责人和商务/法务审核人员更高效地复核标书质量和提交风险。
```

### 2.2 V1 产品目标

1. 从“项目来源 + 外部项目编号”创建项目，并自动获取可公开访问的公告和采购文件；自动获取失败时提供链接补充和文件上传兜底。
2. 将采购文件、澄清更正、企业证据、历史项目、报价版本、章节内容、风险和审核结论统一纳入版本化工作台。
3. 抽取资格条件、实质性要求、评分项、时间节点、附件要求和格式要求，并保留文件版本、页码和原文片段。
4. 形成同类项目推荐、人工确认参考池和章节级参考用途，避免整份历史标书无边界复用。
5. 治理 Excel 报价模板、输入口径、报价假设、计算结果和方案版本；规则过滤无效方案，大模型提供推荐解释，人工最终选择。
6. 按章节生成带来源的响应矩阵、正文初稿、图表、风险提示、数据来源和说明材料。
7. 通过系统预检、项目负责人审核、商务/法务审核、结构化返工和增量复核形成内部审核闭环。
8. 冻结内部交接基线并受控交接给投标递交责任人，记录接收、外部人工递交状态和回执。
9. 通过历史基线与试点项目对比，量化系统自动化程度、编写效率、审核效率和质量风险。

### 2.3 非目标

- 不替代人工决定是否投标、最终报价、风险接受、投标方案或内部交接。
- 不承诺接管所有外部平台；验证码、CA、专用客户端、加密环境和无授权系统保留人工处理。
- 不自动登录电子交易平台完成外部递交，不执行 CA 签章，不替代法定回执和归档系统。
- 不进行中标概率预测，不把大模型推荐等同于中标结论。
- 不在 V1 建立多项目组合管理、多采购包独立闭环、联合体成员级闭环或工程招标完整规则体系。
- 不服务采购文件编制、评标、定标或对其他供应商投标文件的审核。
- 不将演示数据、模拟企业资料或离线评测结果描述为真实生产数据。

### 2.4 产品版本路线

正式产品版本只使用 `V1`、`V2` 和 `V3`，不再使用 `V1.1`、`V1.2` 表示对外产品版本。V1 内部研发阶段使用 `M1` 至 `M6` 或 `Phase A` 至 `Phase C` 标识，避免把开发过程中的半成品误认为正式版本。

| 正式版本 | 产品定位 | 核心范围 |
|---|---|---|
| `V1` | 单项目标书生成与内部交接闭环 | 单个政府采购信息化服务项目、单个采购包；一个主要连接器或受控模拟连接器与人工上传兜底；从输入项目代码到内部提交留痕；实现任务流程可视化、核心结论集中展示、数据证据可查看、标书内容可预览、审批与合规闭环、内部提交和版本可追溯 |
| `V2` | 多场景与团队协同增强 | 多标书类型、更多数据连接器、公告与补充文件监控、更完整历史项目对比、多模板、精细变更影响、灵活审核协同、客户版或对外版本受控生成与分发、多项目协同看板 |
| `V3` | 投标质量运营与平台化 | 投标质量评估产品化、Agent/模型/提示词/检索回测、跨项目质量与风险分析、知识沉淀、效率和成本分析、多组织治理、生产级高可用安全运维，以及更复杂投标场景和外部平台集成评估 |

V2、V3 仅定义方向，不进入当前 V1 验收范围。详细目标、能力方向、依赖和立项规则由 `16-产品版本规划.md` 维护；V2、V3 正式启动前仍需分别建立独立 PRD。`specs/research` 中早期出现的“V2 图 RAG”等表述属于历史研究材料，不构成当前 Agent 项目的正式版本承诺。

V1 内部建议使用以下里程碑：

```text
M1：项目与文件
M2：要求与证据
M3：标书生成与工作台展示
M4：审核、合规与返工
M5：内部交接与版本留痕
M6：评估、修复与交付验收
```

## 三、目标用户与权限边界

| 角色 | 核心职责 | 关键权限 |
|---|---|---|
| 标书编写人 | 处理要求、证据、参考项目和章节初稿 | 编辑章节、处理待办、提交审核 |
| 技术方案人员 | 确认技术需求、评分覆盖和技术方案 | 编辑技术章节、确认技术证据 |
| 商务/报价人员 | 维护商务指标、报价假设和候选方案 | 执行报价模型、选择报价方案 |
| 资料管理员 | 维护资质、人员、业绩、合同和模板 | 发布资料版本、确认有效期与权限 |
| 项目负责人 | 统筹任务、确认策略、审核项目和交接基线 | 分配任务、确认报价、提交审核、确认交接 |
| 商务审核人员 | 复核商务响应、报价引用和证明材料 | 提出问题、复核关闭、确认或退回 |
| 合规/法务人员 | 复核资格、实质性要求、承诺和法律风险 | 提出阻断问题、审批豁免、确认或退回 |
| 投标递交责任人 | 接收内部交接包并人工完成外部递交 | 确认接收、记录递交结果、上传回执 |
| 系统管理员 | 管理连接器、模板、规则、角色和审计 | 配置系统、发布版本、查看运行日志 |

标书编写人不能自行关闭审核人员提出的问题。问题原则上由原审核角色复核关闭；无法处理时可以转交同角色授权人员，但必须记录原因。

## 四、V1 范围与端到端流程

### 4.1 V1 范围

```text
单个政府采购信息化服务项目、单个采购包
→ 项目查询与文件接入
→ 文件版本确认与结构化解析
→ 要求、评分项和时间节点抽取
→ 企业证据匹配与有效性检查
→ 少量受控历史项目推荐、差异说明和参考用途确认
→ Excel 报价测算、方案推荐和人工确认
→ 手动刷新或人工补充公告、澄清、更正和补充文件
→ 响应矩阵、章节初稿、图表和说明材料生成
→ 系统预检、负责人审核、商务/法务审核
→ 结构化返工与对象级或章节级复核
→ 冻结内部交接基线
→ 受控交接给投标递交责任人
→ 人工外部递交并记录结果和回执
```

V1 采用“场景做窄、核心做深”的范围原则：不追求平台数量、标书类型和流程配置广度，但必须把来源、权限、人工关口、状态、版本、失败恢复、审计和证据追溯做成可验收的企业级闭环。

以下能力明确进入 V2，不属于 V1 验收范围：更多采购平台和企业系统连接器、自动定时监控、大规模历史项目分析、高级报价策略模拟、自定义 Dashboard、通用工作流和会签、字段级精确影响分析、自动最小化增量复核、客户版受控分发、动态水印与下载次数控制，以及更多外部递交或归档系统集成。

### 4.2 自动化与人工关口

系统默认自动运行低风险、标准化任务；中风险事项支持批量确认；高风险事项必须逐项人工确认；阻断风险必须解决或由授权人员填写理由并豁免。

必须保留人工确认的关键关口：

1. 当前有效采购文件版本；
2. 关键资格条件和企业证据缺口；
3. 历史参考项目池及章节用途；
4. 最终报价方案；
5. 高风险承诺和风险豁免；
6. 项目负责人、商务及合规审核结论；
7. 内部交接基线和递交责任人接收。

## 六、功能需求

### FR-101 项目创建与数据连接

- 用户选择 V1 已配置的主要来源并输入外部项目编号；系统创建内部 `project_id`。
- V1 建设一个主要数据连接器或受控模拟连接器；对公开且允许访问的数据查询公告并下载公开文件，连接器的来源、授权和适用范围必须明确。
- 需要账号、验证码、CA、专用客户端或加密环境的数据，在无法自动接入时提示用户补充链接或上传文件。
- 企业知识库、历史标书库和内部资料库在 V1 通过受控文件导入或项目级授权目录接入；通用 API、数据库同步和更多系统连接器进入 V2。
- 所有自动或人工导入内容记录来源、获取时间、文件哈希、连接器版本和操作者。
- 单一连接器失败不得阻断项目创建，应创建可重试任务并提供人工兜底。

### FR-102 项目总览、任务与进度

- 展示项目状态、截止时间、有效文件、报价版本、参考池、章节进度、审核状态和交接基线。
- 每项任务记录负责人、截止时间、前置任务、状态、关联版本和待处理问题。
- 支持按角色查看“我的任务”“待确认事项”“临期任务”和“阻断事项”。
- 文件、证据、报价或章节变化后，按对象级或章节级结果重新打开受影响任务和审核项；无法可靠判断范围时扩大复核或执行全量复核。

### FR-201 文件中心与版本监控

- 管理公告、采购文件、澄清、更正、补遗、答疑、附件和内部上传文件。
- 解析 PDF、Word、Excel 和常见扫描件，输出章节、表格、页码、原文片段和解析质量。
- 用户确认当前有效采购文件和文件覆盖关系后，才可进入正式生成与审核。
- V1 支持用户手动刷新主要来源，或人工上传新公告、澄清、更正和补充文件；自动定时监控和临近截止时间高频检查进入 V2。
- 高风险更新进入待确认状态，暂时阻止生成新的有效内部交接基线。
- 用户确认更新后，系统按文件、要求、评分项、证据、报价、章节、风险、审核任务和基线等对象或章节关系判断影响范围；无法可靠判断时，相关下游结果全部失效并进入全量复核。字段级精确影响分析和自动最小化复核进入 V2。

### FR-301 要求、评分项与响应矩阵

- 从已确认文件抽取资格条件、实质性要求、技术/商务要求、评分项、时间节点、附件和格式要求。
- 每条结果展示类型、标准化描述、原文、页码、文件版本、后果、置信度和确认状态。
- `★`、黑体、表格位置只能作为辅助信号，不能单独判定风险等级。
- 系统生成要求—评分项—章节—证据—责任人的响应矩阵。
- 按阻断、待确认、未映射、部分覆盖和已覆盖筛选。

### FR-401 企业证据库

- 管理企业资质、人员、案例、合同、验收材料、授权文件、财务资料和证明附件。
- 每项证据记录主体、有效期、适用范围、保密等级、来源文件和人工确认状态。
- 系统进行有效期、主体、权限和材料完整性检查。
- 检索返回原文片段、页码、有效期和匹配理由；无证据时必须拒答并创建人工补充任务。
- 只有经过确认且权限允许的证据才能进入正式标书。

### FR-402 同类项目与历史参考池

- V1 从甲方受控历史项目中维护少量可用候选，以自有历史中标标书为核心，公开中标结果和同类项目信息只作补充。
- 自有未中标项目可以参与比较，但系统不得推断未中标原因。
- 推荐使用采购内容、预算规模、行业、技术路线、评分结构、资格条件、服务周期和地域等基础维度，并说明推荐理由。
- V1 输出项目概况、关键相似点、主要差异、可复用边界和风险提示，不建设大规模跨项目横向分析、中标/未中标归因或运营复盘。
- 用户确认参考项目池，并按技术、结构、资格、评分、案例、报价和风险等用途授权。
- 参考项目池增删和用途变化生成新版本，章节生成只能使用已确认的绑定关系。

### FR-501 商务指标与报价方案

- V1 至少支持一个受控 Excel 报价模板，记录模板版本、适用范围、审批状态、输入/输出映射和公式校验值；多模板和通用模板管理进入 V2。
- Excel 或甲方内部模型继续负责实际计算；V1 通过受控文件或已明确授权的固定接口读取结果，通用报价系统集成进入 V2。
- 系统记录成本、税率、利润率、风险系数、优惠假设等当前项目必需的报价假设版本。
- 校验预算、最高限价、税率、合计、大小写金额和跨章节一致性。
- 规则引擎排除无效方案；大模型只能在有效候选方案中推荐并说明理由与风险。
- 商务人员最终选择，项目负责人确认；激进策略需要增加授权审批。
- 只有冻结的确认报价版本可写入正文、报价表和交接基线。
- 高级报价模型、敏感性分析、策略模拟和自动最优报价不属于 V1。

### FR-601 章节编制、图表和说明材料

- 当前采购文件决定写什么，团队模板决定结构与格式，历史标书只提供授权范围内的参考。
- 按章节生成，不一次性生成不可控的大文档。
- 每个章节绑定要求、评分项、企业证据、参考项目、报价版本和模板版本。
- 输出在线可编辑文档、DOCX 和内部审核 PDF。
- 图表必须绑定数据来源、生成时间和版本；跨章节人员、金额、日期和参数保持一致。
- 说明材料区分 `BID_ATTACHMENT`、`EXTERNAL_EXPLANATION` 和 `INTERNAL_NOTE`。
- 风险采用双轨内容视图：内部审核视图展示完整风险、证据缺口、报价策略和豁免；V1 导出的正式响应内容只包含审核批准的内容。客户版受控生成与分发进入 V2。
- 系统不得静默覆盖人工编辑内容；局部重生成必须展示差异并由用户确认。

### FR-701 Agent 预检、审核与返工

- 系统预检包括资格与合规、评分点覆盖、一致性、附件完整性、报价引用和风险复核。
- 主 Agent 负责阶段内任务规划、专业 Subagent 委派、重试建议、暂停建议和人工接管建议；它不直接改变项目主状态。
- 主 Agent 与专业 Subagent 之间的每次正式交接必须记录发送方、接收方、阶段、输入版本、任务类型、产物引用、风险信号、幂等标识和下一步建议；自由文本、todo 或模型推理不能直接成为业务状态。
- 系统必须保留七类可审计的阶段决策：`DISPATCH_AGENT`、`WAITING_HUMAN`、`RETRY_TASK`、`EXPAND_REVIEW_SCOPE`、`INVALIDATE_OUTPUTS`、`BLOCK_WORKFLOW` 和 `COMPLETE_STAGE`。
- Agent 阶段运行完成后，产物先处于待确认草稿状态；领域规则、权限、版本和人工关口校验通过后，才能形成正式业务版本。
- V1 使用固定审核顺序：系统预检 → 项目负责人 → 商务审核 → 合规/法务审核；无关角色不必重复审核全部内容，通用工作流、会签和任意审批配置进入 V2。
- 审核视图按角色展示异常、原文证据、版本差异和影响范围，支持批量处理低中风险事项。
- 每条审核意见形成结构化问题任务，记录提出人、责任人、风险等级、证据、修改要求和截止时间。
- Agent 只能生成修改建议；标书编写人确认后才写入正式章节。
- 修改后由原审核角色复核关闭；编写人不能关闭自己的审核问题。
- 能够可靠定位时，只重新运行和复核受影响的对象或章节；无法可靠判断影响范围时扩大复核或执行全量复核。字段级精确影响和自动最小化增量复核进入 V2。

### FR-702 风险中心与人工确认

- 风险分为 `LOW`、`MEDIUM`、`HIGH` 和 `BLOCKING`。
- 低风险默认自动处理并可抽查；中风险支持批量确认；高风险必须逐项确认；阻断风险必须解决或授权豁免。
- 风险豁免记录授权人、理由、适用范围和版本。
- 任何置信度不足、证据缺失或规则冲突转为 `WAITING_HUMAN`。
- 未解决的阻断风险禁止生成有效内部交接基线。

### FR-801 内部交接与递交记录

- 项目负责人生成 `REVIEW_BASELINE` 和 `HANDOVER_BASELINE`，冻结采购文件、正文、报价、附件、证据、风险和审批结果。
- 基线生成文件清单、版本号、哈希和“内部审核版/禁止递交”等标识。
- V1 受控交接记录交接人、接收人、交接时间、接收状态和当前有效基线；动态水印、下载次数、复杂有效期和禁止转发策略进入 V2。
- 关键内容变化后旧基线自动失效，旧交接包或访问入口标记失效，旧文件标记“禁止递交”。
- 投标递交责任人确认收到并确认使用最新版本。
- 外部递交由人工完成，系统记录平台、时间、状态、操作人和上传回执。

### FR-901 质量评估与反馈

- V1 采用四层评估：`L1` 单模块评估、`L2` 业务链路评估、`L3` 单项目端到端评估和 `L4` 试点业务价值评估。
- 离线评测覆盖要求抽取、评分项抽取、证据检索、引用、章节生成、风险检查、一致性和状态转换。
- `L1` 覆盖数据接入、文档解析与 OCR、要求与响应矩阵、企业证据、历史参考池、报价方案、章节生成、审核风险闭环以及版本交接等核心模块。
- `L2` 覆盖项目与采购文件准备、要求与响应依据准备、报价确认与章节引用、初稿审核返工、变更交接与递交留痕五条业务链路。
- 核心 `L1` 模块和五条 `L2` 链路通过后，才能进入 `L3` 单项目端到端评估；`L3` 通过后判定“V1 交付验收通过、试点就绪”，可以完成软件交付验收并进入受控旁路试点；`L4` 独立验证真实业务价值，完成并达到双方确认的门槛后，才能判定“V1 业务价值验证通过”并建议扩大使用。
- 评估必须同时覆盖正常、边界、失败、转人工和版本变化路径；正确拒答、阻断、降级或转人工属于有效结果，不以自动化率单独判断质量。
- 运行指标覆盖自动获取率、自动处理比例、首稿时间、人工查找时间、确认事项数、审核时长、退回轮次和增量复核比例。
- 人工确认、驳回、修改、豁免和重新打开形成结构化反馈，但不得根据单条反馈自动更新线上规则或模型。
- 规则、提示词、检索和模型配置变更必须生成新版本并通过离线评测。
- 详细样本集、金标准、指标公式、数值阈值、样本量、失败处理和回归流程由 `15-评估体系与测试计划.md` 定义，不在 PRD 中重复展开。
- L1、L2 和 L3 的评测对象以本 PRD v3.0 收敛后的 V1 范围为准；质量底线不因连接器数量、监控方式、历史候选规模、影响分析粒度或分发能力收敛而降低。

## 七、核心业务规则

| 编号 | 规则 |
|---|---|
| PRD-BR-01 | 只有人工确认的采购文件版本可以进入正式生成、审核和内部交接基线。 |
| PRD-BR-02 | 澄清、更正、补遗或关键数据变化后，依赖旧版本的结果必须失效或待复核。 |
| PRD-BR-03 | 资格、实质性、评分、报价和风险结论必须能够定位来源；缺少来源时转人工。 |
| PRD-BR-04 | Agent 不得编造企业资质、人员、业绩、报价或履约能力。 |
| PRD-BR-05 | 报价由 Excel 或内部模型计算；大模型只在规则有效的候选方案中推荐，最终选择权属于人工。 |
| PRD-BR-06 | 历史标书按项目池、章节和用途授权，不允许整份无边界复制。 |
| PRD-BR-07 | 未解决的 `BLOCKING` 风险禁止生成有效 `HANDOVER_BASELINE`。 |
| PRD-BR-08 | 是否投标、最终报价、风险接受、审核通过和内部交接必须由授权人员操作。 |
| PRD-BR-09 | 人工修改不得被模型静默覆盖，局部重生成必须展示差异。 |
| PRD-BR-10 | 所有确认、退回、修改、豁免、转交、基线和递交记录必须生成不可修改的审计事件。 |
| PRD-BR-11 | 系统默认例外驱动：低风险自动、中风险批量、高风险逐项、阻断风险强制处理。 |
| PRD-BR-12 | 外部递交仍由投标递交责任人执行，系统记录结果但不代替交易平台。 |

## 九、非功能需求

### 9.1 可追溯性

- 关键输出展示来源文件、版本、页码、原文片段、企业证据、参考项目和报价版本。
- Agent 运行保存输入快照、规则版本、模型配置、提示词版本、输出引用、结构化交接记录、阶段决策和失败原因。
- 状态变化、人工确认、审核问题、风险豁免和基线交接均可审计。

### 9.2 可靠性与可恢复性

- 数据获取、解析、检索、生成和审核任务异步执行，支持失败重试和人工接管。
- 单一连接器、文件或 Agent 失败不得删除已确认事实和人工结论。
- 文件或对象更新优先标记下游结果失效，不得静默沿用旧结果。
- 一个投标流程可以跨多个阶段运行；阶段级 Agent 运行完成并进入人工关口后，确认动作应基于已保存的业务版本、运行记录和审计记录启动下一阶段，不要求恢复上一段 Agent 的自由对话上下文。
- 页面刷新、Worker 重启、任务重投或人工确认重复提交不得造成重复产物、绕过人工关口或覆盖已确认版本。

### 9.3 安全与权限

- 真实部署默认位于甲方内网或 VPC。
- 企业资料、历史标书和报价信息按组织、项目、角色、保密等级和用途最小授权。
- 日志、评测集和导出文件不得泄露未脱敏的个人信息、报价和客户机密。
- 面向其他企业部署时保留 `organization_id`、连接器、规则和模板配置隔离，不在 V1 建设完整多租户 SaaS。

### 9.4 性能与体验

- 长任务展示真实进度、当前阶段、预计剩余步骤、失败原因和重试入口。
- 待确认事项按风险、角色、截止时间和影响范围排序。
- 支持批量确认和增量复核，避免用户机械式逐项点击和全量重复审核。

## 十、价值指标与验收体系

### 10.1 基线方法

优先使用甲方合法授权且完成脱敏的历史项目建立人工流程基线。当前甲方无法提供完整历史项目资料，因此 L3 使用“真实公开采购文件 + 可控模拟企业数据 + 受控报价数据 + 模拟工作流 + 人工构造异常”验证系统正确性、安全边界和流程闭环。

L4 采用前瞻性真实试点建立业务基线：人工团队继续按原流程完成正式投标，系统以旁路方式同步运行并记录任务、耗时、确认、修改、审核和问题数据；首批试点形成可比较基线，后续同类型项目再评估系统辅助后的效率和质量变化。具体提升目标在获得真实试点数据后共同确定，不在缺少数据时承诺未经验证的比例。

### 10.2 指标分类

| 核心价值 | 指标示例 |
|---|---|
| 系统承担重复工作 | 平台查询成功率、文件自动获取率、要求抽取覆盖率、证据匹配率、自动处理比例、来源可追溯率 |
| 编写人聚焦业务判断 | 首稿生成时间、人工查找整理时间、复制录入次数、待确认事项数、章节可用率、业务判断时间占比 |
| 审核人员提高效率 | 平均审核时间、退回轮次、预检发现率、末期阻断问题数、增量复核比例、问题按期关闭率 |
| 质量底线 | 无来源关键结论数、AI 编造事实数、未解决阻断风险数、版本失效正确率、授权确认完整率 |

### 10.3 四层评估基线

| 层级 | 评估对象 | 核心判断 |
|---|---|---|
| `L1` 单模块评估 | 各核心模块的独立输入、输出、规则、拒答、版本和人工兜底 | 单个模块是否达到进入业务链路的最低质量要求 |
| `L2` 业务链路评估 | 多模块之间的数据传递、人工确认、异常处理、版本传播和终点产物 | 多个模块连接后是否能够完成真实业务任务 |
| `L3` 单项目端到端评估 | 从项目编号或文件输入到内部交接和人工递交记录的完整项目 | V1 是否形成完整、正确、可审核、可追溯的项目闭环 |
| `L4` 试点业务价值评估 | 真实项目旁路运行数据与历史或前瞻性人工基线的对比 | 是否实际减少重复劳动、编写耗时、审核耗时和末期风险，并支持业务价值验证和扩大使用决策 |

### 10.4 L1 与 L2 范围摘要

`L1` 单模块评估至少覆盖：

1. 数据接入；
2. 文档解析与 OCR；
3. 要求、评分项与响应矩阵；
4. 企业证据检索、引用与无证据拒答；
5. 同类项目与历史参考池；
6. 商务指标、报价校验与方案推荐；
7. 章节、图表、风险提示、来源与说明材料生成；
8. Agent 预检、人工审核、结构化返工与风险闭环；
9. 版本失效、状态转换、内部交接与递交记录。

`L2` 业务链路评估至少覆盖：

1. 项目编号 → 文件接入 → 有效版本确认 → 文档解析；
2. 要求提取 → 企业证据 → 历史参考 → 响应矩阵；
3. 报价测算 → 规则校验 → 人工确认 → 章节引用；
4. 章节生成 → Agent 预检 → 人工审核 → 结构化返工；
5. 内容变更 → 影响分析 → 增量复核 → 交接基线 → 递交记录。

PRD 只定义评估层级、范围、质量底线和发布门槛。各模块和链路的测试数据、金标准、计算公式、阈值、样本量和失败处理规则由 `15-评估体系与测试计划.md` 维护；该文档不得降低本 PRD 的质量底线。

中标率仅作为长期观察指标，不作为 V1 核心验收标准。

## 十一、验收场景

### AC-01 项目编号与分级数据接入

1. 用户选择 V1 已配置的主要来源并输入项目编号；
2. 主要连接器或受控模拟连接器获取公开公告和文件并记录来源；
3. 一个受限文件获取失败，系统创建人工上传待办；
4. 用户上传文件并确认有效版本；
5. 项目进入正式解析流程，失败连接器可独立重试。

### AC-02 文件解析、变更与影响分析

1. 系统抽取资格、实质性要求、评分项、时间节点和附件要求；
2. 每项结果可定位原文；
3. 用户手动刷新或上传澄清、更正文件并确认覆盖关系；
4. 系统按对象或章节识别影响，受影响的要求、章节、风险、审核任务和基线进入失效或待复核状态；无法可靠判断时执行全量复核；
5. 人工编辑内容不被静默覆盖。

### AC-03 企业证据、历史参考和拒答

1. 系统推荐企业证据和少量受控历史项目；
2. 用户确认企业证据、参考项目池和章节用途；
3. 无有效证据的问题输出“证据不足”并创建待办；
4. 系统不得编造企业能力或推断未中标原因；
5. 初稿引用可定位到证据和历史参考。

### AC-04 报价方案闭环

1. 管理员发布受控 Excel 模板版本；
2. 商务人员填写报价假设并完成计算；
3. 系统读取候选结果并校验预算、最高限价和一致性；
4. 规则排除一个无效方案，大模型解释有效方案差异；
5. 商务人员选择方案，项目负责人确认；
6. 标书只引用冻结的确认报价版本。

### AC-05 章节生成、审核和增量返工

1. 系统按章节生成带来源初稿、图表和内部风险清单；
2. 项目负责人和商务/法务审核人员提出结构化问题；
3. Agent 生成修改建议，编写人确认后写入；
4. 原审核角色查看差异并复核关闭；
5. 能够可靠定位时只重跑受影响对象或章节；无法可靠判断时扩大复核或执行全量复核；
6. 阻断风险未处理时无法生成有效交接基线。

### AC-06 内部交接与人工递交记录

1. 所有必要审核通过或风险已授权豁免；
2. 项目负责人生成交接基线和文件清单；
3. 投标递交责任人确认接收和最新版本；
4. 关键内容变化后旧基线和交接入口失效；
5. 递交责任人人工完成外部递交，并记录平台、时间、状态和回执。

### AC-07 核心价值评估

1. 如果存在合法授权的历史项目数据，系统加载脱敏后的人工流程基线；如果不存在，则通过首批旁路试点前瞻性建立基线；
2. 人工团队继续按原流程完成正式投标，系统不得在 L4 业务价值验证通过前替代人工递交和关键决策；
3. 试点项目自动采集任务、耗时、确认、修改、审核、风险和人工接管数据；
4. 输出自动化、编写效率、审核效率和质量风险对比；
5. 未测指标或样本不足指标明确标记为待评测，不虚构提升比例；
6. 只有 L4 完成并达到双方确认的业务价值门槛，才能判定 V1 业务价值验证通过并建议扩大使用；L4 数据不足或尚未完成不影响已经通过的 V1 软件交付验收。

## 十二、发布门槛

### 12.1 V1 技术完成

- 九类核心 `L1` 模块评估全部达到 `15-评估体系与测试计划.md` 规定的发布阈值，且未触发零容忍门禁。
- 五条 `L2` 业务链路全部通过正常、边界、失败、转人工和版本变化路径评估。
- 所有 P0 验收场景可重复执行并保留来源和版本。
- 关键资格、实质性要求、评分项、报价和风险结论可追溯。
- AI 编造企业事实、未处理阻断风险仍可交接、旧基线未失效、人工修改被静默覆盖均属于阻断级缺陷。
- 无效报价进入标书、未经确认的证据或参考内容进入正式章节、关键审核或交接动作缺少审计记录，同样属于阻断级缺陷。
- 主要数据连接器、解析、检索、生成和审核失败均有人工兜底或恢复路径。

### 12.2 V1 交付验收与试点就绪

- `L1` 和 `L2` 通过后，必须完成 `L3` 单项目端到端评估。
- `L3` 零容忍问题为零，`AC-01` 至 `AC-06` 全部通过，核心质量指标达到 `15-评估体系与测试计划.md` 规定的阈值。
- 达到上述要求后，判定“V1 交付验收通过、试点就绪”；软件开发和交付可以正式验收，系统可以进入真实项目受控旁路试点。
- 旁路试点期间人工团队继续按原流程完成正式投标；系统不得代替最终报价、风险接受、审核通过、内部交接和外部递交决定。
- L3 “有条件通过”只能继续内部验证，不能直接进入正式试点或生产发布。

### 12.3 V1 业务价值验证与扩大使用

- L4 必须完成真实项目旁路运行和历史或前瞻性人工基线对比。
- 自动化、编写效率、审核效率和质量风险指标达到双方在获得真实数据后确认的业务价值门槛。
- L4 只使用三种正式结论：“L4 业务价值验证通过”“L4 业务价值验证未通过”“L4 待继续评测”。
- L4 期间不得出现新的零容忍缺陷；发现后应退回受影响的 L1、L2 或 L3 重新评估。
- 样本不足时标记为“L4 待继续评测”；该状态不撤销已经通过的 V1 软件交付验收，但不能判定业务价值验证通过，也不能虚构提升比例。
- L4 完成但未达到冻结的业务价值门槛时，判定“L4 业务价值验证未通过”；该结论不撤销已经通过的 V1 软件交付验收和已验证技术能力，但不得宣称 V1 已实现预期业务价值或建议扩大使用。
- L4 达到冻结的业务价值门槛时，判定“L4 业务价值验证通过”，并进入扩大使用范围或规模化推广的决策。
- L4 结论本身不撤销已经通过的 L3 软件交付验收；如果 L4 期间发现新的零容忍缺陷，则按缺陷影响范围重新评估 L1、L2 或 L3，并根据复评结果处理相应状态。

### 12.4 评测报告约束

- 评测报告只陈述实际测得结果，未测结果不得包装为真实收益。
- 模拟评测结果、旁路试点结果和正式生产结果必须明确区分。

### 13.2 冲突处理优先级

1. 产品范围、角色权限、业务规则、验收条件发生冲突时，以当前已生效 PRD 为准。
2. 状态名称、转换条件和异常路径以 `09-业务流程与项目状态机.md` 为准，但不得违反 PRD。
3. 领域对象、字段含义和关联关系以 `10-核心业务对象与数据字典.md` 为准，但不得扩大 PRD 范围。
4. 技术实现方式以技术方案为准；物理存储方式以数据库设计为准。
5. 开发计划、版本规划和生产级增强方案均属于下游执行文档，不能覆盖上游需求基线。
6. 发现冲突时不得自行选择对开发更方便的版本，应暂停相关设计，回到 PRD 完成澄清和变更记录。

### 13.4 需求变更流程

```text
提出需求变化
→ 关联现有 FR/PRD-BR/AC 或创建新编号
→ 分析对范围、角色、状态、对象、验收和发布门槛的影响
→ 更新 PRD 版本与变更说明
→ 同步状态机、数据字典和项目难点
→ 更新技术方案、版本规划、开发计划、评估体系、生产级增强方案和数据库设计
→ 重新执行受影响的评审与验收检查
```

任何下游文档不得先行把未确认需求写成既定范围。紧急技术验证可以作为实验记录存在，但在 PRD 批准前不能进入正式开发基线或 V1 验收承诺。

## 十五、项目讲解主线

> 这是一个服务投标企业的投标文件智能编制与合规审核多智能体平台。系统从项目编号出发，分级接入采购文件和企业资料，形成要求、评分项、证据、历史参考、报价版本和章节之间的可追溯关系；再通过章节化生成、专项 Agent 预检、人工审核、结构化返工和版本基线完成内部受控交接。Agent 负责重复、标准化和可规则化的工作，人负责项目判断、报价选择、方案确认、风险接受和最终递交决定。
