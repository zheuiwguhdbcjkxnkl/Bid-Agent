# 第 1 层：产品层——这是什么？（对应 11-PRD）

## 一句话定位

> 这是一个服务投标企业的 **投标文件智能编制与合规审核多智能体平台**。

**给 PM 的翻译**：投标企业写标书是个「高重复、高合规风险、强协作」的活。系统不替代人做投标决策，而是把「读招标文件 → 编标书 → 自查合规 → 内部交接」这条链路上**重复、标准化、可规则化**的工作交给 Agent，人只做项目判断、报价选择、方案确认和最终递交决定。

## 解决的九个痛点（PRD 一、1.1）

| # | 痛点 | 一句话 |
|---|------|--------|
| 1 | 数据和工具分散 | 招标文件、企业资料、报价模板、审核流程散在不同系统 |
| 2 | 数据口径不统一 | 商务指标来自不同 Excel，口径对不上 |
| 3 | 同类项目对比重复劳动 | 历史方案、报价系数反复人工维护 |
| 4 | 标书格式不统一 | 不同人用不同模板，章节图表标准不一 |
| 5 | 合规问题暴露偏后 | 写完才发现数据来源不清、承诺无依据 |
| 6 | 提交维护无闭环 | 版本、更正、分发记录不清晰 |
| 7-9 | （完整清单见 PRD） | 对应评审、返工、追溯三个环节 |

**→ 引出第 2 层**：痛点 5「合规问题暴露偏后」是最核心的——所以系统必须把「审核」内嵌到流程里，而不是写完了再查。怎么内嵌？看流程层。

# 第 2 层：流程层——一次投标怎么走完？（对应 11-PRD 四、16-版本）

## 端到端主链路（V1 单项目闭环）

```text
项目编号 → 分级数据接入 → 文件解析 → 要求/评分项提取
→ 响应规划（证据匹配） → 章节编制 → 多 Agent 审核
→ 人工确认/返工 → 内部交接 → 递交记录
```

## 人工关口（这是产品设计的灵魂）

| 关口 | 谁确认 | 确认什么 |
|------|--------|---------|
| REQUIREMENT_BASELINE_CONFIRMATION | 投标团队 | 要求基线（理解对不对） |
| RESPONSE_PLAN_CONFIRMATION | 投标团队 | 响应计划（怎么答） |
| CHAPTER_DRAFT_CONFIRMATION | 编写人 | 章节草稿（答得好不好） |
| REVIEW_RESULT_CONFIRMATION | 审核人 | 审核结论（能不能交） |

**核心设计思想**：Agent 可以生成、可以建议，但**四个阶段级关口必须人工确认**——这就是「人机责任边界」。产品经理最该记住的一句话：**Agent 干活，人拍板。**

# 第 3 层：系统骨架层——项目跑在什么系统上？（对应 17-技术方案 四/五/六/十）

> 🖼️ 配套图：`docs/diagrams/V1总体架构图.html`

**开场先说清定位**：这一层是项目的**技术底座**（前端、后端、存储、部署），属于团队共建部分，不是我负责的核心模块——我快速带过，重点是让 PM 知道：**下一层的 Agent 编排是跑在一个什么样的骨架上的**。

## 3.1 一张图看懂骨架

```text
浏览器 → Caddy(HTTPS/反向代理) → Next.js(页面) + FastAPI(领域服务/API)
                                        ↓ 发布任务
                               Redis(队列/锁) → Celery Worker(解析/Agent/导出)
                                        ↓ MCP Streamable HTTP
                          bid-tools-mcp(四类聚合工具能力·14 方法)
                                        ↓
   PostgreSQL(业务事实源+pgvector) · Redis · MinIO(原始文件/导出物)
```

## 3.2 四个部件一句话

| 部件 | 干什么 | 一句话 |
|------|--------|--------|
| **前端 Next.js** | 页面与交互（工作台/项目总览/文件解析/响应规划/标书编制/审核风险/交接递交等） | 台面归它摆（界面），规矩在 FastAPI（权限/版本/状态） |
| **后端 FastAPI** | 领域服务 + API（权限/版本/状态转换/事务读写） | 业务规则的「执法者」 |
| **异步 Celery + Redis** | 解析、Agent 运行、导出等长任务排队执行 | 重活不阻塞界面 |
| **存储** | PostgreSQL + Redis + MinIO 各管一摊 | 见下面的「存储三分工」 |

**部署**：单机 Linux + Docker Compose——一套 compose 拉起全部服务。公网访问只走 **Caddy 一个入口**：HTTPS 证书自动申请续期，页面请求转 Next.js、`/api/*` 转 FastAPI；PostgreSQL、Redis、MinIO、MCP 工具间全在内网不暴露——**门越少，安全面越小**。

### 3.2.1 存储三分工（PM 最容易问的「数据都存在哪」）

> 常见误区：以为「MinIO 才是存东西的数据库」。**恰恰相反——存东西的主力是 PostgreSQL，MinIO 只存大文件本体。**

| 存储 | 角色 | 存什么 | 公司比喻 |
|------|------|--------|---------|
| **PostgreSQL** | 唯一核心业务数据库 | 用户/权限/项目/文件版本记录/要求/证据/报价/章节/审核/审计 **+ 文本向量（pgvector 扩展）** | 档案室 + 台账（管账的，主力） |
| **Redis** | 临时设施 | 任务队列 / 可重建缓存 / 限流与短期锁——**不存业务事实** | 传菜滑道 + 便利贴 + 红绿灯 |
| **MinIO** | 对象存储仓库 | 原始招标文件 PDF/Word、页面图片、解析中间产物、导出的 DOCX/PDF | 仓库货架（放货的，只存文件本体） |

**三个讲给 PM 的关键点**：

1. **「记录」vs「文件」的分工**：数据库存「记录」（能查询、关联、事务），对象存储存「文件」（按 key 取回整块二进制）。MinIO 里没有行、没有字段、没有关联查询——它只是个大仓库。
2. **pgvector 只是 PostgreSQL 的一个扩展**：文本块表同时保存正文 + 来源 + 版本 + 权限 + 有效期 + 向量——检索时**先业务过滤、再向量相似度排序**，一步完成。选 pgvector 而不是独立向量库（如 Chroma），就是为了避免「版本、权限、删除状态两套数据对不上」。
3. **为什么文件不存 PostgreSQL**：大文件会让备份巨大、查询变慢、迁移困难——所以 PostgreSQL 只存文件的「身份证」（对象键 + SHA-256 + 大小 + 权限），正文在 MinIO。

> **一句话**：PostgreSQL 是「管账的」，MinIO 是「放货的」，Redis 是「临时打杂的」——管账的才是主力。

## 3.3 骨架和 Agent 的关系（讲这一层的目的）

骨架的每一块都在为下一层的 Agent 服务：

```text
FastAPI   → 给前端和 Agent 提供受控的领域服务
Celery    → 排队执行 Agent 的解析/生成/审核任务
MCP Server→ 给 Agent 提供 14 个受控工具（下一层细讲）
PostgreSQL→ 保存 Agent 的结构化产物（业务事实源）
```

> **一句话**：骨架是「房子」，Agent 是「住客」——房子提供水电（接口/队列/工具/存储），住客负责干活。

# 第 4 层：编排层——多智能体怎么协作？（对应 17-技术方案 三、5.2）★主线

> 这一层是系统的「神经系统」。讲清楚三件事：**Agent 之间怎么说话（A2A）、Agent 会什么（Skill）、Agent 用什么工具干活（MCP）**。三件套关系一句话：**A2A 管「谁处理、处理什么、下一步去哪」，Skill 管「每个 Agent 会什么、按什么规矩干活」，MCP 管「Agent 怎么安全地调用系统能力」。**

## 4.0 三件套全景（先给 PM 一张图）

```text
┌─────────────────────────────────────────────────────┐
│             A2A（结构化消息契约）                       │
│    Supervisor ↔ 专业 Agent 只传结构化消息               │
│    谁处理 / 处理什么 / 返回什么 / 下一步去哪             │
├─────────────────────────────────────────────────────┤
│   Agent ① 招标理解  │  Agent ② 响应规划  │  Agent ③ 编制  │  Agent ④ 复核  │
│       每个 Agent 绑一个 Skill（会什么 + 规矩）          │
├─────────────────────────────────────────────────────┤
│                  MCP（工具协议层）                      │
│    document.* / project.* / knowledge.* / business.*  │
│    4 个工具域 × 14 个方法，按 Skill 白名单调用          │
├─────────────────────────────────────────────────────┤
│    PostgreSQL（业务事实） + LangGraph（运行状态）        │
└─────────────────────────────────────────────────────┘
```

| 机制 | 回答的问题 | 生活类比 | 关键约束 |
|------|-----------|---------|---------|
| **A2A** | Agent 之间怎么协作？ | 部门之间的工作交接单 | 只传结构化消息，不传整份文件/自由文本 |
| **Skill** | 每个 Agent 会什么、按什么规矩干活？ | 岗位说明书 + 胸牌领用清单 | 代码内版本化定义（无 SKILL.md），白名单圈定工具 |
| **MCP** | Agent 怎么调用系统能力？ | 公司共用的工具间（14 件工具） | 4 域 14 方法全局共用，白名单外不可调用 |

> **一句话记忆**：A2A 是「谁跟谁交接」、Skill 是「每个岗位会什么、胸牌许领什么」、MCP 是「共用工具间有哪些工具」——三者各管一段，缺一不可。

## 4.1 总体架构：一张主图 + 五个节点

> **一张持久化 LangGraph 主图 + Supervisor 路由节点 + 四个专业 Agent 受控节点。**

```text
开始/恢复 → 加载校验 → Supervisor 路由
→ 招标理解与合规 Agent → [人工关口1: 要求基线]
→ 响应规划与评分 Agent → [人工关口2: 响应计划]
→ 标书编制 Agent       → [人工关口3: 章节草稿]
→ 质量与风险复核 Agent  → [人工关口4: 审核结论]
→ 确定性交接门禁 → READY_FOR_HANDOVER
```

## 4.2 五个 Agent 的角色卡（讲给 PM 听）

| Agent | 一句话定位 | 回答的问题 | 绑定 Skill | 关键边界 |
|-------|-----------|-----------|-----------|---------|
| **Supervisor** | 确定性状态机上的智能协调器 | 下一步谁处理？ | （路由，无独立 Skill） | 只输出调度决策，不干活、不改状态 |
| **招标理解与合规** | 读懂招标文件 | 采购文件要求是什么？ | 招标文件理解 | 不回答「企业是否满足」 |
| **响应规划与评分** | 把要求变成作战计划 | 怎么答、拿哪些证据、覆盖哪些评分项？ | 响应规划与证据匹配 | 无证据不能自动改成纯文字响应 |
| **标书编制** | 生成带引用的章节草稿 | 每章写什么、引用哪个证据？ | 带引用标书编制 | 不能编造事实、不能静默覆盖人工内容 |
| **质量与风险复核** | 对冻结基线做全面体检 | 哪里有问题、风险多高、该谁修？ | 质量与风险复核 | 不能自己审核通过、不能关闭问题 |

## 4.3 A2A：Agent 之间怎么协作？（讲脉络第 1 段）

### 4.3.1 A2A 的形态：不是服务器，是「消息契约」

先破迷思：文档说 V1 **不引入独立 A2A Server、不建设外部协议**——那 A2A 到底是什么？

> A2A = **Supervisor 与 4 个专业 Agent 之间的「结构化消息契约」**（交接单格式），它落地在 LangGraph 主图上：图节点之间流动的消息，按 A2A 契约定义。

**类比**：LangGraph 图是工厂的**传送带**（管「谁流向谁、何时停下等人工」），A2A 是传送带上的**交接单格式**（管「交接时写什么、怎么写」）。传送带负责「流向」，交接单负责「交接内容」——两者各管一段。

### 4.3.2 A2A 与 LangGraph 图的关系（最容易混的一点）

| | LangGraph 图 | A2A 契约 |
|---|---|---|
| 管什么 | 执行骨架：节点顺序、条件分支、人工中断 | 消息格式：Agent 间传什么、怎么标记收发方 |
| 类比 | 传送带 | 交接单格式 |
| 形态 | 代码里的状态图 | 结构化的消息定义 |

> **一句话**：都在一张图里跑，但「图」回答「流向哪」，「A2A」回答「交接时说什么」——A2A 不是另起炉灶的通信网络，而是这张图上的消息纪律。

### 4.3.3 一条真实的 A2A 消息长什么样（具体化）

Supervisor 派活给「招标理解与合规 Agent」时，消息长这样：

```json
{
  "workflow_run_id": "wf-2026-0818-001",
  "sender": "supervisor",
  "receiver": "requirement_agent",
  "stage": "REQUIREMENT_EXTRACTION",
  "message_type": "DISPATCH_AGENT",
  "task": { "type": "extract_requirements", "target_ref": "dv-17" },
  "context_refs": ["input_refs: dv-17, rb-null"],
  "product_refs": [],
  "blocking_reason": null,
  "gate_status": null,
  "next_action": "完成后进入 REQUIREMENT_BASELINE_CONFIRMATION",
  "input_version": "v2"
}
```

**看到特点了吗**：只传 ID 引用（`dv-17`）、结构化字段、下一步动作——**没有一句自由文本**。干完活回传也一样是结构化产物引用，不是一段「我干完了，结果还行」的自然语言。

### 4.3.4 为什么必须结构化？——自由对话的三个坏处

| 如果 Agent 之间自由对话 | A2A 结构化契约 |
|---|---|
| 「帮我看看这个文件」——谁发的、哪个版本，说不清 | 每条消息绑定 workflow_run_id + 收发方 + 阶段 + 输入版本 |
| 模型说了什么，审计时查不到 | **每条消息可追溯**——合规审核平台的生命线 |
| 想扩一个 Agent 乱接话 | 只传四样：结构化任务 / 业务对象引用 / 上下文引用 / 产物引用 + 阻断原因 / 人工关口状态 / 下一步动作 |

**绝不传**：整份采购文件、完整企业资料、无法追溯的自由文本记忆——正文永远按引用去 PostgreSQL 读。

### 4.3.5 A2A vs MCP（讲给 PM 最容易混的点）

| | A2A | MCP |
|---|---|---|
| 管什么 | Agent 之间「谁处理、处理什么、返回什么、下一步去哪」 | Agent 调用文档/项目/知识/业务规则工具 |
| 谁跟谁 | Supervisor ↔ 专业 Agent（智能体之间） | Agent → 工具服务（智能体到系统能力） |
| 类比 | 部门间的交接单 | 共用工具间 |
| 承载状态吗 | 不承载业务会话状态 | 不承载业务会话状态 |
| 替代关系 | ❌ 不替代 MCP | ❌ 不承担 Agent 编排 |

> **一句话区分**：A2A 是 Agent 之间的「交接单」，MCP 是 Agent 与系统能力的「工具间」——A2A 管交接，MCP 管干活。

## 4.4 Skill：每个 Agent 会什么？（讲脉络第 2 段）

> ⚠️ 先破一个迷思：**本项目没有 SKILL.md 文件**。Skill 不是「给 AI 看的 markdown 手册」，而是代码里定义、随部署走的版本化能力包。

### 4.4.1 为什么不写成 SKILL.md？

| | 教学 demo 的 SKILL.md（如 DeepA2A） | 本项目的 Skill |
|---|---|---|
| 形态 | markdown 文件，AI 开发工具现场读 | 代码/配置里的结构化定义（SkillManifest） |
| 给谁用 | 开发时注入给 AI 助手的提示词 | 运行时 Agent 结构化加载 |
| 存哪 | 项目目录 `skills/xxx/SKILL.md` | 应用代码，随 Docker 部署走 |
| 数据库 | 无 | 不建表；`agent_run` 记录本次用了哪个 `skill_id + skill_version` |

**为什么不一样**：SKILL.md 是「给 AI 开发工具现场读的手册」；本项目是生产系统（PostgreSQL 审计 + 版本冻结），Skill 的 Prompt、Schema、白名单必须**跟代码一起版本化、随部署走**，并且能追溯「哪次运行用了哪个版本」。

**三个理由递进（讲给 PM / 面试官的完整论证）**：

**理由 1：形态不同——文档 vs 结构化定义**
SKILL.md 是 markdown 文档，本质是「提示词」；SkillManifest 是代码/配置里的结构化定义（Schema + 规则 + 白名单），要过 Schema 校验、随部署走、可版本化。**一个是给人/开发工具读的说明，一个是给运行时加载的配置**。

**理由 2：1:1 绑定——根本不需要「渐进式披露」**
传统 SKILL.md 模式之所以要「渐进式加载」（主 prompt 只放技能目录、用到哪个读哪个全文），是因为一个 Agent 可能访问**多个**技能，不渐进加载上下文会爆炸。本项目每个专业 Agent **固定绑定 1 个 Skill**（3.2 角色卡可见），一次 `agent_run` 只加载这 1 个紧凑定义——**没有「目录 + 按需取用」的必要，渐进式披露机制自然用不上**。

| | SKILL.md 模式 | 本项目模式 |
|---|---|---|
| Agent 与 Skill 关系 | 一个 Agent 可访问多个技能 | 每个 Agent 固定绑定 1 个 Skill |
| 加载方式 | 渐进式披露（目录 → 按需读全文） | 固定加载 1 个紧凑定义 |
| 为什么可行 | 上下文必须渐进，否则爆炸 | 1:1 绑定，定义紧凑，无需渐进 |

**理由 3：版本管理与更新——「麻烦一点」换来审计、回滚、权限边界**
传统 SKILL.md 改起来快（改文档即可），但**说不清哪个版本生效、改错了没法回滚、白名单靠模型自觉**。本项目 Skill 走「改定义 → bump 版本号 → 过 Schema 校验 → 部署」四步流程，`skill_id + skill_version` 在 `agent_run` 内固定——**正在跑的老任务用旧版本，新任务用新版本，绝不静默切换**。多两道工序，换来：

- **审计**：`agent_run` 记录每次运行用了哪个 skill 版本——「哪次运行用了什么规则」可查
- **回滚**：部署旧版本即可回退，不需要手动还原文档
- **权限边界**：allowed_tools 白名单 + MCP Server 二次校验，改完即生效的硬边界

> **比喻**：改 SKILL.md 像「改黑板上的注意事项」——快，但谁改的、哪个版本生效说不清；本项目 Skill 像「修改公司章程修订案」——多走一道版本流程，但每次修改有记录、可追溯、可回滚。对合规审核平台来说，这个「麻烦」是设计选择，不是缺陷。

### 4.4.2 Skill 是什么

> Skill = **版本化业务能力包**：业务目标 + Prompt + 输入输出 Schema + 业务规则 + 引用/拒答要求 + **允许调用的 MCP 工具白名单**。

**类比**：每个 Agent 的「岗位说明书 + 操作手册 + 合规红线」。其中**白名单就是「胸牌上印的领用清单」**——允许从共用工具箱里拿哪几件工具（详见 4.5.4）。

### 4.4.3 SkillManifest（一个 Skill 的完整清单）

```text
skill_id / skill_version / display_name / purpose
input_schema / output_schema
allowed_tools          ← 工具白名单（领用清单）
model_policy           ← 模型策略
citation_policy        ← 引用要求
refusal_policy         ← 拒答要求
timeout_seconds / max_retries
```

**关键约束**：`skill_id + skill_version` 在一次 `agent_run` 内**固定**，运行中不得静默切换版本——Skill 也是版本化的，跟业务基线一样。

### 4.4.4 Skill 的关键设计

- **Skill 不是独立进程/容器/微服务**——它是「能力包」，由 Agent 运行时加载
- 专业 Agent **不能因为模型输出而临时扩大工具范围**——白名单由 SkillManifest 声明、MCP Server 二次校验（双保险）
- 六个 Skill 域合并成 **4 个聚合能力域**（避免 6 个 Skill + 7 个工具服务的重复边界）

## 4.5 MCP：Agent 怎么调用系统能力？（讲脉络第 3 段）

### 4.5.1 架构：一个 MCP Server（bid-tools-mcp）

```text
FastAPI / Celery Worker / Agent Runtime
→ MCP Client
→ http://mcp-tools:8000/mcp
→ document.* / project.* / knowledge.* / business.*
```

- 用内部 **Streamable HTTP** 连接（不是 stdio 子进程，也不是普通 Python 函数调用）——**是真实 MCP 协议**
- `mcp-tools` 只加入 Docker 内部网络，**不通过宿主机端口/网关/浏览器直接访问**

### 4.5.2 四域十四方法（全局共用的工具箱）

> 这 14 个方法就是系统的**共用工具箱**——不归任何单个 Agent 所有，谁的白名单允许谁就能调。

| 工具域 | 方法 | 干什么 |
|--------|------|--------|
| `document.*` | ingest / read / render / export | 解析、读取、渲染、导出文档 |
| `project.*` | get_context / validate_inputs / validate_transition | 读项目上下文、校验输入、校验状态转换 |
| `knowledge.*` | search / read_sources / validate_citations | 统一检索、读来源、校验引用 |
| `business.*` | validate_structure / validate_quote / check_consistency / evaluate_gate | 结构校验、报价校验、一致性检查、关口判定 |

**方法粒度原则**：以「职责清晰、权限和失败策略可独立配置」为准——**不拆成 20+ 细工具，也不压缩成带大量 operation 参数的万能方法**。

### 4.5.3 每次调用的审计上下文（MCP _meta）

```text
request_id / trace_id / user_id / project_id
/ workflow_run_id / agent_run_id / skill_id / skill_version
```

→ 每次工具调用都能回答：**谁、在哪个项目、哪个工作流、哪个 Agent、用哪个 Skill、调了什么工具**——全链路可审计。

### 4.5.4 白名单：共用工具箱的「领用清单」（三件套咬合的关键）

**机制三步**：

```text
① 14 个工具全局共用（工具箱，人人可进）
② 每个 Skill 的 allowed_tools 圈出「我能碰哪几个」（胸牌领用清单）
③ MCP Server 收到调用时再核对一遍（保安复查）
→ 模型输出再离谱，也碰不到白名单外的工具（双保险）
```

| Skill / 调用方 | 允许调用的主要方法 |
|---|---|
| 招标文件理解 | document.ingest/read、project.get_context/validate_inputs、knowledge.search/read_sources、business.validate_structure |
| 响应规划与证据匹配 | project.*、全部 knowledge.*、business.validate_structure/validate_quote |
| 带引用标书编制 | document.read/render、project.*、全部 knowledge.*、business.* |
| 质量与风险复核 | document.read/render、全部 project.*、knowledge.read_sources/validate_citations、全部 business.* |
| Supervisor | 全部 project.*、business.evaluate_gate |
| 确定性交接任务 | project.get_context/validate_inputs、business.evaluate_gate、document.export |

**看两个「共用」和一个「独占」的真实例子**：

- `knowledge.search`（检索）——**3 个 Skill 共用**：招标文件理解、响应规划、标书编制
- `business.validate_structure`（结构校验）——**4 个专业 Skill 全用**
- `document.export`（导出交接包）——**仅「确定性交接任务」1 个能碰**，标书编制 Agent 想导也导不了

**→ 白名单的意义**：权限最小化，从工具层就封死越权——这是合规审核平台的底线设计。

## 4.6 三件套咬合：一次 Agent 任务怎么流转？（脉络总结）

```text
Supervisor 收到路由需求
  → A2A：派发结构化任务给「招标理解与合规 Agent」
  → Agent 加载固定版本的 Skill（招标文件理解 SkillManifest）
  → 按 Skill 白名单调 MCP（document.ingest 解析 + knowledge.search 检索）
  → MCP 校验：服务凭证 → Skill 白名单 → 项目权限 → 版本有效
  → 工具执行 + 审计记录（request_id/trace_id/skill_version...）
  → Agent 校验输出 Schema → 领域服务校验业务规则
  → 结构化产物写入 PostgreSQL（RequirementSet 等）
  → A2A 回传：产物引用 + 下一步动作（等人工确认）
  → [人工关口1: REQUIREMENT_BASELINE_CONFIRMATION]
```

**给 PM 的翻译**：Supervisor 派单（A2A）→ 员工按岗位手册干活（Skill）→ 通过统一服务台调资源（MCP）→ 干完交回执并等领导签字（人工关口）→ 签完字才进入下一环节。

## 4.7 给 PM 的三个关键设计（面试/讲解加分点）

**① Agent 不是越多越好，是「按需拆分」**
- 响应规划 + 评分合并成一个 Agent（避免矩阵和评分计划两套状态打架）
- 质量复核是一个 Agent 内的多阶段审核（不拆成多个审核 Agent）
- 稳定步骤（解析、OCR、表格抽取）**不做成 Agent**，只做工具/工作流节点

**② 结构化决策，不是自由对话**
Supervisor 只输出七种结构化决策：
```text
DISPATCH_AGENT / WAITING_HUMAN / RETRY_TASK / EXPAND_REVIEW_SCOPE
/ INVALIDATE_OUTPUTS / BLOCK_WORKFLOW / COMPLETE_STAGE
```
→ 可测试、可审计、可解释（对 PM 和合规都友好）

**③ 节点契约统一，五类节点各司其职**
| 节点类型 | 职责 | 允许写入 |
|---------|------|---------|
| 加载校验 | 校验权限/版本/哈希 | 运行控制状态 |
| Supervisor 路由 | 输出下一步决策 | 临时路由结果 |
| 专业 Agent | 执行业务任务 | PostgreSQL 业务产物 |
| 人工关口 | interrupt 暂停 | pending_gate |
| 确定性门禁 | 校验阶段完成条件 | 合法状态转换 |

**→ 引出第 5 层**：Agent 在流程中运行，但「运行到哪了、之前确认了什么、版本变没变」——系统记住了什么、模型又看到了什么？这就是记忆层与上下文管理。

# 第 5 层：记忆层与上下文管理——系统记住什么、模型看到什么？（对应 17-技术方案 3.1.6）★主线

## 5.0 先分清两个问题（这一层的钥匙）

很多讲解把「记忆」和「上下文」混在一起讲，越讲越晕。这里先一刀切开：

| | 记忆（存储侧） | 上下文（喂给模型侧） |
|---|---|---|
| 回答的问题 | **系统记住什么** | **模型这次看到什么** |
| 存在多久 | 长期保存（业务事实）/ 运行期间（运行状态） | 一次性，用完丢弃 |
| 谁在管理 | PostgreSQL + LangGraph Checkpoint | Context Manager 动态组装 |
| 类比 | **仓库**（档案柜 + 值班日志） | **工作台台面**（每次干活前摆上，干完收走） |

> **一句话**：记忆是仓库，上下文是每次从仓库取货、摆到工作台上的台面。**Envelope 不是记忆，是从记忆组装出来的临时视图。**

## 5.1 两类真记忆（存储侧：仓库里有什么）

| 记忆类型 | 存在哪里 | 装什么 | 类比 | 关键性质 |
|---------|---------|--------|------|---------|
| **长期业务记忆** | PostgreSQL + MinIO | 要求基线、响应计划、章节版本、审核结论、企业证据、历史参考、审计记录 | **档案柜** | 版本化、可授权、可引用、可失效，是唯一业务事实源 |
| **短期运行记忆** | LangGraph Checkpoint + workflow_run / agent_run / task_run | 当前阶段、已完成节点、待处理关口、失败原因、重试信息 | **值班日志** | 用于恢复执行；**不是业务事实源**，Checkpoint 只存 ID 引用 |

**关键区分**：短期记忆回答「这次运行跑到哪了、能不能恢复」，长期记忆回答「业务上确认过什么、有效版本是什么」。两个仓库各管各的，**恢复运行靠值班日志，业务判断靠档案柜**。

## 5.2 上下文管理：Context Envelope（喂给模型侧：台面怎么摆）

**机制**：每次 Agent 运行前，Context Manager 根据以下信息组装 Envelope：

```text
workflow_run.input_refs（本次运行的输入版本引用）
+ input_hash（输入一致性校验）
+ 当前人工关口 / 用户权限 / 项目职责 / 有效业务版本
```

**Envelope 只装三样**：当前任务必需的**摘要**、**结构化对象**、**来源引用**。

**绝不预装**：整份采购文件、完整企业资料、历史对话全量——Agent 需要正文时，通过 `document.read` / `knowledge.read_sources` **按引用读取**，读完即弃。

> **类比**：员工上工前，从档案柜里**只取当前任务需要的几份摘要和借阅单**摆在桌上；要读哪页正文，凭借阅单去取，读完放回，不把整个档案柜搬上桌。

## 5.3 上下文防爆炸：三层压缩（PM 常问「上下文不会爆吗」——用这节接住）

| 层 | 机制 | 装什么 / 不装什么 |
|---|---|---|
| 第 1 层 | **Skill 紧凑定义** | 每次运行只固定加载 **1 个** Skill 的结构化定义（目标+Prompt+Schema+白名单）；Skill 不是大段 md 文本，体积可控 |
| 第 2 层 | **Context Envelope** | 只装当前任务必需的摘要+引用，不是全部资料 |
| 第 4 层 | **正文按引用读取** | 招标文件正文、证据全文**绝不预装**；需要哪页，通过 MCP 工具读哪页，读完即弃 |

```text
一次 Agent 运行的上下文 =
  1 个 Skill 定义（固定、紧凑）
+ Context Envelope（摘要 + 引用清单）
+ 按需临时读取的正文片段（用完丢弃，不进记忆）
```

**类比**：胸牌印一行岗位+规矩（Skill），进考场只带当前题目的纸条（Envelope），书留图书馆按借书单取用（按引用读取）——**不是把整本操作手册背进考场**。

**诚实说明**：以上是**已确认的机制**；具体的 token 预算数字（Envelope 上限、Prompt 上限）待实测后写入文档，不预先承诺。

## 5.4 记忆 ↔ 上下文的关系图（一张图收口）

```text
        长期业务记忆（档案柜：基线/章节/证据/审核）
                │ ① Context Manager 按需抽取（摘要+引用）
                ▼
        Context Envelope（工作台台面：一次性视图）
                │ ② 喂给模型
                ▼
        Agent 运行（模型上下文 = Skill + Envelope + 按需正文）
                │ ③ 产出结构化产物（Skill Schema）
                ▼
    领域服务校验（权限/版本/规则/人工关口）
                │
   ┌────────────┴────────────┐
   ▼                         ▼
写回长期记忆（新业务版本）   短期记忆更新（Checkpoint 阶段推进）
```

**读图口诀**：**抽取 → 组装 → 喂入 → 产出 → 校验 → 写回**。Envelope 用完即弃，绝不回写——模型说过的自由文本永远成不了记忆，只有通过领域服务校验的结构化产物才能进档案柜。

## 5.5 三条设计铁律（讲出来就是专业度）

**铁律 1：Checkpoint 不存业务正文，只存 ID 引用**
```text
WorkflowState 七个字段：
workflow_run_id / project_id / current_stage
/ pending_gate / active_agent_run_id / retry_count / last_error_code
```
→ 业务正文永远在 PostgreSQL 查，恢复时重新读真实版本 + 校验 input_hash

**铁律 2：Agent 不能直接写长期记忆**
```text
Agent 输出结构化产物（Skill Schema）
→ 领域服务校验权限/版本/规则/人工关口
→ 才允许形成新业务版本
```
→ 模型自由文本永远不能直接变成业务事实（防幻觉的根基）

**铁律 3：长期记忆必须版本化、可授权、可引用、可失效**
- 要求基线更新 → 旧基线标 STALE，新基线创建，**不覆盖历史**
- 证据失效 → 定位相关矩阵项和章节，增量失效
- 报价版本变化 → 只更新金额相关块，触发商务复核

**→ 引出第 6 层**：记忆保证「状态正确、上下文干净」，但怎么证明「输出正确」？这就是评估层。

# 第 6 层：评估层——怎么证明做好了？（对应 15-评估体系）★主线

## 6.1 四层评估金字塔（讲评估的核心框架）

```text
        ┌─────────────┐
        │ L4 试点业务价值 │  ← 真实项目旁路对比，业务价值验证
        ├─────────────┤
        │ L3 单项目端到端 │  ← 输入→交接完整闭环，交付验收
        ├─────────────┤
        │ L2 业务链路     │  ← 多模块协作，V1 技术完成
        ├─────────────┤
        │ L1 单模块       │  ← 每个模块独立准入
        └─────────────┘
```

| 层级 | 核心问题 | 结论用途 |
|------|---------|---------|
| L1 | 模块是否达到链路最低要求 | 模块发布与链路测试准入 |
| L2 | 链路是否完成真实业务任务 | V1 技术完成 |
| L3 | 是否形成正确/安全/可追溯闭环 | 交付验收与试点就绪 |
| L4 | 是否产生可验证的真实业务价值 | 扩大使用决策 |

**发布关系**：L1+L2 通过 → 技术完成；L3 通过 → 交付验收；L4 通过 → 扩大使用。**上一级不过，不进下一级**（分层准入）。

## 6.2 八条通用原则（讲 3 条最出彩的）

1. **零容忍优先**：严重错误不能被高分掩盖（不是平均分游戏）
2. **隐藏验收**：正式验收集不得用于调优（防数据泄漏）
3. **禁止综合分掩盖风险**：L3/L4 不用一个总分替代分域判断

## 6.3 Agent 链路如何被评估（跟主线呼应）

| 评估对象 | 代表指标（PRD/15 号） | 对应 Agent |
|---------|---------------------|-----------|
| 要求映射 | 实质性条款识别 P/R/F1 | 招标理解与合规 |
| 评分覆盖 | 关键评分项覆盖率 | 响应规划与评分 |
| 证据引用 | 引用正确率、无证据拒答正确率 | 响应规划 + 标书编制 |
| 章节质量 | 无来源事实数、承诺来源率 | 标书编制 |
| 审核质量 | 阻断/高风险召回率、误报率、返工轮次 | 质量与风险复核 |
| 编排质量 | 任务成功率、重试率、人工接管率 | Supervisor + 全链路 |

**→ 引出第 7 层**：评估证明「系统内部是对的」，但前端怎么操作、怎么看到这些状态？这就是接口层。

## 7.2 跟主线呼应的三个 API 特征

# 第 8 层：数据层——业务事实存在哪？（对应 18-数据库）

## 8.1 八大表域（跟流程一一对应）

| 表域 | 核心表 | 对应流程 |
|------|--------|---------|
| IAM | user / user_session / organization | 登录与权限 |
| 项目 | bid_project / bid_package / project_member / project_party | 项目创建 |
| 文件和解析 | procurement_document / document_version / document_parse / document_segment / document_correction | 文件解析 |
| 业务要求和知识 | requirement_item / scoring_item / evidence_item / reference_project | 要求理解 |
| 响应规划和编制 | response_matrix_entry / response_section / content_block / quotation_version | 响应规划+编制 |
| 审核和风险 | review_task / review_issue / risk_item | 质量复核 |
| 工作流基线和交接 | workflow_run / agent_run / gate_action / project_baseline / handover_package / submission_record | 编排+交接 |
| 审计 | audit_event | 全程追溯 |

## 8.2 三个保证「版本不打架」的关键设计

1. **workflow_run 的 input_refs + input_hash**：一次运行绑定确定输入版本，恢复前重新校验哈希，不一致就停止恢复
2. **版本失效机制**：旧基线 STALE、新基线创建，从不覆盖历史（要求/响应/章节/审核/交接五类基线）
3. **agent_run 幂等**：按输入版本+阶段+幂等键限制重复有效产物——Agent 重试不会产生两份标书

# 收尾：洋葱芯——三条主线如何贯穿

```text
        Agent 编排链路（17号：一张主图 + 5节点 + 4人工关口）
                 ↓ 运行状态交给
        记忆系统（3.1.6：短期Checkpoint + 长期PostgreSQL + Envelope上下文）
                 ↓ 输出质量交给
        评估体系（15号：L1→L2→L3→L4 四层金字塔 + 零容忍）
                 ↓ 操作与存储落地
        API（14号：按流程组织） + 数据库（18号：8表域 + 版本失效）
```

**给 PM 的三句话总结**：
1. **编排**：Agent 干活，人拍板——四个阶段关口，机器永远不能自己通过
2. **记忆**：机器记住的是「业务事实 + 版本」，不是「聊天记录」——防幻觉、可追溯
3. **评估**：四层金字塔证明「每个模块对、链路通、项目闭环、业务有价值」，零容忍优先
