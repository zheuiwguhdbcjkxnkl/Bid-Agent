## 零、文档职责与决策规则

### 0.1 文档职责

本文档负责记录投标文件智能编制与合规审核平台 V1 的技术方案，包括：

- 总体架构、模块边界和运行方式；
- Agent、Skill、工具和共享状态设计；
- 前端、后端、任务、数据、文件、检索、模型和解析技术栈；
- 每项技术的实现方式、选择原因、替代方案和未采用原因；
- V1 实现边界、失败降级、人工兜底和后续替换接口；
- 部署、安全、可观测性、测试和评估映射。

本文档不修改 PRD 已确认的业务范围、角色权限和人工决策权。若技术限制需要调整产品范围，必须先修改 PRD 和项目决策记录。

### 0.2 决策状态

| 状态 | 含义 | 使用规则 |
|---|---|---|
| 已确认 | 用户已明确确认 | 可以作为后续接口、数据库和实施计划的正式输入 |
| 推荐待确认 | 当前推荐方案，但尚未单独确认 | 不得作为不可变实现承诺 |
| 待实测 | 需要用真实招标文件、成本或性能数据裁决 | 必须记录测试样本、指标和结果后再冻结 |
| 后续版本 | 不进入 V1 | 只保留扩展接口，不提前实现 |

### 0.3 总体原则

1. 状态机负责“是否允许”，Agent 负责“如何理解和建议”，人工负责“关键结论是否接受”。
2. PostgreSQL 是业务事实源，Redis、LangGraph Checkpoint、向量索引和缓存均不得成为第二套业务真相。
3. Agent 只通过结构化对象协作，不把聊天记录当作正式业务状态。
4. 原文、版本、来源、权限、确认、审核和失效关系必须可追溯。
5. 无证据、低置信度、版本冲突或规则无法判断时，宁可暂停转人工，不生成确定性结论。
6. 前端先行不等于页面字段驱动数据库；领域对象和 API 契约必须同步设计。

## 一、建设目标与范围

### 1.1 建设标准（已确认）

> **单组织、多角色、支持多个独立项目的可部署旁路试用版。核心流程真实、可恢复、可审计，可供小团队受控试用，但不建设完整企业 SaaS。**

V1 必须实现：

- 真实登录和后端角色权限；
- 项目、文件、要求、证据、报价、章节和审核版本；
- 文件解析、Agent 长任务的异步执行、重试和恢复；
- 人工确认、风险豁免、基线冻结和审计记录；
- 页面刷新或 Worker 重启后的任务状态恢复；
- 单台 Linux 服务器上的容器化部署。

V1 不实现：

- 企业注册、组织管理后台和多租户计费；
- 复杂实时多人协同编辑；
- Kubernetes、微服务集群和自动扩缩容；
- 数据库高可用、跨地域容灾和生产 SLA；
- 外部电子交易平台自动递交、CA 签章和法定回执。

### 1.2 开发顺序（已确认）

采用“前端先行 + 契约驱动 + 纵向切片”：

```text
领域对象与状态
→ OpenAPI / JSON Schema
→ TypeScript 类型
→ Mock API
→ Next.js 页面
→ FastAPI 按纵向切片替换 Mock
```

纵向切片顺序：

1. 项目创建与文件接入；
2. 文档解析与要求确认；
3. 响应矩阵与企业证据；
4. 章节编制；
5. 审核与风险闭环；
6. 交接基线与文档导出。

## 二、总体架构

### 2.1 架构风格（已确认）

> **模块化单体 + 异步任务执行 + LangGraph 状态编排。**

```text
浏览器
  ↓ HTTPS
反向代理
  ├── Next.js 前端
  └── FastAPI 后端
          ├── 领域服务与权限
          ├── LangGraph 工作流
          ├── Celery 任务发布
          ├── PostgreSQL + pgvector
          ├── Redis
          └── MinIO

Celery Worker
  ├── 文件解析与 OCR
  ├── Embedding 与重排
  ├── Agent 工作流
  └── DOCX/PDF 导出
```

### 2.2 为什么采用模块化单体

**实现方式**：前端和后端分别部署，后端内部按领域模块拆分；Agent、Skill、工具、API、Worker 和数据访问层共享代码仓库、领域模型和数据库，不拆独立微服务。

**选择原因**：

- V1 由个人主导开发，微服务会增加接口治理、部署、日志追踪和数据一致性成本；
- 项目最难的是版本、证据、人工关口和 Agent 可靠性，不是服务拆分；
- 模块化边界仍可独立测试，并为后续拆出解析或检索服务保留接口。

**替代方案**：

- 全部单进程：部署更轻，但 OCR 和 Agent 长任务会阻塞 API；
- 微服务：独立扩缩容更强，但 V1 运维成本和分布式一致性风险过高。

**后续拆分条件**：解析任务需要独立 GPU 资源、检索规模显著增长、团队形成独立发布边界，或单机资源成为经过监控证明的瓶颈。

## 三、Agent、Skill 与工具架构

### 3.1 数量基线（已确认）

```text
逻辑 Agent：5 个
业务 Skill：4 个
MCP 工具域：4 个
MCP Server：1 个
```

#### 5 个逻辑 Agent

1. Supervisor Agent；
2. 招标理解与合规 Agent；
3. 响应规划与评分 Agent；
4. 标书编制 Agent；
5. 质量与风险复核 Agent。

#### 4 个业务 Skill

1. 招标文件理解；
2. 响应规划与证据匹配；
3. 带引用标书编制；
4. 质量与风险复核。

#### 4 个 MCP 工具域

1. `document.*`：解析、OCR、复杂图表理解、Document IR 读取、预览和导出；
2. `project.*`：项目上下文、版本、状态、人工关口、失效、审计、基线和交接；
3. `knowledge.*`：招标文件、企业证据和历史参考的混合检索、来源读取和引用校验；
4. `business.*`：业务规则、报价读取与校验、一致性检查和确定性门禁。

以上 4 个工具域由一个 `bid-tools-mcp` 服务统一暴露，不部署 4 个独立 MCP Server。具体操作仍按方法拆分，并拥有独立的 Pydantic 输入输出模型、权限规则、超时、错误码和审计记录。原 6 Skill、7 工具方案由本方案替代，业务能力和质量门槛不减少。

### 3.1.1 Skill 与 MCP 实现原则（已确认）

- Skill 是版本化业务能力包，包含业务目标、Prompt、输入输出 Schema、规则、引用和拒答要求、允许调用的 MCP 工具白名单；
- Skill 不作为独立进程、容器或微服务运行；
- Agent 通过 MCP Client 调用 `bid-tools-mcp`，不得直接动态发现和调用白名单外工具；
- `bid-tools-mcp` 是工具协议层和能力适配层，不成为第二套业务后端；
- 高风险状态变更仍调用确定性领域服务，并由 PostgreSQL 事务、权限和状态机校验；
- Pydantic 基础结构校验在 Agent 进程内完成，业务规则和门禁通过 `business.*` 执行；
- 每次 MCP 调用记录工具名、版本、输入摘要、输出引用、耗时、状态和标准化错误；
- V1 不建设 Skill 市场、动态安装、MCP 服务发现、多个 MCP Server 编排和第三方任意工具接入。

**选择原因**：真实使用 Skill 与 MCP 能体现可复用能力、工具协议和 Agent 工具白名单，同时使用 4 个聚合能力域和 1 个 MCP Server，可避免 6 个 Skill、7 个工具服务带来的重复边界和部署负担。

### 3.1.2 MCP 通信与访问控制（已确认）

V1 使用内部 `Streamable HTTP` 连接 `bid-tools-mcp`，不使用每个 Worker 独立启动 MCP 子进程的 `stdio` 方式，也不以普通 Python 函数调用代替 MCP 协议。

**调用路径**：

```text
FastAPI / Celery Worker / Agent Runtime
→ MCP Client
→ http://mcp-tools:8000/mcp
→ document.* / project.* / knowledge.* / business.*
```

**实现约束**：

- `mcp-tools` 只加入 Docker 内部应用网络，不通过宿主机端口、网关或浏览器直接访问；
- V1 不建设完整 OAuth 授权服务器，调用方使用部署时配置的内部服务凭证访问 MCP Server，凭证不得写入代码仓库；
- 每次调用在 MCP `_meta` 中携带 `request_id`、`trace_id`、`user_id`、`project_id`、`workflow_run_id`、`agent_run_id`、`skill_id` 和 `skill_version`；
- 工具业务参数只放在工具输入 Schema 中，不把用户身份、追踪字段重复混入每个工具的业务参数；
- `bid-tools-mcp` 先校验内部服务凭证，再校验 Skill 工具白名单、项目访问权限、对象所属项目和输入版本有效性；
- 状态修改、基线冻结、人工关口推进和交接等高风险操作仍由 FastAPI 领域服务执行，MCP Server 不直接绕过领域服务写业务主状态；
- MCP 连接不承载业务会话状态，业务事实、运行状态和幂等记录仍保存在 PostgreSQL；
- 网络超时和临时不可用由调用方按工具配置有限重试，权限、白名单、版本冲突和业务门禁错误不得自动重试；
- V1 只暴露内部健康检查和 MCP 端点，不建设外部第三方 Client 接入能力。

**选择原因**：内部 Streamable HTTP 可以由多个 FastAPI/Celery Worker 共享同一个 MCP Server，符合单机 Docker Compose 和一个 MCP Server 的部署方案。通过内网隔离、服务凭证和业务权限复核，可在不引入完整 OAuth 基础设施的情况下满足 V1 的真实 MCP 调用、权限控制和审计要求。

### 3.1.3 Skill 与 MCP 最小调用契约（已确认）

V1 统一使用五个逻辑契约对象：`SkillManifest`、`McpCallContext`、`McpToolRequest`、`McpToolResponse` 和 `McpError`。它们是应用层统一模型，不额外建设通用插件平台。

#### `SkillManifest`

Skill 清单至少包含：

```text
skill_id
skill_version
display_name
purpose
input_schema
output_schema
allowed_tools
model_policy
citation_policy
refusal_policy
timeout_seconds
max_retries
```

Skill 的正式定义是 Prompt、输入输出 Schema、业务规则、引用要求、拒答要求、工具白名单和失败策略的组合。`skill_id + skill_version` 在一次 `agent_run` 内固定，运行中不得静默切换版本。

#### `McpCallContext`

每次调用通过 MCP `_meta` 携带：

```text
request_id
trace_id
user_id
project_id
workflow_run_id
agent_run_id
skill_id
skill_version
```

身份、运行和追踪上下文不重复进入每个工具的业务参数。没有工作流或 Agent 运行上下文的后台任务允许对应字段为空，但 `request_id`、`trace_id`、调用主体和项目上下文必须可审计。

#### `McpToolRequest`

逻辑请求包含：

```text
tool_name
tool_version
arguments
idempotency_key
input_refs
```

`tool_name` 对应 MCP 方法名，例如 `knowledge.search_tender`；`arguments` 由该方法独立的 Pydantic Schema 定义；`input_refs` 只保存文件版本、基线、报价版本等稳定引用，不传递整份项目状态。读操作可使用确定性请求哈希作为幂等键，写操作必须由调用方提供业务幂等键。

#### `McpToolResponse`

统一响应包含：

```text
status
data
output_refs
warnings
audit_ref
```

`status` 只使用 `SUCCEEDED`、`PARTIAL` 和 `REJECTED`。小型结构化结果可以直接放入 `data`；大文本、文件、解析结果和批量记录写入 PostgreSQL 或 MinIO 后通过 `output_refs` 返回。`PARTIAL` 必须带警告和缺失范围，调用方不得静默视为完整成功。

#### `McpError`

标准错误码为：

```text
TRANSIENT_ERROR
VALIDATION_ERROR
PERMISSION_DENIED
VERSION_CONFLICT
BUSINESS_BLOCKED
DUPLICATE_REQUEST
NOT_FOUND
INTERNAL_ERROR
```

错误同时返回 `message`、`retryable`、`details` 和 `audit_ref`。`TRANSIENT_ERROR` 按 Skill 或工具配置最多重试 2 次；`INTERNAL_ERROR` 最多重试 1 次；校验、权限、版本冲突、业务阻断、重复请求和资源不存在不得自动重试。`DUPLICATE_REQUEST` 优先返回首次成功结果引用，而不是重复执行。

#### 标准调用流程

```text
Agent 加载并固定 SkillManifest
→ 校验工具白名单
→ 组装 McpCallContext 和请求
→ MCP 校验凭证、权限、版本和幂等
→ 执行工具并记录审计
→ 返回小结果或业务结果引用
→ Agent 校验 Skill 输出 Schema
→ 领域服务写入最终业务产物
```

V1 不建设动态工具发现、万能 `execute` 方法、运行时新增工具、MCP Session 业务状态、复杂事件总线和独立 MCP Outbox。

### 3.1.4 MCP 方法清单与 Skill 白名单（已确认）

V1 冻结为 4 个工具域、14 个 MCP 方法。方法粒度以“职责清晰、权限和失败策略可独立配置”为准，不继续拆成 20 个以上细工具，也不压缩成带大量 `operation` 参数的万能方法。

#### `document.*`

```text
document.ingest
document.read
document.render
document.export
```

- `document.ingest`：执行原生解析、OCR、版面识别和 Document IR 写入，并按复杂度规则将复杂图表转入多模态分析；
- `document.read`：按文件版本、页码、片段和来源位置读取 Document IR；
- `document.render`：根据章节内容块和模板生成预览；
- `document.export`：生成 DOCX、PDF 和交接文件，并返回对象存储引用。

复杂图表不单独暴露 MCP 方法，由 `document.ingest` 内部确定性识别后调用多模态适配器。`document.export` 默认只允许确定性交接任务调用，不开放给专业 Skill 自主触发。

#### `project.*`

```text
project.get_context
project.validate_inputs
project.validate_transition
```

- `project.get_context`：读取当前项目、有效版本、基线、工作流和人工关口摘要；
- `project.validate_inputs`：检查文件、要求、证据、报价、章节和审核输入是否仍有效；
- `project.validate_transition`：判断状态转换和前置条件是否合法，但不直接绕过领域服务修改业务主状态。

审计由 MCP 中间件统一记录，不新增 `project.write_audit` 方法。

#### `knowledge.*`

```text
knowledge.search
knowledge.read_sources
knowledge.validate_citations
```

- `knowledge.search`：统一检索招标文件、企业证据和历史参考，通过请求参数限制知识范围；
- `knowledge.read_sources`：读取命中项对应的完整来源片段和版本信息；
- `knowledge.validate_citations`：检查引用是否存在、版本有效、内容相符且用途允许。

#### `business.*`

```text
business.validate_structure
business.validate_quote
business.check_consistency
business.evaluate_gate
```

- `business.validate_structure`：校验要求、响应矩阵、章节和审核结果的结构及必要字段；
- `business.validate_quote`：读取报价版本，执行限价、金额、计算公式和引用规则校验；
- `business.check_consistency`：检查跨章节、证据、人员、日期、参数和承诺的一致性；
- `business.evaluate_gate`：检查人工关口和确定性交接门禁是否满足。

#### Skill 工具白名单

| Skill / 调用方 | 允许调用的主要方法 |
|---|---|
| 招标文件理解 | `document.ingest`、`document.read`、`project.get_context`、`project.validate_inputs`、`knowledge.search`、`knowledge.read_sources`、`business.validate_structure` |
| 响应规划与证据匹配 | `project.get_context`、`project.validate_inputs`、全部 `knowledge.*`、`business.validate_structure`、`business.validate_quote` |
| 带引用标书编制 | `document.read`、`document.render`、`project.get_context`、`project.validate_inputs`、全部 `knowledge.*`、`business.validate_structure`、`business.validate_quote`、`business.check_consistency` |
| 质量与风险复核 | `document.read`、`document.render`、全部 `project.*`、`knowledge.read_sources`、`knowledge.validate_citations`、全部 `business.*` |
| Supervisor | 全部 `project.*`、`business.evaluate_gate` |
| 确定性交接任务 | `project.get_context`、`project.validate_inputs`、`business.evaluate_gate`、`document.export` |

白名单由 `SkillManifest` 声明并由 MCP Server 二次校验。专业 Agent 不能因为模型输出而临时扩大工具范围。

### 3.1.5 MCP 同步执行与 Celery 异步边界（已确认）

V1 采用“单层 Celery 异步 + MCP 方法同步执行 + `task_run` 统一进度”的方式。MCP Server 不再创建第二层 Celery 任务，避免嵌套任务、重复重试和两套状态。

```text
前端或工作流触发
→ FastAPI 创建 task_run
→ 投递 Celery
→ Worker 调用同步 MCP 方法
→ MCP 返回结果或结果引用
→ Worker 更新 task_run
→ 前端轮询任务状态
```

如果专业 Agent 本身已经运行在 Celery Worker 中，则直接调用 MCP 方法，不再创建子任务。只有独立的文件处理、预览、导出和全项目检查由 FastAPI 或工作流预先创建对应 `task_run`。

#### 默认进入 Celery 的耗时方法

```text
document.ingest
document.render
document.export
business.check_consistency
```

#### 默认同步调用的方法

```text
document.read
project.get_context
project.validate_inputs
project.validate_transition
knowledge.search
knowledge.read_sources
knowledge.validate_citations
business.validate_structure
business.validate_quote
business.evaluate_gate
```

同步方法必须限制输入规模：单次检索最多返回 50 条候选，单次来源读取和引用校验最多处理 100 个片段或引用。超过上限由调用方拆批；需要全项目扫描时使用已有 Celery 任务调用相同 MCP 方法，不新增异步 MCP 协议。

#### 默认任务预算

| 方法类别 | 默认超时预算 |
|---|---:|
| 项目状态、输入和门禁校验 | 5 秒 |
| 结构与报价校验 | 10 秒 |
| 检索、来源读取和引用校验 | 20 秒 |
| 文件解析、OCR 和复杂图表分析 | 30 分钟 |
| 章节或整本预览 | 10 分钟 |
| 最终导出 | 15 分钟 |
| 全项目一致性检查 | 10 分钟 |

超时属于任务预算，不表示无限等待。临时错误按既定策略有限重试；版本、权限、白名单和业务门禁错误不重试。

#### 进度与查询

`McpCallContext` 增加可选 `task_run_id`。长任务通过该引用更新 `current_step`、`progress_percent` 和 `heartbeat_at`，结果写入 `result_refs`，失败写入 `last_error_code`。FastAPI 或工作流负责创建和排队任务，Celery Worker 负责开始、完成、失败与重试状态，MCP 方法只更新执行步骤、近似进度和心跳。

前端通过以下接口每 2～3 秒轮询，完成后停止：

```http
GET /api/v1/task-runs/{task_run_id}
```

V1 不建设 WebSocket、SSE、消息推送和 MCP 内部任务队列。

### 3.1.6 内部 A2A、上下文管理与记忆系统（已确认）

V1 的 A2A 指统一 LangGraph 主图内部的 Agent-to-Agent 结构化协作，不引入独立 A2A Server、外部 A2A 网络协议、动态 Agent 注册中心或跨系统 Agent 市场。

**A2A 消息内容**：Supervisor 与专业 Agent 之间只传递结构化任务、业务对象引用、上下文引用、产物引用、阻断原因、人工关口状态和下一步动作，不直接传递整份采购文件、完整企业资料或无法追溯的自由文本记忆。A2A 消息必须关联 `workflow_run_id`、发送 Agent、接收 Agent、阶段、输入版本和追踪标识。

**A2A 与 MCP 的区别**：A2A 负责 Agent 之间“谁处理、处理什么、返回什么、下一步去哪”；MCP 负责 Agent 调用文档、项目、知识和业务规则工具。A2A 不替代 MCP，MCP 也不承担 Agent 编排和业务会话状态。

**上下文管理**：每次 Agent 运行由 Context Manager 根据 `workflow_run.input_refs`、`input_hash`、当前人工关口、用户权限、项目职责和有效业务版本组装 `Context Envelope`。Envelope 只包含当前任务必需的摘要、结构化对象和来源引用；Agent 需要正文时通过 `document.read` 或 `knowledge.read_sources` 按引用读取，避免把全部文件和历史对话一次性塞入模型上下文。

**短期运行记忆**：由 LangGraph Checkpoint、`workflow_run`、`agent_run` 和 `task_run` 共同表示当前执行阶段、已完成节点、待处理人工关口、任务状态、失败原因和有限重试信息。Checkpoint用于恢复执行，但不是业务事实源。

**长期业务记忆**：由 PostgreSQL 和 MinIO 中的项目版本、要求基线、响应计划、章节版本、审核结论、企业证据、历史参考、人工确认和审计记录构成。长期记忆必须版本化、可授权、可引用、可失效，不建设不可解释的全局聊天记忆池。

**记忆写入原则**：Agent 不能把模型自由文本直接写成长期事实。专业 Agent 先输出符合 Skill Schema 的结构化产物，领域服务完成权限、版本、规则和人工关口校验后，才能形成新的业务版本或长期记忆。

### 3.2 Supervisor Agent（已确认）

**定位**：LangGraph 确定性状态机上的智能协调器。负责判断下一步由哪个专业 Agent 处理，不能绕过规则、人工关口或直接修改项目主状态。

**实现方式**：

- LangGraph 节点读取 PostgreSQL 中的项目状态和有效基线引用；
- Supervisor 输出结构化调度决策；
- 状态管理工具校验权限、前置条件和状态转换；
- Celery 执行专业 Agent 任务；
- 幂等键防止 Worker 重投造成重复生成。

**结构化决策类型**：

```text
DISPATCH_AGENT
WAITING_HUMAN
RETRY_TASK
EXPAND_REVIEW_SCOPE
INVALIDATE_OUTPUTS
BLOCK_WORKFLOW
COMPLETE_STAGE
```

**边界**：不解析文件、不执行证据检索、不计算报价、不生成章节、不认定资格通过、不关闭高风险问题、不确认报价、不豁免风险、不冻结交接基线。

**人工关口**：文件、要求、证据用途、报价版本未确认；可能覆盖人工章节；存在阻断问题；需要风险豁免；版本冲突；重试达到上限。

### 3.3 招标理解与合规 Agent（已确认）

**定位**：建立系统对有效招标文件的结构化理解，回答“采购文件要求是什么”，不回答“本企业最终是否满足”。

**实现方式**：

```text
确定性预处理
→ 规则召回候选
→ LLM 结构化抽取
→ Schema 与来源校验
→ 跨文件冲突检查
→ 要求原子化和去重
→ 风险与置信度分级
→ 人工确认
→ Requirement Baseline
```

**主要职责**：

- 抽取项目事实、预算、限价、截止时间和采购包信息；
- 抽取资格、否决项、实质性要求、评分项和证明材料要求；
- 抽取技术参数、服务、工期、验收、附件、签章和格式要求；
- 识别正文、评分表、附件、澄清和补遗之间的引用、覆盖和冲突；
- 形成待人工确认的要求基线和文件差异。

**主要输出**：

```text
ProjectFactSet
RequirementSet
ScoringCriterionSet
SubmissionChecklist
DocumentConflictSet
```

每条要求必须包含类型、标准化文本、强制等级、后果类型、来源片段、文件版本、页码、置信度、确认状态和判断摘要。

**Skill**：招标文件理解。

**MCP 工具域**：`document.*`、`knowledge.*`、`business.*` 和受限的 `project.*`。

**边界**：不判断企业资格满足、不确认企业证据、不生成响应矩阵、不生成章节、不计算报价、不关闭风险。

**人工关口**：抽取完成后必须进入 `REQUIREMENT_BASELINE_CONFIRMATION`。未确认前所有结果为 `DRAFT`，不能驱动正式响应矩阵和章节生成。

**文件更新**：补遗确认后生成 `Requirement Diff`，旧基线标记 `STALE`，人工确认后创建新基线，不覆盖历史基线。

### 3.4 响应规划与评分 Agent（已确认）

**定位**：把已确认的招标要求转换成可执行、可追踪、可进行评分覆盖检查的响应计划，统一规划要求、评分项、章节、证据、责任人和依赖关系。

**方案取舍**：不只生成简单响应矩阵，也不单独拆出评分 Agent。将响应规划、企业证据候选匹配和评分覆盖合并，可以缩短调用链并避免矩阵与评分计划形成两套状态。

**实现方式**：

```text
读取已确认 Requirement Baseline
→ 要求分类与响应方式规划
→ 企业证据候选检索
→ 主体、权限、有效期和用途过滤
→ 历史参考候选检索
→ 评分项覆盖规划
→ 章节目录与任务拆分
→ 依赖、缺口和冲突识别
→ 完整度与覆盖率计算
→ 人工确认
→ Response Plan Baseline
```

**响应方式**限定为 `DIRECT_RESPONSE`、`EVIDENCE_RESPONSE`、`FORM_RESPONSE`、`QUOTE_RESPONSE`、`DECLARATION_RESPONSE`、`MANUAL_ATTACHMENT`、`NOT_APPLICABLE`、`EVIDENCE_MISSING`、`CONFLICT` 或 `WAITING_CONFIRMATION`。没有证据时不能自动改成纯文字响应。

**证据匹配状态**限定为 `MATCHED_CANDIDATE`、`CONFIRMED_MATCH`、`INSUFFICIENT`、`EXPIRED`、`WRONG_SUBJECT`、`OUT_OF_SCOPE`、`PERMISSION_DENIED` 或 `MISSING`。语义相似不能直接推出企业满足要求。

**主要输出**：

```text
ResponseMatrix
ScoringCoveragePlan
ChapterPlan
EvidenceMatchSet
EvidenceGapSet
HistoricalReferenceSet
WorkAssignmentPlan
PlanningConflictSet
```

每个响应矩阵项至少记录要求 ID、响应方式、目标章节、候选和已确认的证据、评分项、责任人、状态、阻断原因和来源要求基线。

**评分规则**：只有在评分公式可以确定性计算且相关证据已确认时，才允许输出潜在得分区间，并明确其不是评标结果或中标预测。主观评分项只记录覆盖状态，使用 `NOT_EVALUATED`，不得猜测分数。

**历史参考边界**：历史项目只能用于章节结构、实施方案表达、风险提示、资源安排和差异分析；不得作为当前企业事实、当前报价、当前人员或技术参数承诺。候选参考必须记录差异、允许用途、禁止用途和人工确认状态。

**章节和任务规划**：章节计划记录负责人、关联要求、评分项、证据、报价依赖、参考项目、阻断任务、截止时间和审核状态。上游证据、报价或人工确认未完成时，下游章节不能标记为可正式生成。

**Skill**：响应规划与证据匹配。

**MCP 工具域**：`knowledge.*`、`business.*` 和受限的 `project.*`。报价方法只提供已确认版本、有效候选、校验结果和引用字段，Agent 不能修改公式或确认最终报价。

**明确不负责**：不修改要求基线、不判定企业最终通过资格、不编造或自动确认企业证据、不自动确认历史项目用途、不计算或确认最终报价、不生成正式章节、不审核通过、不承诺人员、工期、服务和技术参数、不预测中标概率。

**人工关口**：规划完成后必须进入 `RESPONSE_PLAN_CONFIRMATION`。人工确认高风险要求响应方式、证据用途、历史参考用途、评分项与章节映射、缺失材料任务、章节责任人、报价依赖、确定性分值测算和不适用理由。未确认前只能生成预览草稿。

**变更与失效**：要求基线更新时响应计划整体标记 `STALE`；证据失效时定位相关矩阵项和章节并增量失效；报价版本变化时定位金额引用并触发商务复核；人工章节目录修改不得被 Agent 静默覆盖。

**失败降级**：向量检索失败时降级关键词检索并标记降级；重排失败时使用融合召回分数；没有证据时创建缺口；评分规则无法解析时转人工；报价未确认时阻断金额相关矩阵项；结构化校验持续失败时转人工。

**评估重点**：要求映射准确率、关键评分项覆盖率、证据引用正确率、无证据拒答正确率、错主体或过期证据误用数、历史参考用途边界、缺口发现率、确定性评分计算、人工修改比例和增量失效正确率。

### 3.5 标书编制 Agent（已确认）

**定位**：根据已确认的响应计划和证据，生成带引用、可局部修改、可版本比较的章节草稿，但不能静默覆盖人工内容。

**方案取舍**：采用结构化内容块生成，不使用整章单一 Markdown 字符串。结构化内容块支持块级来源、版本、锁定、局部重写、差异比较和定向失效，同时仍能组合导出完整 DOCX/PDF。

**章节内容模型**：

```text
Chapter
  ├── HeadingBlock
  ├── ParagraphBlock
  ├── TableBlock
  ├── FigureBlock
  ├── QuoteDataBlock
  ├── EvidenceBlock
  ├── NoticeBlock
  └── PlaceholderBlock
```

每个内容块记录块类型、内容、顺序、来源类型、来源对象、关联要求与评分项、生成方式、编辑状态、锁定状态、创建人和基础版本。

**内容来源类型**限定为 `GENERATED`、`TEMPLATE`、`MANUAL`、`DATA_BOUND`、`HISTORICAL_REFERENCE`、`PLACEHOLDER` 和 `SYSTEM_NOTICE`。导出时必须区分正式内容、内部提示和待补充内容，内部风险提示不得混入外发标书。

**实现管线**：

```text
读取 Response Plan Baseline 与当前章节版本
→ 检查要求、证据、报价和模板依赖
→ 识别人工锁定块
→ 检索允许使用的证据和历史参考
→ 生成结构化内容块
→ 确定性数据块填充
→ 引用、事实和禁用承诺校验
→ 生成 VisualAssetSpec
→ 生成版本差异
→ 人工确认
→ Chapter Draft Version
```

**主要输出**：`ChapterDraftVersion`、`ContentBlockSet`、`CitationManifest`、`VisualAssetSpecSet`、`GenerationDiff`、`MissingInputSet` 和 `GenerationWarningSet`。

**引用约束**：企业资质、人员、案例、招标要求、报价和技术参数必须分别引用有效企业证据、人员材料、项目证明、招标文件片段、确认报价字段或产品材料。引用记录包含来源对象、来源版本、片段、页码、用途、引用文本和校验状态。无有效来源时创建 `PlaceholderBlock` 和 `MissingInput`，不得生成确定性事实。

**事实与承诺分类**：生成内容区分 `VERIFIABLE_FACT`、`PLANNED_RESPONSE`、`COMMITMENT`、`REFERENCE_CONTENT` 和 `GENERAL_DESCRIPTION`。可验证事实必须有证据，正式承诺必须来自已确认响应计划或人工输入，历史参考不能伪装成当前事实，一般描述不能伪装成企业已有能力。

**报价处理**：LLM 不直接生成金额。金额、税率、单位和大小写由系统锁定的 `QuoteDataBlock` 引用已确认报价版本并通过报价工具确定性填充。报价版本变化只增量更新金额块和相关商务表述，并触发商务复核。

**图表处理**：Agent 生成 `VisualAssetSpec`，记录图表类型、标题、数据来源、渲染器、图注和确认要求；文档渲染工具生成甘特图、流程图、架构图和统计图。没有数据来源时只能生成占位项。

**人工编辑保护**：生成任务创建时固定 `base_chapter_version_id` 和块版本。任务完成时若当前版本已变化，不覆盖现有章节，而是创建冲突候选版本和差异。内容块状态包括 `AI_GENERATED`、`AI_MODIFIED`、`MANUAL_EDITED`、`MANUAL_CREATED`、`LOCKED`、`STALE` 和 `CONFLICTED`。人工创建、人工修改和锁定内容默认禁止自动覆盖。

**局部重写**：支持按段落、表格、图表说明、审核问题、证据变化或报价变化定向重写。结果作为差异建议，用户选择 `ACCEPT_AGENT_CHANGE`、`KEEP_CURRENT_CONTENT` 或 `MERGE_MANUALLY`。

**Skill**：带引用标书编制。

**MCP 工具域**：`knowledge.*`、`business.*`、`document.*` 和受限的 `project.*`。

**明确不负责**：不修改要求或响应计划、不确认企业证据、不确认报价、不生成无来源企业事实、不擅自承诺人员工期参数、不关闭审核问题、不判定审核通过、不接受风险豁免、不修改锁定内容、不冻结交接基线、不执行外部递交。

**人工关口**：生成完成后进入 `CHAPTER_DRAFT_CONFIRMATION`。编写人确认内容、引用、承诺、历史参考、报价字段、图表来源、待补充项和版本差异后，可将章节置为 `READY_FOR_REVIEW`，该状态不代表审核通过。

**审核返工**：质量与风险复核 Agent 只创建结构化修改要求。标书编制 Agent 根据问题生成候选版本，不能自行关闭问题或降低风险，修改后必须重新提交复核。

**变更与失效**：要求或响应计划变化时受影响块进入 `STALE`；证据失效时阻断相关事实并生成引用差异；报价变化只更新金额相关块；模板变化只能生成候选排版版本，不得静默改变已确认内容。

**失败降级**：LLM 失败由 Celery 有限重试；结构化输出持续失败时保留原版本；引用校验失败时删除未验证内容或转占位；报价工具不可用时阻断金额块；图表渲染失败时保留规格和占位；版本冲突时创建冲突候选；输入基线变化时废弃本次结果。

**评估重点**：章节和评分覆盖、事实引用、无证据生成、承诺来源、历史参考边界、报价字段、图表来源、人工编辑保护、局部重写范围、版本差异、审核返工修复率、人工采纳比例、耗时和成本。

### 3.6 质量与风险复核 Agent（已确认）

**定位**：对不可变的当前审核基线执行资格合规、评分覆盖、证据引用、报价、跨章节一致性、履约承诺和外发内容检查，统一形成问题、风险和安全复核范围，但不能自行审核通过、关闭问题或接受风险。

**方案取舍**：采用一个逻辑 Agent 内的多阶段审核，不拆成多个独立审核 Agent。确定性问题由规则工具执行，语义一致性和履约风险由 LLM 辅助，最终问题合并、分级并交人工审核。

**风险等级**统一为 `BLOCKING`、`HIGH`、`MEDIUM` 和 `LOW`，分别对应阻断、高、中和低风险。纯提示使用 `ReviewNotice`，不增加 `INFO` 风险等级。规则认定的阻断风险不能被 Agent 自动降级。

**审核模式**包括 `CHAPTER_REVIEW`、`INCREMENTAL_REVIEW`、`FULL_PROJECT_REVIEW` 和 `PRE_HANDOVER_REVIEW`。

**审核基线**：每次审核先创建不可变 `ReviewBaseline`，固定要求基线、响应计划、章节版本、报价版本、证据版本、附件、模板、规则、模型和提示词版本。审核结论只对该基线有效；任一输入变化后原审核运行与相关风险进入 `STALE`。

**实现管线**：

```text
创建 ReviewBaseline
→ 确定性预检
→ 资格与合规检查
→ 评分覆盖检查
→ 证据与引用检查
→ 报价与数据一致性检查
→ 跨章节语义一致性检查
→ 履约与承诺风险检查
→ 附件、格式与外发内容检查
→ 问题合并与去重
→ 风险分级和责任路由
→ 复核范围判断
→ 人工审核
```

**确定性预检**检查必备章节和附件、版本、引用对象、确认报价、金额大小写、合计、日期、目录、内部提示、占位块、版本冲突和证据有效性。确定性检查失败时不得调用 LLM 猜测结果。

**主要输出**：`ReviewRun`、`ReviewBaseline`、`ReviewIssueSet`、`RiskItemSet`、`CoverageReviewReport`、`CitationReviewReport`、`ConsistencyReviewReport`、`CommercialReviewReport`、`ReviewScopeDecision` 和 `ReviewSummary`。

**状态模型规范化**：

- `review_issue.status` 沿用数据字典：`OPEN`、`PROPOSED`、`WRITER_CONFIRMED`、`PENDING_REVIEW`、`CLOSED`、`REOPENED`、`WAIVED`；
- `risk_item.risk_status` 沿用数据字典：`OPEN`、`IN_PROGRESS`、`RESOLVED`、`WAIVED`、`STALE`；
- Agent 只能创建 `OPEN` 问题或风险、提出 `PROPOSED` 修改建议，并在依赖版本变化时使风险结论 `STALE`；
- `CLOSED`、`RESOLVED` 和 `WAIVED` 必须由有权限人工角色经复核或授权后设置。

**责任路由**：章节响应问题路由编写人；资格和否决项路由合规审核人；报价和商务条款路由商务负责人；法律承诺和豁免路由法务或授权负责人；跨章节总体风险路由投标经理；文件与版本问题路由资料责任人或投标经理。Agent 只建议路由，状态工具验证权限。

**修改建议**必须说明问题、原因、来源、影响对象、建议动作、责任人和修改后的复核范围。不得直接覆盖章节、编造材料、替换报价、降低招标标准或把不满足包装成满足。

**复核范围**分为 `OBJECT`、`CHAPTER`、`MULTI_CHAPTER` 和 `FULL_PROJECT`。纯语言、非事实格式或证明范围不变的单证据替换可以局部复核；要求、报价、主体、人员、工期、日期、参数、证据范围、评分映射、正式承诺或共享内容变化必须扩大复核。无法可靠判断影响范围时扩大，而不是缩小。

**返工闭环**：Agent 创建 `OPEN` 问题并提出 `PROPOSED` 修改；责任人确认后进入返工；标书编制 Agent 生成候选修改；编写人确认后问题进入 `PENDING_REVIEW`；有权审核人复核后设置 `CLOSED` 或重新 `REOPENED`，授权角色可以设置 `WAIVED`。Agent 不能跳过人工复核。

**风险豁免**记录问题、等级、理由、范围、授权人、角色、有效对象版本、有效期和时间。豁免只对明确对象和版本有效，版本变化后重新判断；资格、法定无效和系统安全类问题能否豁免由确定性规则控制，不由 Agent 决定。

**Skill**：质量与风险复核。

**MCP 工具域**：`document.*`、`project.*`、`knowledge.*` 和 `business.*`。高风险 `project.*` 方法必须经过角色、版本、问题状态和确定性门禁校验。

**明确不负责**：不自动审核通过、不关闭问题、不降低风险、不批准豁免、不直接修改章节、不确认资格和报价、不冻结基线、不代替人工签字、不因截止临近降低标准、不根据单次反馈自动更新规则或模型。

**人工关口**：预检完成后进入 `REVIEW_RESULT_CONFIRMATION`。审核人确认问题、等级、责任人、修改建议和复核范围，处理误报并补充人工问题。只有所有必审任务完成、所有 `BLOCKING` 风险为 `RESOLVED` 或合法 `WAIVED` 且审核基线仍有效时，状态管理工具才允许进入 `READY_FOR_HANDOVER`。

**失败降级**：语义审查失败时保留确定性结果并重试；持续失败不能以“无问题”结束，必须转人工；规则或报价工具失败时阻断对应审核域；引用无法定位至少升级为高风险；影响范围不明扩大复核；导出预览失败阻断交接前审核；输入变化使审核结果失效；问题去重不确定时保留并交人工合并。

**评估重点**：阻断和高风险召回、错误降级、误报、责任路由、修改建议、报价和跨章节冲突、证据引用、内部信息外泄、影响判断、复核范围安全性、自动关闭或豁免、问题重开、审核耗时和返工轮次。

## 四、前端技术方案

### 4.1 Next.js（已确认）

**承担职责**：登录、项目工作台、文件中心、要求矩阵、证据中心、章节编制、审核风险、交接导出和任务进度展示。

**实现方式**：

- 使用 Next.js App Router 和 TypeScript；
- 页面按纵向切片组织，业务状态通过服务层访问，不在组件中直接拼接 API；
- OpenAPI/JSON Schema 生成或约束 TypeScript DTO；
- Mock API 与真实 API 使用相同响应结构；
- 长任务通过任务 ID 每 2～3 秒轮询，完成后停止；V1 不使用 WebSocket 或 SSE；
- 编辑页面保留章节版本号，提交时进行乐观锁校验；
- 前端隐藏无权限按钮，FastAPI 仍执行最终权限校验。

**选择原因**：

- 复杂工作台、状态展示、证据引用和章节编辑能力显著强于 Streamlit；
- TypeScript 有利于契约驱动和前后端字段一致性；
- 支持容器化部署，后续可独立扩展前端工程。

**未采用**：

- Streamlit：原型快，但复杂状态、权限、编辑器和长期维护能力不足；
- 纯 React SPA：可行，但需要额外处理路由、构建和服务端能力，Next.js 提供更完整工程基线。

**V1 边界**：不做实时多人协同编辑和离线应用；任务状态只使用轮询，不同时维护 SSE 或 WebSocket 通道。

### 4.2 现有原型迁移与视觉设计系统（已确认）

V1 复用组员现有单文件 HTML 原型的页面布局、业务交互和部分演示内容，但不在原文件中继续堆叠正式功能。原型作为只读视觉参考保存，正式前端迁移为 Next.js、TypeScript 和组件化工程。

**复用边界**：

- 优先复用项目概览、文件解析、响应矩阵、章节编制、风险审核、资料卡片、版本时间线、原文抽屉和模态交互；
- 重新实现数据请求、路由、状态管理、权限、表单校验、任务轮询和 Mock 契约；
- 不复用单文件全局状态、大量 `onclick`、字符串 `innerHTML` 拼接和 `localStorage` 业务状态；
- 增加登录页、我的工作台、全局项目入口和四个人工关口；
- 将企业资料库移到全局导航，将项目内导航改为项目总览、文件与解析、要求与评分、响应规划、标书编制、审核与风险、交接与递交、项目记录；
- 原型中的“一键生成最终投标书”、五个专业 Agent 和企业 VPC 内网文案必须按已确认流程、5 Agent 总数和公网部署边界修正。

**视觉方向**：采用白灰政务商务风，以 Swiss 信息设计为基础，强调清晰网格、左对齐、细边框、克制装饰和高信息密度。AI、Agent、Skill 和 MCP 不作为界面视觉中心，页面优先突出阶段、待办、来源、人工确认、责任、风险和版本。

```text
页面背景       #F5F7FA
卡片与导航     #FFFFFF
主要文字       #1D2633
次要文字       #667085
辅助文字       #98A2B3
边框           #DDE3EA
主操作蓝       #1F5AA6
深色政务蓝     #153E73
浅蓝选中背景   #EAF2FB
成功           #237B55
提醒           #B7791F
高风险         #C2413B

```

中文使用 `PingFang SC`、`Microsoft YaHei` 等系统字体，数字和英文可使用 Inter。正文默认约 14px，密集表格可使用 13px。卡片圆角控制在 6～8px，以 1px 边框代替发光和重阴影；表头使用浅灰背景，主按钮使用政务蓝，红色只表达危险、阻断和高风险。

字符图标如 `◈`、`⌗`、`◇` 不进入正式版本，统一使用可访问的图标组件。界面减少 `AI 一键生成投标书`、`AI AUTHORING STUDIO`、`MULTI-AGENT REVIEW` 等营销式表达，改为“生成章节草稿”“标书编制”“质量与风险复核”等正式业务名称。

**选择原因**：现有原型已经验证了高密度投标工作台、表格、抽屉和移动端布局，复用其成熟部分可以减少重复设计；迁移而非直接扩展单文件，可避免后续接入 API、权限和状态机时大规模返工。白灰政务蓝更符合政府采购项目的正式、可信和长时间阅读需求。

### 4.3 信息架构与两层导航（已确认）

用户登录后首先进入“我的工作台”，不直接跳入最近项目。工作台按当前用户权限聚合我的待办、待人工确认、阻断事项、临期项目、运行中任务和最近访问项目，再由用户进入具体项目工作区。

桌面端采用“顶部全局导航 + 项目内左侧导航”：

```text
顶部全局导航
├── 我的工作台
├── 项目
├── 企业资料库
├── 模板与规则
└── 系统管理

项目内左侧导航
├── 项目总览
├── 文件与解析
├── 要求与评分
├── 响应规划
├── 标书编制
├── 审核与风险
├── 交接与递交
└── 项目记录
```

顶部同时保留当前项目切换器、全局搜索、运行任务入口和用户菜单，但不建设独立消息中心。企业资料库、模板与规则和系统管理属于组织级能力，不放入具体项目侧边栏。

四个人工关口不单独建设“确认中心”，而是放在对应业务页面：要求基线确认位于“要求与评分”，响应计划确认位于“响应规划”，章节草稿确认位于“标书编制”，复核结果确认位于“审核与风险”。“我的工作台”只汇总这些待确认项并链接到原页面处理。

菜单根据平台角色、项目成员关系和对象权限隐藏或禁用，但前端显示控制不是安全边界，FastAPI 必须重新校验。移动端顶部导航和项目侧边栏收进抽屉，保留当前页面标题、关键状态和主要操作；不要求在手机上完成大规模章节编辑或复杂矩阵操作。

V1 不建设 Agent、Skill、MCP 独立管理页面，不提供自定义菜单、通用流程设计器和复杂大屏。技术运行详情统一在任务详情与项目记录中按权限查看。

**选择原因**：两层导航将组织级资源与单项目流程分离，既支持多项目工作台，又保持项目阶段顺序清晰；同时可直接复用现有原型的项目侧边栏布局，而不让全局资料和系统管理继续混入项目菜单。

### 4.4 V1 核心页面清单与原型映射（已确认）

V1 冻结为 14 个一级页面入口，其中登录页独立于登录后导航。一级入口用于组织业务，不代表每项都建设独立复杂子系统；详情、编辑、对照和轻量操作优先使用标签页、抽屉或对话框。

**全局入口 6 个**：

```text
登录
我的工作台
项目
企业资料库
模板与规则
系统管理
```

**项目内入口 8 个**：

```text
项目总览
文件与解析
要求与评分
响应规划
标书编制
审核与风险
交接与递交
项目记录
```

现有原型迁移关系：

| 原型能力 | 正式页面处理 |
|---|---|
| 首次上传引导 | 保留交互思路，迁移为“新建项目向导” |
| 项目概览 | 保留为“项目总览” |
| 招标文件解析 | 保留并增加文件版本、解析任务和人工确认 |
| 响应与评分矩阵 | 拆为“要求与评分”和“响应规划”，分别承载两个阶段关口 |
| AI 智能编写 | 改名为“标书编制”，增加章节版本、引用和人工确认 |
| 多 Agent 合规审核 | 改为“审核与风险”，按 5 Agent 总体架构修正展示 |
| 企业材料库 | 移到全局“企业资料库” |
| 版本与导出 | 拆为“交接与递交”和“项目记录” |

“系统管理”保持单一入口，内部使用账号与角色、审计记录、运行状态等标签页；“模板与规则”统一管理文档模板、报价模板和已发布规则版本，不为每类对象增加一级菜单。

V1 删除或取消原型中的全局“AI 一键生成投标书”、独立通知中心、用户直接配置模型策略、企业 VPC 状态卡、Agent/Skill/MCP 技术管理页、不经过门禁的快速导出和与正式运行记录重复的虚构 Agent 动态。运行事件统一来自 `workflow_run`、`agent_run` 和 `task_run`。

**选择原因**：该清单完整覆盖已确认的核心价值和四个人工关口，同时通过合并管理入口、使用页面内标签和删除技术管理页控制前端规模，避免将原型中的演示按钮直接变成正式功能负担。

### 4.5 角色权限视图与页面操作（已确认）

V1 保留 PRD 的 9 类业务角色，但前端不建设 9 套页面。页面呈现归并为 6 种权限视图，具体授权仍由 `user.system_role + project_member.project_role + object scope` 共同决定。

| 前端权限视图 | 对应业务角色 |
|---|---|
| 编制视图 | 标书编写人、技术方案人员、商务/报价人员 |
| 项目管理视图 | 项目负责人 |
| 审核视图 | 商务审核人员、合规/法务人员 |
| 资料管理视图 | 资料管理员 |
| 递交视图 | 投标递交责任人 |
| 系统管理视图 | 系统管理员 |

权威项目职责统一为：

```text
BID_MANAGER
BID_WRITER
TECHNICAL_WRITER
PRICING_OWNER
COMMERCIAL_REVIEWER
COMPLIANCE_LEGAL_REVIEWER
SUBMISSION_OWNER
```

资料管理员和系统管理员主要使用组织级 `system_role`，不要求成为每个项目的成员。六种权限视图只用于共享布局、默认筛选和按钮展示，不能合并审核责任或绕过职责分离。

**页面操作矩阵**：

| 页面 | 主要编辑或确认角色 | 其他角色边界 |
|---|---|---|
| 我的工作台 | 所有用户处理自己的任务 | 只展示有权访问的项目和对象 |
| 项目总览 | `BID_MANAGER` 分配任务和维护项目摘要 | 项目成员按权限查看 |
| 文件与解析 | `BID_MANAGER`、授权编制角色上传和处理解析 | 审核角色只读并可提出问题 |
| 要求与评分 | 编制、技术和审核角色处理各自范围 | 阶段关口由有权负责人确认 |
| 响应规划 | `BID_WRITER`、`TECHNICAL_WRITER`、`PRICING_OWNER` 编辑职责范围 | `BID_MANAGER` 确认响应计划 |
| 标书编制 | 编制、技术和报价角色按章节或内容块编辑 | 审核角色只读、评论或创建问题 |
| 审核与风险 | `COMMERCIAL_REVIEWER`、`COMPLIANCE_LEGAL_REVIEWER` 复核和关闭各自问题 | 编制人员整改但不能关闭自己的审核问题 |
| 交接与递交 | `BID_MANAGER` 生成并确认交接，`SUBMISSION_OWNER` 接收和记录递交 | 其他角色只读或不可见 |
| 项目记录 | 项目成员查看授权范围内记录 | 系统管理员可查看完整审计但不能代替业务确认 |
| 企业资料库 | `MATERIAL_ADMIN` 维护、发布和失效资料 | 其他角色只按权限检索与引用 |
| 模板与规则 | 管理员发布，项目负责人查看有效版本 | 普通用户只使用已发布版本 |
| 系统管理 | `ADMIN` 管理账号、角色、审计和运行状态 | 其他角色不可见 |

商务审核人员只能复核商务响应、报价引用和证明材料；合规/法务人员处理资格、实质性要求、承诺、法律风险和授权范围内的豁免。系统管理员拥有配置和审计权限，但不能替代项目负责人、审核人或递交责任人完成业务确认。

前端无权限时隐藏操作按钮；已进入页面但对象权限不足时显示只读或明确拒绝状态。所有写操作和状态转换仍由 FastAPI 根据当前 Session、平台角色、项目职责、对象归属、业务状态和输入版本重新校验。

**选择原因**：共享六类页面视图可降低前端组件和 Mock 场景数量，七个明确项目职责仍能保证编制、审核、豁免、交接和递交之间的职责分离，功能与审计价值不打折。

### 4.6 Mock 契约与场景数据（已确认）

V1 前端使用 TypeScript DTO、Zod 运行时校验和 MSW 拦截真实 API 路径。Mock 与未来 FastAPI 使用相同 URL、请求参数、状态码、响应结构、错误码和状态枚举；页面组件不能直接导入 Fixture 作为业务数据。

每个核心页面至少支持 6 个统一基础场景：

```text
default
empty
loading
error
readonly
forbidden
```

- `default`：正常有数据并可执行当前角色允许的操作；
- `empty`：新项目或当前筛选下无业务记录；
- `loading`：首屏加载或任务状态查询中；
- `error`：接口失败、数据不可用或可重试错误；
- `readonly`：允许查看，但当前角色、状态或版本不允许修改；
- `forbidden`：用户无权访问页面或对象，使用统一 `PERMISSION_DENIED` 契约。

代表性权限身份控制为 7 个：

```text
bid_writer
bid_manager
commercial_reviewer
compliance_reviewer
material_admin
submission_owner
system_admin
```

这些身份覆盖六类前端视图和审核域差异，不为 9 个业务角色与所有页面生成全组合 Fixture。技术方案人员和报价人员通过 `bid_writer` 基础身份叠加 `project_role` 与职责范围进行验证。

**页面专属场景**：

| 页面 | 必须覆盖的关键场景 |
|---|---|
| 我的工作台 | 无待办、临期项目、阻断事项、待人工确认、任务失败 |
| 文件与解析 | 未上传、上传中、排队、解析中、部分成功、失败、新澄清版本、复杂图表待确认 |
| 要求与评分 | 低置信度、高风险未确认、基线可确认、门禁未满足、输入失效 |
| 响应规划 | 证据缺失、覆盖不足、负责人未分配、报价未确认、计划可确认、退回修改 |
| 标书编制 | 未生成、生成中、已有草稿、无来源内容、引用失效、人工锁定、版本冲突、草稿可确认 |
| 审核与风险 | 审核中、一般问题、高风险、阻断、整改中、待原审核人复核、合法豁免、结果可确认 |
| 交接与递交 | 未达门禁、生成中、全部成功、DOCX 成功但 PDF 失败、待接收、递交成功、递交失败、基线失效 |

四个人工关口必须分别有“可确认”和“门禁未满足”场景，并包含 `pending_gate`、剩余必确认数量、阻断原因、输入哈希和允许动作，保证前端不能通过 Mock 设计绕过真实后端门禁。

Fixture 使用固定 ID、固定时间和可重复数据，统一标记 `[SIMULATED]`，不得随机生成关键业务值或伪装成真实企业和政府项目。每条重要数据包含来源、版本、权限范围、更新时间和状态；错误场景使用统一错误对象，不单独在组件中拼错误文案。

推荐目录：

```text
frontend/src/
├── contracts/
├── api/
└── mocks/
    ├── handlers/
    ├── fixtures/
    └── scenarios/
```

V1 总量控制为约 35～45 份固定 Fixture。场景通过开发配置、Storybook 类预览入口或测试参数切换，不将 `scenario` 查询参数带入生产业务语义。FastAPI 完成后以 OpenAPI 为实现权威，使用契约测试验证真实响应和 Mock 均能通过同一 Zod/Schema 校验。

**选择原因**：统一基础状态能保证加载、空数据、失败和权限体验不遗漏；有限专属场景足以覆盖四个人工关口和核心失败路径，同时避免 `14 页面 × 多状态 × 多角色` 的组合爆炸。

### 4.7 我的工作台页面（已确认）

“我的工作台”是登录后的默认入口，定位为个人行动中心，不建设管理驾驶舱。页面只展示当前用户有权访问且需要关注的任务、确认、风险、项目和运行状态，不展示模型 Token、Agent 数量或与当前工作无关的复杂统计图。

**页面结构**：

```text
顶部
页面标题｜当前日期｜新建项目（有权限时）

摘要区
待办数量｜待人工确认｜阻断事项｜临期项目

主体左侧
我的待办

主体右侧
最近访问项目与项目进度

底部
运行中任务｜最近失败任务
```

“我的待办”每项至少展示任务名称、所属项目、任务类型、风险等级、截止时间、责任动作和跳转目标。工作台只提供“前往处理”“查看项目”“重试允许重试的任务”等入口，具体业务修改仍在对应页面完成。

默认排序固定为：

```text
阻断事项
→ 今日到期
→ 待人工确认
→ 高风险事项
→ 普通待办
```

同一优先级内先按截止时间，再按创建时间排序。超期任务显示明确超期时长；无截止时间的普通事项排在有截止时间事项之后。

不同权限视图使用同一布局，但摘要和待办范围不同：编制视图突出章节、证据和整改；项目管理视图突出阶段关口、临期项目和阻断；审核视图突出待审核与待复核；资料管理视图突出待发布、临期和失效资料；递交视图突出待接收交接包与递交回执；系统管理视图突出账号、安全和运行异常。

**Mock/API 初版契约**：

```http
GET /api/v1/me/workbench
```

响应聚合 `summary`、`action_items`、`recent_projects`、`running_tasks` 和 `recent_failures`，并返回 `generated_at`。V1 使用单个聚合读取接口减少首屏请求数量；各卡片操作继续调用所属业务资源接口，工作台接口不承担状态修改。

工作台专属 Mock 场景为：正常待办、完全空状态、多个临期项目、存在阻断事项、存在待人工确认、运行任务失败和只读身份。空状态提供“查看项目”或有权限时“新建项目”，不使用虚构图表填充页面。

移动端将摘要卡横向紧凑排列或两列换行，待办保持单列；运行任务和失败任务可折叠。手机端支持查看和跳转，不在工作台直接完成复杂编辑。

**选择原因**：行动优先的工作台能够让不同角色快速进入当前最重要任务；单一聚合读取契约降低前端首屏复杂度，具体状态变更仍回到领域页面，避免形成第二套业务入口。

### 4.8 项目列表页面（已确认）

“项目”页面用于查找和进入当前用户有权访问的投标项目。桌面端使用高密度表格，移动端自动转换为项目卡片；不使用全卡片桌面布局，避免多个项目之间难以比较截止时间、阶段和风险。

**页面顶部**：标题与说明、项目名称或编号搜索、项目状态筛选、当前阶段筛选、负责人筛选、“只看我的项目”和有权限时的“新建项目”。搜索与筛选条件保留在 URL 查询参数中，便于返回列表和分享相同视图。

**表格字段**：

```text
项目名称与编号
采购方式
当前阶段
项目状态
距截止时间
待确认事项
阻断风险
项目负责人
最近更新
操作
```

模拟项目名称显式显示 `[SIMULATED]`。截止时间同时展示绝对时间和剩余时间；已过期项目显示超期，不用负数倒计时。项目状态和当前阶段分开显示，例如 `ACTIVE + 标书编制 + 等待章节草稿确认`，不得以单一“进行中”替代状态机信息。

默认排序为：

```text
存在阻断风险
→ 7 天内截止
→ 等待人工确认
→ 正常进行中
→ 草稿项目
→ 已完成或已终止
```

同一分组内按截止时间升序，再按最近更新时间降序。用户可切换截止时间和最近更新时间排序。

普通项目成员可执行“进入项目”和“查看我的任务”；项目负责人可额外进入基本信息与成员管理。项目删除、人工关口确认、交接包生成和递交记录不放入列表快捷操作，必须进入对应详情页面并执行权限与业务门禁校验。

**Mock/API 初版契约**：

```http
GET  /api/v1/projects
POST /api/v1/projects
```

列表查询支持 `page`、`page_size`、`keyword`、`project_status`、`current_stage`、`manager_user_id`、`mine_only` 和 `sort`。响应返回分页信息、筛选摘要与项目列表；每个项目包含 `current_stage`、`pending_gate`、`blocking_risk_count`、`pending_confirmation_count`、`deadline_at` 和当前用户允许动作。

Mock 场景覆盖正常多项目、没有项目、仅一个项目、多个临期项目、存在阻断项目、只读用户和项目创建失败。空状态只对有创建权限用户显示“新建项目”，其他用户显示等待项目分配说明。

移动卡片保留项目名称、编号、状态、阶段、截止时间、阻断和主要操作，其余字段进入展开区；不牺牲风险与人工关口信息来追求卡片简洁。

**选择原因**：桌面表格符合政府项目和企业项目管理的比较习惯，移动卡片保证小屏可用；将状态、阶段、关口和风险并列展示，可以让用户快速判断项目真正处于什么位置。

### 4.9 新建项目向导（已确认）

新建项目使用三步向导，不使用单页长表单。向导支持中途保存和恢复，基本信息、成员和文件分别提交，避免文件上传失败导致已填写内容全部丢失。

#### 第一步：项目基本信息

必填字段为项目名称、采购方式、投标截止时间和项目负责人。项目编号、采购人、代理机构、预算、最高限价、主标包名称和项目说明可选或稍后完善。V1 只创建一个主标包，不提供多标包编辑器。

第一步完成后调用 `POST /api/v1/projects` 创建 `DRAFT` 项目并返回 `project_id`。创建人默认成为 `BID_MANAGER`，如其平台权限不允许承担该职责则阻断创建。项目名称允许业务上相似，但组织内项目编号存在时必须唯一；系统对名称和采购人组合提供重复提示，不自动拒绝合法重复名称。

#### 第二步：项目成员

可分配标书编写人、技术方案人员、商务/报价人员、商务审核人员、合规/法务人员和投标递交责任人。项目负责人必填，其他职责可暂缺并在项目总览补充。

系统校验用户是否有效、平台角色是否允许承担项目职责、同一职责是否允许多人、同一用户是否重复分配以及编制与审核职责分离。V1 不禁止一个用户承担多个编制类职责，但同一对象的编写人与最终复核人不能是同一人。

#### 第三步：采购文件上传

上传类型分为主采购文件、澄清/更正/补遗、附件和投标文件格式模板。初次启动解析前必须有一个当前主采购文件；澄清和附件允许多文件。每个文件显示名称、大小、类型、SHA-256 计算状态、数据分类、上传状态和是否可用于解析。

项目外部 AI 策略默认 `PUBLIC_ONLY`，不在普通向导中要求用户选择复杂出域策略。数据分类默认按文件类型和项目策略给出建议，由有权限用户确认或后续修改。

向导底部提供：

```text
保存草稿
创建并启动解析
```

“保存草稿”允许暂未上传主采购文件，项目保持 `DRAFT` 且不创建工作流。“创建并启动解析”必须通过基本信息、负责人、主文件、文件校验和权限检查，然后创建 `document_version` 与 `task_run`，调用 `document.ingest` 并跳转“文件与解析”页面轮询进度。

**Mock/API 初版契约**：

```http
POST  /api/v1/projects
PATCH /api/v1/projects/{project_id}
PUT   /api/v1/projects/{project_id}/members
POST  /api/v1/projects/{project_id}/documents
POST  /api/v1/projects/{project_id}/ingestion-runs
```

文件上传采用独立请求并返回文件记录与校验状态，不设计包含项目、成员和二进制文件的巨型创建接口。向导重新进入时读取草稿项目、成员和已上传文件，定位到第一个未完成步骤。

Mock 场景覆盖正常创建、保存草稿、名称或编号重复提示、截止时间已过去、成员角色不匹配、职责分离失败、文件上传失败、不支持的文件类型、超过 200 MB、文件校验失败以及创建成功但解析任务排队。

**选择原因**：三步结构与用户真实建项顺序一致；草稿项目和分步接口支持断点恢复，也为后端按纵向切片实现项目、成员、文件和解析能力提供清晰边界。

### 4.10 项目总览页面（已确认）

项目总览是进入单个项目后的阶段导航与行动入口，不做复杂数据大屏，也不在总览页直接执行人工关口确认。页面优先回答“项目现在在哪个阶段、当前最需要做什么、有什么事项会阻断继续推进”。

#### 项目抬头与阶段进度

顶部展示项目名称与编号、采购方式、项目负责人、投标截止时间、项目状态、当前阶段和当前人工关口。项目状态、业务阶段和人工关口分别展示，不合并为模糊的“进行中”。

横向阶段条固定为：

```text
文件解析
→ 要求与评分
→ 响应规划
→ 标书编制
→ 审核与风险
→ 交接与递交
```

每个阶段使用以下状态之一：

```text
未开始
进行中
等待人工确认
已完成
已失效
阻断
```

当上游采购文件、澄清文件或已确认基线发生变化时，受影响阶段显示“已失效”，不能继续沿用旧版本结果。

#### 当前行动卡

页面最突出区域为“当前行动卡”，明确当前责任人需要处理的事项、数量、风险和下一入口。例如：

```text
当前需要：确认要求基线
3 条高风险要求未确认
2 条低置信度要求待处理
1 个复杂图表待人工确认
操作：进入要求与评分
```

总览只提供前往对应业务页面的操作，不直接放置四个人工关口的确认按钮，避免用户脱离证据和业务上下文完成确认。无操作权限的成员看到只读说明和责任人信息。

#### 摘要与项目动态

摘要区展示：

```text
文件版本
要求与评分覆盖
章节编制进度
阻断风险
待确认事项
运行任务
```

页面其余区域包括阻断和高风险事项、项目成员待办、最近变化与运行任务。最近变化只读取 `audit_event`、`workflow_run` 和业务版本记录等真实数据，不展示虚构的 Agent 活动或无法追溯的“智能体正在思考”信息。

#### Mock/API 初版契约

```http
GET /api/v1/projects/{project_id}/overview
```

响应包含：

```text
project
stage_progress
current_action
summary
blocking_items
member_tasks
recent_changes
running_tasks
allowed_actions
```

Mock 场景覆盖草稿项目、正在解析、等待要求基线确认、正在标书编制、存在阻断风险、即将截止、等待交接、已完成项目、输入版本失效和只读成员。

**选择原因**：阶段条提供稳定的项目全局位置，当前行动卡减少用户判断成本；将关口确认保留在对应业务页面，可以保证确认动作始终与证据、版本和风险上下文绑定。

### 4.11 文件与解析页面（已确认）

文件与解析页面负责采购文件及其版本的上传、解析、原文校对、人工修正和影响提示，不承担要求基线确认、风险关闭或标书生成。桌面端采用三栏校对工作台，使用户能同时查看文件上下文、原文定位和结构化结果；小屏按左侧抽屉、原文与结果上下切换实现，不删除风险和版本信息。

```text
左侧：文件与版本、解析目录、异常筛选
中间：原文件预览、页码定位、原文高亮和上下文
右侧：结构化结果、置信度、修正、复核与处理状态
```

#### 文件、版本与解析目录

左侧文件列表展示文件名称、类型、版本号、上传时间、状态、是否当前有效及是否已纳入解析。文件类型为主采购文件、澄清/更正/补遗、附件和投标文件格式模板；状态为 `PENDING_PARSE`、`PARSING`、`PARSED`、`PARTIALLY_PARSED`、`PARSE_FAILED`、`STALE` 与 `WAITING_HUMAN`，前端分别展示为待解析、解析中、解析完成、部分完成、解析失败、已失效和待人工处理。

澄清文件不覆盖原采购文件，而是通过版本关系和当前有效分析版本显示关联。例如：

```text
主采购文件 v1
    └── 澄清文件 v1
        └── 当前有效分析版本 v2
```

当新文件影响下游结果时，列表显示受影响要求、评分项、章节和审核结论数量，并进入影响明细。左侧解析目录固定提供全文、目录结构、资格条件、实质性要求、评审因素、时间节点、表格、图片与复杂图表和解析异常；选择目录后中间原文与右侧结果同步定位。

文件区允许的操作为查看原文件、上传新版本、上传澄清文件、重新解析、设为当前有效版本和查看版本影响。确认要求基线、关闭风险和生成标书等动作不放在此处。

#### 原文预览与结构化结果联动

中间区域以原始文件为唯一依据，统一提供 PDF、Word 转换预览和扫描图片的页码视图，支持缩放、页内搜索与翻页。右侧选中要求、表格或图表结果时，页面自动跳转到对应页并高亮原文区域；默认展示选区上下相邻段落或表格相邻行，防止脱离上下文判断。

高亮仅表达对象和处理状态：蓝色表示普通结构或事实、橙色表示低置信度解析、红色表示关键字段或冲突、绿色表示人工已核对/修正、灰色表示已失效版本。原文件始终只读；用户修正的是右侧结构化结果，原文区展示差异、来源定位和修正依据。历史文件查看时明确标记为“历史版本，不用于当前分析”。

右侧结果卡统一包含对象类型、文件与页码、原文定位、机器解析值、置信度和处理状态。对象类型覆盖正文、标题、表格、图片和复杂图表；处理状态覆盖未处理、已核对、已修正、待确认和解析失败。

不同内容使用针对性处理：正文和标题可修正文本、层级和分段；表格按单元格修正并保留表头、行列与合并单元格信息；普通图片可补充说明或标记为不参与业务提取；复杂图表显示 OCR、图表类型判断与多模态结果。多模态不可用、被数据出域策略拦截或结论低置信度时，保留原图和 OCR，转人工确认，不伪造解析结果。

可执行的处理动作为确认机器结果、提交修正、标记待人工确认、忽略非业务内容和重新解析当前区域。提交修正必须记录原值、修正值、修正人、时间和原因，不能覆盖机器原始结果。截止时间、资格条件、实质性要求、最高限价、评分分值和格式签章要求属于关键字段；其修正需由投标经理或合规审核人员二次复核后，才能作为下游抽取依据。

右侧支持按全部、待人工处理、低置信度、关键字段、复杂图表、解析失败和已修正筛选。

#### 解析完成与人工关口边界

解析完成不等于已确认要求基线，流程边界为：

```text
文件与解析：解析、校对与关键字段处理
→ 要求与评分：抽取并组织资格、实质性、评分和时间要求
→ REQUIREMENT_BASELINE_CONFIRMATION：确认后续编制依据
```

普通低置信度内容可带风险标记进入“要求与评分”。关键字段未处理、解析失败，或可能影响要求/评分的复杂图表待确认时，不允许发起 `REQUIREMENT_BASELINE_CONFIRMATION`。

#### 新澄清文件与影响分析

上传澄清、更正或补遗文件后，系统创建新文件版本而不覆盖旧结果，并执行：

```text
上传新文件
→ 解析新版本
→ 对照当前有效文件与已确认结果
→ 标出受影响对象
→ 创建待办与失效标记
→ 跳转对应业务页面处理
```

页面顶部明确显示新文件及影响数量，例如“影响 6 条要求、2 个评分项、1 个已编制章节，当前要求基线已失效”。影响明细至少包含原来源与新来源、变更摘要、影响对象、处理状态、处理责任人与跳转目标。资格条件变化跳转要求与评分，章节引用变化跳转标书编制，旧审核结论转待复核而不删除历史。

#### 权限、任务与初版契约

所有项目成员可查看当前有效文件、原文、解析结果、版本关系和影响提示。编写与技术、报价职责成员可处理职责范围内的普通解析修正并标记待人工确认；投标经理可上传文件、发起重新解析、查看全部影响和指派处理责任人；商务与合规审核人员复核关键字段修正。资料管理员只有在被加入项目并承担相应项目职责时才处理项目采购文件；系统管理员仅查看配置与审计，不能替代项目成员进行业务确认。

上传、重新解析、OCR 和复杂图表识别均只创建异步任务并返回 `task_run_id`，页面轮询任务状态后刷新文件、目录和异常数量。失败时提供重试或转人工处理；多模态受策略拦截时展示策略原因并保留本地原图和 OCR。

```http
GET  /api/v1/projects/{project_id}/documents
POST /api/v1/projects/{project_id}/documents
GET  /api/v1/projects/{project_id}/documents/{document_id}/versions
GET  /api/v1/document-versions/{document_version_id}/parse-view
POST /api/v1/document-versions/{document_version_id}/reparse
POST /api/v1/document-segments/{segment_id}/corrections
POST /api/v1/document-corrections/{correction_id}/review
GET  /api/v1/projects/{project_id}/document-impact
```

Mock 场景覆盖新建项目未上传文件、解析中、解析完成无异常、普通低置信度待处理、关键字段待复核、复杂图表待人工确认、多模态被策略拦截、解析失败可重试、新增澄清导致下游失效和只读成员。

**选择原因**：三栏视图将来源、结果和操作放在同一工作面，降低人工校对的定位成本；版本关系和影响分析保证新澄清不会静默覆盖已确认结果；将第一个人工关口放在要求与评分页面，确保确认对象是可用于后续编制的业务基线，而非单纯 OCR 成功状态。

### 4.12 要求与评分页面（已确认）

要求与评分页面负责将当前有效采购文件中的要求、评分规则与待处理冲突组织为可确认的业务基线。页面只确认“采购文件要求什么、评分如何计算或关注什么”，不匹配企业实际证据、不生成响应矩阵、不预测实际得分，也不生成标书内容。

页面使用同一工作台的三个标签页：

```text
要求清单｜评分项｜冲突与待确认
```

每个标签页采用“左侧分类与数量、中间清单与筛选、右侧详情与来源”的骨架。评分项复用相同骨架，不另建独立页面；小屏将分类收进抽屉、详情改为抽屉或上下切换，但不得隐藏来源、风险或基线状态。

#### 要求清单

要求清单中央字段为类型、要求摘要、强制等级、后果、来源、置信度和状态。类型包括资格、实质性、技术、格式、时间、商务和其他；强制等级为必须满足、需要响应、建议响应和待判断；后果为可能废标、影响资格、影响评分、影响交付和仅作提示。状态使用 `DRAFT`、`PENDING_CONFIRMATION`、`CONFIRMED`、`WAITING_HUMAN` 和 `STALE`，前端对应草稿、待确认、已确认、待处理和已失效。

左侧只保留分类与数量。中间顶部支持按当前有效版本、强制等级、后果、置信度、状态、仅看待处理和仅看本次澄清影响筛选；默认排序为可能废标、影响资格、高风险未确认、低置信度、截止时间临近和其余要求。

右侧详情展示标准化要求、判断摘要、原文上下文、关联文件版本、置信度、冲突提示和变更历史。允许确认要求、退回重新抽取、标记待人工判断、合并重复项、拆分为多条要求和查看相关评分项。确认或修改只更新结构化要求记录，不能修改采购文件原文。

资格、实质性、截止时间、格式签章等关键要求必须逐条确认。低风险同类要求允许基于筛选结果批量确认，但确认前必须展示数量、共同来源范围和审计摘要。

#### 评分项

评分项字段为评分维度、分值、评分条件摘要、评分方式、需要的证明材料、来源、置信度和状态。证明材料只表示采购文件要求的材料类型，不在本页判断企业是否已经具备材料。

评分方式使用：

```text
OBJECTIVE：客观可核验
SUBJECTIVE：主观评审
FORMULA：可确定性计算的公式型评分
MIXED：客观与主观混合
UNKNOWN：无法明确判断
```

详情区显示评分项名称与所属评分表、总分/子项分值、完整条件、评分方式、材料要求、是否可确定性计算、原文定位与上下文、以及与其他评分项的重叠或冲突。公式型评分只保存原始公式、变量含义和解析结果；单位、区间、上下限或比较基准不能确定时必须标记待确认。主观评分项只保存覆盖目标和评分关注点，后续不得输出预计得分。

评分项可关联多个要求项，表达同一采购规则同时具有资格、实质性或评分含义；该关系不表示企业已经满足。允许确认评分项、退回重新抽取、标记规则歧义、拆分子评分项、合并重复评分项和关联已有要求项。分值、公式、报价评分规则、门槛条件或材料要求的修正必须逐条确认，不能批量确认。

#### 冲突与待确认

冲突与待确认集中展示不能静默带入要求基线的问题，包括跨文件冲突、澄清覆盖、低置信度关键字段、重复或矛盾要求、评分表与正文不一致、公式/分值/材料规则不完整和人工退回重新抽取。

列表字段为风险级别、问题摘要、影响对象、来源文件与页码、发现原因、当前状态、责任人和处理动作。状态为 `PENDING`、`IN_PROGRESS`、`WAITING_HUMAN`、`RESOLVED`、`WAIVED` 和 `STALE`，前端展示待处理、处理中、等待人工判断、已解决、已豁免和已失效。

“已豁免”只可记录规则解释或处理方式的业务决定，不能豁免采购文件中的资格、实质性或法定要求；这类要求无法满足时必须继续阻断或进入后续项目决策处理。跨文件冲突应并排展示来源、版本与覆盖关系；规则歧义由投标经理或合规审核人员给出处理结论，无法确定时保持阻断，系统不得自行解释。

澄清、补遗或采购文件版本更新后，系统创建新的待确认结果版本，旧 `Requirement Baseline` 标记 `STALE`，不覆盖历史基线。

#### 第一个人工关口：要求基线确认

页面顶部固定展示基线状态：

```text
草稿
→ 待确认
→ 已确认
→ 已失效
```

只有同时满足以下条件时，才允许投标经理发起 `REQUIREMENT_BASELINE_CONFIRMATION`：

```text
当前有效采购文件已解析
关键字段已处理并完成必要复核
影响要求或评分的复杂图表已处理
冲突与待确认中没有阻断项
要求与评分项均可定位到来源
```

发起确认时生成只读基线确认摘要，包含当前有效文件版本、要求总数及分类统计、评分项总分与维度统计、关键要求与关键评分规则、仍带标记的普通低置信度事项、确认人、确认时间和备注。投标经理负责完成确认；合规审核人员可以协助复核，但不能代替投标经理通过该关口。确认成功后创建新的只读 `Requirement Baseline`，下游响应规划只读取已确认且未失效基线。

#### 权限、接口与 Mock 契约

投标经理可确认要求基线、处理跨文件冲突和分派责任人；编写人与技术方案人员可查看要求、提出修正并处理职责范围内普通项；商务与合规审核人员可复核资格、实质性、格式、时间和评分规则；报价人员可查看商务/报价要求并提出报价规则修正，但不能确认完整基线；资料管理员只查看来源与材料要求；只读成员只能查看。

```http
GET  /api/v1/projects/{project_id}/requirements
GET  /api/v1/projects/{project_id}/scoring-items
GET  /api/v1/projects/{project_id}/requirement-conflicts
GET  /api/v1/requirements/{requirement_id}
PATCH /api/v1/requirements/{requirement_id}
POST /api/v1/requirements/{requirement_id}/merge
POST /api/v1/requirements/{requirement_id}/split
POST /api/v1/requirement-baselines/validation
POST /api/v1/requirement-baselines/confirmation
GET  /api/v1/projects/{project_id}/requirement-baselines/current
```

`validation` 校验基线确认前置条件，`confirmation` 创建新的已确认基线；已确认基线不可直接编辑，只能通过新版本或重新确认演进。Mock 场景覆盖抽取完成无异常、普通低置信度、高风险待确认、评分公式完整、评分规则歧义、跨文件截止时间冲突、澄清导致基线失效、存在阻断项不可确认、基线可确认、已确认基线只读和只读成员。

**选择原因**：将要求、评分与异常放入同一工作台，既保留采购规则的完整视图，也能聚焦需要人工判断的问题；以来源、版本和关口条件约束基线确认，可防止不完整或过期的采购规则驱动下游响应规划与章节生成。

### 4.13 响应规划页面（已确认）

响应规划页面将已确认且未失效的 `Requirement Baseline` 转换为响应矩阵、评分覆盖、证据候选、章节任务、责任人、报价依赖和缺口任务。页面不修改要求基线、不生成正式章节、不自动确认企业满足资格、不确认最终报价。

页面使用“响应矩阵｜评分覆盖｜章节与任务｜缺口与冲突”四个标签页，统一采用左侧分类/章节与状态数量、中间清单、右侧要求原文/证据候选/处理记录的布局。

响应矩阵至少展示要求、响应方式、目标章节、证据状态、责任人、截止时间、状态和阻断原因。响应方式限定为 `DIRECT_RESPONSE`、`EVIDENCE_RESPONSE`、`FORM_RESPONSE`、`QUOTE_RESPONSE`、`DECLARATION_RESPONSE`、`MANUAL_ATTACHMENT`、`NOT_APPLICABLE`、`EVIDENCE_MISSING`、`CONFLICT` 和 `WAITING_CONFIRMATION`；`NOT_APPLICABLE` 必须填写理由并逐条确认。

证据候选展示材料名称、主体、有效期、适用范围、匹配理由、来源版本和权限状态。语义相似只能形成候选，用户必须明确确认使用、拒绝使用或创建补充材料任务。主观评分只展示覆盖状态，不预测得分；公式型评分仅在输入完整且证据已确认时展示确定性测算。章节计划记录负责人、关联要求与评分项、证据、报价依赖、历史参考、截止时间和阻断事项。

仅当高风险要求响应方式、不适用理由、关键证据用途、评分项映射、缺失材料任务、章节负责人、报价依赖和规划阻断均处理完成时，投标经理才能发起 `RESPONSE_PLAN_CONFIRMATION`。确认后生成只读 `Response Plan Baseline`。

PATCH /api/v1/response-matrix-entries/{entry_id}

PUT   /api/v1/projects/{project_id}/chapter-plan
PUT   /api/v1/projects/{project_id}/work-assignments

POST /api/v1/response-plan-baselines/confirmation
```

Mock 覆盖无要求基线、规划中、证据充分、证据缺失、报价未确认、规划冲突、可确认、已确认只读、输入失效和只读成员。

### 4.14 标书编制页面（已确认）

标书编制页面依据已确认 `Response Plan Baseline` 编写章节草稿、引用、表格、图表和附件提示。页面不修改响应计划、不编造证据、不通过审核、不直接生成最终交接文件。

页面采用左侧章节目录/负责人/状态，中间结构化章节编辑器，右侧要求、评分项、证据、历史参考和生成记录。顶部展示当前草稿版本、基线版本、编制进度、引用警告、待补充项和版本冲突。

章节由标题、段落、列表、表格、图表、报价数据、证据引用、附件提示、待补充占位和内部提示等结构化内容块组成。每个内容块记录来源、创建方式、版本、编辑人、锁定状态和是否允许外发。

页面支持生成章节草稿、编辑内容块、插入确认资料和报价字段、生成图表、局部重新生成、查看版本差异和提交章节完成。企业事实、人员、业绩、报价和技术参数必须引用有效来源；无证据时创建待补充项；历史标书只用于结构和表达；人工编辑默认锁定，局部重生成不得静默覆盖；报价未确认时仅显示占位；图表必须记录数据来源。

提交编辑使用乐观锁。版本过期时并列展示用户修改、最新版本和冲突内容，由用户选择保留、采用最新或人工合并。

GET  /api/v1/sections/{section_id}/versions
POST /api/v1/chapter-draft-baselines/validation

```

Mock 覆盖未生成、生成中、正常编制、无来源、报价待确认、引用失效、人工锁定、版本冲突、可确认和已确认只读。

### 4.15 审核与风险页面（已确认）

审核与风险页面对已确认章节草稿执行资格合规、评分覆盖、商务报价、技术响应、格式签章、跨章节一致性和引用有效性复核，形成结构化问题与风险闭环。页面不自动接受风险，不允许编写人关闭自己的问题。

页面使用“审核总览｜审核问题｜风险清单｜一致性检查”标签页，采用左侧审核域/风险等级/状态数量，中间问题清单，右侧来源、影响内容和处理记录的布局。

审核问题记录审核域、问题类型、风险等级、描述、来源要求、影响章节、责任人、整改状态和审核轮次。状态为待处理、整改中、待复核、已关闭、已驳回和已失效。流程为审核人提出问题、章节责任人修改或说明、原审核人复核、关闭或重新打开。商务审核与合规审核只能关闭各自审核域的问题。

## 五、后端与工作流技术方案

### 5.1 FastAPI（已确认）

**承担职责**：REST API、认证授权、领域服务、状态转换、任务创建、人工确认、文件签名地址和 OpenAPI 契约。

**实现方式**：

- 按 `projects`、`documents`、`requirements`、`evidence`、`chapters`、`reviews`、`workflows`、`handoffs` 等模块组织；
- Pydantic 模型定义 API 输入输出和 Agent 结构化 Schema；
- SQLAlchemy 与 Alembic 管理数据访问和迁移；
- API 只创建长任务并返回任务 ID，不在请求线程执行 OCR 或 Agent；
- 权限在依赖层与领域服务双重校验；
- 所有状态变化经过领域服务，不允许路由直接更新状态字段。

**选择原因**：Python 与 LangGraph、Celery、文档解析和 AI 生态一致；OpenAPI 自动生成有利于契约驱动；异步 API 适合文件和任务状态接口。

**未采用**：Django 功能完整但框架较重；Node.js 后端会造成 AI 与解析代码跨语言维护。

### 5.2 LangGraph（已确认）

**承担职责**：Agent 工作流图、节点条件、人工中断、恢复、重试策略选择和共享运行状态。

**实现方式**：

- 以状态节点和条件边表达合法执行路径；
- 使用 Checkpoint 保存运行控制状态，但业务正文只保存 ID 引用；
- 人工关口使用 interrupt/resume 语义；
- 每次恢复重新校验项目状态、输入基线和权限；
- Agent 节点输出必须通过 Pydantic Schema 校验；
- 工作流运行与 `agent_run`、`task_run`、`audit_event` 关联。

**选择原因**：显式状态图适合本项目的大量人工中断、版本失效和恢复路径；比自由对话式多 Agent 更容易测试、审计和解释。

**未采用**：CrewAI 更适合角色协作演示，但复杂状态与人工关口控制较弱；自研状态机需要重复实现持久化和中断机制。

#### 5.2.1 单主图编排与 Agent 节点（已确认）

V1 采用：

> **一张持久化 LangGraph 主图 + Supervisor 路由节点 + 四个专业 Agent 受控节点。**

V1 不为五个 Agent 分别建设五套独立工作流，也不提前把四个专业 Agent 拆成嵌套子图。某个专业 Agent 只有在内部出现多个稳定阶段、独立人工中断或独立恢复需求后，才升级为受限子图。

**总体执行路径**：

```text
开始或恢复
→ 加载 PostgreSQL 业务状态
→ 校验权限、有效版本和输入基线
→ Supervisor 路由
→ 招标理解与合规 Agent
→ REQUIREMENT_BASELINE_CONFIRMATION
→ 响应规划与评分 Agent
→ RESPONSE_PLAN_CONFIRMATION
→ 标书编制 Agent
→ CHAPTER_DRAFT_CONFIRMATION
→ 质量与风险复核 Agent
→ REVIEW_RESULT_CONFIRMATION
→ 确定性交接门禁
→ 允许进入 READY_FOR_HANDOVER
```

**职责边界**：

- Supervisor 只输出结构化下一动作和目标 Agent，不直接修改项目主状态；
- LangGraph 表达节点顺序、条件分支、人工中断和恢复位置；
- 确定性状态机与领域服务校验权限、前置条件和状态转换合法性；
- Celery 负责排队并在 Worker 中执行或恢复主图，不承担 Agent 路由和业务状态判断；
- PostgreSQL 保存项目、基线、Agent 产物、任务、人工确认和审计事件，是唯一业务事实源；
- LangGraph Checkpoint 只保存运行控制字段和业务对象 ID，不保存完整要求、证据、章节或审核正文。

**人工中断粒度**：V1 采用阶段级中断，不为单条要求、证据、章节或风险分别创建 LangGraph 中断。四个业务阶段各最多存在一个当前人工关口：`REQUIREMENT_BASELINE_CONFIRMATION`、`RESPONSE_PLAN_CONFIRMATION`、`CHAPTER_DRAFT_CONFIRMATION` 和 `REVIEW_RESULT_CONFIRMATION`。具体条目的确认、修改、驳回和备注逐条保存在 PostgreSQL，并由前端批量处理；LangGraph 只记录当前处于哪个人工关口。用户提交“确认并继续”后，领域服务先检查该阶段所有必确认项、权限、版本和门禁，全部通过才允许恢复工作流。

**选择原因**：阶段级中断保留逐项确认与审计，同时避免一个项目因数十或数百条业务数据产生同等数量的 Checkpoint、恢复请求和图状态分支。

**最小共享状态**：V1 将 LangGraph Checkpoint 中的共享状态固定为七个运行控制字段：

```text
WorkflowState
├── workflow_run_id
├── project_id
├── current_stage
├── pending_gate
├── active_agent_run_id
├── retry_count
└── last_error_code
```

| 字段 | 说明 |
|---|---|
| `workflow_run_id` | 一次绑定确定输入版本的端到端编排运行 |
| `project_id` | 所属投标项目 |
| `current_stage` | 当前业务阶段，不等同于项目主状态 |
| `pending_gate` | 当前等待的阶段级人工关口，无人工中断时为空 |
| `active_agent_run_id` | 当前或最近一次专业 Agent 运行记录 |
| `retry_count` | 当前节点的有限重试次数 |
| `last_error_code` | 最近一次标准化错误代码，无错误时为空 |

`thread_id` 不重复进入 State，LangGraph 运行配置直接使用 `thread_id = workflow_run_id`。Supervisor 的 `next_action` 只作为当前路由节点的临时结构化输出；人工恢复请求的幂等标识保存在接口幂等记录和审计事件中，不进入长期图状态。

V1 不单独建设 `workflow_input_snapshot` 表。一次运行所依赖的业务版本统一保存在 PostgreSQL 的 `workflow_run.input_refs` JSONB 中，并计算 `input_hash`：

```text
{
  document_version_ids: [],
  requirement_baseline_id: null,
  response_plan_id: null,
  evidence_scope_version: null,
  quote_version_id: null,
  chapter_version_ids: [],
  review_baseline_id: null,
  rule_set_version: null,
  model_config_version: null,
  prompt_config_version: null
}
```

字段允许按运行阶段为空，但已写入的输入引用在该次运行内不可静默修改。恢复前重新读取实际有效版本并计算哈希；与 `input_hash` 不一致时停止恢复，将旧运行标记为 `STALE` 或 `INVALIDATED`，再按影响范围创建新运行。

完整要求、证据、响应矩阵、章节、审核问题、阻断问题、人工确认明细和已完成任务列表均不进入共享状态，由节点根据 `workflow_run_id` 从 PostgreSQL 查询。

**选择原因**：七字段 State 足以回答“哪次运行、哪个项目、执行到哪里、是否等待人工、当前任务和错误情况”，把业务版本集合集中在 `workflow_run` 后，可以避免新增快照实体和频繁修改图状态结构。

**未采用**：不把完整业务正文放进 Checkpoint；不为每种基线和业务版本分别增加 State 字段；不采用只有 `workflow_run_id` 一个字段的极简方式，因为保留当前阶段、人工关口和错误信息有利于图路由、监控和故障诊断。

**统一节点契约**：V1 只建设五类顶层节点：

| 节点类型 | 职责 | 允许写入 |
|---|---|---|
| 加载校验节点 | 加载 `workflow_run.input_refs`，校验权限、状态、版本和 `input_hash` | 运行控制状态、标准化错误 |
| Supervisor 路由节点 | 根据业务事实输出下一步结构化调度决策 | 临时路由结果、运行控制状态 |
| 专业 Agent 节点 | 执行招标理解、响应规划、标书编制或质量复核 | PostgreSQL 业务产物、`agent_run`、运行控制状态 |
| 人工关口节点 | 使用 `interrupt` 暂停在四类阶段级人工关口 | `pending_gate`、审计事件 |
| 确定性门禁节点 | 校验阶段完成条件和交接条件 | 合法状态转换、门禁失败原因 |

所有节点接收同一个七字段 `WorkflowState`。需要业务正文时，节点根据 `workflow_run_id` 查询 PostgreSQL，不依赖上一个节点传递大对象。节点只返回发生变化的 State 字段，不重复返回未变化字段，也不通过 State 返回业务产物正文。

专业 Agent 节点的标准执行步骤为：

```text
读取 workflow_run 和 input_refs
→ 校验权限、输入版本和节点前置条件
→ 按幂等键查找或创建 agent_run
→ 执行 Skill、工具和模型调用
→ 校验结构化输出
→ 在事务边界写入业务产物、来源和审计
→ 返回少量 WorkflowState 更新
```

节点层统一使用五种 `NodeOutcome`：

| `NodeOutcome` | 含义 | 后续动作 |
|---|---|---|
| `CONTINUE` | 当前节点成功，可沿条件边继续 | 进入下一节点 |
| `WAITING_HUMAN` | 已进入阶段级人工关口 | 保存 Checkpoint 并暂停 |
| `RETRY` | 发生允许自动重试的临时错误 | 由 Celery 有限重试 |
| `BLOCKED` | 当前运行不能自动继续 | 转人工处理、修复输入或新建运行 |
| `COMPLETED` | 本次主图运行正常结束 | 完成 `workflow_run` |

`NodeOutcome` 是图执行层结果，不替代 Supervisor 已确认的业务调度决策。两者映射如下：

| Supervisor 决策 | 通常映射的 `NodeOutcome` |
|---|---|
| `DISPATCH_AGENT` | `CONTINUE` |
| `WAITING_HUMAN` | `WAITING_HUMAN` |
| `RETRY_TASK` | `RETRY` |
| `EXPAND_REVIEW_SCOPE` | 完成范围更新后 `CONTINUE` |
| `INVALIDATE_OUTPUTS` | 完成确定性失效处理后 `CONTINUE`；当前输入已失效时为 `BLOCKED` |
| `BLOCK_WORKFLOW` | `BLOCKED` |
| `COMPLETE_STAGE` | 中间阶段为 `CONTINUE`，最终阶段为 `COMPLETED` |

节点允许更新 `current_stage`、`pending_gate`、`active_agent_run_id`、`retry_count` 和 `last_error_code`；`workflow_run_id` 与 `project_id` 在一次运行内不可修改。临时模型限流、网络超时和可恢复 Worker 异常可以返回 `RETRY`；权限不足、输入版本变化、业务前置条件缺失、人工确认未完成和结构化输出持续失败必须返回 `BLOCKED` 或 `WAITING_HUMAN`，不得无限自动重试。

**选择原因**：五类节点覆盖 V1 的加载、路由、专业处理、人工确认和确定性门禁；五种执行结果足以表达继续、暂停、重试、阻断和结束。统一契约便于单元测试、运行监控和未来将专业节点替换为子图。

**V1 边界**：不建设通用工作流 DSL、动态节点注册平台、跨项目图编排或允许模型自由新增节点。节点图和条件边由代码显式定义，业务变化通过版本化规则、节点实现和数据库输入表达。

**人工确认与恢复 API**：V1 不为四个人工关口分别建设四套接口，也不向前端暴露可绕过业务门禁的通用 LangGraph `resume` 接口。统一提供一个关口查询接口和一个关口动作接口。

```http
GET /api/v1/workflow-runs/{workflow_run_id}/pending-gate
```

返回当前 `gate_type`、`current_stage`、`input_hash`、当前用户可执行动作、必确认项总数、已完成数、阻断原因和 `can_continue`。要求、证据、章节和风险明细仍通过对应业务资源接口查询，不塞入关口响应。

```http
POST /api/v1/workflow-runs/{workflow_run_id}/pending-gate/actions
Idempotency-Key: <client-generated-key>
```

请求只包含 `gate_type`、`action`、`expected_input_hash` 和可选 `reason`。`action` 固定为：

- `CONFIRM_AND_CONTINUE`：确认当前阶段并申请继续执行；
- `RETURN_FOR_REWORK`：记录退回原因，由后端影响规则决定返回的最早阶段。

前端不能提交任意目标节点。修改或驳回单条要求、调整证据用途、修改章节以及处理风险，继续调用对应业务对象接口；关口动作只负责阶段级确认和流程推进。

**确认并继续的事务流程**：

```text
校验用户、项目和角色权限
→ 锁定 workflow_run
→ 校验当前 pending_gate 与请求 gate_type 一致
→ 校验 Idempotency-Key
→ 比较 expected_input_hash
→ 检查必确认项、阻断问题和阶段门禁
→ 写入阶段确认记录与 audit_event
→ 清空 pending_gate
→ 创建 QUEUED task_run
→ 提交 PostgreSQL 事务
→ 投递 run_workflow(workflow_run_id)
→ 返回 202 Accepted
```

PostgreSQL 事务提交前不投递 Celery 消息。V1 不新增独立 Outbox 表，`task_run` 本身承担轻量可靠投递记录：接口提交后立即尝试投递；若 Redis 或 Celery 不可用，`task_run` 保持 `QUEUED`，定时恢复任务扫描超时未投递记录并重新发布。Worker 按 `task_run` 幂等键和 `workflow_run_id` 去重。

相同 `Idempotency-Key`、同一用户和同一工作流的重复请求返回首次处理结果，不重复创建阶段确认、审计事件或恢复任务。相同键但请求体不同返回 `409 Conflict`。

**退回返工流程**：领域服务记录原因，根据对象依赖和影响范围确定最早受影响阶段，将相应下游产物标记为 `STALE`，清除当前关口并创建恢复任务。仅业务结果需要修正且输入版本未变化时继续使用同一个 `workflow_run`；采购文件、报价或其他关键输入版本变化时停止旧运行并创建新运行。

**主要响应语义**：

| HTTP 状态 | 场景 |
|---|---|
| `200 OK` | 查询关口成功，或幂等重复请求返回首次结果 |
| `202 Accepted` | 关口动作已可靠记录，等待异步恢复 |
| `403 Forbidden` | 当前用户无该关口操作权限 |
| `404 Not Found` | 工作流不存在或当前用户不可见 |
| `409 Conflict` | 关口不匹配、输入哈希变化、运行已恢复或幂等键冲突 |
| `422 Unprocessable Content` | 必确认项未完成、存在阻断问题或退回原因不符合规则 |

**选择原因**：统一业务动作接口避免四套重复逻辑；后端门禁阻止前端直接恢复图；`expected_input_hash`、行锁和幂等键处理并发与重复点击；使用已有 `task_run` 进行失败补投，在不引入额外消息基础设施的情况下覆盖 V1 的可靠恢复要求。

**运行数据模型**：V1 使用四类职责明确的运行记录，不把工作流、Agent、Celery 任务和人工动作塞入同一张通用表：

```text
bid_project
    ↓
workflow_run
    ├── agent_run
    ├── task_run
    └── workflow_gate_action
             ↓
         audit_event
```

- `workflow_run`：一次绑定确定输入版本的端到端主图运行，保存运行状态、当前阶段、人工关口、`input_refs`、`input_hash` 和历史派生关系；
- `agent_run`：Supervisor 或某个专业 Agent 的一次真实调用，保存 Agent 类型、阶段、输入输出引用、模型与提示词版本、幂等键和错误；
- `task_run`：工作流执行、解析、OCR、Embedding、多模态分析、导出和失败补投等异步或确定性任务；
- `workflow_gate_action`：阶段级 `CONFIRM_AND_CONTINUE` 或 `RETURN_FOR_REWORK` 动作，保存操作人、角色、输入哈希、幂等键、结果和恢复任务。

`agent_run` 不再同时表示 Agent 和工具任务。原数据字典中的 `DOCUMENT_PARSE`、`RAG_RETRIEVAL` 等运行类型迁移到 `task_run.task_type`；只有真实 Agent 调用进入 `agent_run`。单条要求、证据、章节和风险的确认状态继续保存在各自业务表中，`workflow_gate_action` 只记录整个阶段的推进或退回。

**关键约束**：

- `workflow_run.id` 直接作为 LangGraph `thread_id`；
- 一个运行内 `project_id` 不可修改，输入引用不得静默覆盖；
- `agent_run` 的幂等键约束同一输入和同一阶段只能形成一个有效产物版本；
- `task_run` 使用 `queued_at`、`dispatched_at` 和 `celery_task_id` 区分“数据库已记录”和“消息已发布”；
- `workflow_gate_action` 对 `(workflow_run_id, actor_user_id, idempotency_key)` 建立唯一约束；
- 所有表保存对象引用，不保存文件正文和大段 Agent 输出；
- 状态变更同时写入 `audit_event`，但审计事件不代替当前状态表。

**选择原因**：四类记录分别回答“整条流程怎样”“哪个 Agent 做了什么”“后台任务是否真正执行”“人工在关口做了什么”。继续压缩会混淆状态语义；继续增加节点运行表、通用事件表和独立 Outbox 则超出 V1 需要。

**权威字段定义**：详见 `10-核心业务对象与数据字典.md` 第 9.4 至 9.7 节。

**Celery 与 LangGraph 的调用方式**：

- FastAPI 创建或恢复 `workflow_run` 后，统一提交 `run_workflow(workflow_run_id)`；
- Celery Worker 加载对应 Checkpoint，从当前节点继续执行，直到正常完成、失败或触发人工中断；
- 人工确认接口写入确认记录并重新提交同一个 `workflow_run_id`；
- V1 不实现“LangGraph 节点发布 Celery 子任务、Celery 再回调 LangGraph”的双层调度；
- 文档解析、OCR、Embedding 和导出等独立技术任务仍可使用普通 Celery 任务，但其完成状态通过 PostgreSQL 供主图读取。

**返工和局部回退**：

- 要求抽取错误返回招标理解与合规阶段；
- 评分映射、证据用途或章节规划错误返回响应规划与评分阶段；
- 章节内容、引用或承诺问题返回标书编制阶段；
- 复核问题按影响范围返回规划或编制阶段，再重新进入质量复核；
- 返回前由确定性影响规则使受影响的下游产物进入 `STALE`，不得由 Supervisor 自行推断并覆盖有效产物。

**版本变化和恢复规则**：

- 每次恢复必须重新校验项目状态、用户权限、文件版本、要求基线、响应计划、报价版本、章节版本和审核基线；
- 采购文件或关键输入版本变化后，当前 `workflow_run` 标记为 `STALE` 或 `INVALIDATED`，创建绑定新输入的新运行；
- 不倒带并改写旧 Checkpoint，旧运行、旧产物和旧人工确认继续保留用于审计；
- 新运行从确定性影响规则计算出的最早受影响阶段开始，可复用仍然有效且输入哈希一致的上游结果；
- 节点使用幂等键检查已有 `agent_run` 和产物，Celery 重投不得重复生成同一版本。

**运行标识映射**：

- `project_id` 标识业务项目；
- `workflow_run_id` 标识一次绑定确定输入版本的端到端编排运行；
- LangGraph `thread_id` 使用 `workflow_run_id`，避免一个项目的多次运行共享同一 Checkpoint；
- `agent_run_id` 标识一次专业 Agent 调用；
- `task_run_id` 标识一次 Celery 或确定性工具执行；
- `agent_run` 和 `task_run` 均关联 `workflow_run_id`、输入版本、输出版本和幂等键。

**选择原因**：单主图保留人工中断、状态恢复和完整审计能力，同时避免巨型图和五套独立工作流带来的维护成本；Agent 先作为普通节点也更适合 V1 的开发规模，后续可以在不改变顶层接口的情况下升级为子图。

**未采用**：巨型图会把解析、工具、Agent 和所有业务细节混在同一层；五个独立图需要额外处理跨图事件、Checkpoint 协调和版本失效；V1 预先拆嵌套子图没有足够的真实复杂度依据。

**V1 边界与失败降级**：V1 只建设一张业务主图和统一恢复入口。临时网络、模型限流和 Worker 异常由 Celery 有限重试；结构化输出持续失败、权限变化、版本冲突或超过重试上限时进入人工处理或阻断。若 Checkpoint 不可恢复，以 PostgreSQL 中的 `workflow_run`、`agent_run`、输入基线和审计记录重建新运行，不把 Redis 或 Checkpoint 当作最终恢复依据。

### 5.3 Celery + Redis（已确认）

**承担职责**：解析、OCR、Embedding、重排、Agent 运行、文档导出等长任务的排队、执行和重试。

**实现方式**：

- Redis 作为 Broker，Celery Worker 消费任务；
- PostgreSQL 的 `task_run` 保存最终任务状态、进度、输入版本、输出版本、失败原因和重试次数；
- Celery 状态只用于运行期辅助，不能覆盖 PostgreSQL 业务状态；
- 网络超时和限流采用指数退避；
- 权限错误、版本冲突和结构化输出持续失败不自动无限重试；
- 使用幂等键防止消息重复投递造成重复产物；
- Worker 重启后根据数据库状态识别未完成、失效或需要人工接管的任务。

**选择原因**：生态成熟、支持多个 Worker、重试和任务状态，适合 Python AI 与文档任务；避免在 FastAPI 请求中执行耗时操作。

**未采用**：自研 PostgreSQL 队列需要自行实现锁、抢占、心跳和超时；轻量队列更简单，但 Celery 的成熟度和资料更适合作品与旁路试用双重目标。

## 六、数据与存储技术方案

### 6.1 PostgreSQL（已确认）

**承担职责**：唯一核心业务数据库，保存用户、权限、项目、文件版本、要求、证据、报价、章节、Agent 运行、审核问题、基线和审计事件。

**实现方式**：

- 使用事务、外键、唯一约束和检查约束保护领域不变量；
- 核心对象包含组织、项目、创建人、时间和版本字段；
- 章节等可编辑对象使用版本号进行乐观锁；
- 项目级访问在后端强制过滤，必要时增加 PostgreSQL Row-Level Security 作为纵深防御；
- JSONB 只用于模型原始输出、可变扩展字段和评测详情，不代替核心关系模型；
- 使用 Alembic 管理可回滚的数据库迁移。

**选择原因**：项目需要强事务、复杂关联、版本和审计；单库能够让业务状态、权限和检索过滤保持一致。

**未采用**：SQLite 不适合多人试用、并发任务和可靠迁移；MongoDB 对强关系、状态约束和审计查询没有优势。

### 6.2 pgvector（已确认）

**承担职责**：在 PostgreSQL 内保存文本向量并执行企业证据、采购文件和历史片段的语义检索。

**实现方式**：

- 文本块表同时保存 `content`、来源、版本、权限、有效性和 `embedding`；
- 查询先执行项目、主体、版本、权限和有效期过滤，再进行向量相似度排序；
- 初期数据量小可使用精确检索，规模增长后增加 HNSW 索引；
- 向量结果与 PostgreSQL 全文检索候选合并，再进入重排；
- 文件或证据失效时，在同一事务边界更新可检索状态。

**选择原因**：避免 Chroma 与业务库之间出现版本、权限和删除同步问题；V1 数据规模不需要独立向量数据库。

**未采用**：Chroma 原型轻，但需要维护双库一致性；Qdrant 和 Milvus 更适合更大规模或独立检索服务，V1 复杂度过高。

### 6.3 MinIO（已确认）

**承担职责**：原始招标文件、企业材料、页面图片、解析中间产物、章节附件和导出文件。

**实现方式**：

- 使用 S3 兼容接口和私有 Bucket；
- PostgreSQL 保存对象键、哈希、大小、MIME、业务版本和权限，不保存大文件正文；
- 上传和下载通过 FastAPI 生成短时签名地址；
- 对象键按组织、项目、对象类型和版本组织；
- 删除业务对象时优先逻辑失效，物理清理通过受控后台任务执行；
- PostgreSQL 备份和 MinIO 对象备份必须保持可恢复对应关系。

**选择原因**：文件与数据库解耦、S3 接口标准、可本地 Docker 部署，并可在未来替换为云对象存储。

**未采用**：直接保存服务器本地目录不利于容器迁移、签名访问和后续扩展；数据库大对象会增加备份和查询负担。

### 6.4 Redis（已确认边界）

Redis V1 只承担 Celery Broker、可重建缓存、限流计数和短期分布式锁，不保存业务事实，不成为工作流状态数据库。

#### 可缓存内容

- 检索候选结果：Key 必须绑定 `project_id`、知识范围、文件版本、要求基线、查询哈希和检索配置版本；
- 查询 Embedding：Key 必须绑定 Embedding 模型版本和标准化查询哈希；
- 草稿预览结果：只缓存临时对象引用，不缓存最终交接状态；
- 限流计数、短期锁和 Celery 临时投递信息。

缓存 Key 包含项目、版本、模型或配置版本后，输入版本变化会自然产生新 Key，不依赖复杂的全局主动失效。所有缓存都必须设置 TTL，并允许随时丢失和重建。

#### 不以 Redis 为事实源的内容

```text
project_status
pending_gate
permission_result
input_hash
quote_version
citation_validity
workflow_run state
task_run final status
agent_run
audit_event
```

这些内容始终以 PostgreSQL 为准。幂等性依赖 PostgreSQL 唯一约束和事务，Redis 锁只能减少并发，不替代数据库校验。

#### Redis 故障降级

- Broker 暂时不可用：任务保持 `QUEUED`，由恢复任务重新投递；
- 缓存不可用：直接读取 PostgreSQL、pgvector 或重新执行 CPU 推理；
- 限流计数不可用：退化为应用级保护，不改变业务状态；
- 短期锁不可用：由数据库行锁、唯一约束和幂等键兜底；
- Redis 恢复后不得把旧缓存直接视为最新业务状态。

Redis 故障允许性能下降，但不能改变人工关口、项目状态、版本有效性、任务最终状态和审计结果。

#### 敏感内容缓存边界

Redis 检索缓存只保存来源引用、文件版本、召回路线、词法/向量/RRF/重排分数和过期时间，不保存完整企业证据、招标文件或章节正文。命中缓存后仍必须回 PostgreSQL 校验用户权限、项目归属、文件版本、有效期、保密等级和引用状态，再从 PostgreSQL 或 MinIO 读取原文。

Redis 允许保存查询 Embedding、结果 ID、排序分数和必要的脱敏短摘要；禁止保存完整企业证据、身份证件与联系方式、报价明细、完整章节、内部审核意见和权限判断最终结果。查询缓存不得保存原始敏感查询文本，Key 使用带模型版本的标准化查询哈希。

默认 TTL：检索和重排结果 5～15 分钟，脱敏短摘要不超过 15 分钟，查询 Embedding 30 分钟至 24 小时；具体值根据内存和命中率调整。任何权限或版本校验失败都必须丢弃缓存并重新检索。

## 七、文档解析技术方案

### 7.1 统一 Document IR（已确认）

V1 不建设完整的通用文档结构平台。统一 Document IR 压缩为以下关系：

```text
document_version
真实文件版本
    ↓
document_parse
一次解析结果
    ↓
document_page
页面文本和页面图片
    ↓
document_segment
章节、段落、表格或图表区域

document_correction
针对 Segment 的人工修正覆盖层
```

`document_segment` 继续作为要求抽取、检索、引用和原文定位的稳定业务来源单元；`document_parse`、`document_page` 和 `document_correction` 是解析技术支撑对象，不取代既有文件和业务对象。

#### 7.1.1 `document_parse`

记录同一 `document_version` 的一次解析结果：

```text
id
document_version_id
parser_name
parser_version
parse_config_json
status
quality_score
raw_artifact_key
created_by_task_id
created_at
```

状态使用 `PENDING`、`RUNNING`、`WAITING_HUMAN`、`SUCCEEDED`、`FAILED` 或 `STALE`。同一文件更换解析器或重新解析时创建新的 `document_parse`，不产生新的文件版本，也不覆盖旧解析结果。

#### 7.1.2 `document_page`

每个物理页面保存：

```text
id
parse_id
page_no
printed_page_label
text
image_key
ocr_used
quality_score
status
```

`page_no` 表示 PDF 或文件中的物理页码；`printed_page_label` 表示页面正文印刷的页码。页面图片存入 MinIO，用于原文对照、坐标高亮和人工修正。

#### 7.1.3 `document_segment`

V1 的主要解析与引用对象沿用既有 `document_segment`，补充以下技术字段：

```text
parse_id
page_id
segment_type
section_path
content_text
char_start
char_end
source_bbox
source_hash
metadata_json
confidence
segment_status
```

`segment_type` 只保留 `HEADING`、`PARAGRAPH`、`LIST`、`TABLE`、`TABLE_ROW`、`FIGURE` 和 `OTHER`。表格行列、视觉解释、解析器特有结果和其他扩展信息放入 `metadata_json`，V1 不拆完整节点树和单元格表。

Segment 必须绑定文件版本、解析记录、物理页码及可用的字符或坐标范围。要求、评分项、证据引用和审核问题应引用 `segment_id`，高风险结论不能只保存页码。`source_hash` 用于校验引用原文是否仍匹配。

#### 7.1.3.1 语义切片与检索过滤（已确认）

切片优先按标题及正文、自然段落、列表项、表格逻辑区域或表格行、资格/评分/否决等规则单元、图表 OCR 文本与多模态摘要形成完整语义单元。只有语义单元过长时，才按句子或段落继续拆分；不以固定 Token 数作为首要边界。

`parent_segment_id` 表达章节、列表和表格内部的轻量父子关系，不扩展为通用节点树。表格和图表的详细结构继续保存在 `metadata_json`。

检索前必须应用：

```text
project_id
knowledge_scope
document_version_id
document_status
effective_from
effective_to
organization_scope
confidentiality_level
segment_type
```

这些字段从所属项目、文件版本、知识资料和证据对象解析，不要求全部冗余写入 `document_segment`。权限、版本、有效期和保密范围在召回前过滤，不能交给模型事后判断。

`knowledge.validate_citations` 校验片段存在、版本有效、`source_hash` 匹配、页码与章节一致、引用文本属于该片段且引用用途允许。文件版本变化或来源哈希不匹配时，旧引用和依赖结果标记为 `STALE`，重新检索后才能恢复使用。

#### 7.1.4 `document_correction`

人工修正作为覆盖层保存，不直接改写原始解析文本：

```text
id
segment_id
original_content
corrected_content
reason
status
created_by
created_at
reviewed_by
reviewed_at
```

状态使用 `PROPOSED`、`CONFIRMED` 和 `REJECTED`。系统读取 Segment 时，存在已确认修正则使用 `corrected_content`，同时保留原始内容和完整审计记录。

#### 7.1.5 表格、图表与检索

- 普通表格保存原始区域图片、Markdown 或 HTML、简单行列 JSON、页码和坐标，不在 V1 建独立单元格关系表；
- 复杂图表的 OCR 文本、视觉类型、多模态解释和确认状态保存在 `document_segment.metadata_json`；
- V1 直接在 `document_segment` 上保存词法检索字段和向量；
- 后续只有在切块策略、Embedding 版本或数据规模确实需要独立治理时，才拆出 `retrieval_chunk`；
- 更换 Embedding 时重建 Segment 向量，不改变 Segment ID 和业务来源引用。

#### 7.1.6 版本与失效规则

- 小范围 OCR 或表格人工修正：新增 `document_correction`，重新评估受影响 Segment 和下游对象；
- 更换解析器或全量重跑：新增 `document_parse`，人工确认后将旧解析及依赖结论标记 `STALE`；
- 文件内容变化：新增 `document_version`，旧文件解析结果和下游结论按覆盖关系失效；
- 多模态解释不能覆盖 OCR 原文；
- 高风险区域未确认时，不能进入正式 `Requirement Baseline`；
- 关键页面不可用时，阻断要求抽取和后续正式生成。

#### 7.1.7 未进入 V1 的复杂模型

V1 不单独建设：

- 通用 `document_node` 树；
- 独立 `source_anchor` 表；
- 独立 `document_table_cell` 表；
- 独立 `retrieval_chunk` 表；
- 完整的跨页逻辑表格关系模型；
- 通用文档结构编辑器。

这些能力只有在真实样本证明 JSONB 难以支撑查询、表格精细抽取或检索版本治理时再拆分。

**选择原因**：该方案已经满足多解析器适配、页码和坐标定位、人工修正、版本追溯、Agent 引用和向量检索，同时显著减少 V1 表数量和开发工作量。

### 7.2 分层解析路由（已确认）

| 文件或区域 | 实现方式 | 选择原因 | 失败降级 |
|---|---|---|---|
| 原生文本 PDF | PyMuPDF 快速提取文本、页码和坐标 | 速度快，避免无意义 OCR | 质量不足转精细解析或 OCR |
| DOCX | 原生段落、标题、表格和关系解析 | 保留文档结构，不先转 PDF | 异常文档转人工或格式转换 |
| XLSX | 读取工作表、单元格、公式、合并区域和格式信号 | 报价和清单需要确定性结构 | 公式或外链无法计算时转人工 |
| 扫描页和普通图片 | OCR + 版面检测 | 提供文字、坐标和区域类型 | 低置信度区域进入人工复核 |
| 常规表格 | 表格结构恢复 | 保留行列和单元格关系 | 合并复杂时转多模态或人工 |
| 复杂图表 | 外部多模态 API 按区域解释 | 适合流程图、架构图、甘特图和复杂图文关系 | API 失败保留 OCR 和图片，转人工 |

### 7.3 OCR 引擎（推荐待确认、需实测）

**推荐**：PaddleOCR 或其文档解析组件作为中文 OCR 和版面检测主候选。

**实现方式**：封装 `OcrProvider` 接口，输出文字、坐标、置信度和区域类型；只在扫描页或文本质量不足时触发，不重新 OCR 全部原生文本页面。

**选择原因**：中文文档生态成熟，可本地运行并输出坐标；适合招标文件的可追溯要求。

**待实测项**：中文政务扫描件、低清页面、印章覆盖、倾斜页面、跨页表格和 CPU 推理耗时。

**替代方案**：MinerU、Docling 或云 OCR。最终以真实样本的文字准确率、表格恢复率、定位正确率、速度、资源和许可证核验裁决。

### 7.4 外部多模态 API（已确认使用方式，供应商待确认）

**承担职责**：只解释传统解析难以处理的复杂图表和图文关系，不负责整份普通文档 OCR。

**实现方式**：

- 解析器识别复杂区域并裁剪页面局部图片；
- `VisionProvider` 发送图片、区域类型、OCR 文本和结构化输出 Schema；
- 输出 `visual_summary`、结构化元素、置信度和需要人工确认的字段；
- 原图、OCR 原文和多模态解释同时保存；
- 金额、日期、资格、否决、评分、参数、人员、签章等高风险结论必须人工确认；
- 供应商适配层支持外部 API 与未来本地模型替换。

**选择原因**：复杂图表的语义关系超出纯 OCR 能力；区域级调用比整文档视觉解析更低成本、更可控。

**失败降级**：API 超时或限流时重试；持续失败时不阻断原文保存，标记 `WAITING_HUMAN`，不让模型猜测。

### 7.5 文档渲染与导出（已确认）

V1 采用“结构化内容块 → 中立 `DocumentModel` → 受控 DOCX 模板 → DOCX → PDF”的同源管线，不以 Markdown 或 HTML 作为最终文档事实源。

```text
PostgreSQL 章节与内容块
→ DocumentModel
→ document_template_version
→ docxtpl + python-docx
→ 可编辑 DOCX
→ LibreOffice Headless
→ 预览或最终 PDF
```

`DocumentModel` 是运行时中立结构，不新增数据库表，至少包含元数据、封面、章节、标题、段落、列表、表格、图表、分页、页眉页脚和附件引用。业务内容块不直接操作 Word XML，渲染器负责将块类型映射到模板样式。

#### 7.5.1 受控模板版本

持久化对象统一命名为 `document_template_version`，避免和 `handover_package` 混淆。主要字段包括模板代码、版本、DOCX 对象引用、变量 Schema、样式映射、章节映射、允许的块类型、内容哈希和状态。

模板由管理员上传并通过验证后才能进入 `ACTIVE`。模板变量、循环和条件必须来自允许清单，普通用户不能上传任意可执行表达式。模板验证至少覆盖占位符、样式、表格循环、分节、页眉页脚、目录字段和一份标准样例渲染。

#### 7.5.2 `document.render`

草稿预览流程为：

```text
读取章节、内容块和模板版本
→ 构建 DocumentModel
→ 隔离正式内容与内部提示
→ 生成预览 DOCX
→ 更新目录、编号和字段
→ 转换预览 PDF
→ 添加草稿/内部使用标识
→ 写入 MinIO
```

预览允许存在占位块、待确认内容和引用警告，但 `SYSTEM_NOTICE`、内部审核意见和外发正文必须使用不同的数据通道和样式。预览文件不得进入正式交接包。

#### 7.5.3 `document.export`

最终导出只允许确定性交接任务调用。执行前必须校验 `REVIEW_RESULT_CONFIRMATION`、交接门禁、章节与模板版本、报价、证据、附件和审核基线。

以下任一情况阻断导出：

```text
存在 PlaceholderBlock
SYSTEM_NOTICE 或内部审核内容混入外发正文
存在失效或未验证引用
报价版本未确认或失效
存在未解决的 BLOCKING 风险
章节或模板版本冲突
模板未验证或已失效
```

导出成功后生成可编辑 DOCX、同源 PDF、文件清单、SHA-256 哈希和对象存储引用，并写入 `handover_package.manifest_json`。DOCX 成功但 PDF 失败时返回 `PARTIAL`，不能形成有效交接包。

#### 7.5.4 Worker 与文件安全

- `document.render` 和 `document.export` 都通过 Celery 执行；
- LibreOffice 转换初始并发限制为 1，避免单机 CPU 和临时配置争用；
- 每个任务使用独立临时目录和独立 LibreOffice 用户配置目录；
- 任务结束或超时后清理临时文件；
- 文件先写入临时对象，格式、页数、大小和哈希校验成功后再发布正式引用；
- worker 镜像包含 `docxtpl`、`python-docx` 和 LibreOffice，不新增在线 Office 或独立渲染服务。

V1 不建设在线 Office 编辑器、不在浏览器完整复刻 Word 排版、不支持用户任意模板脚本、不让 Agent 直接执行最终导出，也不自动向外部交易平台递交文件。

## 八、检索与模型技术方案

### 8.1 混合检索（架构已确认，具体模型待确认）

**实现方式**：

```text
查询标准化
→ 项目、权限、版本和有效期过滤
→ PostgreSQL 原生词法检索候选
→ pgvector 语义候选
→ 候选合并去重
→ RRF 融合排序
→ 有限候选 Reranker 重排
→ 返回带来源定位的片段
```

**实现约束**：词法和向量两路默认各召回 Top 30，去重后使用 RRF 取 Top 30，再将最多 30 个候选交给 Reranker，最终返回 Top 10。单次检索最多返回 50 条候选；大范围扫描由 Celery 任务分批执行。

**返回内容**必须包含 `source_segment_id`、`document_version_id`、页码、章节路径、字符或坐标范围、原文、召回路线和得分。Agent 只能引用已返回且仍有效的来源片段。

**选择原因**：资格名称、证书编号、条款编号、型号、日期和金额需要词法精确匹配；自然语言改写和长句要求需要向量召回；RRF 提供无需训练的稳定融合；有限候选重排用于控制最终上下文质量。检索索引是派生层，PostgreSQL 业务表仍是唯一事实源。

**失败降级**：pgvector 不可用时降级为 PostgreSQL 词法召回并记录 `DEGRADED_VECTOR_UNAVAILABLE`；Reranker 不可用时使用 RRF 并记录 `DEGRADED_RERANKER_UNAVAILABLE`；两路检索都不可用时不得生成确定性结论，创建证据缺口并转人工。检索结果版本失效时必须丢弃并重新召回。

### 8.2 Embedding（架构已确认，具体模型待实测）

**当前候选**：BGE-M3。

**推荐原因**：早期调研认为其适合中文长文本和混合检索；可本地部署，减少企业资料发送外部服务的范围。

**部署方式**：V1 按无 GPU 的单台 Linux 服务器设计。`EmbeddingProvider` 在 `mcp-tools` 容器中本地 CPU 加载一个持久模型实例，不增加独立模型容器。文档片段批量向量化通过 Celery 异步任务调用 `knowledge.*`，查询向量化允许同步执行。

**实现方式**：向量维度、模型版本、归一化方式和输入截断策略写入索引元数据；模型变更时创建新索引版本，不在原向量上静默覆盖。初始批量大小从 8～16 实测，输入优先使用已确认的语义片段，默认不把整章或模型最大上下文作为输入。

**冻结条件**：使用真实招标要求与企业证据评测 Recall@K、MRR、nDCG、引用正确率、耗时和资源后确认。

### 8.3 Reranker（架构已确认，具体模型待实测）

**当前候选**：bge-reranker-v2-m3。

**部署方式**：`RerankerProvider` 与 Embedding 共用 `mcp-tools` 的单一 CPU 推理通道，模型只加载一份。RRF 后最多将 30 个候选交给重排，最终返回 Top 10。

**实现方式**：记录候选数量、模型版本、输入截断、得分和最终入选片段。重排队列已满、超时或模型不可用时直接降级为 RRF，不阻断主要检索流程。全项目批量复核通过 Celery 调用，不占用 FastAPI 请求线程。

**选择原因**：高风险资格和评分证据需要比单纯向量相似度更精确的最终排序。

V1 不引入 Elasticsearch 或 OpenSearch。后续只有在 PostgreSQL 词法检索、pgvector 和有限重排经过真实样本评测仍无法满足召回质量或规模要求时，才评估独立搜索引擎。

### 8.3.1 CPU 推理资源边界（已确认）

`mcp-tools` 内只建立一个有界 CPU 推理通道，Embedding 与 Reranker 复用同一资源控制器：

```text
一个持久模型实例/模型类型
一个有界推理队列
默认单路模型推理
固定 CPU 线程上限
容器内存限制
独立超时与健康检查
```

队列已满时，查询检索可以跳过 Reranker 并使用词法、向量与 RRF 结果；文档向量化任务继续保留在 Celery 队列。不得为了追求吞吐动态启动多个模型进程，避免重复加载权重和占满单机 CPU、内存。

V1 优化顺序为缩短输入、限制批量和候选、调整线程、增加安全缓存，再通过准确率与性能评测决定是否使用 ONNX 或 INT8。初始版本不同时引入量化、独立推理服务和外部 Embedding API。

**实测门禁**：使用真实招标要求和企业证据记录 Recall@K、MRR/nDCG、引用正确率、P95 延迟、CPU 和内存。Embedding 候选保留 BGE-M3；Reranker 需要将当前候选与更小的 CPU 候选比较。若重排性能不满足要求，V1 可关闭 Reranker 并使用 RRF，不影响业务主流程。

### 8.4 ModelGateway 与模型路由（架构已确认，供应商待实测）

V1 在 Python 应用内部建设统一 `ModelGateway` 模块，不部署独立模型微服务。该模块供专业 Agent 和 `document.ingest` 的复杂图表适配器使用，统一封装模型客户端、结构化输出、超时、有限重试、脱敏、用量记录和调用审计。

#### 两个模型配置档

```text
TEXT_PRIMARY
VISION_CHART
```

- `TEXT_PRIMARY`：统一支持招标理解、响应规划、带引用编制和质量复核四个专业 Agent；
- `VISION_CHART`：只处理 `document.ingest` 通过确定性复杂度规则识别出的复杂图表；
- OCR、Document IR 构建、报价计算、状态转换和业务门禁继续由确定性程序执行。

模型不能自行选择或升级配置档。`SkillManifest.model_policy` 指定专业 Skill 使用 `TEXT_PRIMARY`；复杂图表路由由文档处理规则决定。V1 不为每个 Agent 配置独立模型，也不做基于成本或模型自评的动态智能路由。

#### 结构化输出管线

```text
模型生成
→ JSON Schema / Pydantic 校验
→ 引用完整性检查
→ 确定性业务规则校验
→ 领域服务写入 PostgreSQL
```

JSON 结构错误允许一次仅修复结构的重试；再次失败返回 `VALIDATION_ERROR` 并转人工。缺少必需来源引用的输出不得写入正式业务表。内容拒答或业务信息不足时保留拒答与缺口，不通过提示词强迫模型编造。

网络和限流错误最多重试 2 次。多模态调用失败时保留 OCR 与原图，将对应图表标记为待人工确认。模型不得直接修改项目状态、计算或确认报价、关闭风险、通过人工关口或冻结交接基线。

#### 版本与审计

每次 `agent_run` 记录 `model_profile`、`provider`、`model_name`、`resolved_model_id`、`model_config_version`、`model_parameters_hash`、`skill_version`、`prompt_config_version`、`schema_version` 和 `token_usage`。`workflow_run.input_refs` 固定本次工作流使用的模型配置、Skill 和 Prompt 版本。

同一次运行中不得静默更换模型配置。配置变化需要创建新运行或按影响范围使原结果失效。V1 不保存模型完整思维过程，只保存结构化输入摘要、输出引用、用量、错误和必要审计信息。

**供应商边界**：具体供应商、模型名称和备用模型在开发前通过真实招标文件评测确认。架构只依赖 `ModelGateway` 契约，不将业务代码绑定到单一供应商 SDK。

### 8.4.1 外部模型数据出域控制（已确认）

`ModelGateway` 在调用外部文本或多模态 API 前必须经过应用内部 `DataEgressGuard`。该组件是 Python 模块，不新增服务或容器。

```text
Agent / VisionProvider
→ DataEgressGuard
→ 数据分类、项目授权、权限和用途校验
→ 最小化、字段白名单和脱敏
→ 外部模型 API
```

数据等级统一为 `PUBLIC`、`INTERNAL`、`CONFIDENTIAL` 和 `RESTRICTED`。项目 `external_ai_policy` 默认 `PUBLIC_ONLY`，投标经理可以明确批准 `ALLOW_INTERNAL` 或 `ALLOW_CONFIDENTIAL`；`RESTRICTED` 永远禁止出域，项目开关不能放行。

文本模型只接收当前任务所需的来源片段、已确认结构化事实、输出 Schema 和业务规则，不发送整份知识库、完整合同或无关项目材料。多模态模型只接收复杂图表的局部裁剪、必要 OCR 文本、图表类型和输出 Schema，裁剪区域中的无关人员、报价和敏感内容先遮盖。

禁止发送账号密码、API Key、完整身份证件号码、非必要联系方式、完整报价底表与成本明细、内部审核意见、风险豁免记录和 `RESTRICTED` 数据。企业证据或草稿的实际发送等级取所有来源对象分类的最高值。

每次外部调用写入追加审计事件，至少记录供应商、模型、项目、Agent 运行、数据分类、来源对象引用、实际发送字段名、脱敏策略版本、请求/响应哈希、Token 用量和时间。普通日志不记录完整 Prompt、图片和回复正文。

策略拒绝返回 `EXTERNAL_DATA_BLOCKED`，不得自动重试。调用方继续使用确定性规则和本地检索，创建人工补充或确认任务；不能通过删除关键安全字段强行调用模型。

V1 不建设完整 DLP 平台，仅使用对象数据分类、项目级授权、字段白名单、规则脱敏和调用审计。供应商选择必须验证企业数据使用、保存期限和审计能力，但具体供应商条款在选型阶段单独核验。

## 九、权限、安全与审计

### 9.1 权限模型（已确认方向）

V1 使用单组织 RBAC，预置投标经理、编写人、商务负责人和审核负责人。权限在 FastAPI 后端校验，前端按钮控制不是安全边界。

每个敏感操作至少校验：

- 当前用户角色；
- 项目成员关系；
- 对象所属项目；
- 当前业务状态；
- 输入版本是否仍有效；
- 是否存在阻断问题或未完成审核。

缓存命中不是授权依据。所有从 Redis 返回的对象引用在读取原文前必须重新执行项目权限、对象归属、版本、有效期和保密等级校验。

### 9.2 身份认证与会话（已确认）

V1 使用平台本地账号和 PostgreSQL 服务端 Session，不开放用户自行注册，不建设独立身份服务。账号由系统管理员创建、禁用和重置密码；未来通过认证适配器接入 OIDC 或企业统一登录，不改变后端权限模型。

```text
浏览器提交账号密码
→ FastAPI 校验 Argon2id 密码哈希
→ 创建随机高熵 Session Token
→ PostgreSQL 仅保存 Token 哈希与会话状态
→ 浏览器通过 HttpOnly Cookie 携带 Token
→ 后端加载用户、平台角色和项目成员权限
```

**Cookie 与会话规则**：

- Cookie 使用 `HttpOnly`、生产环境 `Secure`、`SameSite=Lax`，不向前端 JavaScript 暴露 Session Token；
- Cookie 只保存随机 Token，不保存用户信息、角色、权限或业务状态；
- PostgreSQL 保存 `user_session`，支持主动撤销、管理员强制下线和审计；
- 默认空闲 30 分钟过期，单次登录绝对最长 8 小时；有效活动可以刷新空闲时间，但不能突破绝对期限；
- 修改密码、禁用账号或修改关键平台角色后，撤销该用户全部有效 Session；
- 使用 Cookie 发起的写操作必须执行 CSRF 防护，不能只依赖 `SameSite`；
- 登录失败使用 Redis 做账号与来源组合的短期限流；Redis 不可用时退化为应用进程内的保守限流，不改变账号状态；
- 报价确认、风险豁免、最终交接等敏感操作要求重新输入密码，后端记录最近重新认证时间；
- 登录、退出、登录失败、密码重置、账号禁用、会话撤销和重新认证写入审计事件。

V1 不实现自助注册、短信或邮箱验证码、Refresh Token、JWT 黑名单、复杂设备管理和多因素认证。密码只保存 Argon2id 哈希；管理员重置后用户首次登录必须修改密码。Session Token 原文不写入数据库、日志或审计记录。

**选择原因**：PostgreSQL Session 比无状态 JWT 更容易立即退出、禁用账号和撤销权限；比 Redis Session 更符合“Redis 故障不影响核心人工操作”的边界。V1 用户量较小，每次请求的轻量会话查询可接受，不需要增加服务。

### 9.3 审计

以下事件必须写入不可静默覆盖的审计记录：

- 登录、上传、下载和文件版本确认；
- 要求、证据、报价和章节确认；
- Agent 运行、失败、重试、暂停和恢复；
- 审核问题创建、整改、关闭和风险豁免；
- 基线冻结、内部交接和人工递交记录；
- 权限拒绝和高风险操作失败。
- 外部模型数据发送、脱敏策略、调用结果和策略阻断；

## 十、部署技术方案

### 10.1 Docker Compose（已确认）

V1 使用单台 Linux 服务器部署以下容器：

```text
gateway
frontend
backend
worker
mcp-tools
postgres
redis
minio
```

**实现方式**：

- `compose.yaml` 定义基础服务；
- `compose.dev.yaml` 和 `compose.prod.yaml` 覆盖开发与试用环境差异；
- `backend` 与 `worker` 使用同一个 Python 镜像和不同启动命令；
- 只有网关暴露 `80/443`；
- PostgreSQL、Redis、MinIO 和 `mcp-tools` 只加入内部网络；
- `backend` 与 `worker` 通过 `MCP_SERVER_URL=http://mcp-tools:8000/mcp` 和部署密钥访问 MCP Server；
- `mcp-tools` 提供内部健康检查，不向网关配置外部路由；健康检查区分 MCP 服务可用和 CPU 模型是否就绪；
- V1 服务器不要求 GPU，Embedding 与 Reranker 在 `mcp-tools` 内以单实例、有界队列和固定线程上限运行；
- Docker 为 `mcp-tools` 设置 CPU 和内存限制，模型队列拥塞时优先降级 Reranker，不影响项目状态和人工操作接口；
- 健康检查控制数据库迁移、API、Worker 和前端的启动依赖；
- PostgreSQL 与 MinIO 使用持久化卷；
- 发布时先备份、执行 Alembic 迁移，再滚动重建应用容器。

**选择原因**：单机 Compose 足以满足旁路试用，部署可复现，复杂度明显低于 Kubernetes。

### 10.2 密钥与凭证管理（已确认）

V1 采用 **Docker Compose Secrets + 宿主机仓库外受保护文件**，不引入 Vault、云 KMS 或独立密钥管理服务。普通非敏感配置继续使用环境变量，密码、签名密钥、内部服务凭证和外部 API Key 通过文件挂载到对应容器的 `/run/secrets/<name>`，应用优先支持 `*_FILE` 配置读取方式。

推荐宿主机目录：

```text
/opt/bid-agent/
├── compose/
├── data/
└── secrets/
    ├── postgres_admin_password
    ├── postgres_app_password
    ├── postgres_migration_password
    ├── redis_password
    ├── session_signing_key
    ├── minio_root_password
    ├── minio_app_secret
    ├── mcp_service_secret
    ├── text_model_api_key
    └── vision_model_api_key
```

**实现方式**：

- `secrets/` 位于代码仓库外，不进入 Git、镜像、构建参数或普通 `.env` 文件；
- Secret 文件归部署专用系统账号所有，文件权限设为 `600`，目录权限限制为仅部署账号可访问；
- Compose 按服务最小挂载，`frontend` 不读取后端 Secret，各服务只读取职责所需凭证；
- PostgreSQL 至少拆分管理员、应用运行和迁移三类账号，日常服务不使用管理员凭证；
- MinIO 拆分 Root 管理凭证和应用访问凭证，应用账号只允许访问规定 Bucket 和操作范围；
- MCP 凭证只校验内部服务身份，不能替代用户权限、项目权限、对象归属和输入版本校验；
- Redis 启用认证时使用独立凭证，但仍不保存业务事实或长期敏感正文；
- 外部模型 API Key 只由 `ModelGateway` 所在服务读取，不保存到 PostgreSQL；
- 日志、异常、健康检查、任务参数、审计元数据和诊断包不得输出 Secret 值、请求头或完整连接串；
- `.env.example` 只描述非敏感变量和 Secret 文件名，真实 `.env` 与 Secret 文件不得进入仓库或复用生产凭证。

**轮换流程**：新旧凭证短期并存，先创建新值并更新服务授权，再滚动重建调用方容器，验证后撤销旧值。紧急泄露时先禁用旧凭证，再重建受影响服务并检查审计记录。

Compose Secrets 在非 Swarm 模式下主要提供受控文件挂载和服务隔离，不负责加密宿主机文件。因此还必须依赖宿主机权限、仓库外存放、最小挂载、凭证分权和日志脱敏。未来升级 Vault/KMS 时沿用 `*_FILE` 接口替换密钥来源，不修改业务模块。

**选择原因**：该方案比集中写入 `.env` 更容易控制服务可见范围和泄露风险，又比 V1 直接引入 Vault/KMS 更轻，适合单台 Linux 与 Docker Compose 部署。

### 10.3 公网入口与 Caddy 反向代理（已确认）

V1 不部署在企业内网，使用正式公网域名和固定公网 IP。域名 DNS 指向部署服务器，由现有 `gateway` 容器运行 Caddy，不新增容器。

```text
公网用户
→ 正式域名 :80/:443
→ Caddy gateway
   ├── 页面与静态资源 → frontend:3000
   └── /api/*          → backend:8000
```

**实现方式**：

- 服务器公网只开放 `80/443`，`frontend`、`backend`、PostgreSQL、Redis、MinIO 和 `mcp-tools` 不暴露公网端口；
- Caddy 自动申请和续期 TLS 证书，HTTP 强制跳转 HTTPS；证书与 Caddy 状态目录使用持久化卷；
- `/api/*` 转发至 FastAPI，其余页面、静态资源和 Next.js 服务请求转发至 `frontend`；
- 单文件上传初始限制为 200 MB，上传接口最长允许 10 分钟；普通 API 请求超时为 60 秒；
- 上传完成后只创建文档与 `task_run` 并返回任务 ID，解析、OCR、Embedding、Agent 和导出不能长期占用 HTTP 连接；
- 登录接口按账号与来源地址限流，普通 API 按用户和来源执行基础限流；业务权限仍由 FastAPI 校验；
- 统一添加 HSTS、`X-Content-Type-Options`、`Referrer-Policy` 和经过前端实测的基础 CSP；
- 访问日志不记录 Cookie、Authorization、请求正文、文件内容或 URL 中的敏感参数，并贯通请求 ID；
- MinIO 不提供公网匿名访问，文件下载必须先经过后端权限、项目归属和版本校验，再返回短期签名地址；
- Caddy 健康检查和错误页不得暴露容器地址、软件堆栈、密钥路径或内部服务信息。

Caddy 只负责 TLS、公网入口、路由和基础入口保护，不负责登录状态、RBAC、业务限流结论、文件权限或工作流状态。V1 不引入 Nginx + Certbot 的双组件证书链路，也不增加云负载均衡或 WAF；公网试用规模、攻击风险或可用性要求提高后再评估云 WAF/CDN。

**选择原因**：Caddy 将 HTTPS 申请、续期、HTTP 跳转和反向代理集中在一个轻量网关内，适合单域名、单服务器的公网 V1，运维复杂度低于 Nginx 配合独立证书续期工具。

### 10.4 轻量备份与恢复（已确认）

V1 暂不接入云对象存储、NAS 或自动异机灾备，采用“本机自动备份 + 每周人工导出加密包 + 预留备份目标接口”。该方案不增加长期运行容器，提供误操作和应用故障后的本机恢复能力，但不承诺服务器整机损坏、勒索或彻底入侵后的自动灾难恢复。

本机备份目录：

```text
/opt/bid-agent/backups/
├── postgres/
├── minio/
├── config/
├── manifests/
├── packages/
└── recovery/
```

**自动备份**：

- PostgreSQL 每 6 小时使用 `pg_dump -Fc` 生成自定义格式备份；
- MinIO 对象每天增量复制到本机备份目录，保留对象路径、版本引用和文件清单；
- Compose、Caddy、`systemd`、迁移版本和部署脚本每天备份一次，不包含明文 Secret；
- 本机自动备份保留最近 7 天，过期文件由备份脚本清理；
- 每次生成 `backup_manifest.json`，记录批次 ID、时间、应用版本、Alembic 版本、对象数量、文件大小和 SHA-256；
- 自动检查命令退出状态、备份文件大小、SHA-256、`pg_restore --list` 可读性和关键对象存在性；
- 备份失败、连续校验失败或最近成功备份过期时触发本地可观测性告警。

**人工离机副本**：每周由管理员执行部署命令生成加密备份包，例如 `bid-agent-backup-2026-08-19.tar.age`，下载到管理员电脑、加密移动硬盘或企业批准的网盘。V1 不建设备份管理页面，也不自动上传第三方存储；加密私钥不保存在部署服务器。

**扩展接口**：应用内部定义 `BackupTarget`，统一提供 `upload`、`download`、`list`、`verify`、`delete_expired` 和 `health_check`。V1 只实现 `LocalBackupTarget`；`S3BackupTarget` 和 `NasBackupTarget` 仅保留适配接口，不提前接入厂商 SDK。

```text
BACKUP_TARGET=local
BACKUP_LOCAL_PATH=/opt/bid-agent/backups
```

**恢复演练**：上线前必须在空环境中至少完成一次 PostgreSQL、MinIO、配置和关键项目恢复；之后每季度执行一次。演练需要验证登录、项目读取、文件下载、引用定位、任务记录和文档导出，不能只检查备份文件存在。

**能力边界**：本方案不能正式承诺 RPO 6 小时或 RTO 4 小时，也不能防止服务器磁盘与本机备份同时损坏。V1 对外只表述为“具备本机自动备份、人工离机副本和恢复演练能力；自动异机灾备待后续接入”。

**选择原因**：保留基本恢复能力和可替换接口，同时避免在 V1 引入用户尚未具备运维条件的云存储账号、权限、生命周期和费用管理。

## 十一、可观测性与任务可靠性

### 11.1 任务状态

每个长任务保存：任务 ID、类型、项目、状态、当前步骤、输入版本、输出版本、进度、失败原因、重试次数、创建人和时间戳。

标准状态建议为：

```text
PENDING
QUEUED
RUNNING
WAITING_HUMAN
RETRYING
SUCCEEDED
FAILED
CANCELLED
STALE
BLOCKED
```

### 11.2 本地日志、运行看板与告警（已确认）

V1 采用零新增容器的本地可观测性方案，不接入外部 Sentry，不部署 Prometheus、Grafana 或 Loki。异常堆栈和运行日志保留在部署服务器，主动通知只发送脱敏摘要。

**结构化日志**：FastAPI、Celery Worker、MCP 和 Caddy 输出 JSON 日志，贯通 `request_id`、`project_id`、`workflow_run_id`、`agent_run_id`、`task_run_id`、服务名、错误码和时间。日志不得记录文件正文、Prompt、模型完整回复、Cookie、Authorization、密码、Session Token、报价明细或完整企业证据。

Docker 日志启用本地轮转，初始配置为单文件最大 20 MB、最多保留 5 个文件。完整异常堆栈仅保存在服务器本地，并在输出前过滤 Secret、请求头、连接串和业务敏感字段。业务审计继续写入 PostgreSQL `audit_event`，不得以应用日志替代审计记录。

**业务运行看板**：管理员页面直接读取 PostgreSQL 中的 `task_run`、`agent_run`、`workflow_run` 和 `audit_event`，展示任务状态、失败原因、重试、耗时、模型用量、OCR 触发率、人工接管率和版本失效次数，不部署独立 Grafana。

**宿主机巡检**：部署轻量 Watchdog 脚本，由 `systemd timer` 每分钟执行，不增加容器。脚本检查 Docker 服务健康状态、Caddy/FastAPI/MCP 健康检查、Worker 心跳、PostgreSQL/Redis/MinIO 连通性、磁盘使用率、队列积压、连续任务失败和数据库/对象备份时效。

**告警分级**：

- `WARNING`：磁盘使用率超过 80%、失败任务明显增加、队列持续积压或备份接近过期；
- `CRITICAL`：服务连续 3 次不可用、磁盘使用率超过 90%、PostgreSQL 不可连接、Worker 心跳失效或备份严重过期；
- 通过企业微信机器人或管理员邮箱发送脱敏通知，只包含环境、服务、错误编号、时间、请求或任务 ID、错误分类和后台查看路径；
- 通知不得包含投标文件内容、Prompt、报价、企业证据、凭证或完整异常堆栈；
- 相同告警按指纹合并并设置冷却时间，恢复后发送恢复通知，避免重复轰炸。

当项目量、用户量或专职运维需求提高时，优先增加 Prometheus + Grafana；只有本地日志检索成为明确瓶颈时再增加 Loki。升级不得改变现有结构化日志字段和运行记录对象。

**选择原因**：该方案复用现有数据库运行记录和 Docker 能力，可以满足 V1 的故障发现、业务追踪和主动告警，同时不增加容器数量，也避免异常数据发送第三方平台。
