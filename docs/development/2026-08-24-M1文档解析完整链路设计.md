# M1 文档解析完整链路设计

> 日期：2026-08-24
> 状态：用户已确认
> 范围：显式启动首次解析任务、任务查询、Celery 调度、内部 MCP `document.ingest`、MinerU/Python 原生混合解析与 Document IR 持久化

## 一、目标与边界

本切片在已有文件列表与首版本上传基础上，贯通以下确定性链路：

```text
POST /api/v1/document-versions/{document_version_id}/parse
→ FastAPI 领域层校验并创建 PostgreSQL task_run/document_parse
→ 事务提交后发布 Celery
→ Celery Worker 同步调用内部 MCP document.ingest
→ 从对象存储读取原文件
→ PDF/图片使用内部 MinerU，DOCX/XLSX 使用原生解析器
→ 统一 Document IR 写入 PostgreSQL
→ 更新 document_parse、document_version、task_run 最终状态
→ 前端通过任务接口轮询 PostgreSQL 状态
```

本切片不引入 Agent，不新增人工关口，不实现要求抽取、Embedding、检索、人工修正、影响分析、`reparse` 和外部多模态。PDF 与普通图片由内部自托管 MinerU 执行原生文本提取、OCR、版面、表格和公式识别；加密、损坏、低置信度或无法可靠定位的内容不得静默跳过或猜测，必须形成标准失败或待人工处理信息。

## 二、状态与数据模型

### 2.1 文件版本状态

最新项目决策已确认上传后使用 `PENDING`。本切片采用：

```text
PENDING → PARSING → PARSED
                  ↘ PARSE_FAILED
```

- `PENDING`：文件已上传，尚未创建解析任务；
- `PARSING`：首次解析任务已受理；
- `PARSED`：Document IR 已完整持久化；
- `PARSE_FAILED`：解析不可恢复失败或当前能力不支持。

同步修订状态机和数据字典中的旧 `UPLOADED` 初始状态，保持最新决策、API、迁移和代码一致。

### 2.2 `workflow.task_run`

`task_run` 是异步任务唯一业务事实记录，至少保存：

- 组织、项目、文件版本和解析批次引用；
- `task_type=DOCUMENT_PARSE`；
- `task_status=QUEUED/DISPATCHED/RUNNING/SUCCEEDED/FAILED/CANCELLED/STALE`；
- `progress_percent`、`retry_count`、`max_retries`；
- 幂等键、请求哈希、`celery_task_id`；
- `queued_at`、`dispatched_at`、`started_at`、`heartbeat_at`、`finished_at`；
- 标准错误码与脱敏错误信息。

数据库必须保证同一文件版本不会同时存在两个有效的首次解析任务。

### 2.3 Document IR

最小结构为：

```text
document_version
→ document_parse
→ document_page
→ document_segment
```

- `document_parse`：解析批次、解析器及版本、状态、质量摘要、错误和完成时间；
- `document_page`：物理页或逻辑工作表，保存序号、尺寸与扩展元数据；
- `document_segment`：标题、段落、列表、表格、表格行、图形或其他片段，保存父子关系、页码、章节路径、正文、来源哈希、定位信息、元数据和置信度。

更换解析器或后续重新解析时创建新的 `document_parse`，不得覆盖旧解析批次；文件内容变化才创建新的 `document_version`。

## 三、API 契约与权限

### 3.1 启动首次解析

```http
POST /api/v1/document-versions/{document_version_id}/parse
```

要求：

- 有效 PostgreSQL Session；
- `X-CSRF-Token`；
- `Idempotency-Key`；
- 当前组织内 ACTIVE 项目负责人；
- 目标文件版本属于当前组织和项目，且状态为 `PENDING`。

成功返回 `202 Accepted` 和 `task_run` 摘要。同作用域、同键、同请求重放首次响应；同键不同请求返回 `409 IDEMPOTENCY_CONFLICT`。文件处于 `PARSING`、`PARSED` 或其他不允许首次解析的状态时返回明确冲突。

### 3.2 查询任务

```http
GET /api/v1/task-runs/{task_run_id}
GET /api/v1/projects/{project_id}/task-runs
```

当前组织内 ACTIVE 项目成员可读取所属项目任务。项目任务列表可按 `task_type` 和 `task_status` 过滤，不以 Celery Result Backend 作为返回来源。

## 四、事务、发布与幂等

### 4.1 FastAPI 受理事务

在单个 PostgreSQL 事务中完成：

1. 锁定并校验文件版本、项目、组织和 ACTIVE 负责人；
2. 认领或重放 HTTP 幂等键；
3. 校验文件状态与有效解析任务唯一性；
4. 创建 `document_parse`；
5. 创建 `task_run(QUEUED)`；
6. 将文件版本改为 `PARSING`；
7. 写入解析受理审计；
8. 保存幂等成功响应。

消息不得在事务提交前发布，避免 Worker 读取未提交事实。

### 4.2 Celery 发布

事务提交后发布 Celery，并在独立短事务中记录 `celery_task_id`、`dispatched_at` 和 `DISPATCHED`。发布失败时保留 `QUEUED`，不伪造失败或回滚已经受理的业务任务；恢复发布器可扫描超时 `QUEUED` 任务并安全重投。

### 4.3 Worker 幂等

Worker 通过 PostgreSQL 条件更新领取任务：仅 `QUEUED` 或 `DISPATCHED` 可进入 `RUNNING`。重复投递不得创建第二份有效 Document IR；已终态任务直接返回。成功或失败均在 PostgreSQL 事务中同步更新解析批次、文件版本和任务最终状态。

## 五、解析器与 MCP 边界

### 5.1 MCP

新增单一内部 MCP Server 骨架，本切片只实现正式冻结方法 `document.ingest`。Celery Worker 使用内部 Streamable HTTP 同步调用该方法；MCP 不创建第二层 Celery 任务。

MCP Server 必须二次校验调用凭证、用户/系统主体、组织、项目、文件版本、任务类型、方法白名单、幂等键和输入版本。MCP 不能绕过领域层修改项目主状态；Document IR 写入和任务状态更新走确定性应用服务。

### 5.2 MinerU 混合解析

- PDF 与普通图片：调用 Docker 内部网络中的自托管 MinerU 服务，自动执行原生文本提取、OCR、版面分析、表格和公式识别；
- DOCX：使用 `python-docx` 按文档顺序读取标题、段落、列表和表格结构；
- XLSX：使用 `openpyxl` 读取工作表、单元格、公式和合并单元格，生成稳定片段；
- MinerU 不处理业务权限、幂等或任务状态，也不直接写 PostgreSQL；适配器必须将 MinerU 输出转换并校验为统一 Document IR；
- 当前阶段仅使用内部自托管 MinerU，不调用外部托管 API，不需要 API Key，采购文件不得因解析发送到第三方；
- 所有解析器只返回统一、可校验的 Document IR，不直接驱动业务状态。

来源哈希由标准化来源内容计算 SHA-256。`document_parse` 必须保存 MinerU、模型、后端模式、DOCX/XLSX 解析器及参数版本，以支持后续重解析和结果追溯。

## 六、错误处理与恢复

标准错误至少覆盖：

- 文件版本不存在、跨组织、非项目成员、非负责人；
- CSRF 或幂等键缺失；
- 文件状态冲突、已有有效解析任务；
- 对象存储读取失败；
- MIME/格式不支持；
- 空内容、损坏文件、加密 PDF、MinerU 低置信度或结果 Schema 不完整；
- MCP 权限或输入版本拒绝；
- Celery 发布失败；
- Document IR Schema 校验失败；
- 数据库写入失败。

错误消息不得包含对象存储凭证、数据库连接、完整堆栈或敏感文件正文。原文件只读，解析失败不得删除或覆盖原始对象。

## 八、依赖与合规

新增依赖：

- `celery`：正式架构指定的异步任务框架；
- 官方 Python MCP SDK：内部 Streamable HTTP MCP；
- `httpx`：调用 Docker 内部自托管 MinerU HTTP API，项目已有该依赖；
- `python-docx`：DOCX 原生结构解析；
- `openpyxl`：XLSX 原生结构解析。

MinerU 作为独立内部解析服务固定版本部署，不把 `mineru[all]` 及其重型模型依赖安装进 FastAPI API 进程。MinerU 使用自定义 `MinerU Open Source License`；生产交付前必须核验许可证条款、归属披露和商业适用条件，并记录 MinerU、模型与解析参数版本。

测试 Compose 复用正式架构中的 Redis，不引入新的基础设施类型。生产 MinIO 适配器是完整部署前置条件；测试继续使用对象存储内存替身。
