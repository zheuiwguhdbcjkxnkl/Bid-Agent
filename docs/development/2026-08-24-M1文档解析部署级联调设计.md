# M1 文档解析部署级联调设计

> 日期：2026-08-24
> 状态：用户已确认
> 范围：单机 Docker Compose 下的 FastAPI、PostgreSQL、Redis、Celery Worker/Beat、MCP Server、MinIO 与内部自托管 MinerU 部署级联调

## 一、目标与边界

本任务在已完成并通过代码级验证的 M1 文档解析链路上补齐真实容器网络和服务生命周期验证。目标是证明以下链路可以在单机 Docker Compose 中运行：

```text
FastAPI
→ PostgreSQL 受理解析任务
→ Redis Broker
→ Celery Worker
→ 内部 Streamable HTTP MCP Server
→ MinIO 原文件
→ DOCX/XLSX 原生解析或 MinerU PDF/图片解析
→ Document IR 写回 PostgreSQL
→ API 查询任务终态
```

本任务不新增业务对象、API 契约、Agent、Skill、MCP 工具、人工关口或前端页面，不修改冻结前端，不建设反向代理、Kubernetes、监控平台、Redis Cluster、MinIO 集群或自动扩缩容。PostgreSQL 继续作为任务状态、文件版本、解析批次、Document IR 和审计的唯一业务事实源；Redis、Celery、MCP、MinerU 和 MinIO 不得承载业务主状态。

## 二、方案选择

### 2.1 采用分层 Compose

采用单独的 `compose.integration.yaml`，不修改现有 `compose.test.yaml` 的测试数据库职责。部署级联调服务如下：

```text
compose.integration.yaml
├── postgres
├── redis
├── minio
├── minio-init
├── migrate
├── backend
├── celery-worker
├── celery-beat
├── mcp-tools
└── mineru（profile: mineru）
```

`backend`、`celery-worker`、`celery-beat` 和 `mcp-tools` 复用同一个 Python 3.12 后端镜像，使用不同启动命令。`mineru` 使用独立 Compose profile 和固定本地镜像标签，仅在 PDF/图片联调阶段启动。

### 2.2 未采用方案

- 不采用一次构建并启动全部服务的单个重型流程：MinerU 镜像和模型下载耗时大，容易阻塞基础链路验证。
- 不采用宿主机运行 FastAPI、Worker 和 MCP 的混合模式：虽然改动更少，但网络和生命周期与最终单机 Compose 部署不一致，会留下二次联调风险。

## 三、容器与网络边界

### 3.1 后端共享镜像

新增后端 `Dockerfile`，固定 Python 3.12 和锁文件依赖。镜像供以下进程复用：

- FastAPI：`uvicorn app.main:create_app --factory`；
- Celery Worker：消费 `DOCUMENT_PARSE`；
- Celery Beat：周期扫描超时 `QUEUED` 任务；
- MCP Server：内部 Streamable HTTP `document.ingest`。

镜像不得包含真实 Secret、原文件、解析产物或 MinerU 模型。MinerU 重型依赖继续位于独立服务镜像，不安装到 FastAPI 镜像。

### 3.2 内部网络

容器使用 Docker 内部 DNS：

```text
DATABASE_URL=postgresql+psycopg://...@postgres:5432/...
REDIS_URL=redis://redis:6379/0
MCP_ENDPOINT=http://mcp-tools:8000/mcp
MINERU_ENDPOINT=http://mineru:8000
MINIO_ENDPOINT=minio:9000
```

只有 FastAPI 在本地联调时映射宿主端口。PostgreSQL、Redis、MinIO API、MCP 和 MinerU 不映射宿主端口；诊断统一通过 `docker compose exec` 或容器内健康检查执行，不增加 Compose override 或诊断 profile。

### 3.3 持久化

- PostgreSQL 使用持久化卷保存唯一业务事实；
- MinIO 使用持久化卷保存长期原始文件；
- Redis 不配置持久化为业务恢复依据；
- MinerU 模型缓存可使用独立卷，但缓存不是业务事实；
- `minio-init` 只幂等创建私有 bucket，不写业务数据库，也不扩大权限。

## 四、配置与 Secret

新增 `.env.integration.example`，只包含变量名、安全说明和非敏感占位符。真实联调值放在被 Git 忽略的 `.env.integration` 或 Docker Secret 中。

必须配置：

- PostgreSQL 数据库、用户和密码；
- `MCP_SERVICE_TOKEN`；
- MinIO root 用户、密码、应用 access key/secret key；
- `MINIO_BUCKET_NAME`；
- 内部服务 URL。

所有进程读取同一 MCP 内部服务凭证，但该凭证不得写入镜像层、Compose 文件、日志、测试快照、项目文档或 Git。用户曾在对话中发送的旧凭证不得使用；内部自托管 MinerU 不需要外部 API Key，该旧凭证仍应撤销。

## 五、健康检查与启动顺序

### 5.1 健康检查

- PostgreSQL：`pg_isready`；
- Redis：`redis-cli ping`；
- MinIO：`/minio/health/live`；
- FastAPI：`GET /health`；
- MinerU：`GET /health`；
- MCP：容器进程健康检查加内部 MCP 初始化探针，不新增外部业务 API。

健康检查只说明进程和依赖可访问，不代表业务解析已成功。

### 5.2 启动顺序

1. PostgreSQL、Redis 和 MinIO 达到 healthy；
2. `minio-init` 幂等创建私有 bucket；
3. `migrate` 执行 `alembic upgrade head` 并成功退出；
4. FastAPI 和 MCP Server 启动；
5. Celery Worker 和 Beat 启动；
6. PDF/图片阶段通过 `mineru` profile 启动 MinerU；
7. 运行正式 API 驱动的端到端验收脚本。

服务依赖使用 `service_healthy` 或 `service_completed_successfully`，不得仅依靠固定 sleep。

## 六、MCP 与资源生命周期

MCP Server 必须显式监听容器网卡 `0.0.0.0:8000`，并保持 Streamable HTTP `/mcp` 契约不变。入口使用 MCP SDK lifespan 管理资源：

- 启动时创建 SQLAlchemy engine、session factory、MinIO client、MinerU `httpx.AsyncClient` 和解析服务依赖；
- 停止时关闭 MinerU HTTP client 并释放 SQLAlchemy engine；
- 内部凭证校验、`McpCallContext` 校验、组织/项目/任务/版本二次校验保持不变；
- MCP Server 不直接越过确定性领域服务修改项目主状态。

该修改只修复容器监听和资源释放，不改变业务 API、MCP 工具名、输入 Schema 或任务状态语义。

## 七、两阶段真实联调

### 7.1 第一阶段：DOCX 全链路

先使用最小 DOCX 验证不依赖 MinerU 的完整真实链路：

```text
种子命令创建初始组织和账号
→ 登录获取 Session 与 CSRF
→ 通过 API 创建项目
→ 通过 API 上传 DOCX 到真实 MinIO
→ POST /api/v1/document-versions/{id}/parse
→ PostgreSQL 写 QUEUED/DISPATCHED
→ Redis 投递
→ Worker 原子领取为 RUNNING
→ MCP 校验内部 token 与 _meta
→ MCP 从 MinIO 读取原文件
→ python-docx 生成 Document IR
→ PostgreSQL 写 SUCCEEDED/PARSED/page/segment
→ API 查询任务终态
```

验收脚本不得直接插入项目、文件版本、解析任务或解析结果。只允许使用受控种子命令创建初始组织和登录账号；其余步骤必须通过正式 API 完成。

### 7.2 第二阶段：PDF/MinerU

在同一链路中上传最小文本 PDF 和扫描 PDF，通过 `mineru` profile 启动内部自托管 MinerU。适配器继续调用同步 `/file_parse`，固定 `backend=pipeline` 并请求结构化 `content_list`，结果经 Schema 校验后转换为统一 Document IR。

MinerU 镜像必须固定版本、构建输入和模型版本。官方当前部署方式以本地构建 `mineru:latest` 为基础，因此项目 Compose 不能假设公共 registry 中存在稳定官方预构建镜像。生产交付前需要记录 MinerU、模型、后端模式和解析参数版本。

## 八、端到端验收标准

DOCX 阶段必须验证：

1. FastAPI、PostgreSQL、Redis、MinIO、MCP、Worker 和 Beat 真实容器运行；
2. 原文件存在于真实 MinIO，且对象 URI 与项目、文档绑定；
3. `task_run` 最终为 `SUCCEEDED`，进度为 100；
4. `document_version.parse_status=PARSED`；
5. `document_parse.parse_status=SUCCEEDED`；
6. 至少存在一条 `document_segment`；
7. 任务查询 API 从 PostgreSQL 返回终态；
8. Celery 未配置 Result Backend；
9. 重复消息投递不会重复写入有效 IR；
10. 停止 Worker 后创建的新任务保持 `QUEUED`，恢复 Worker/Beat 后可以补投并完成；
11. 日志不包含 Secret、数据库密码、对象存储凭证、完整连接串或文件正文。

PDF 阶段在上述断言基础上增加：

- MinerU `/health` 可用；
- `/file_parse` 真实返回可校验内容；
- 文本 PDF 和扫描 PDF 至少各产生一条来源可追溯片段；
- `document_parse` 保存 MinerU、模型和 backend 版本信息。

## 九、错误处理与完成口径

必须覆盖：

- 数据库、Redis、MinIO、MCP 或 MinerU 未就绪时依赖服务不应误报 healthy；
- Broker 发布失败时 PostgreSQL 任务保持 `QUEUED`；
- Worker 重启和重复投递不重复执行已终态任务；
- MCP token、组织、项目、任务或文件版本不匹配时明确拒绝；
- MinIO bucket 缺失或权限错误时返回脱敏错误；
- MinerU 超时、非 2xx、非法 JSON 或不完整结果时写入标准失败终态；
- 任何失败不得删除或覆盖原始对象。

如果 MinerU 镜像或模型构建因外部下载、8 GB 显存、CUDA 兼容性或许可证核验受阻，DOCX 真实全链路仍可作为独立完成结果，但必须明确记录“PDF/MinerU 部署级联调未完成”，不得声称整个解析部署完成。

## 十、测试策略

严格按 TDD 推进：

1. 先为 Dockerfile、Compose 服务、profile、healthcheck、Secret 和依赖顺序编写静态契约测试；
2. 为 MCP host/port 和 lifespan 编写失败测试，再修改入口；
3. 为 MinIO bucket 初始化和配置拒绝编写测试；
4. 构建后端镜像并执行容器内单元/集成测试；
5. 启动不含 MinerU 的核心服务，执行 DOCX 端到端验收；
6. 验证 Worker 停止、`QUEUED` 保留和 Beat 补投；
7. 构建并启动固定版本 MinerU，执行文本 PDF 和扫描 PDF 验收；
8. 最终执行后端全量 pytest、Ruff、mypy、Compose config、健康检查、敏感信息扫描和 `git diff --check`。

端到端测试使用专用联调数据库和专用 MinIO bucket，不连接生产资源。验收结束是否保留持久化卷由显式命令决定，默认不执行 `down -v`，避免误删未确认数据。
